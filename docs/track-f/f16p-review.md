## 1. Требуемые изменения

**RC1. `kept_applied` на сайте `adopt` ставится без исполнения очистки — правило (з) прочтёт событие как «`НЕ ДЕФЕКТ`», когда ничего не исполнено.**
- Что не так. П. 504(е)(3): «`kept_applied` — сохранено **и в том же вызове исполнено** (материализация на `adopt`, очистка на `prepare`)». Код:
  `f26.Applied(found->second.clear_mask != 0, Mask)` (`d5cbcbe2:src/graphics/host_gpu/renderer/cache/textureCache.cpp:3771`) — `kept_applied` =
  «принята с ненулевой маской». `AdoptPendingDccForTexture` (`textureCache.cpp:3711`–`3793`) `ClearImage` не зовёт; очистку исполняет **другой вызов
  позже** — `RenderExecutor::MaterializeDeferredDccClear` (`d5cbcbe2:src/graphics/host_gpu/renderer/pipeline/descriptors.cpp:3517`), и он может
  отказать: `!decoded` → возврат без очистки, счёт `dcc_mat_undecoded` (`descriptors.cpp:3606`–`3611`); для кода `0x20` декодирование требует
  слот цели, ещё адресующий поверхность (`descriptors.cpp:3569`–`3581`).
- Сайт `adopt` имеет три вызывающих [c `git grep` по `d5cbcbe2`]: привязка текстуры (`descriptors.cpp:3143`, комментарий `:3136`–`:3142` — «so
  CommitBindings materializes the clear»; материализация — `descriptors.cpp:6729`), попадание мемо привязок (`descriptors.cpp:3269`), DCC-ветка
  FCE-скана (`FindDccSurfaceImage` `descriptors.cpp:4023` → `textureCache.cpp:3702` → материализация `descriptors.cpp:4045`). Отчёт F16o §2.3
  (`4cf5b97a:docs/track-f/f16o.md:76`–`:77`) называет исполнителем только «вызывающий FCE-скан» — неполно.
- **Сценарий отказа.** Гость заливает DCC текстуры кодом `0x20` (очистка по регистрам), соседняя запись в той же корзине 64 КиБ делает корзинный
  ответ «устарела», точный — «свежая». В `f26_1` привязка текстуры (`descriptors.cpp:3143`) принимает заливку: строка
  `DiagF5Ev: dcc_stale site=adopt … exact=fresh fix=kept_applied`, `f26_kept_applied` +1. В `CommitBindings` ни один слот цели не адресует
  поверхность → `MaterializeDeferredDccClear` не декодирует ключ → очистки нет (`dcc_mat_undecoded` +1). Лист окна p − 1 … p + 2 без отличий (ничего
  не исполнено) → по п. 504(з) «`kept_applied` без отличий ⇒ событие `НЕ ДЕФЕКТ`»; при всех таких событиях — «Ф26 `НЕ ДЕФЕКТ` по п. 228(д) на
  `enemy_final`» на событиях, где правка картинку не трогала. То же — если материализация не наступила до конца окна (поверхность не привязана
  снова) [I: частота в игре не измерена].
- **Что изменить (выбор лида, пунктом до F16q):** (а) код: на `adopt` при сохранённой заливке с маской ≠ 0 — `kept why=deferred` (новое имя
  последним в `CmuWhy`), а `kept_applied` для этой заливки — только когда `MaterializeDeferredDccClear` того же изображения очистил ≥ 1 слой
  (одноразовая метка, поставленная `adopt` под `m_lock` и снятая в материализации; без ручки — не ставится), отдельной строкой или полем; тест-сайт
  — случай `0x20` без слота (`kept`, очистки нет) и случай с очисткой; дельта-ревью F16p2; или (б) правило: `site=adopt fix=kept_applied` читается
  в (з) как `kept` («не определено»), печать F16q называет это, отчёт F16o §2.3 поправляется (три вызывающих, исполнитель — не только FCE-скан).
  Вариант исполнителя ревью — (а): при (б) все события `adopt` выпадают из чтения, и Ф26 на `adopt` остаётся «не определено» при любом исходе тегов.
- Без изменения: F16r может вынести «Ф26 `НЕ ДЕФЕКТ`» на событиях, где очистка не исполнялась ни одним путём.

**RC2. Плечо `f5cmu_1b` проверяет DCC-сайты точной пробой, плечо `f5cmu_0b` — нет: поле `exact` строк `dcc_stale` в паре различается по
конструкции.**
- Что не так. `F26Scope::Arm` (`textureCache.cpp:1971`–`1976`): проба отдаётся при `ExactRingOn() && (DiagF5::On() || m_fix)`;
  `ExactRingOn` включает `FixCmuOn()` (`d5cbcbe2:src/graphics/host_gpu/renderer/diagF5.cpp:609`–`612`). В форме п. 504(ж)(2) (`KYTY_DIAG_F5=1`,
  `KYTY_FIX_F5CMU=1`, `KYTY_DIAG_F5ID` не задан) на обоих DCC-сайтах теперь зовётся `LastGpuWriteSeqExact` (`d5cbcbe2:src/graphics/host_gpu/renderer/cache/bufferCache.cpp:2875`,
  без замка, только чтение; ответ прежний — `exact_decides` = 0), строки — `exact=<fresh|stale|fallback>`; у `f5cmu_0b` кольца нет — `exact=na`.
  У F16m (`ed4f96d8`) плечо `f5cmu_1` DCC-сайты не пробовало. Решение не меняется, поток и замки те же [c] — это не дефект кода, но разница плеч.
- **Сценарий отказа.** Ридер F16q сопоставляет строки `dcc_stale` пары по всем полям (или заявляет «пара той же формы и того же пути, что F16m»):
  все строки пары расходятся по `exact` → пара объявляется несимметричной (помеха (е)(6)) или различие плеч приписывается правке `KYTY_FIX_F5CMU`.
- **Что изменить:** печать F16q (`docs/track-f/f16q.md`, Harness Engineer) — строки `dcc_stale` в паре `f5cmu_*` сопоставляются по `(site, image,
  dcc)` и `fix` (оба `off`), поле `exact` между плечами не сравнивается; фраза: «`f5cmu_1b` читает кольцо на DCC-сайтах (только чтение, решение
  прежнее), `f5cmu_0b` — нет». Код не меняется.
