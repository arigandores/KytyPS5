## 2. RC1 — ветка `clip_disable` не покрыта правилом ножниц

**Что не так.** П. 788(б)(1) и отчёт M9d2 §2 (стр. 36–39) утверждают: правило «площадь ножниц > 0» покрывает пустой слот,
ножницы нулевой площади «и ветку `clip_disable` одним правилом». По коду `main` `6fde3e0c` это неверно [c]:

- `renderDraw.cpp:436–439`: при `clip_disable` `viewport.width = min(maxViewportDimensions[0], 16384)` — **не 0**, у всех
  `viewport_count` слотов, независимо от гостя;
- `renderDraw.cpp:456–460`: правило пустого слота (`scissor.extent = {0, 0}`) срабатывает только при `viewport.width == 0.0f`
  — в ветке `clip_disable` **никогда**;
- `renderDraw.cpp:450–455` → `debug.cpp:816–861`: ножницы слота `i` = экранные ∩ оконные ∩ общие ∩ (только при
  `smc.vport_scissor_enable`, `debug.cpp:833`) ножницы вьюпорта `i` ∩ клип-прямоугольники. При `vport_scissor_enable = 0`
  ножницы **одинаковы у всех 16 слотов** и имеют площадь > 0 всякий раз, когда draw вообще растеризуется;
- `renderDraw.cpp:445–448`: `minDepth`/`maxDepth` слота `i` берутся из `zoffset`/`zscale` гостя и в ветке `clip_disable`.

**Сценарий отказа.** D32-цель, `test` или `write`, Z-экспорт или смещение; VS пишет `ViewportIndex` (`viewport_count` = 16);
`PA_CL_CLIP_CNTL.CLIP_DISABLE` = 1; `vport_scissor_enable` = 0 (или у неиспользуемого слота гость оставил ножницы
ненулевой площади); неиспользуемый слот `i ≥ 1` с `zscale = zoffset = 0` (как пустой слот RC1(а) M9e). Тогда слот `i`
проходит проверку площади, `lo = hi = 0`, `hi < 1` ⇒ `narrow`; `zx_narrow` / `bias_narrow` += 1 — ровно ложный `narrow`
RC1(а), ради которого вариант (1) выбран. По правилу п. 785(г)(3) тег получает «условие расхождения достигнуто», (г)(4)
(`НЕ ДЕФЕКТ` для форм, видимых счётчиком) по нему становится недостижимым. Встречается ли такой draw в ASTRO BOT — [U]
(так же, как RC1(а) и (б) — п. 788(а)); стенд T109 этого не видит: он зовёт `NoteDraw` напрямую, а ветка живёт в
`SetGraphicsDynamicParams`, и в `NoteDraw` нет признака `clip_disable`.

**Что изменить (решение лида — один из вариантов, записать до действия):**
1. **Свидетель кодом (рекомендую).** `NoteDraw` получает `bool clip_disable`; новое поле `T109Stat` `narrow_cd` — draw с
   `narrow`, у которых `clip_disable` и `count > 1`, — последним в строке; случай стенда `t109_cd16` (16 слотов, слоты 1–15
   `0/0` с ножницами 64×64, `clip_disable` ⇒ `zx_narrow` 1, `narrow_cd` 1) и мутант «поле не считается»; строка чтения п. 785(г):
   в (3) тег засчитывается, только если `zx_narrow − narrow_cd ≥ 1` (или `bias_d32 ≥ 1`), иначе — «не определено».
   Путь `=0` и подпись не меняются (то же место, тот же `Mode() >= 1`).
2. **Исправление признака** (слот считается, если ещё и `guest.xscale ≠ 0` до расширения `clip_disable`) — **не рекомендую**
   без свидетеля: если в draw с `clip_disable` гость не программирует вьюпорт и у слота 0, слот 0 выпадет и `narrow` пропадёт —
   ложный `0`, т. е. ошибка в сторону (г)(4) `НЕ ДЕФЕКТ`, хуже исходной.
3. **Без кода:** снять фразу «покрывает ветку `clip_disable`» из (б)(1) и записать строку чтения M9g: любой `zx_narrow ≥ 1`
   по (г)(3) — «не исключён ложный от `clip_disable`», следующий шаг (пара / снимок) обязан это различить. Цена — (г)(4)
   не выносится ни на одном теге с `narrow`, хотя причина может быть ложной.

Если RC1 не закрыть ни одним вариантом, отчёт M9d2 и п. 788(б)(1) содержат ложное утверждение о коде, а серия M9f может
дать (г)(3) вместо (г)(4) по причине, которую правка объявила устранённой.

## 3. Наблюдения (не RC)

- **Н1.** y1 и y2 выжили — эквивалентны на достижимых входах [c]: `ScissorRectClamp` (`debug.cpp:782–785`) при неверном
  прямоугольнике ставит обе стороны в 0, правило пустого слота — `{0, 0}`; ножниц с одной нулевой стороной код не строит.
  Действия не нужно; если путь построения ножниц поменяется — первым проверить это место.
- **Н2.** Аргумент места вызова (`scissors.data()`, а не другой массив) доказан только чтением: стенд зовёт `NoteDraw`
  напрямую. Того же класса, что Н4 п. 788(г); строка чтения M9g: нулевой или странный счёт `narrow` — сначала место вызова.
- **Н3.** Слот с `NaN` в глубине: отчёт M9d2 §2 стр. 40 («`narrow` не ставится этим слотом» [I]) неточен —
  `std::min(0,5f, NaN)` = 0,5 ⇒ `lo > 0` ⇒ `narrow`; `std::min(NaN, 0,5f)` = `NaN` ⇒ нет. Несимметрично по порядку [c по
  определению `std::min`/`std::max`]. Без `VK_EXT_depth_range_unrestricted` такой вьюпорт — нарушение правил Vulkan; на счёт
  T109 влияет только в этом вырожденном случае. Поправка текста отчёта, кода не нужно.
- **Н4.** В закреплённой копии две строки версии: `…-1938-g3f5d8725d` и устаревшая `…-1936-g3d2270241` (та же устаревшая —
  в `751bfa7f` M9d; в `ea35b679` одна). Отчёт M9d2 §1 называет только первую; `binary_m9d2.out.txt` печатает первой вторую.
  Опознание бинаря серии M9f — только по полю `binary_sha256` (п. 788(д)), не по строке версии.

клэмпу на ГП (в какой слот VS пишет на самом деле — [I], п. 788(е)); `shader_cfg_tests` и сверку SPIR-V M9d2 — не повторял
(файлов набора подписи в дифе 0 [c]); поведение бинаря в игре; всё из п. 785(ж). Ни одно число — не выигрыш; 60 FPS не
