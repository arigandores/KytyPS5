# S14b — враждебный отзыв проекта S-early `docs/track-s/s14a-design.md` (трек S, `HPP-503`, Red Team)

**Вердикт: `SOUND_WITH_CHANGES` — 12 RC.** Фаза A (диагностика `KYTY_S_EARLY_DIAG`) к коду годна после RC3, RC4, RC8, RC9;
фаза B (§6.2, §10) в нынешней форме к коду не допускается до RC1, RC2, RC5, RC6, RC7, RC11 — она может пройти критерий-кандидат
п. 408(г) по букве, показывая пользователю фриз (RC1), а её «потолок» оракулом может убить маршрут, который жив (RC2).

Вход: `docs/track-s/s14a-design.md` (KytyPS5 `887825c7`, проект `2280a6b4`); `ROADMAP.md` «СЕССИЯ 122» п. 408 целиком, 414(б)–(з),
229(д)(4), (е)(2) (`99e37f0` ps5-em; KytyPS5 `887825c7:docs/ROADMAP.md:21526`, якорь «408. **Звено S11 трека S»; +1 — «отгрузка под (B));
C5 — НЕТ»). Код читан на `2b1b8787` (база проекта). Игру не запускал, код не правил. Метки: [c] — по названной строке кода или лога,
[I] — вывод. Ни одно число — не выигрыш; 60 FPS не обещается.

## 0. Что проект делает верно (снимать нельзя)

- Главный факт §0 подтверждаю по коду: цена события держится на первой компиляции пайплайна, а не на трансляции. Строка
  `AvTrace: pipeline gfx … async` печатает `create_end - create_begin` вокруг `CreatePipelineInternal` на воркере
  (`2b1b8787:src/graphics/host_gpu/renderer/pipeline/pipelineCache.cpp:5505`–`5517`; ниже `:N` — этот файл на `2b1b8787`) [c]. Вывод §5 «одна трансляция (е)(2) не
  достигает» верен во всех трёх прочтениях модели (74–161 % ≫ 20 %).
- Вывод §3 «путь `CsPretranslate` на VS/PS не переносится без предсказания ключа» верен: `ProgramKey` включает `static_state`
  (`:2036`–`:2043`), а `BuildStageStaticKey` для VS кладёт в ключ таблицы вершинных атрибутов и даже числа `clip_space`
  (scale/offset/half_extent, `shader.cpp:862`–`:917`), для PS — `vs_export_count`, `wave_size`, интерполяторы (`:918`–) [c]. На
  регистрации этого нет.
- Порядок «сначала диагностика A, потом прототип B» и правило «C < 0,8 ⇒ стоп» — верная форма (дешёвый фальсификатор впереди
  дорогого кода). Отзыв ниже — о том, что фальсификатор в нынешней форме меряет не то.

## 1. Требуемые изменения

### RC1 — форма W превращает пропуск в видимый фриз, и критерий-кандидат этого не видит (картинка/фриз; MAJOR)

**Что не так.** Асинхронно создаётся только пара, которой нет в `m_ready_shader_pairs`
(`pipelineCache.cpp:5468`–`5469`: `pair_key = ShaderPairKey(vs_id, ps_id)`; `if (AsyncPipelinesMode() != 0 &&
!m_ready_shader_pairs.contains(pair_key))`). Любое создание пары — асинхронное (`:5524`), синхронное (`:5569`) и **precache**
(`:6675`) — вставляет пару в этот набор. Форма W (§10) создаёт пайплайн пары «существующим путём precache» по рецепту соседа —
значит, после прогрева пара «готова», и **настоящий** пайплайн этой пары на первом draw строится синхронно на GuestGpu
(`:5553` `CreatePipelineInternal` в вызывающем потоке), без пропуска draw и без удержания флипа.

**Сценарий отказа.** Прогрев W по соседу дал пайплайн с другим форматом цели рендера / другой раскладкой вершин. Переиспользует ли
драйвер компиляцию модуля при другом состоянии — [I] проекта (11 синхронных созданий по 137–215 мкс — это варианты пар, у которых
неизвестно, какие слова состояния различались). Если не переиспользует — каждое настоящее создание 61–287 мс идёт **на GuestGpu**:
показанный кадр 80–300 мс, `skipped draw` 0, `flip held` 0. Сумма п. 408(г) «строк пропуска + удержанных флипов» падает к 0,
член «0 атрибутированных кадров ≥ 1 с» выполнен (кадр < 1 с) ⇒ критерий-кандидат **пройден**, а пользователь видит фриз той же
длины, что раньше прятался удержанием. Запрет формы п. 229(д) («удержание флипа есть фриз и считается») обойдён переводом удержания
в длинный показанный кадр, которого сумма (е)(2) не считает.

**Что изменить.** (а) Проект называет: спекулятивный/прогревочный пайплайн **не** вставляет пару в `m_ready_shader_pairs` (свой
набор, например `m_warmed_pairs`), настоящее создание пары, прогретой спекулятивно, остаётся асинхронным; строка
`SEarly: real-after-warm vs= ps= us=` печатает цену настоящего создания такой пары (это и есть измерение гипотезы «драйвер ключует
модулями»). (б) Вопрос лиду (S14c), вариант рецензента: член критерия «на каждом уровне показанных кадров ≥ 100 мс после первого
кадра сцены у `=1` не больше, чем у `=0`, плюс шум пары» или их перевод в кадры `Σ (ceil(dt / 16 667) − 1)` внутри суммы (е)(2).
Без (а) или (б) приёмка B по букве п. 408(г) может принять фриз за исправление.

### RC2 — «потолок оракулом» не потолок: вывод «маршрут мёртв при любом предсказателе» не следует (MAJOR)

**Что не так.** §6.2: оракул — таблица «хэш → ключ, специализация, push, пара» из строк `SEarlyKey` / `SEarlyPipe` прошлого прогона.
Состояние пайплайна в `SEarlyPipe` есть только как XXH3 (`state`, §6.1) — восстановить рецепт из хэша нельзя. Значит, плечо оракула =
идеальные **модули** + состояние пайплайна **предсказателя W по соседу**. Это не идеальное предсказание.

**Сценарий отказа.** Оракул даёт сумму 35 % (> 20 %) потому, что W по соседу промахивается состоянием (RC1: цвет цели другой) —
проект объявляет «маршрут мёртв при любом предсказателе» (§6.2, §9(е)), хотя предсказатель состояния лучше соседского (или форма L,
которой состояние не нужно) достиг бы порога. Обратная ловушка: если Emu Engineer сделает оракул полным — с настоящими рецептами
`=0`-плеча того же уровня (`pipelines.bin` после `e0_<lvl>`), — плечо оракула есть S-cat одного уровня, а S-cat по пробе `u_1`…`u_5`
уже даёт `skipped draw` 0 (п. 408(е)) — «потолок» пройден тавтологически и ничего не говорит о предсказателе.

**Что изменить.** Два плеча оракула, названные до кода: **O-mod** (идеальные модули, состояние — предсказатель W) и **O-full**
(идеальные модули + настоящие рецепты новых пар из файла рецептов `=0`-плеча того же уровня, только пар, созданных после строки
входа). Правило: O-full > 20 % ⇒ маршрут мёртв (ни модули, ни состояние не спасают — значит, цена не в подготовке); O-full ≤ 20 % и
O-mod > 20 % ⇒ узкое место — предсказание состояния (вопрос форм W/L); O-mod ≤ 20 % ⇒ потолок W есть. O-full — справка, а не
кандидат отгрузки (это S-cat). Правило 32 для обоих файлов — как в проекте.

### RC3 — чтение A3 меряет «существует ли где-то раньше подходящий ключ», а прототип B предсказывает «последний ключ класса на момент регистрации» (MAJOR для порога C ≥ 0,8)

**Что не так.** §6.1 A3: «есть ли более ранний `SEarlyKey` **другого** хэша того же класса, у которого `key`, `spec` и `push` равны
фактическим». Два расхождения с B (§6.2 п. 1): (i) «более ранний» не привязан к моменту регистрации: B ставит задание на
`TraceShaderRegistration` (`:6316`) и повторно не предсказывает, а залп регистраций — за 3,1–5,5 с до первого использования (§4);
ключи, увиденные между регистрацией и первым использованием, B недоступны, A3 их засчитывает. (ii) «есть ли» (любой из ранних) против
«последний наблюдённый» — у класса с чередованием K1/K2 A3 видит K1 и засчитывает, B берёт K2 и промахивается.

**Сценарий отказа.** На `hero_kratos` 13 модулей серии 282–299; у 3 из них совпадающий ключ соседа появляется в кадрах 250–280 (после
залпа регистраций) — A3 засчитывает, C = 0,82 ⇒ фаза B открыта (2–4 дня кода, ≈ 1,9 ч замка), а B в серии промахивается теми же
тремя ⇒ серия остаётся целиком (правило «всё или ничего» самого проекта). Порог открывает дорогую фазу на завышенном числе.

**Что изменить.** A3 считает **ровно предсказатель B**: ключ = последний `SEarlyKey` того же класса с `host_us` < `host_us` строки
`SEarlyReg` цели; печатается рядом вариант «существование» как верхняя граница. Порог C ≥ 0,8 читается только по предсказателю B.
Сверх того — член A2+A3: предсказанный ключ засчитывается, только если `first_use.host_us − SEarlyReg.host_us` ≥ позиция в очереди
FIFO × 16,3 мс + цена создания (иначе предсказан, но не успеет).

### RC4 — порог фазы A меряет только модули, а 64 % стены — создание; C ≥ 0,8 необходим, но не достаточен (MAJOR)

**Что не так.** A4: «C = Σ кадров серий, все новые модули которых предсказаны». Но по §2 самого проекта max-задержка создания —
64,2 % стены, трансляция — 23,5 %. Модуль, предсказанный точно, без пары и состояния пайплайна оставляет создание на первом draw (§5:
74–161 % потерянных кадров). Строка «доля пар `SEarlyPipe`, у которых `SEarlyMap` пришёл раньше» печатается «отдельной строкой» и в
порог не входит.

**Сценарий отказа.** Модули предсказаны в 6 из 6 серий (C = 1,0), пары — в 2 из 6, состояние соседа совпадает по `state` в 0 случаях
⇒ фаза B открыта, B-код написан, B-прогоны дают 70 %+ потерянных кадров — ровно число §5 «трансляция снята, создание как есть».
Вывод был виден по данным A, но порог его не читал.

**Что изменить.** A4 печатает два покрытия: `C_mod` (как сейчас) и `C_pipe` — серии, у которых для **каждого** асинхронного
создания пара (`SEarlyMap` или сосед) и `state` соседа равны фактическим (XXH3 `state` из `SEarlyPipe` у обоих — достаточно для
сравнения). Порог фазы B (вариант рецензента, решение лида): `C_pipe` ≥ 0,8 для формы W; `C_mod` ≥ 0,8 при `C_pipe` < 0,8 — только
вопрос формы L (§10), не B-код W.

### RC5 — источник `snap1` (а) «цена 0 замка» не доказан и по общим правилам невозможен

**Что не так.** §8.3(а): `snap1` = «каталог сбора S13b», кэши после 19 входов. Но по общим правилам звена прогонов установленный
бинарь, его кэши и `GLCache` возвращаются после **каждого** плеча по sha и манифесту (задание `HPP-503`, общие правила; п. 408(л)).
После S13b накопленных `_ShaderCache/PPSA21564/<вариант>`, `_PipelineCache` и `GLCache` «после 19 входов» на диске нет — есть только
экспорт `_ShaderSeeds`. Каталог как стартовый (`ShaderSeed: installed`) — другая форма (не APP «тёплая локальная база»), и
`snap1_drv` из S13b не берётся вовсе.

**Сценарий отказа.** Harness Engineer берёт «каталог S13b» как есть: (1) если это возвращённые кэши установленной сборки — в них
уровни серий с. 143–146 (входили 59 из 114); попадёт ли туда любой из пяти уровней T2 — не проверено, гейт холода выбьет его уже на
плече `=0` после сбора и серии; (2) если это экспорт — форма меняется, а плечо `=0` сравнивается не с базой S10.

**Что изменить.** (а) Проект называет файлы, которые S13b оставит, и доказывает, что это накопленное состояние, или вычёркивает
вариант (а) и считает свой сбор (≈ 1,5 ч замка [I]). Накопление без возврата между 19 входами — исключение из правила возврата;
вопрос лиду. (б) До серии — офлайн-проверка без игры: хэши 35 новых шейдеров S10 (`false_s14a.out.txt`) против индекса кэша
трансляции `snap1` — 0 совпадений; иначе уровень выбывает до замка, а не после.

### RC6 — `bad = 0` в критерии тавтологичен: `VERIFY` в тегах §9 не включён (картинка; MAJOR)

**Что не так.** §6.2: `se_bad` / `bad` считаются только при `KYTY_S_EARLY_VERIFY=1`; §9 (в) требует `bad = 0`, но теги `e1_<lvl>`
`VERIFY` не включают ⇒ `bad = 0` по построению. Включать `VERIFY` в плечо A/B нельзя: на каждом попадании идёт обычная трансляция на
GuestGpu — экономия съедена, плечо не меряет то, что заявлено. Кроме того, `VERIFY` сравнивает только SPIR-V, а попадание отдаёт и
`CompiledShaderInfo` (привязки, план ресурсов, `AdvancePushData` — `pipelineCache.cpp:4039`): SPIR-V равен, привязки
разные ⇒ неверные дескрипторы ⇒ неверная картинка без единой строки `bad`.

**Сценарий отказа.** Спекулятивная трансляция VS берёт полный `input_info` соседа (другой хэш); транслятор читает поле, которого нет в
`static_state` (ключ — подмножество полей `input_info`, `shader.cpp:862`–`:952`). Ключ совпал ⇒ `hit`; модуль отличается
⇒ искажение геометрии на одном уровне. Теги A/B: `bad` 0 (не считался), видео — 3 000 кадров, детектор глитчей ловит одно-кадровые
дефекты, а не постоянный (п. 349 — Б42 детектор не видел) ⇒ приёмка.

**Что изменить.** (а) Отдельные плечи `v1_<lvl>` (`KYTY_S_EARLY=1`, `VERIFY=1`) на пяти уровнях и Sky Garden, член «`hits` ≥ 1 и
`bad` = 0» в каждом; (б) положительный контроль `VERIFY`: стенд, портящий одно слово готового SPIR-V и одно поле привязок, ⇒ `bad`
≥ 1; (в) `VERIFY` сравнивает SPIR-V **и** `CompiledShaderInfo` (привязки, план ресурсов, размер push-данных); (г) офлайн-тест на
корпусе T1 до B-кода: для шейдеров с ≥ 2 наблюдёнными `input_info` одного `static_state` — трансляция с чужим полным `input_info` ⇒
SPIR-V и `CompiledShaderInfo` байт в байт. Это доказывает предпосылку «равный ключ ⇒ равный результат», на которую спекуляция
опирается много сильнее, чем `ProgramCache` (там чужой `input_info` того же хэша, здесь — другого хэша).

### RC7 — форма W противоречит контракту §6.2 п. 2: нужны модули и id программ в `ProgramCache` до draw

**Что не так.** §6.2 п. 2: воркер «Vulkan, `ProgramCache` и живые дескрипторы не трогает». Но пайплайн (форма W) требует
`VkShaderModule` (`CreateCachedModule` в `CompilePermutation`, `pipelineCache.cpp:2197`) и id перестановки (`++next_shader_id`,
`:2212`), а `pair_key` строится из этих id (`:5468`). Значит, W вставляет спекулятивные перестановки в `ProgramCache` (`by_id`,
`programs`, `programs_epoch`) и, через `SaveToTranslationCache` (`:4020`), в **файл** кэша трансляции.

**Сценарий отказа.** (1) 245–274 ни разу не использованных VS/PS за запуск (§7) с ложными ключами записываются в кэш трансляции
пользователя и в каталог S-cat/S13 при следующем экспорте — рост файлов и стартового `LoadFromTranslationCache`; (2) `programs_epoch++`
и `g_programs_epoch_mirror` (`:4011`–`:4012`) сбрасывают `prog_memo` GuestGpu на каждой спекулятивной вставке — путь draw меняется
при `=1` вне попаданий; (3) id, выданный спекулятивной перестановке, на первом draw либо совпадает (попадание), либо пара прогрета
впустую — что именно ищет `GetGraphicsPipeline`, проект не говорит.

**Что изменить.** Проект называет для W: где живут спекулятивные перестановки, кто выдаёт id, пишутся ли они в кэш трансляции (вариант
рецензента: нет, до попадания), как их видит `prog_memo`; запись в состояние — таблицей «место в проекте / место в настоящем пути»
(чек-лист Red Team). Иначе B-ревью найдёт это в коде (прецедент `74d06051`, п. 175(в)).

### RC8 — фаза A не только измеряет: `known` берёт `m_mutex` на потоке гостя и меряет не то

**Что не так.** `SEarlyReg known=` — «есть ли в `ProgramCache` программа с этим хэшем; через `TryLock`». `programs` — `unordered_map`
по полному `ProgramKey` (`:3626`; у CS сайт `:6359` ищет `contains(key)` по полному ключу); поиск по одному хэшу — полный проход. 1 516–1 640 регистраций за 3–5 с залпа ⇒ каждое
удачное `TryLock` держит `m_mutex` на проход, пока GuestGpu ждёт (у CS такой сайт есть; для VS/PS он новый). Смысл тоже не тот: шейдер,
чья трансляция лежит в файле кэша, но не загружена в `ProgramCache` к моменту регистрации, печатается `known=0` ⇒ A2 завышает очередь.

**Таблица записей в состояние (чек-лист для ручки ТОЛЬКО ИЗМЕРЕНИЯ):**

| Запись / захват фазы A | Место в проекте | Та же запись в настоящем пути | Оценка |
|---|---|---|---|
| захват `m_mutex` (`TryLock`) | `TraceShaderRegistration`, каждая VS/PS-регистрация | для VS/PS — нет (только CS, `:6359`) | **новая**, RC8 |
| `LOGF` под `m_mutex` | `SEarlyKey` на трёх сайтах (`Compile`, `LoadFromTranslationCache`, `Resolve`) | `AvTrace` на тех же сайтах — при AvTrace | допустимо, если A-теги идут с AvTrace; ≈ 3 500 строк на precache меняют время экрана подготовки — в A не читается |
| поля `q/b/e_host_us` | хвост строки `:5517` | моменты уже снимаются (`queued_at`, `create_begin`, `create_end`) | без новой записи |
| таблицы, LRU, эпохи, биты трекера | — | — | нет |

**Сценарий отказа.** Залп регистраций совпадает с первыми кадрами сцены на части уровней (§4: последние 2 с — 41–110 VS/PS); GuestGpu
ждёт `m_mutex` за проходом по `programs` ⇒ первый кадр серии длиннее в DIAG=1, A1 «стена удержания» мерена на изменённом прогоне.

**Что изменить.** `known` — без `m_mutex`: либо свой хэш-набор, пополняемый на трёх сайтах перестановок (под их же замком), и чтение
атомарным снимком; либо `known` считает скорер офлайн по строкам `SEarlyKey` с тем же хэшем и меньшим `host_us`. Отдельное поле
`disk=` (есть ли в индексе кэша трансляции), если читается без замка; правило для `-` (неудачный `TryLock`) — если сайт с замком
останется — печатается и считается отдельной строкой, не как 0.

### RC9 — положительный контроль фазы A — путь печати; у A3 нет контроля, который может провалиться

**Что не так.** Контроли §6.1 («`SEarlyReg` ≥ 1 000», «`SEarlyKey src=cache` ≥ 1», T3 `e − b = us`) доказывают только, что строки
печатаются: T3 тождественна по построению — `us` и есть `create_end − create_begin`, печатаемые теми же отсчётами (`:5505`, `:5513`).
Тавтология. Вывод фазы A — число C из офлайн-скрипта A3, и у него контроля нет.

**Сценарий отказа.** Строка `key=` VS — до `13 + RES_MAX·13` слов hex (`:2143`); если логгер или выжимка `xt.py` обрежет длинную строку,
два разных ключа с общим префиксом совпадут ⇒ A3 «предсказал» ⇒ C завышен; или скрипт сравнивает `key` без `push` ⇒ то же.

**Что изменить.** (а) В строке `SEarlyKey` рядом с `key` — `key_n` (число слов) и `key_h` (XXH3 полных слов, посчитанный в процессе);
A3 сравнивает `key_h`+`key_n`+`spec_h`+`push`. (б) Положительный контроль A3 на данных: 2 строки `permutations` > 1 и 5 случаев «два
ключа на один код» (§3) — A3 в режиме «тот же хэш разрешён» обязан их найти. (в) Отрицательный: перестановка меток классов ⇒ C падает
к ≈ 0; иначе скрипт сломан. (г) Фикстуры на край: ключ, совпадающий только префиксом; класс с чередованием (RC3).

### RC10 — порядок плеч и тепло драйвера: доказательство есть в S10, но проект его не цитирует и не держит

**Что не так.** §9: «тепло драйвера возвратом не нейтрализовано [U]», чередование 0→1 / 1→0. Сумма п. 408(г) на 63 % — `hero_kratos`
(S10: 31 + 34 из 103) — порядок плеч одного уровня решает исход.

**Данные, которых проект не взял [c]:** в S10 `t2_cs0` (`hero_kratos`, ручка CS = 0) шёл сразу после `t2_1` (`hero_kratos`)
(`C:/kyty/s288/s10/times.txt` строка 211 — порядок серии «t2_1 (APP) -> t2_cs0 -> …», строка 213 — вызов `t2_1`; время изменения `log_t2_1.txt` 07:38:17, `log_t2_cs0.txt` 07:43:03 — часы файловой системы) — 30 / 32 против 31 / 34 после
возврата `snap0` и `snap0_drv`. Это одна пара свидетельства, что перенос тепла между плечами мал.

**Сценарий отказа.** На `hero_kratos` порядок 0→1; форма W при `=1` пишет блоб драйвера, возврат `snap1_drv` его снимает, но если тепло
живёт вне `GLCache` (место тепла — [U], п. 408) — `=1` проходит теплом; без контроля переноса в том же порядке это не отличить.

**Что изменить.** Цитировать пару `t2_1`→`t2_cs0` как довод; `e0b_hero_kratos` ставить **сразу после** `e1_hero_kratos` (контроль
переноса 1→0 в том же порядке, что опасен), `hero_kratos` — порядок 1→0; печатать сумму критерия и без `hero_kratos` (сколько решает
один уровень).

### RC11 — прогрев W «ниже приоритетом, ≥ 2 воркеров за настоящими» на машине с 2 воркерами не работает вовсе

**Что не так.** §6.2 п. 3: «≥ 2 воркеров остаются за настоящими»; `AsyncPipelineThreads` — 2–4 (`:243`, §1). При 2 воркерах прогреву
остаётся 0 — форма W не исполняется ни разу, и при 4 — 2. Сколько на этой машине — проект не говорит. Кроме того, «настоящее задание
не ждёт спекулятивного дольше одной идущей компиляции» = до 287 мс ожидания на воркер (`wait_us` уже до 146 мс [c]).

**Сценарий отказа.** На стенде 2 воркера ⇒ `warm=0` во всех плечах `=1` ⇒ плечо `=1` = «только трансляция», результат 74–161 %
(§5) ⇒ B объявлен неудачным, маршрут убит без проверки второй половины. Или 4 воркера и 2 занятых прогревом ⇒ настоящая очередь
серии `t2_1` (12 заданий) идёт вдвое медленнее ⇒ серия длиннее, чем при `=0`.

**Что изменить.** Проект печатает число воркеров на стенде (строка лога) и член плеча `=1` «`warm` ≥ 1» (положительный контроль W);
A2 моделирует обе очереди — трансляцию (1 воркер FIFO) и прогрев (воркеры W) против опережения; правило отказа — если прогрев на стенде
невозможен, B-код W не пишется.

### RC12 — фаза B без `VERIFY` и оракула не имеет условия, при котором её «нет вреда» проверяем на известных сценах

**Что не так.** §9 нулевой контроль `=1` — только «тёплый Sky Garden: `queued = 0`». Но `=1` ставит спекуляцию на **каждую**
регистрацию с `known=0` (§6.2 п. 1) и на известных уровнях — кэш драйвера и очередь растут на любом входе. Член п. 229(е)(1) (19
известных уровней: 0 пропусков, 0 удержаний) на `=1` не проверяется до отгрузки; проект его не упоминает.

**Сценарий отказа.** На известном уровне с тёплым каталогом спекулятивный прогрев 41–46 с воркеров (§7, [I]) занимает очередь в
момент входа; настоящее (редкое) создание ждёт ⇒ появляется `skipped draw`, которого при `=0` не было ⇒ (е)(1), принятое S13c на `=0`,
ломается отгрузкой S-early, а A/B на пяти холодных уровнях этого не видит.

**Что изменить.** Член B-прогонов: два известных уровня из списка S13 при `=1` против приёмки S13c — 0 пропусков и 0 удержаний
(вариант рецензента; решение лида), строка `dropped` / `queued` на них.

## 3. Вопросы лиду (S14c), варианты рецензента

1. RC1(б): член «показанные кадры ≥ 100 мс после первого кадра сцены у `=1` ≤ `=0` + шум» в критерий B — или их перевод в кадры в сумме.
2. RC4: порог фазы B по `C_pipe`, а не по `C_mod`.
3. RC5: исключение из правила возврата кэшей для сбора `snap1` (19 входов без возврата) — или вычеркнуть вариант (а).

## 4. Что этот отзыв НЕ доказывает

Что драйвер не переиспользует компиляцию модулей при другом состоянии (RC1 — сценарий, не измерение); что транслятор читает поля
`input_info` вне `static_state` (RC6 — риск, который проверяет офлайн-тест); что логгер обрезает длинные строки (RC9 — защита дешевле
проверки); число воркеров на стенде; что каталог S13b не годится как `snap1` (RC5 — по общим правилам возврата, не по файлам S13b).
