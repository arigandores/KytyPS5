# Трек P, звено P0 — офлайн-реверс источника шага симуляции (HPP-284)

Исполнитель: Lever Researcher. Основание: `d700ee60:docs/ROADMAP.md:11991` (п. 226, якорь «226. **Трек P — патч шага
симуляции игры», контроль +1 — строка 11992 «`date -u`, записано ДО задания агентам») и `d700ee60:docs/ROADMAP.md:12027`
(п. 226(е), якорь «(е) **Звено P0»). Игры, кода эмулятора и сборок нет. Замок `C:/kyty/SEALED_RUN.lock` на момент работы отсутствовал;
разбор — только `C:/kyty/eboot.elf` (sha256 `1f063c0cbf45123d…`, база 0x900000000, адреса ниже — без базы).

Скрипты — `C:/kyty/p283/p0/*.py`, выводы — `C:/kyty/p283/p0/out/`; sha256 (первые 16 знаков) — таблица в конце. Каждая ссылка
на код игры — адрес и файл вывода дизассемблера (`s8_func.py`/`s8_dis.py` capstone 5 или свой скрипт). Метки: [c] — прочитано
из дизассемблера/скана; [I] — суждение исполнителя; [U] — не установлено.

## Главное

1. **Общая переменная шага есть, одна, и она следует частоте кадров игры** [c]. Функция `0x34c0` = `SetFrameRate(double fps)`
   (`out/dis_34c0.txt`) пишет три глобала: `0x8fd4040` double `fps` (образ 60.0), `0x8fd4048` float `1/fps` (образ `0x3C888889`),
   `0x8fd4050` u64 `1e6/fps` мкс (образ `0x411A` = 16 666). Читают их только три геттера: `0x3520` → мкс, `0x3530` → `1.0/[0x8fd4040]`,
   `0x3550` → float (`out/dis_3513.txt`). Других обращений к глобалам в коде нет: RIP-скан всего сегмента кода — 6 ссылок, все
   внутри `0x34c0` и геттеров (`out/refs_dtglob.txt`); абсолютных указателей и записей `R_X86_64_RELATIVE` на глобалы, сеттер и геттеры — 0
   (`out/absptr_dtglob.txt`, `out/rela_dt.txt`; контроль метода: у `0x2a0980` запись RELATIVE находится — 1).
2. **Вызовы** (`out/callers_dt.txt`, E8/E9 по всему коду): `SetFrameRate` — 2 места; геттер мкс `0x3520` — 2 413 мест (1 612 функций);
   `0x3530` — 38; `0x3550` — 69. Из 2 413 вызовов `0x3520` **2 377** сразу превращают значение в множитель кадра
   `dt_us / 1e6 × 60` (умножение на double 60.0 по `0x8350930`; `out/usage_summary.txt`, `out/getter_uses.tsv`), 24 — в секунды
   (`/1e6`), 12 — целые мкс. То есть системы игры считают «сколько кадров по 1/60 прошло» из глобала, а не из литерала.
3. **Цель частоты — `[+0xac]`, не `[+0x1b4]`** (поправка к HANDOFF §2.13 `f1c3339:HANDOFF.md:5509`, якорь «Реверс: менеджер кадров
   `0x2a54c0`», контроль +1 — строка 5510 «(`[+0x1b4]`, выбор в 0x2a2680)»). `[+0x1b4]` — частота развёртки для замера FPS
   (60/90/120), `[+0xac]` — частота кадров игры (конструктор `0x29fc80`: 60). Обработчик режима дисплея `0x2a23d0` («Change Frame Rate
   from %d to %d») на смене режима зовёт `SetFrameRate((double)frameRate)` (`0x2a2788`–`0x2a2791`). **Шаг = 1 / частота кадров игры** —
   в режиме 90/120 игра шагает 1/90 или 1/120, а не 1/60 [c].

## Вопрос (1): кто читает `[+0x1b4]` и производные

Скан полей по модулю `OrbisBase` `0x29f000`–`0x2b2000` (`out/field_orbis.txt`, `p0_fieldscan.py`):

| адрес | функция | доступ | что |
|---|---|---|---|
| `0x29fcef` | `0x29fc20` конструктор | W | `[+0x1b4] = 60` |
| `0x2a269a` / `0x2a272d` / `0x2a2742` | `0x2a23d0` режим дисплея | W | `= 120` / `= 60` / `= 90` |
| `0x2a552a` | `0x2a54c0` замер FPS | R | `fps = [+0x1b4] × [+0xac] / Δvblank` → `[+0x9b0]` (float) |
| `0x2a553a` | `0x2a54c0` | W | `[+0x9b0]` — единственная запись производной |

Других читателей `[+0x1b4]` в модуле нет. Вне модуля смещение `0x1b4` у объекта менеджера не отделимо от чужих полей — не сканировалось [U].
`[+0x9b0]` читателей в модуле нет [c]; вне модуля — [U].

Выбор (`out/func_2a2680.txt`, 409 строк; ключевые, ≤ 30):

```
0x002a2513..: r15d = [props+0x560]+0x28   ; свойство «частота кадров»
0x002a264b: cmp [rbp-0x68], 0xc            ; новый режим дисплея == 0xc
0x002a2680: cmp r15d, 0x78 ; je 0x2a269a   ; 120 -> [+0x1b4]=120
0x002a2686: cmp r15d, 0x5a ; je 0x2a2742   ; 90  -> [+0x1b4]=90
0x002a2690: cmp r15d, 0x3c ; jne 0x2a274e  ; 60  -> [+0x1b4]=120; иначе assert OrbisBase.cpp:0x4ac
0x002a26a9: cmp r12d, 0xc ; jne 0x2a2739   ; выход из режима 0xc:
0x002a2723: mov [rbx+0xac], 0x3c ; 0x2a272d: mov [rbx+0x1b4], 0x3c
0x002a2739: mov r15d, [rbx+0xac]           ; иначе частота прежняя
0x002a2781: mov [rbx+0xac], r15d
0x002a2788: vcvtsi2ss xmm0, xmm1, r15d
0x002a278d: vcvtss2sd xmm0, xmm0, xmm0
0x002a2791: call 0x34c0                    ; SetFrameRate(frameRate)
```

## Как игра переходит на 90/120

[c] `0x2a23d0` вызывается каждым кадром из главного цикла (`0x2a35fd`), выходит сразу, если не изменились: флаг `[+0xb4]`, режим дисплея
`[+0x1a8]`, частота `[+0xac]`, свойство `[+0xb0]` (`0x2a258a`–`0x2a25a3`). Частота из свойства (60/90/120) принимается **только в режиме
дисплея 0xc**; при выходе из него — принудительно 60. Затем `SetFrameRate(частота)`. Режим 0xc [I] — выход 120 Гц (развёртка 120 для
частот 60 и 120), 90 — вероятно VRR. На эмуляторе игра шагает 1/60 (с. 10: 756 кадров на анимацию 12,0 с), то есть частота 60.
**Шаг следует цели — это главный кандидат** (указание звена).

## Вопрос (3): общая переменная, под-шаги, счётчик кадров

* Общая переменная dt: **да** — `0x8fd4040` / `0x8fd4048` / `0x8fd4050`; писатель один (`0x34c0`), вызывается 2 раза: старт
  `0x2a0cad` (аргумент — double 60.0 из `0x8350930` в `0x2a0ca5`, `out/func_2a0cad.txt`) и смена режима дисплея `0x2a2791`. Каждым кадром
  игра её **не пересчитывает** [c].
* Под-шаги физики: аккумулятора в пути dt не найдено [c: в диапазоне модуля физики `0x9f0000`–`0xb40000` вызовов геттеров 0,
  `out/getter_uses.tsv`]. Физика — Havok hknp (строки `hknpWorldCInfo_expectedDeltaTime…`, `hknpVariableTimeStepUtil`, `enableDynamicSubstep`,
  `out/strings_time.txt`); конфиг мира держит 1/60 (`0xa74f44`–`0xa74f74`). Откуда шаг hknp — аргумент из вызывающего или своё 1/60 — **[U]**,
  вопрос P1.
* Счётчик кадров: `[+0x58]` (`0x2a3626 inc`) — делитель замера FPS; `[+0x24c]` сравнивается с 60 (`0x2a4853`) — усреднение профиля.
  Таймеры систем идут в «кадрах по 1/60» × множитель кадра из глобала (2 377 мест), то есть следуют dt [c-форма, смысл [I]].

## Вопрос (4): вердикты маршрутов п. 226(в)

**P-target — ЖИВ.** Условие убийства дословно (`d700ee60:docs/ROADMAP.md:12008`, якорь «шаг = 1 / цель, патч — цель 30»; контроль +1 —
12009): «Убит, если реверс показывает, что шаг игрового процесса не читает цель (или её производную) либо цель 30 отвергается кодом без
обхода ≤ 3 правками.» Не выполнено: шаг = `1/частота` через `SetFrameRate` (`0x2a2791`); значение 30 путь свойства отвергает assert-ом
(`0x2a274e`) только в режиме 0xc, а обход — **2 правки** (аргумент `SetFrameRate` в обоих местах вызова). P(жив после P1) ≈ 0,8 [I]:
основание — единственный писатель и нулевые косвенные ссылки [c]; риск — неразобранные 27 функций и физика [U].

**P-const — условие убийства НЕ выполнено; как отдельный патч совпадает с P-target.** Условие дословно (`d700ee60:docs/ROADMAP.md:12011`,
якорь «Убит, если независимых источников шага»; контроль +1 — 12012): «Убит, если независимых источников шага в системах игрового
процесса (движение игрока, физика/коллизии, анимация, камера, таймеры уровня) больше 5 без общей переменной.» Два прочтения (правило:
печатать оба): (а) «> 5 источников И общей переменной нет» — общая переменная есть → **не убит**; (б) «> 5 источников в обход общей
переменной» — кандидатов в обход 27 функций, доказанных источников шага 0 → **не определено [U]**. Вопрос лиду: какое прочтение.
Ловушка [c]: «постоянная» шага — double 60.0 по `0x8350930`, но та же ячейка — множитель `×60` в 2 377 местах; правка самой ячейки даёт
`33 333 / 1e6 × 30 = 1,0` — ускорения нет, все переводы единиц ломаются. Правится только загрузка в `0x2a0ca5`. P ≈ P-target [I].

**P-var — ЖИВ.** Условие дословно (`d700ee60:docs/ROADMAP.md:12014`, якорь «Убит, если общей переменной dt нет»; контроль +1 — 12015):
«Убит, если общей переменной dt нет (тогда он совпадает с убийством P-const) или игра пересчитывает её после записи эмулятора без точки
перехвата ≤ 3 правками.» Не выполнено: переменная есть; игра пишет её только на старте и при смене режима дисплея (на эмуляторе не
ожидается [I]); чтение — всегда через геттеры, без встраивания [c]. Точка — 3 записи эмулятора, 0 правок игры. P(жив после P1) ≈ 0,75 [I]
(риск: гонка записи с потоками игры посреди кадра; ограничитель берёт шаг прошлого кадра).

## Вопрос (5): байты патча и проверка

**P-target / P-const, шаг 1/30 (2 места, адреса относительно базы, форма `KYTY_POKE`):**

| `2a2788` | `c4c1722ac7c5fa5ac0` | `c5fb1005d0d90a0890` | `vcvtsi2ss; vcvtss2sd` (частота) → `vmovsd xmm0,[0x8350160]; nop` (следующая — `call 0x34c0` на `0x2a2791`) |


`27e46c:909090909090` — уже принятая правка лога игры (`f1c3339:docs/env-vars.md:913`, якорь «**Лог самой игры**»; контроль +1 — 914

обе правки на месте до первого `SetFrameRate`. Кодировки проверены декодом (`vmovsd xmm0, qword ptr [rip + 0x80af4b3]` → `0x8350160`).

Вариант исполнителя (не рекомендован первым): частота 30 в конструкторе `0x29fc80` (`48c783ac0000003c000000` → `…ac0000001e000000`) +
`2a0ca5`; меняет и делитель замера FPS, а прочие читатели `[+0xac]` вне модуля не отделены [U].

**P-var:** правок игры нет; эмулятор на каждом флипе пишет `k` = число вблэнков кадра (кламп 3, то есть 1/20):
`[база+0x8fd4040]` double `60/k`, `[база+0x8fd4048]` float `k/60`, `[база+0x8fd4050]` u64 `1 000 000·k/60`. Все три — иначе `0x3530`
(`1/[fps]`) и `0x3550` разойдутся. Ручка по умолчанию 0 (п. 226(в)(3)); это Emu Engineer.

**Проверка в прогоне (часы игры п. 226(г)(1)):** `GuestOut: Play/Finished: <имя>.anim` с длительностью из заголовка `.anim` (float +4,
fps +8) — `f1c3339:HANDOFF.md:5506` (якорь «**Игра фиксированного шага.**»; контроль +1 — 5507 «длительность по +4, fps 60.0 по +8»).
Без патча 12,0 с — 756 кадров; с шагом 1/30 ожидаемо ≈ 378 кадров [I]; скорость = длительность / стена между `Play` и `Finished`.
Второй признак — логотип Sony 3,0 с = 180 кадров → ≈ 90. Прямой признак правки — не часы (не независим): чтение `0x8fd4048` отладчиком
или `Change Frame Rate` в логе игры.

## Риски корректности (для P1 и прогона; не выигрыш)

* Ограничитель `0x2a470b`: при шаге 1/30 кадр ≥ 30 мс → каденс 2 вблэнка; кадр > 33,3 мс уходит в 3 вблэнка, и тогда шаг 1/30 отстаёт
  (скорость < 1) [I]. P-var этого не имеет (шаг = фактические вблэнки).
* Физика Havok: шаг hknp и конфиг 1/60 (`0xa74f74`) — [U]; вдвое больший шаг → туннелирование, провалы, прыжки.
* 27 функций с арифметикой над литералом 1/60 и 173 неразобранных — если среди них шаг, эта система пойдёт вдвое медленнее [U].
* Режим 0xc на эмуляторе не включается [I] — второй `SetFrameRate` может не вызываться; патч держит оба места.

Не заявляется: что патч возможен до прогона п. 226(г); что шаг один; что 1/30 не ломает физику; ни одно число — не выигрыш; 60 FPS не
обещаются.
