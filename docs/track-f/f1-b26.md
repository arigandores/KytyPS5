## 1. Что это за опкоды (руководство ISA RDNA2)

Первоисточник: AMD, «"RDNA 2" Instruction Set Architecture Reference Guide», 30 ноября 2020 (локальная текстовая копия
`C:/kyty/s49/rdna2-official.txt`). Разделы: 12.3 «SOP1 Instructions», 12.9 «VOPC Instructions», 13.1.3 «SOP1» (таблица 68
«SOP1 Opcodes»), 13.3.3 «VOPC», 6.2.1 «Instruction Inputs» (подраздел «Literal Expansion to 64 bits»).

| строка лога | номер | имя по ISA | семантика по ISA (дословно) | сырое слово → разбор |
|---|---:|---|---|---|
| `family=SOP1 opcode=0x21` | 33 | **`S_SWAPPC_B64`** | «Save current program location and jump to a new location. S0.u64 is a byte address of the instruction to jump to. Destination receives the byte address of the instruction immediately following the SWAPPC instruction. D.u64 = PC + 4; PC = S0.u64.» | `0xbe8e210e` → `s_swappc_b64 s[14:15], s[14:15]` (SDST=14, OP=0x21, SSRC0=14) |
| `family=SOP1 opcode=0x0c` | 12 | **`S_BREV_B64`** | «Reverse bits. D.u64[63:0] = S0.u64[0:63].» | `0xbe8a0cff 0x20468000` → `s_brev_b64 s[10:11], 0x20468000` (SSRC0=0xff — литерал) |
| `family=VOPC opcode=0xe3` | 227 | **`V_CMP_LE_U64`** | «D[threadId] = (S0 <= S1). // D = VCC in VOPC encoding.» | `0x7dc60200` → `v_cmp_le_u64 vcc, s[0:1], v[1:2]`; `0x7dc60004` → `…, s[4:5], v[0:1]`; `0x7dc60008` → `…, s[8:9], v[0:1]` |

Сверка с таблицами декодера эмулятора (`f19c0f32`): SOP1 `0x1f` → `S_GETPC_B64`, `0x20` → `S_SETPC_B64`
(`src/graphics/shader/recompiler/frontend/decode/ScalarAluOps.cpp:58–59`), `0x0b` → `S_BREV_B32` (`:47`) — нумерация gfx10, и
`0x21`/`0x0c` — следующие за ними `S_SWAPPC_B64`/`S_BREV_B64`; VOPC `0xe1`/`0xe2`/`0xe4`/`0xe5` → `V_CMP_LT/EQ/GT/NE_U64`
(`frontend/decode/VectorAluOps.cpp:247–249`) — пропуск `0xe3` и есть `V_CMP_LE_U64`.

Проверка семантики `S_BREV_B64` на месте [c]: по правилу 6.2.1 литерал для 64-битного беззнакового операнда расширяется нулём,
`rev64(0x00000000_20468000)` = `s10 = 0`, `s11 = rev32(0x20468000) = 0x00016204`; соседняя ветка того же шейдера пишет
`s_mov_b32 s11, 0x16204` (`57c4d5848e02ecdc`, pc `0x154`) — то же значение, т. е. это дескриптор буфера, собранный другим путём.

## 3. Почему строка есть и что было бы при исполнении

1. Все 101 строки печатает **предтрансляция** `CsPretranslate` [c]: `PipelineCache::TraceShaderRegistration`
   (`src/graphics/host_gpu/renderer/pipeline/pipelineCache.cpp:5968–6014`) ставит в очередь каждый **регистрируемый** CS
   (не только исполняемый), рабочий поток переводит его с нулевыми user data под перехватчиком фатальной ошибки
   (`computePretranslation.h:212–232`) и печатает `CsPretranslate: skipped … reason=…ShaderCFG.cpp:44 shader CFG build failed:
   unsupported decoded instruction in CFG …`. Проверка CFG останавливается на **первой** неподдержанной инструкции
   (`frontend/cfg/ShaderCFG.cpp:2082–2089`) — дальнейшие неподдержанные инструкции тех же шейдеров в лог не попадают [c по коду].
2. Рабочий путь (перевод шейдера при dispatch) идёт через тот же `CFG::BuildGraph`, но **без перехватчика**: перехватчик
   ставится только в предтрансляции (`src/common/assert.h:12–15`, единственное использование — `computePretranslation.h:212`),
   а `EXIT` без него — `DbgExit(321)` (`assert.h:63–67`). Значит, dispatch любого из 101 шейдера = остановка эмулятора с
   `shader CFG build failed` без префикса `CsPretranslate` [c по коду].
3. На 12 логах с. 142 таких строк 0 [c], процессы шли дальше. Следовательно, **в наблюдаемых сценах ни один из 101 шейдера не
   исполнялся** [I, по 2 и 3]; видимого последствия у Б26 на этих входах нет, картинка от него не зависит. Скрытое последствие —
   **K1 (крэш) в любой сцене, которая исполнит один из этих шейдеров**; такой сцены в логах с. 142 нет, в 151/155 логах с. 113–140
   — не проверялось этим звеном (свип F0).
4. Строка лога — цена спекулятивной предтрансляции, а не дефект кадра. «Убрать строку» можно и не исполняя опкод (например,
   молча пропустить предтрансляцию таких шейдеров) — это спрятало бы маркер, а не починило механизм; такая правка не предлагается.

## 4. Проект: поддержка `S_SWAPPC_B64` (вызов по указателю из user data)

**Что поддержать.** Шейдер с `s_swappc_b64 s[R:R+1], s[T:T+1]`, где `s[T:T+1]` при dispatch равно адресу функции в памяти
гостя; функция возвращается `s_setpc_b64 s[R:R+1]`. Цель — перевести шейдер с **встроенной** (inline) копией функции на каждом
месте вызова, специализированной по значению указателя.

**Как (вариант A — встраивание при dispatch, предлагаемый).**
1. Декодер: `S_SWAPPC_B64` в таблицу SOP1 (`0x21`) как управляющая инструкция (рядом с `S_SETPC_B64`,
   `ScalarAluOps.cpp:59`, `ShaderDecoder.cpp:528–531`).
2. Разрешение цели: скалярная трасса до начального SGPR (у CFG уже есть трасса констант для `S_SETPC_B64` —
   `ShaderCFG.cpp:339–351`, `:436`, `:520–547`); значение берётся из user data dispatch (`CompileOptions::user_data`). Не
   разрешилось (регистр пишется в шейдере, цикл, 339 мест из п. 2 с поздней записью) — отказ **без EXIT**: dispatch
   пропускается с явной строкой лога (как `AsyncPipelines: skipped draw`), это не исправление, а страховка от K1.
3. Чтение тела функции из памяти гостя через `Libs::LibKernel::Memory::TryReadBacking` (как `shader.cpp:231–238`) до
   `s_setpc_b64 s[R:R+1]` с пределом длины; вложенные `S_SWAPPC_B64` — рекурсивно с пределом глубины; `S_GETPC_B64` внутри
   функции должен давать адрес **функции** (сейчас GETPC shader-relative, `backend/spirv/spirvEmitterFlow.cpp:749`) —
   нужен отдельный сегмент pc.
4. CFG: программа из нескольких сегментов кода — функция размещается в синтетическом диапазоне pc за концом шейдера, отдельная
   копия на каждое место вызова (возврат статичен: `s[R:R+1]` = pc следующей за SWAPPC инструкции); SWAPPC → запись констант
   адреса возврата в `s[R:R+1]` + безусловный переход; `s_setpc_b64 s[R:R+1]` в функции → переход на возврат. Если функция
   сохраняет/портит `s[R:R+1]` (спилл в VGPR/память) — отказ по п. 2.
5. Ключ программы и кэш трансляции: хэш шейдера + адреса и хэши тел всех встроенных функций (иначе смена указателя вернёт чужую
   трансляцию); предтрансляция без user data такие шейдеры не переводит, а откладывает с одной строкой `deferred: needs dispatch
   user data` (строка другой формы, не `unsupported`).
6. Ручка `KYTY_FIX_B26` (`gates.cpp`, последней строкой; 0 — прежнее поведение байт в байт: декодер отдаёт `UNSUPPORTED`).

**Вариант B (не предлагается как исправление).** Только п. 2 «отказ без EXIT» — убирает скрытый K1, но шейдер не исполняется;
по (B) это не отгрузка.

**Риски.** (а) Нет стенда: в 12 логах с. 142 эти шейдеры не исполнялись (п. 3.3) — доказать правильность встраивания игрой

## 5. Готовый план двух ALU-опкодов (не исполнен: «СТОП правкам» задания; исполняется по пункту лида)

`S_BREV_B64` и `V_CMP_LE_U64` — обычная арифметика, не управление потоком; их поддержка не требует нового CFG.

* `S_BREV_B64`: `Opcode::S_BREV_B64` последней строкой перечисления; `{0x0cu, Opcode::S_BREV_B64}` в таблицу SOP1
  (`ScalarAluOps.cpp:47` рядом); 64-битный назначение/источник как у `S_BCNT1_I32_B64`; перевод рядом с `S_BREV_B32`
  (`frontend/translate/Scalar.cpp:169`): `lo' = BitReverse32(hi)`, `hi' = BitReverse32(lo)` (нового IR-опкода не нужно);
  литерал — расширение нулём (6.2.1). Тест: `s_brev_b64 s[10:11], 0x20468000` → `s10 = 0`, `s11 = 0x00016204`; и 64-битный
  регистр-источник с разными половинами.
* `V_CMP_LE_U64`: `{0xe3u, Opcode::V_CMP_LE_U64, false}` (`VectorAluOps.cpp:247–249`), перевод рядом с `V_CMP_LT_U64`
  (`frontend/translate/Vector.cpp:103–105`) — `ULessThanEqual64` отсутствует в `ir/opcodes/ValueOpcodes.inc`, поэтому либо
  новый IR-опкод (эмиттер SPIR-V `OpULessThanEqual`, свёртка констант), либо `LogicalNot(UGreaterThan64)`. Тесты: равные,
  меньше, больше, старшая половина решает, форма VOP3 с SGPR-назначением.
* Ручка `KYTY_FIX_B26`: при 0 обе записи таблиц отдают `UNSUPPORTED` — прежнее поведение байт в байт.
* Что это даст [I]: 5 шейдеров пройдут свою **первую** точку отказа; переведутся ли они целиком, неизвестно (после первой
  неподдержанной инструкции проверка не идёт, п. 3.1) — `ALL OK` тестов и 0 строк этих двух опкодов на входе — да, видимый
  эффект — нет (шейдеры не исполнялись, п. 3.3). Профиль после правки: 96 / 0 / 0 (или новые строки других опкодов тех же
  5 шейдеров).
