## 0. Итог

1. **Развязка ограничителя — одна правка игры, одно место `2a470b`, 25 байт:** ограничитель берёт double 1/60 из неиспользуемой ячейки
   `0x8352430` (сегмент R) вместо `call 0x3530`; результат бит в бит тот же, что у плеча A (§1). Правок игры P-var — **1** (с правкой лога
   `27e46c` — 2) ≤ 3: условие убийства п. 226(в)(3) не выполнено, **P-var жив**.
2. **Флип гостя выдаёт не тот поток, который читает шаг.** Игра не импортирует `sceVideoOutSubmitFlip`; флип — `sceAgcDcbSetFlip` +
   `sceAgcDriverSubmitDcb` из `0x4a5a50`, которую зовёт **поток рендера «DrawThread»** `0x2a9cb0`; шаг читает **главный поток** в кадровой
   функции `0x2a34d0`, идущей параллельно рендеру предыдущего кадра (рукопожатие `[obj+0x168]`). Запись «в вызове флипа» (буква
   п. 276(е)(1)) попадает в произвольное место обновления следующего кадра: часть систем кадра шагает на старое k, часть на новое (§3.4).
   **Вариант исполнителя [В 1] — значение ручки 2:** защёлка в начале кадровой функции главного потока — там же, где шаг меняет сама игра
   (`0x2a35fd` → `SetFrameRate`): HLE `sceKernelGetProcessTimeCounter` с адресом возврата `база+0x2a352a`. Источник k прежний (вблэнки
   между двумя последними флипами), меняется только момент записи.
3. **Кто читает шаг не как шаг (§2):** ограничитель `0x2a470b` (развязан); `0xd254b3` — бюджет по длительности кадра; `0x103e92e`,
   `0x103e9fb` — сон длиной в шаг; **две статические копии шага**, инициализируемые один раз из геттера (`0xe7d65e8`, `0xeb9ef4c` — пороги
   «скачок времени больше кадра»): при переменном k они застывают на k первого исполнения [В 5]; у ячейки `0x834f34c` (P3) от k в момент
   расчёта зависят инерция Havok `0x687370` (×k) и пять порогов длины узла AnimDriver. Замер FPS `0x2a54c0` шаг не читает.
4. **Скорер [В 2], [В 3]:** r̂ по букве п. 276(ж)(1) ≈ 1,0, а ожидаемое отношение кадров пар qv/qa ≈ 1 / (среднее k) ≈ 0,51; правило
   целостности пар ±2 % по кадрам (п. 243(в)) при переменном шаге теряет смысл: число кадров пары гуляет вместе с k. Вариант — считать пары
   в игровом времени Σ k/60 по строкам `PVar:`.
5. **`KYTY_AUDIO_SYNC` [В 4]:** по умолчанию темп гостевых часов при 30 FPS — 0,5, а симуляция под P-var идёт в реальном времени: звук
   растянут вдвое против картинки [c-form]. Вариант исполнителя — `qv_` (и `qa_A`) с `KYTY_AUDIO_SYNC=0`.
6. **Предсказание [I] (§4):** Σ s / Σ `dt` на Sky Garden 0,999 (проекция по `pa_A`/`pa0_A0` 0,9994–0,9999), на `sponge_dirty_bath`
   0,998–1,000, на `hoover_beach` 0,986–0,989 (кламп сверху); доля кадров ≥ 3 вблэнков ≈ `qa_A` ± 2 п. п.; k меняется на 21–22 % кадров Sky

### 2.2 Замер FPS, делители, динамическое разрешение

### 2.3 Ячейка `0x834f34c` (44 места P3 и строки «lost») при переменном k

### 3.2 Источник k и публикация

В `FlipQueue::Flip` сразу после `videoOut.cpp:1229`, под `r.cfg->mutex` (взят в `:1163`, отпущен в `:3164`), на **каждом учтённом флипе** —

совпадает с `FrameTrace: n=`. `kraw = vblank_status.count − (его значение на предыдущем учтённом флипе)`; первый учтённый флип только
запоминает счётчик и ничего не публикует. Публикация — **одно атомарное 64-битное слово**: биты 0–15 `min(kraw, 0xffff)`, биты 16–39 —
младшие 24 бита `vblank_status.count`, биты 40–63 — младшие 24 бита `flip_status.count` (прогон короче 2^24 вблэнков ≈ 77 ч); слово 0 —
«ещё не опубликовано». Флип — не больше одного на тик (`Flip(0)` между `VblankBegin` и `VblankEnd`) ⇒ **`kraw ≥ 1`**; `kraw` = 0 —
нарушение: `pvar_k0` + 1 и строка `PVar: k0 n=<u>`, слово публикуется как есть. Тик — `Config::GetVblankFrequency()` (`:828`; ключ
`--vblank-frequency`, умолчание 60), обязан быть 60, иначе отказ вооружения. Петля Present догоняет пропущенные тики без сна ⇒ Σ `kraw` =
вблэнки стены [c-form]: на девяти логах этапов 1–2 Σ k · 16 667 / Σ `dt` = 1,0000–1,0001 (k — бин `dt`; §4) [c] — флипы лежат на сетке
60 Гц; равенство `kraw` бину своего кадра — [I], его печатает T7. k = min(max(kraw, 1), 3) — кламп п. 276(е)(1).

### 3.4 Момент записи и гонки чтения внутри кадра

Читатели шага в кадровой функции главного потока по порядку [c]: `0x2a3525` — первый вызов `sceKernelGetProcessTimeCounter` (маркер
**M0**, адрес возврата `0x2a352a`; от `0x2a34d0` до него ни одного ветвления) → `0x2a35fd` обработчик режима дисплея (сама игра пишет шаг
здесь) → `0x2a3612` `0x3550` → `0x2a413a` обновление приложения (`0x10afe2d` `0x3530` → `Game::Update`; дальше по дереву — места `0x3520`) →
`0x2a4698` вызов `sceKernelGetProcessTimeCounter` (маркер **M1**, адрес возврата `0x2a469d`) → `0x2a470b` ограничитель → ожидание рендера →
хвост `0x2a4966`…`0x2a4c24` (в нём `0x73a8e90` с `0x3530` в `0x73a9085`) → пуск рендера `0x2a4d9c`. Оба маркера — вызовы одного HLE; у
каждого свой адрес возврата. **Фаза главного потока** P: 0 — до первого M0; 1 — от M0 до M1 (обновление); 2 — от M1 до следующего M0
(ограничитель, ожидание, хвост). В теле потока рендера прямых вызовов геттеров 0, среди 27 функций, которые оно зовёт прямо (191 вызов),
вызывающих геттеры нет (сверка с `p0/out/getter_uses.tsv`); 45 косвенных вызовов и второй уровень — [U]; рабочие потоки заданий — [U].

**Значение 1 (буква п. 276(е)(1)): запись в каждом вызове `AgcDcbSetFlip`** (все три места игры; пишущих потоков гостя может быть
несколько — состояние писателя под своим мьютексом). Флип кадра N выдаётся между пуском рендера N и концом ожидания в кадре N+1 главного
потока: либо внутри обновления N+1 (P = 1), либо после него (P = 2), но до хвоста N+1. Следствия [c-form по порядку вызовов]: (1) запись при
P = 1 и смене k (k меняется на 21–22 % кадров Sky Garden, §4) даёт кадр, где `Game::Update` и мир hknp шагнули на старое k, а системы после
точки записи — на новое; (2) точка записи плавает относительно читателей, поэтому система может одно значение пропустить, а соседнее взять
дважды — суммы шагов у систем расходятся случайным блужданием [I]; (3) запись при P = 2 и смене k — хвост кадра видит не то k, что его
обновление; (4) строки `PVar:` в логе не привязаны к кадрам главного потока — скорер не может сложить шаги пары `Play→Finished`. Инструмент
это мерит: `pvar_inupd`, `pvar_tear`, `pvar_tail` (§3.6).

**Значение 2 (вариант исполнителя [В 1]): защёлка на M0.** `sceKernelGetProcessTimeCounter` — HLE `KernelGetProcessTimeCounter`
(`4fc501f4:src/kernel/pthread.cpp:4012`, якорь «uint64_t KYTY_SYSV_ABI KernelGetProcessTimeCounter() {»; +1 — 4013 «return
KernelGetElapsedTsc();»), регистрация `src/libs/libKernel.cpp:3352` (якорь «LIB_FUNC("fgxnMeTNUtY",
LibKernel::KernelGetProcessTimeCounter);»; +1 — 3353, пустая строка). Гость зовёт HLE напрямую, адрес возврата гостя —
`__builtin_return_address(0)` (прецедент `pthread.cpp:4708`, якорь «reinterpret_cast<uint64_t>(__builtin_return_address(0)) -
0x900000000ull,»; +1 — 4709). При вызове с адресом возврата `база+0x2a352a` главный поток стоит на границе кадра: все его чтения шага этого
кадра — после, хвост предыдущего кадра — до. Запись — в этом вызове, ДО перевода фазы в 1; значение — последнее опубликованное слово.
Пишет только поток первого M0: M0 из другого потока — `pvar_bad` + 1, строка `PVar: bad reason=thread n=<u>`, записи нет. Остаточная гонка:
другие потоки гостя, читающие геттер в момент четырёх записей, — [U], ограничена одним кадром. Слабое место: фазы, где кадровая функция не
идёт, а флипы идут (второй путь флипа `0x464d90`) — шаг стоит на последнем значении; видно по `pvar_skip`.

**До первой публикации** (слово 0) оба режима не пишут, строк не печатают и счётчиков не трогают: ячейки остаются равны образу (k = 1).

**Задержка k:** шаг кадра — интервал флипа двумя-тремя кадрами раньше (обновление → рендер → GuestGpu → тик). В сумме потерь нет, на смене
k шаг не равен интервалу показа своего кадра (§4). Величину задержки скорер печатает сам — сдвиг, при котором k строк `PVar:` лучше всего
совпадает с бинами `FrameTrace` (не гейт).

### 3.5 Чтение ручки, вооружение, строка лога

`KYTY_PVAR` читается `std::getenv` **один раз на процесс**, при первом обращении (функция со статической переменной); первое обращение —
регистрация библиотек: при значении 1 или 2 под `fgxnMeTNUtY` (`sceKernelGetProcessTimeCounter`) и `YUeqkyT7mEQ` (`sceAgcDcbSetFlip`)
регистрируются обёртки, при 0 или отсутствии — прежние функции. Значения 0 (умолчание), 1, 2; иное — отказ `value` (как 0, обёрток нет).
**Не Knob и не гейт: плечом расписания быть не может** (смена посреди прогона меняет игру); строк в `KNOB_DEFINITIONS` и файлах гейтов
нет. Если P14 всё же оформит ручку как Knob — последняя строка `KNOB_DEFINITIONS`, `check_gate_order.py` после патча и до сборки, в файлах
гейтов «заменить на месте». Правок в `src/graphics/shader/**` нет — подпись кэша трансляции не меняется.

**Вооружение** — один раз, после блока `KYTY_POKE` (`runtimeLinker.cpp:1542`; `StartAllModules();` — `:1538`), строка всегда при значении 1–2:

```
PVar: armed mode=<1|2> base=0x<hex> vbl=<частота> cells=<fps %.3f>/<float hex8>/<u64>/<float hex8> lim=<50 hex знаков: 25 байт база+0x2a470b>
PVar: refused reason=<image|vbl|limiter|value>
```

Отказ (`pvar_bad` + 1; обёртки стоят, но только передают вызов прежней функции — записей и строк нет): ячейки образа ≠
`60.000/3c888889/16666/3c888889` (`image` — не тот eboot); частота вблэнков ≠ 60 (`vbl`); 25 байт по `база+0x2a470b` ≠ новым байтам §1
(`limiter` — P-var без развязки даёт храповик RC9) [В 7].

**Строка на каждую запись** (режим 2 — на кадр главного потока, режим 1 — на вызов флипа):

```
PVar: n=<u> w=<u> kraw=<u> k=<1|2|3> s_us=<16666|33333|50000> new=<u> vb=<u> ph=<0|1|2> mode=<1|2>
```

`n`, `vb`, `kraw` — поля опубликованного слова на момент записи (`n` — ключ к `FrameTrace: n=`); `w` — номер записи с 1; `k` — после
клампа; `new` — разность `n` с прошлой записью (0 — повтор того же слова, ≥ 2 — пропущено `new − 1` флипов), у первой записи `new` = 1 по
определению; `ph` — фаза P главного потока в момент записи (в режиме 2 всегда 0: запись раньше перевода фазы; в режиме 1 — 0, 1 или 2).
Шаг скорер берёт как `k / 60`. «Предыдущее k» для `pvar_chg`, `pvar_tear`, `pvar_tail` у первой записи — 1 (образ).

**Редкие строки:** `PVar: foreign n=<u> cells=<fps %.3f>/<float hex8>/<u64>/<float hex8>` — перед записью все четыре ячейки сравниваются
побитно с записанным в прошлый раз (у первой записи — с образом); при расхождении печатаются найденные значения, `pvar_foreign` + 1,
запись идёт дальше (`n` — запись, которая заметила; шаг предыдущего кадра был чужим). `PVar: bad reason=thread n=<u>` и `PVar: k0 n=<u>` —
выше; каждая редкая строка — не больше 8 раз за процесс, счётчик — всегда.

### 3.6 Счётчики `FrameTrace-x`, инварианты, тождества

Все — **сырые штуки** (`micros = false`), в конец `enum class Counter` перед `Count` и в конец `named[]` (после `{"rts_early", …}`,
`videoOut.cpp:3098`; +1 — 3099 «};»). Счётчики живут только при `KYTY_FRAME_TRACE` без гейта `fslean`
(`4fc501f4:src/common/frameStats.h:2541`, якорь «// Counters with an index below the limit are counted»; +1 — 2542) — так шли этапы 1–2
(строки `FrameTrace-x` есть во всех девяти логах, `out/predict.txt`) и так обязаны идти `qa_A`, `qv_`. `FrameStats::Add` из потока гостя
допустим (`frameStats.h:2581`: шард потока создаётся первым `Add`). Всё, кроме `pvar_kraw`, читается и из строк `PVar:`.

| имя | единица | поток | прибавка |
|---|---|---|---|
| `pvar_w` | записи | писатель | 1 на запись |
| `pvar_k` | вблэнки | писатель | k записи |
| `pvar_kraw` | вблэнки | Present | `kraw` каждого учтённого флипа, начиная со второго |
| `pvar_lost` | вблэнки | писатель | max(0, `kraw` − k) на каждой записи, повторы включены |
| `pvar_dup` | записи | писатель | 1, если `new` = 0 |
| `pvar_skip` | флипы | писатель | max(0, `new` − 1) |
| `pvar_chg` | записи | писатель | 1, если k ≠ предыдущему k |
| `pvar_inupd` | записи | писатель | 1, если `ph` = 1 |
| `pvar_tear` | записи | писатель | 1, если `ph` = 1 и k ≠ предыдущему k |
| `pvar_tail` | записи | писатель | 1, если `ph` = 2 и k ≠ предыдущему k |
| `pvar_k0` | флипы | Present | 1, если `kraw` = 0 |
| `pvar_foreign` | записи | писатель | 1 на строку `PVar: foreign` (и сверх восьми напечатанных) |
| `pvar_bad` | события | все | отказ вооружения; M0 из другого потока |

**Обязаны быть 0:** `pvar_k0`, `pvar_bad` — всегда; `pvar_foreign` — на удержании; в режиме 2 ещё `pvar_inupd`, `pvar_tear`, `pvar_tail` (по
построению). **Тождества для скорера** (по строкам `PVar: n=` окна; Σ — по строкам окна):
T1 — число строк = Σ `pvar_w`; T2 — Σ k = Σ `pvar_k`;
T3 — `n` последней − `n` первой = Σ `new` без первой строки; и по каждой строке `new` = 1 − [`new` = 0] + max(0, `new` − 1), откуда Σ `new` =
`pvar_w` − `pvar_dup` + `pvar_skip`;
T4 — `vb` последней − `vb` первой ≥ Σ `kraw` без первой строки, равенство — когда на участке нет пропусков (`new` ≤ 1 у всех строк); по
счётчику: `vb` последней − `vb` первой = Σ `pvar_kraw` флипов между ними;
T5 — Σ k = Σ `kraw` строк − Σ `pvar_lost` (при `pvar_k0` = 0; самопроверка разбора строк, не мера);
T6 (гейт п. 276(ж)(3)) — Σ k / 60 строк `PVar:`, лежащих в логе между первой и последней строкой `FrameTrace` удержания, к Σ `dt_us` этих
строк `FrameTrace`;
T7 (печать) — доля строк, у которых `kraw` равен бину `dt_us` строки `FrameTrace` с тем же `n` (бин — max(1, round(`dt_us` / 16 666,67))).
«Потеря клампа» — Σ `pvar_lost` / Σ `kraw` строк. Сверка строк со счётчиками — на отрезке лога до последней строки `FrameTrace-x`; допуск
края — одна запись: T1 и T3 ± 1, T2 и T5 ± 3 вблэнка.

### 3.7 Положительный и нулевой контроль

**Положительный:** (1) строка `PVar: armed` с ячейками образа и `lim` = новым байтам §1; (2) строк `PVar: n=` в окне удержания (по
позиции в логе, как T6) = строк `FrameTrace` удержания ± 1 % (в режиме 2 разность — `pvar_dup` − `pvar_skip`); (3) доли строк с k = 1, 2, 3
в пределах ± 3 п. п. от долей строк `FrameTrace` удержания с бином 1, 2, ≥ 3 (бин — как в T7), доля k = 3 > 0: k не постоянная (на Sky
Garden ожидается ≈ 400 записей k = 3 на удержании, P(0) ≈ 0); (4) игровой, **только режим 2**: для пары `Play→Finished` имени часов Σ k / 60
по строкам `PVar:` между ними = D(X) из `qa_A` в пределах ± 2 % + 3/60 с [В 3] — шаг, который записал эмулятор, и есть шаг анимации.
