# Сессия 51 — direct-copy измерен, гейты A/B внутри одного прогона, план на архитектуру draw

2026-09-13. База `8c2c6bf` (код `ef26182`), ветка `merge-upstream`. Код сессии — коммит **49d9be7**,
push не выполнялся. Цель «~60 FPS» **не достигнута и точечными правками недостижима** (см. §6).

## 1. Результат

- **`KYTY_CBUFFER_DIRECT_COPY` включён по умолчанию.** В одном прогоне, на одном участке, гейт
  переключался на лету: три пары фаз дали **+1,2…2,2% FPS** и −0,6…0,7% CPU на draw в двух парах,
  где число draw совпадало. `KYTY_CBUFFER_DIRECT_COPY=0` возвращает путь через ObtainBuffer.
- **Новый механизм гейтов `KYTY_GATE_FILE`** (`Common::Gates`, `src/common/gates.*`): файл вида
  `copy=1 srtpages=1 clamp=1` перечитывается раз на flip и переключает опции по ходу игры.
  Проверено в игре (`Gate: ...` в логе, обе стороны каждой опции). Прежний `KYTY_CBUFFER_COPY_GATE`
  удалён — его заменяет общий файл.
- **Три оптимизации CPU не дали измеримого выигрыша** (§3). Оставлены включёнными, таблицы
  увеличены до 4096 записей уже **после** измерения и в этом виде не измерялись; добавлены счётчики
  промахов `srt_miss` / `clamp_miss` в `FrameTrace-draw`, чтобы в следующем прогоне решать по данным.
- **Диагностические прогоны больше не держат зависший GPU**: `KYTY_GPU_HANG_ABORT_S` (по умолчанию
  8 с, 0 — ждать вечно) заставляет `MasterSemaphore::Wait` напечатать историю checkpoints/submit'ов
  и выйти. В обычных прогонах (без checkpoints/queue trace) поведение не изменилось.
- Бинарь установлен, SHA256 **71BC047E1660ED6765F113F83696AAFBFE91D48D0221649467E3EFA1DAB4C4E2**.
  Встроенная метка сборки прежняя (`9cfdb7d-dirty`), пересборка ради метки не выполнялась.

## 2. Зависание входа в уровень (открыто)

Первый прогон сессии (`copy1`) повторил редкий hang: **present 15929, до `MeshRestartBegin`**,
сразу после `GuestOut: LoadLevelResources: underwater_aerial_garden : 1.106 sec`. У пользователя
при этом **намертво замёрз весь компьютер**; watchdog снял процесс через 12 с.

Новый `KYTY_QUEUE_TRACE=1` впервые дал картину:

```
GpuWaitSlow: role=3 requested=385959 known=385958 current=385996 master=0xff623d2a10
GpuWaitSlow: role=1 requested=15948  known=15947  current=15950  master=0xff623d2b50
```

`GpuSubmitHistory` показывает, что submit тика 385959 прошёл штатно (`phase=returned result=0`),
**ожиданий семафоров у графических submit'ов нет** — то есть это не дедлок на CPU и не потерянный
сигнал: очередь GPU перестала завершать работу, а CPU успел отправить ещё ~37 submit'ов.
Отсюда и заморозка десктопа. Какая именно операция зависла — **не установлено**: в этом прогоне
GPU-checkpoints были выключены (ошибка планирования: их стоило оставить).

Известные случаи: s50 `base` (present 15329, старый exe), s50 `direct_sweep` (15287), s51 `copy1`
(15929) — все до `MeshRestart`, все в прогонах с `KYTY_ASYNC_COPY_GPU_WAIT=0`. Воспроизводится
не всегда: `copy2` тот же маршрут прошёл без hang. **По решению пользователя специально не ловим**
до следующего случая; тогда прогон должен идти с `KYTY_GPU_CHECKPOINTS=nv`, чтобы получить
`op=... 0x<hash>` последней незавершённой операции.

## 4. Код

1. `src/common/gates.{h,cpp}` — `Common::Gates::Enabled(Gate)` (расслабленное чтение атомика) и
   `Poll(frame)` из `videoOut.cpp` на каждом flip. Значения по умолчанию берутся из переменных
   окружения: `KYTY_CBUFFER_DIRECT_COPY` (теперь 1), `KYTY_SRT_PAGE_PERSIST` (1), `KYTY_CLAMP_MEMO` (1).
2. `VirtualRanges` получил эпоху (инкремент под локом во всех восьми мутирующих методах), а
   экспортируемый `Memory::ClampRangeSize` — потоко-локальную таблицу на 4096 записей, где каждая
   запись помечена эпохой. Непоклампленный ответ доказывает, что участок не короче запрошенного;
   склампленный даёт точную длину участка. `descriptors.cpp:FindBuffers` звал эту функцию на каждую
   привязку буфера (~57 тыс. захватов CRITICAL_SECTION на кадр).
3. `GuestBackingStore` получил `MapEpoch()` (инкремент при каждой правке `m_maps`), экспорт
   `Memory::BackingMapEpoch()`. `ShaderReadCache` в `pipelineCache.cpp` больше не пересоздаётся на
   каждую стадию каждого draw: живые трансляции страниц лежат в потоко-локальной таблице на 4096
   записей и сбрасываются только при смене эпохи карты. GPU-clean трансляции остались per-call —
   они зависят от GPU-dirty состояния, а не от карты.
4. `Common::BitArray::AnyInRange` — ответ на «есть ли бит в диапазоне» без 128-байтной временной
   копии; используется в `RegionManager::IsModified` и в двух проверках конфликта в `ChangeState`.
5. `MasterSemaphore::Wait` — аварийный выход по `KYTY_GPU_HANG_ABORT_S` (см. §2).
6. Счётчики `FrameStats::SrtPageMisses` / `ClampMemoMisses` → `srt_miss` / `clamp_miss`.

## 5. Тесты

Прошли: `bit_array_tests` (добавлен исчерпывающий дифференциальный тест `AnyInRange` против
маскированной копии), `memory_tracker_tests`, `virtual_memory_allocation_tests` (добавлен
`ClampRangeSizeMemoFollowsMapChanges`: повтор запроса, меньший размер, больший размер, unmap,
повторный map), `resource_materialization_tests`, `image_page_table_tests`.
GPU-тест `shader_recompiler_compute_tests --direct-constant-copy-only` прошёл при
`KYTY_CBUFFER_DIRECT_COPY` default/1/0 и один раз с запрошенным слоем валидации
(`VK_INSTANCE_LAYERS=VK_LAYER_KHRONOS_validation`, `VK_LAYER_VALIDATE_SYNC=1`) — сообщений не было,
но факт включения слоя отдельно не подтверждён.

Прежние падения не трогались: `resource_tracking_tests` — «SRT runtime: runtime evaluation failure
was not transactional» (доисторическое, после него процесс падает), `page_manager_tests` не
линкуется (`OverlapsGuestStack`). Большая GPU-suite не запускалась и чистой не объявляется.
Полная игровая Vulkan-валидация в этой сессии не выполнялась.

## 6. Куда дальше (план следующей сессии)

Текущее состояние сцены: **CPU ~64 мс, GPU ~20 мс, ~5300 draw → ~12 мкс CPU на draw**.
Для 60 FPS нужно ≤16,7 мс на обе стороны, то есть примерно **3 мкс на draw** и вдвое более быстрый
GPU. Точечные правки (direct-copy = +2%) к этому не ведут; упор — в устройство пути draw.

Разбор горячего пути (счётчики сессии 50 с подробными таймерами, кадр ~5500 draw):

- `d_prog` ≈ 20 мс, из них `p_mat` ≈ 16 мс, `m_eval` ≈ 11 мс и **454 тыс. чтений памяти гостя**
  (`p_reads`) — примерно 82 чтения на draw. `MaterializeResources` выполняется на каждый draw
  целиком: `memo_hit` считает не кэш значений, а лишь то, что сработал скомпилированный обход SRT
  (`SrtWalker.cpp:2107`, комментарии `ResourceMaterialization.cpp:309-311`). Результат
  материализации нигде не кэшируется, и он же служит ключом поиска пермутации
  (`pipelineCache.cpp:712-719`), поэтому пропустить его нельзя, не заведя memo.
- `d_bind` ≈ 27 мс: `b_texn` ≈ 53 тыс. вызовов `ResolveTexture`, столько же `FindTexture`/`FindView`
  (каждый под spin-локом `TextureCache::m_lock`, поиск view — линейный по списку), `ob_n` ≈ 64 тыс.
  `ObtainBuffer`, `bb_sync` ≈ 6,4 мс. Memo текстур (`tex_hits` ≈ 94%) покрывает только разбор T#,
  но не поиск view и не привязку.
- `d_commit` ≈ 6,7 мс и `d_emit` ≈ 6,6 мс — на каждый draw пишется новый descriptor set
  (`KYTY_DESCRIPTOR_REUSE` переиспользует только выделения, но не содержимое) и делается
  `Transit` каждого образа.

Порядок работ, от дешёвого к дорогому:

0. **Прочитать `srt_miss` / `clamp_miss` в первом же прогоне** и решить судьбу двух memo сессии 51:
   если промахов мало, а выигрыша нет — значит цена этих путей мала, и их можно упростить/убрать.
1. **Memo материализации SRT** — ключ `(ProgramKey, user_data, shader_base)`, свидетель годности —
   поэпоховые счётчики трекера по страницам, которые читал обход (сейчас глобальная
   `MemoryTracker::CpuWriteEpoch` меняется тысячи раз за кадр из-за page fault'ов, поэтому нужна
   эпоха на регион, а не одна общая). Цель — снять большую часть `p_mat` и почти все `p_reads`.
2. **Кэш разрешённых привязок на draw**: держать в memo текстуры ещё и готовый `vk::ImageView`
   (снимает 53 тыс. `FindTexture` под спин-локом), и переиспользовать `ObtainBuffer`, который
   повторяет работу уже выполненного `FindBuffer`.
3. **Переиспользование descriptor set между draw'ами.** Блокирует то, что `flattened_srt`,
   `shader_data` и копии константных банков каждый draw кладутся в stream-ring по новому смещению
   (`descriptors.cpp:929-937`) — сначала нужно сделать их стабильными при неизменных данных.
4. GPU (~20 мс) — отдельная ветка: нужен захват RenderDoc (F1 пользователем) и разбор самых
   дорогих шейдеров именно этой сцены; в сессии 50 один шейдер, объясняющий просадку, не нашёлся.
