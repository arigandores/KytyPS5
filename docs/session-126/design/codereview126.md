## Требуемые правки

### MAJOR-1 (BLOCKING). На каждом переходе плеч C→B гонка печатает `Rk3Census: refused reason=pathlap`

**Что не так.** `Gates::ApplyText` (`src/common/gates.cpp:582–615`) применяет текст плеча в фиксированном порядке:
сначала все **гейты** в порядке `DEFINITIONS`, потом все **ручки** в порядке `KNOB_DEFINITIONS`. После каждого
изменённого имени идёт `LOGF("Gate: …")`. Значит, на переходе C (`rk3cen=1 pathlap=1 mutsite=1`) → B (`rk3cen=0
pathlap=0 mutsite=0`) поток презентации делает следующее:
1. сохраняет `pathlap=0` и пишет строку лога;
2. сохраняет `mutsite=0` и пишет строку лога;
3. только потом сохраняет `rk3cen=0`.

В этом окне, от единиц до десятков мкс с двумя записями в лог, поток GuestGpu продолжает рисовать. `Rk3LatchSlow`
(`renderDraw.cpp`, ветка `!G::Enabled(G::Gate::PathLap)`) видит `rk3cen=1, pathlap=0`. Дальше:
- `Rk3Nt` получает +1;
- **`Rk3Refuse(10, "pathlap")` печатает строку `Rk3Census: refused reason=pathlap`**.

**Сценарий отказа.** Опора Sky Garden: ≈ 5 000 draw за кадр ≈ 33 мс, то есть ≈ 0,15 draw/мкс. ABBA с периодом 90 при
300 с даёт ≈ 100 границ блоков, из них ≈ 50 переходов C→B. Ожидаемое число draw в окне — порядка 1 на переход [I];
вероятность ни разу не попасть за прогон близка к нулю [I]. Одной строки достаточно, потому что строка печатается один
раз на причину. Печать по п. 68(в)(2) требует «ни одной `Rk3Census: refused`» во всём логе, поэтому прогон становится
**не оцениваемым**. Тег `k3c126` израсходован (п. 66(а)), сессия потеряна. `rk3_nt` на строках окна 10–88 при этом
остаётся 0 (гонка ложится в граничную строку блока), так что сама популяция чиста. Ломает только строка лога.

Переход B→C безопасен: `pathlap=1` сохраняется раньше `rk3cen=1`. Прочие причины отказа (`spcen`, `slicecen`,
`bindfloor`, `m4baton`, `skipceil`, `spine`, `frametrace`, `thread`) в прогоне постоянны, гонки у них нет.

**Расхождение с проектом.** §4.1 ред. 2 пишет: «`PathLap` вооружён (`pathlap=1`, иначе `rk3_nt`)», а строку
`Rk3Census: refused` задаёт только для `spcen` / `slicecen` / `bindfloor` / `m4baton` / `skipceil` / `spine`. Код добавил
строку и для `pathlap`: это причина `pathlap` в списке отчёта шага 3, вопрос (2).

**Что изменить (код, Emu Engineer):**
1. В `Rk3LatchSlow` для случая `!G::Enabled(G::Gate::PathLap)` оставить `Add(Rk3Nt, 1)` и отказ (`armed = 0`), а вызов
   `Rk3Refuse(10, "pathlap")` удалить. Строка лога на эту причину не печатается.
2. Неверно настроенное плечо (C без `pathlap`) страж всё равно ловит: при нём `rk3_nt > 0` на каждой строке окна
   10–88, и печать требует `rk3_nt = 0` по п. 68(в)(2).
3. Альтернатива без правки кода — решение лида: плечо B с `pathlap=1 mutsite=1`, различие только в `rk3cen`. Но это
   меняет базу (ж)(5), решённую п. 63(е), и я её не рекомендую.
4. Дым шага 5 на sha после правки обязан показать: `Rk3Census: refused` — 0 строк на отрезке с переходами C↔B.
   Отказ `spine` по-прежнему печатается: это сегмент дыма `spine=1`, RC9.

### MINOR-1. Цена инструмента в спане С5: утверждение §4.7 «ни одна из этих работ не лежит в спане С5» неверно

**Что не так.** В спан `pl_em_rt` (С5) попадают три вещи, при `rk3cen = 0` и `1` одинаково:

- в `AcquireRenderTargets` идут `Rk3SpBegin()` / `Rk3SpEnd()`: по TLS-сравнению `t_rk3 == 2` на каждую цель, 2 на

**Сценарий.** На число это не влияет: сторона «верх», единицы нс на draw [I], и в плече B то же самое. Но печать шага 6,
которая процитирует §4.7 дословно, заявит ложное.

**Что изменить (печать шага 6, Harness Engineer; код не трогать):** писать так: «в спане С5 лежат только
TLS-проверки инструмента, 2·`color_count` + 4 на draw (сторона „верх“, в обоих плечах); пост, резолюционная бухгалтерия С4 и крючки — вне
С4/С5».
