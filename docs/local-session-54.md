## 1. Результат одной строкой

**60 FPS нет.** Основные замеры — на игровой пустыне (без пользователя); в конце сессии пользователь
довёл игру до Sky Garden, и там снята отдельная серия (§6а): **все три правки дают −3,8 … −5,4 % CPU на

в vblank 60 FPS), решение по CPU потока GuestGpu на draw. Числа **несравнимы** с Sky Garden
сессии 53 (~5200 draw, 12,5 мкс/draw).

На пустыне поток GuestGpu тратил **15,0–15,3 мкс CPU на draw**; три включённые по умолчанию правки
сессии вместе дают **−14,7 / −15,2 / −16,4 % CPU на draw** (15,0 → 12,8 мкс, CPU потока 11,3 → 9,6 мс на кадр) (итоговый прогон `fin`, §6). По отдельности, каждая против
соседних базовых фаз в своём прогоне:

| правка | гейт (умолчание) | CPU/draw против базы | прогон |
|---|---|---|---|
| отправка `vkQueueSubmit` отдельным потоком (шаг 0 M3) | `asyncsubmit` (**1**) | **−8,1 / −9,1 / −6,1 %** | `as1` |
| пул переиспользования `VkImage` (§6.1) | `imgrecycle` (**1**) | **−6,0 / −5,8 / −6,8 %** (поверх предыдущей) | `rec1` |

Самый большой вывод — не из плана: **на пустыне 17 % активного времени потока GuestGpu уходило в

## 3. M1 — материализация SRT на воркерах (`drawahead`, `dause`, `dathreads`)

### 3.1 Что сделано

- **Теневое состояние обхода PM4 засеивается живым `m_sh_ctx`** и ведётся в тех же кодировках, что
  живые обработчики (`pm4Handlers.cpp`): вершинная программа — **ES** (`SPI_SHADER_PGM_LO/HI_ES`) с
  user data и счётчиком **GS**, адрес `lo<<8 | (hi&0xff)<<40`, счётчик user SGPR с битом MSB, 32 слота.
  M0 шадовил GS-регистры и собирал адрес в 256 раз меньше — отсюда его «10 % готовых draw».
  Держать тень между submission'ами не нужно: обход идёт на первом слайсе submission'а, когда живой
  контекст ровно в состоянии конца предыдущего submission'а этой очереди.
- Обход на каждый draw формирует запросы (адрес программы, user data) пачками по 64 в
  `PipelineCache::QueueDrawAhead`. `ProgramCache` по **hint-таблице** (какой `SourceEntry` draw-путь
  использовал для программы — до четырёх статических вариантов) ставит задачи в 32 768 слотов с
  атомарным состоянием Empty/Queued/Running/Ready/Failed. Воркеры (по умолчанию 4) делают
  `MaterializeResources` с записью чтений и публикуют результат со **свидетелем** сессии 52.
- `ProgramCache::Get` (под `m_mutex`) находит слот, проверяет свидетель против памяти гостя в момент
  draw и берёт snapshot/specialization вместо обхода плана; последний предсказанный пользователь
  забирает векторы обменом.
- Воркеры ничего общего не мутируют: план неизменен после `srt_compiled` (проверяется при постановке),
  трансляции страниц потоко-локальные; GPU-clean чтения, которые можно спросить только на потоке
  GuestGpu, воркер читает оптимистично, а draw проверяет их clean-читателем (частично грязная
  страница проверяется по словам). Удалённый `SourceEntry` не освобождается (`retired_sources`).
- Ключ слота — отпечаток сериализованного плана (`ShaderTranslationCache::PlanFingerprint`),
  базы шейдера и user data. **Дедупликации вариантов он не дал** (планы статических вариантов
  различаются), но остаётся корректным ключом.
- Гейты на лету получили числовые ручки (`Common::Gates::Value`, `dathreads=N`).

### 3.2 Как дошли до работающего варианта (все прогоны — пустыня)

| v3: до 4 статических вариантов программы | **1071 / 1075** | 0 | **4** | −2,4 / −3,0 (2 потока) / −0,8 (8) / −0,5 / +0,2 (1) % |

### 3.3 Почему потолок низкий (измерено таймерами только на двух вызовах за стадию)

| где | мкс/кадр | на единицу |
|---|---:|---:|
| проверка результата и обмен (`da_take_us`) | 540–590 | ≈0,5 мкс на стадию |
| постановка задач под `m_mutex` (`da_queue_us`) | 350–380 | ≈0,17 мкс на задачу (2184 задачи) |
| построение запросов в обходе (`da_walk_us` − база) | ≈60 | |
| собственная материализация на критическом потоке | ≈1070 | **≈1 мкс на стадию** |

Материализация на пустыне — ≈9 % CPU потока, и половину сэкономленного съедает проверка: она
делает те же чтения гостевой памяти (сессия 53: дорого само число чтений). Воркеры выполняют вдвое
больше задач, чем используется (варианты), и тратят на это ≈5 мс CPU за кадр на своих потоках.
**Ожидание плана «−12…17 мс» (из профиля с таймерами) не подтвердилось:** на пустыне реальный
потенциал M1 ≈ −9 %, получено ≈ −2 %.

## 4. Шаг 0 M3 — `vkQueueSubmit` отдельным потоком (`asyncsubmit`, по умолчанию 1)

Семплер пустыни: `CommandScheduler::Submit` — **9,9 % всех семплов потока GuestGpu** (41,5 % —
ожидание flip), листья `nvoglv64` 5,3 %, `win32u` 3,0 %; цепочки — `BufferFlushLazy` на
`RELEASE_MEM` (6,4 %) и концы слайсов. 28 отправок на кадр ≈ 48 мкс каждая.

- Одна FIFO на процесс для всех планировщиков; тик `MasterSemaphore` берётся **при постановке**
  под её локом, поэтому тики попадают в очередь по порядку, а `CurrentTick/IsFree/Wait` не меняют
  смысла (стоящий в очереди тик просто ещё не завершён).
- Синхронно (после слива очереди до своего номера): present-отправки и отправки с семафорами
  вызывающего, `KYTY_SYNC_SUBMIT`, а после ревью — и те, которые вызывающий сразу ждёт
  (`FlushAndWait`, `Finish`, `Wait` текущего тика). Слив — перед `waitIdle` swapchain, границами
  захвата RenderDoc, остановкой устройства и в `Shutdown`.
- `vkEndCommandBuffer` остаётся на потоке записи (рекомендация NVIDIA).
- Замер `as1` (всё интро прошло с гейтом с первого кадра): **CPU/draw −8,1 / −9,1 / −6,1 %**,
  `Submit` на критическом потоке 1350 → 305 мкс/кадр; поток отправки ≈1,37 мс/кадр. 0 длинных
  кадров, 0 ошибок, **видео 12 027 кадров — 0 однокадровых дефектов**.
- Ревью: блокирующих дефектов нет. Учтено: синхронные отправки для ждущих путей, слив по номеру,
  повторное ожидание асинхронных копий на present-пути после слива, отдельное время API и ожидания
  `queue_mutex` (`as_us`/`as_lock_us`), глубина очереди в `GpuWaitSlow`/`GpuHangAbort`.
- **Оговорка к числу:** работа не исчезла, а переехала на другой поток. Это ровно цель проекта —
  критический поток один, машина свободна на три четверти.

## 5. §6.1 — пересоздание образов (`imgrecycle`, по умолчанию 1)

### 5.1 Что перезаливается

Разбор агента по логам сессий 49 и 53 (Sky Garden) и трасса этой сессии (пустыня, новые
`KYTY_IMAGE_UPLOAD_TRACE`, `KYTY_IMAGE_LIFETIME_MIN_KB`):

- **Пустыня:** одна поверхность 1920×1080 (`0x541010000`) используется за кадр как B10G11R11-цвет
  (с DCC), D32-глубина и R32F-глубина — **5 созданий и 5 уничтожений образа на кадр** через
  `ResolveDepthOverlap`/`ResolveOverlap` (копия содержимого на GPU при каждой переинтерпретации),
  плюс полная загрузка 8,8 МБ R32F. Ещё два R8-образа 1024×1320 пересоздаются сборщиком каждые два
  кадра.
- **Sky Garden («пол» 156 МБ/кадр):** тот же механизм — пул RT полуразрешения `0x53a500000`
  (5 образов) и пара RGBA16F/RGBA8 1080p, ~7 созданий/освобождений на кадр, 15 detile; сверх того
  ~11 полных перезаливок существующих образов (вероятно, пинг-понг с буферами-алиасами, не
  доказано). Причина частоты: `safe_to_delete` сравнивает **тики** (43 на кадр) с порогом
  `NumFramesBeforeRemoval = 32`.

### 5.2 Что сделано

Семантику перекрытий не трогал. Образ, который кэш текстур удаляет **после завершения GPU-тика**
(отложенная операция планировщика), отдаёт `VkImage` и выделение VMA в пул; `CreateImage` с теми
же параметрами берёт их оттуда, раскладка начинается с undefined, как у нового образа. Пул ≤256 МиБ,
≤64 образа, ≤2 с; сливается при выключении гейта, уничтожении аллокатора и при неудаче
`vmaCreateImage`.

Замер `rec1` (поверх асинхронной отправки и M1): **CPU/draw −6,0 / −5,8 / −6,8 %**, `InsertImage`
520 → 10 мкс/кадр, `ResolveDepthOverlap` 337 → 50 мкс/кадр, GPU занят на ~150 мкс меньше.
Видео 12 038 кадров — 0 дефектов; лист кадров совпадает с калибровочным прогоном.
Ревью: ссылок на удалённый образ после отложенной операции не найдено; учтены слив пула и повтор
выделения. Vulkan + sync-валидация с пулом (интро и пустыня) — 0 ошибок (§10). **Не проверено:** Sky Garden;
переиспользованный образ несёт
старое содержимое вместо нулей свежего выделения (по спецификации оба undefined; путей без копии в
пустыне лог не показал).

### Зависание на входе в Sky Garden — найден триггер

Первый запуск пользователя (`play1`) упал через 144 кадра после загрузки `underwater_aerial_garden`:
`vkWaitSemaphores failed: ErrorDeviceLost` (GPU завис, драйвер сбросил устройство). Пользователь
заметил закономерность: **после новой сборки первый вход в уровень виснет, после перезапуска проходит**.
Логи подтверждают: `shaderTranslationCache.cpp` (и `gpu_format.h`, `gpu_defs.h`, всё `graphics/shader`)
входит в хэш транслятора (`generate_version.cmake`, `SHADER_CACHE_EXTRA_FILES`); правки этой сессии и
даже нормализация концов строк перед коммитом сменили подпись, кэш трансляции и рецепты пайплайнов
сбросились (рецептов 691 → 375), и вход в Sky Garden транслировал шейдеры и компилировал пайплайны прямо
в полёте. Второй запуск (`play2`, тёплый кэш) дошёл до сцены без сбоя. Это, по всей видимости, то же
редкое зависание входа сессий 49–52 — **теперь у него есть воспроизведение: холодный кэш трансляции**.
Какая GPU-операция зависает, не установлено (checkpoints не были включены); что его вызывают новые
правки сессии, не исключено одним случаем.

## 7. §6.2 — разрывы render pass и барьеры

- Разбор агента (регрессия по 47 тыс. кадров, R² = 0,9995; скан SPIR-V кэша трансляции): в Sky
  Garden ≈780 из 927 начал прохода дают **15 пиксельных шейдеров per-pixel linked list (OIT)**, и
  каждый их draw рвёт проход трижды: GDS-барьер до draw, повторный барьер записи storage-образа до

  927 → ~150 начал прохода.
- Сделано инструментирование: `FrameTrace-rp` — закрытия прохода по 15 причинам и «перезапуски на
  тех же целях» по причинам (`RenderPassEnd` протянут через `EndRendering`, `Transit`,

## 11. Где мы относительно 60 FPS
