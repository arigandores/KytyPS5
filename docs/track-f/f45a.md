## 0. Механизм [c кода FS12 `730ed40a`] — написан и закоммичен до выводов

### 0.1 Постановка отложенной заливки

1. **Производитель один.** Вычислительный dispatch гостя, который `ResolveComputeBufferFill` опознал как заливку буфера одним словом, сначала
   пробует `ClearImageFromBuffer` (`730ed40a:rc:230`); если адрес — не данные изображения, dispatch **исполняется как есть** (метаданные гостя в
   памяти пишет сам dispatch), а кэш записывает его логический смысл: `cache.TrackDccFill(addr, size, value)` (`730ed40a:rc:245`). Других
   производителей записей `PendingDcc` нет (комментарий там же и `TrackDccFill` — единственное место `try_emplace` с этим типом).
2. **`TrackDccFill`** (`730ed40a:tc:3204`): запись по адресу метаданных создаётся (тип по умолчанию `PendingDcc`) или обновляется, если она
   `PendingDcc`/`Dcc`/`CMask`. Маска очистки: для DCC — `UINT32_MAX`, если слово — повтор байта-кода из {`0x00`, `0x20`, `0x40`, `0x80`, `0xc0`},
   иначе 0 (`730ed40a:tc:3230`); `fill_value`, `fill_size` запоминаются; у `PendingDcc` `fill_seq = 0` (`730ed40a:tc:3243`) и адрес ставится в
   «штамп».
3. **Штамп** (`StampPendingDccFill`, `730ed40a:tc:3251`) зовётся сразу после записи dispatch в буфер команд (`730ed40a:rc:1162` — путь
   `recpack`, `730ed40a:rc:1188` — прямой путь): `fill_seq` = `LastGpuWriteSeq(addr, fill_size, false)` (`730ed40a:tc:3258`) — наибольший номер
   записи GPU по **корзинам 64 КиБ** диапазона заливки на момент штампа.
4. **Корзины.** `NoteGpuWrite(vaddr, size)` (`730ed40a:bc:2848`) даёт записи номер `++m_gpu_write_seq` и пишет его во **все корзины**
   `vaddr >> 16 … (vaddr + size − 1) >> 16` (`730ed40a:bc:2855`, `730ed40a:bc:2858`; `HotBucketBits = 16` — `730ed40a:bh:478`); запись > 16 МиБ
   идёт в общий `m_large_write_seq`, который проверка заливки не читает (`include_large = false`). `LastGpuWriteSeq` (`730ed40a:bc:2862`) —
   максимум номеров корзин диапазона. **Точности ниже корзины нет:** запись соседнего буфера в ту же корзину 64 КиБ, не пересекающая байтов
   заливки, поднимает номер так же, как запись поверх метаданных.

### 0.2 Проверка устаревания (`PendingDccFillStale`, `730ed40a:tc:3266`)

- Отвечает «устарела» только для записи `PendingDcc` с `fill_seq ≠ 0` при `KYTY_DCC_STALE` ≠ `0` (умолчание — проверка включена,

- **Ф26 (определение строки, §60/§64 реестра):** ответ «устарела» по корзине при том, что точная проверка (кольцо записей F16k, только в коде

### 0.4 Что делает ложный сброс при `=0` с содержимым поверхности и метаданными

- **Метаданные:** запись по адресу становится `Dcc` с маской 0 (С1) или исчезает (С2). Ни И2, ни И3 после этого заливку не находят
  (`MetaClearMask` → 0). Восстановить её может только новая заливка того же адреса (П1). Байты метаданных гостя в памяти (коды «очищено»,
  записанные самим dispatch) остаются, но эмулятор их не читает.
- **Содержимое поверхности:** `ClearImage` не вызывается. Сразу после И1 идёт `RefreshImage` (`730ed40a:tc:2310`, `730ed40a:tc:2435`):
  если изображение помечено изменённым буфером или CPU — в него **загружаются байты данных гостя** (на железе быстрая заливка данные
  цвета не пишет, там — прежнее содержимое памяти), иначе остаются **прежние тексели изображения хоста**. Цвет заливки в поверхность не
  попадает ни на каком пути.
- **Итог по коду:** при `=0` ложный ответ «устарела» **теряет заливку** (не «исполняет иначе», не «исполняет позже»). Видимо ли это,
  зависит от того, читается ли хоть один тексель затронутых слоёв (выборка, смешивание, показ) раньше, чем игра перезапишет его целиком; по
  коду эмулятора это не определяется — свойство кадра игры [U].
- **Цена:** лишней работы при `=0` нет — сброс дешевле исполнения; вопрос строки — только корректность.

### 0.5 Класс `kept why=decode` при `=1` (код `KYTY_FIX_F26`, `365cc3c2`; на FS12 — после переноса §1)

- При `KYTY_FIX_F26=1` точная проверка кольца решает «свежая», запись проходит И1 как не устаревшая. Класс `kept why=decode` — возврат И1 на
  `DecodeDccClearFill` (`730ed40a:tc:1924` → `DecodeDccClear`, `730ed40a:tc:98`): код не из пяти или код `0x20` у привязки, которая не цель
  цвета либо без действительного слова очистки регистра (`730ed40a:tc:108` и ниже), или формат вида без кодировки. Запись остаётся `Dcc` **с
  маской** — заливка не потеряна, но в этом вызове не исполнена.
- **Позднее исполнение — тремя путями [c]:** (а) следующий И1 той же поверхности, где декодирование удалось (например, привязка целью цвета с
  действительным словом регистра) — **строки нет**; (б) И2 при привязке шейдеру — строка `MaterializeDeferredDccClear: … decoded=1`, первые 32
  на процесс, все — при `KYTY_DCC_TRACE=1`; (в) И3 на draw удаления быстрой заливки — та же строка. Если ни один путь не наступил — заливка
  висит до П1/С4, и плечо `=1` по содержимому совпадает с плечом `=0` (оба без очистки) — событие **не различимо парой по построению**.
- **Риск плеча `=1` [c кода, частота U]:** путь (б)/(в) очищает **все уровни слоёв маски целиком** (`730ed40a:ds:3492` и ниже). Если между
  постановкой и поздним исполнением игра рисовала в поверхность целью цвета (И1 не декодировал), позднее исполнение сотрёт нарисованное —
  «очистка после записи». Это свойство пути отложенной заливки FS12 для любой заливки, не только ложно устаревшей; при `=1` Ф26 направляет в
  него события, которые при `=0` сбрасывались. Отличие листа плеча `=1` в окне такого исполнения — не доказательство дефекта `=0`.

### 2.2 Бинарь T и новый код измерения (проект; константы — решения лида)

  вызова или `dcc_stale_apply result=cleared`), пишет вместо декодированного значения цвет (1, 0, 1, 1) в формате вида (форматы без такой

  Счётчики `f26_tint_applied`, `f26_tint_skip` (штуки, u64) — последними в `F5Names`.
  **Это не измерение:** при `≠ 0` меняется картинка (и байты, которые гость может выгрузить из этой поверхности) — значение только для плеча
  контроля, не отгружается.
- **Нулевые инварианты:** при `KYTY_F26_TINT=0` — `f26_tint_applied` = `f26_tint_skip` = 0 и строк `F26Tint:` 0; при `KYTY_FIX_F26=0` — строк
  `dcc_stale_apply` 0, `f26_*` = 0; строк `dcc_stale_apply result=cleared` с `site=prepare` ≤ событий `kept why=decode`; на каждую метку — не
  больше одной строки `cleared`.
- **Тождества для скорера:** `f26_kept` = строкам `dcc_stale` с `fix` ∈ {`kept`, `kept_applied`} (п. 507(б)(4)); `f26_kept_applied` = строкам
  `kept_applied` + строкам `dcc_stale_apply result=cleared`; при `=1` и `=0` одного тега `KYTY_F26_TINT` — `f26_tint_applied` ≥ 1 у плеча `=2`.
- **Цена [I]:** метка — одна запись хэш-таблицы на событие (4 на вход); окраска — та же очистка другим значением; при всех ручках 0 — 0.

### 2.4 Правило чтения на событие (предложение до данных; решает лид)

Для события `e` из S1–S4 (ключ — `image`, `dcc`) по плечу `f26s_1`: **момент исполнения** `p(e)` — `present` строки `dcc_stale` при
`fix=kept_applied`; при `kept why=decode` — `present` строки `dcc_stale_apply result=cleared` его метки (М1); метки без `cleared` до конца
удержания — **`NO_APPLY`**. Окно — показы [`p(e)` − 1; `p(e)` + 3] (п. 504(з)). `M(f)` — число пикселей кадра видео с R ≥ 200, G ≤ 40, B ≥ 200
(кадр 960×540; детектор — скрипт печати с фикстурами на окрашенный и обычный кадр).

1. **Контроль способа (`f26s_tc`):** `f26_tint_applied` ≥ 1 и хотя бы один кадр удержания с `M` ≥ `θ` + max `M` того же номера показа у
   `f26s_1` (`θ` = 500 пикселей, ≈ 0,1 % кадра). Нет — **способ мёртв**.
2. **Отрицательный контроль:** у `f26s_0` и `f26s_1` строк `F26Tint:` 0, `f26_tint_applied` 0.
3. **Видимость заливки события `V(e)` (`f26s_t`):** да, если в окне `e` есть кадр с `M_t` − `M_1` ≥ `θ` (тот же номер показа; кадры экрана входа
   — средняя яркость ≤ 5 — исключаются по правилу п. 504(з)).
4. **Отличие `D(e)`:** лист лида пары `f26s_0` / `f26s_1` в окне `e` — отличие содержимого кадра по определению п. 504(з) (среднее абсолютное
   отличие кадров — справка, не член).
5. **Класс события:** `V` = да и `D` = да ⇒ **кадр-свидетель**; `V` = нет ⇒ событие `НЕ ДЕФЕКТ` (очищенное содержимое до перезаписи не
   показывается — сила по живому контролю 1); `V` = да и `D` = нет ⇒ событие `НЕ ДЕФЕКТ` (видимые тексели старого содержимого равны значению
   заливки); `V` = нет и `D` = да ⇒ «не определено» (отличие не от заливки — помеха прогона); `NO_APPLY` ⇒ «не определено, не различимо по
   построению» (оба плеча без очистки), в счёт строки не идёт; строки `skipped draw` в окне ⇒ «не определено».
6. **Строка Ф26 (на Sky Garden):** ≥ 1 свидетель ⇒ `дефект` (K4) и итерация кода «ИСПРАВЛЕНО Ф26» пунктом лида (кандидат правки — умолчание
   `KYTY_FIX_F26=1`, уже в `main`); контроль 1 жив, ≥ 1 событие класса `НЕ ДЕФЕКТ`, свидетелей 0 ⇒ `НЕ ДЕФЕКТ` по п. 228(д) на пути входа
   Sky Garden с переоткрытием (кадр-свидетель на событии `dcc_stale`, эталон PS5); контроль 1 мёртв или все события «не определено» ⇒ `ТУПИК`
   (п. 698(з)(3)).

## 4. Риски и что проект не доказывает

- **Позднее исполнение при `=1` может стереть нарисованное** (§0.5, риск плеча `=1`): поэтому свидетель требует и `V`, и `D`, а отличие плеча
  `=1` само по себе дефект `=0` не доказывает; какое из плеч ближе к железу — без эталона PS5 [U].
- Окраска меняет кадр после события (временное накопление может разнести цвет на кадры после окна) — читается только окно; `f26s_t` и
  `f26s_tc` в видимость `=0`/`=1` не входят.
- Ноль `V` на четырёх событиях доказывает только, что содержимое **этих** поверхностей на **этом** входе не видно до перезаписи; другие сцены
  и события сайта `adopt` (в игре 0 — F16q) не покрываются.
- Код М1 зависит от того, что одна метка на `ImageId` не перезаписывается другой заливкой той же поверхности до исполнения [I]; перезапись —
  строкой `dropped`.
- Перенос не собирался (§1) — компилируемость и прохождение тестов [U].
