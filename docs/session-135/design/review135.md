## 0. Итог

Проект измеряет то, что заявляет: условие «попало бы» совпадает с настоящим `buffast` по ключу, индексу, свидетелям, правилу
вставки и очистки (§2); перепись не меняет путь (§3); семь частей делят выбранную итерацию `Slow` целиком и книжатся на том же
множестве итераций, что `rb_slow_ns` (§4). Дефекты — в чтении и в нескольких незаданных краях:

- **RC1 (MAJOR):** тождества И0–И2 «= 0 по тегу плеча 0» (п. 167(в) В2) — сумма по ПОДМНОЖЕСТВУ строк не телескопируется; на
  каждой границе блока строка может разрезать итерацию между `SlotEnd` и `RsSlotEnd`. Ожидаемо ≈ 50 % прогонов читаются
  «перепись не приняла место» без дефекта инструмента [I].
- RC2: в POST не задан приоритет «попало бы» над очисткой на выходе `Stream` — от него зависит `rs_bf_strm` в разы.
- RC3: контроль `rs_bf_xdiff` считает другой предикат, чем `rs_bf_diff` — живость контроля не доказывает живость второго члена сверки.
- RC4: «попало бы» на гонке (PRE раньше `:1387`) несёт в U3 цену загрузки, которую `buffast` не снял бы, — не считается.
- RC5: область `rs_bf_would`/`rs_bf_diff`/`rs_bfw_*` в §5.2 двусмысленна; «попало бы» на выходе `Epoch` не считаются и не сверяются.
- RC6: эквивалентность статической `g_rs_table` и `thread_local` таблицы `buffast` держится только при `m4baton=0` — не записано.
- RC7: признак книжения `rs_bfw` в POST не назван; нет неравенства, ловящего книжение `rs_bfw` не на тех итерациях.

## 4. Проверки сверх брифа (п. 167(е))

**(1) Одно множество итераций.** `rb_slow_ns` книжит `SlotEnd` при `selected ∧ rb.cls == Slow` (`frameStats.h:3756–3772`); класс `Slow`
пишет только внешний `ObtainScope` на `:1592` (`frameStats.h:3827–3831`), путь `:1570–1591` линеен и предшествует `:1592` ⇒ на
итерации класса `Slow` отметки a0…a5 исполнены. Решение `m_rsel` берёт `t_rb.next`; единственный писатель `t_rb.next` —
`frameStats.h:3768` (внутри `SlotEnd`), единственный читатель вне — `descriptors.cpp:4258`; `SlotBegin` `:3725–3732` его не трогает ⇒
между S0 и S1 `t_rb.next == rb_sel(i)`, т. е. `have ⇔ selected` на итерациях `Slow`. Семь лап-отрезков a0−t0, a1−a0, …, t1−a5
суммируются в t1 − t0 точно, если `RsSlotEnd` получает тот же t1, что `:3770` (проект: вызов внутри `SlotEnd` после `:3772`–`:3780`) —
верно. **POST:** на `:4291` `rb_sel` ПЕРЕЗАПИСЫВАЕТСЯ возвратом `SlotEnd` (решением СЛЕДУЮЩЕЙ итерации), а `t_rb.next` уже переписан
на `:3768` — оба источника в POST неверны; признак обязан быть сохранён до `:4291` — RC7. `rs_bfw_k` книжится тем же `Add`-сайтом, что
`rs_bfw_ns` (п. 167(б)(1)) — верно при RC7.

**(2) `rs_bf_xchk` и `rs_bf_strm` против `:1388–1401`, `:1524–1555`.** Двойного счёта риска нет, если `rs_bf_would`/`rs_bf_diff`
считаются только при `rb.cls == Slow`, а `rs_bf_strm` — при `ocls == Stream`: `rb.cls == Slow ⇒ ocls == Slow` (класс `Slow` пишется
только `:1592`) ⇒ множества не пересекаются. Знаменатель доли риска (`would` + `strm`) не содержит «попало бы» выходов `Epoch` —
доля риска завышена, т. е. чтение консервативно (не ложный проход). Ложная живость контроля — RC3; величина `rs_bf_strm` зависит от
незаданного приоритета — RC2.

**(3) Однопоточность.** `IsGpuThread()` = `g_gpu_thread` (`graphicsRun.cpp:4155–4157`), истинный на потоке GuestGpu (`:693`, один на

таблицы, у переписи — одна ⇒ «попало бы» выше настоящего — RC6.

**(4) Между PRE и `:1387`/`:1397`.** `m_registration_epoch` двигает только `ChangeRegister` (`bufferCache.cpp:117`) из `Register`/`Unregister`

## 5. Требуемые изменения

**RC1 (MAJOR) — форма И0–И2.** Что не так: п. 167(в) В2 читает «приняла место» ⇔ И0 = И1 = И2 = 0 «по тегу плеча 0»; §7 проекта —
«тег». Строка `FrameTrace` — разность накопленных сумм, которые поток презентации читает из шарда GuestGpu без синхронизации
(`frameStats.cpp:220–222`, `Add` — `frameStats.h:2847–2857`), т. е. снимок может лечь между `Add(RbSlowN)` в `SlotEnd` (`:3765`) и
`Add` счётчиков `rs_*` в `RsSlotEnd`. Сумма по ВСЕМ строкам тега телескопируется до невязки последнего снимка; сумма по строкам
плеча 0 (или окна 10–88) — нет: каждая граница блока несёт свою невязку ∈ {0, 1} итерации. Сценарий отказа: окно между `Add(RbSlowN)`
и последним `Add` `RsSlotEnd` ≈ 5–30 нс × ≈ 24 000 итераций `Slow` ≈ 0,2–0,5 мс на кадр ≈ 0,5–1,5 % времени [I]; ≈ 39 блоков плеча 0 × 2
края ≈ 78 разрезов ⇒ P(И1 ≠ 0 без дефекта) ≈ 1 − 0,99⁷⁸ ≈ 0,5 [I]; для И0 — одна итерация t1 − t0 на разрез, P ≈ 0,2 [I] ⇒ чтение (д)(1)
«не приняла» при исправном инструменте. Изменить (решение лида, пункт `ROADMAP.md` до кода шага 3 и до скорера шага 0): И0–И2 —
бегущая невязка R_n по ВСЕМ строкам тега подряд (оба плеча), знак фиксирован порядком `Add` (сначала `SlotEnd`, затем `RsSlotEnd`):
И1, И2 — 0 ≤ R_n ≤ 1 на каждой строке (один поток пишет — K = 1); И0 — 0 ≤ R_n ≤ K_ns на каждой строке, K_ns — константа лида
(дефект книжения копится линейно — миллионы итераций за тег, — разрез не копится; K_ns = 10⁷ нс, больше любой одной итерации, [I]).
Фикстура скорера — строка, разрезающая итерацию, на краю блока плеча 0 (должна пройти) и пропуск книжения на 1 из 1 000 итераций
(должен упасть).

**RC2 — приоритет в POST.** Что не так: §5.1 даёт два правила для одной итерации — «`ocls == Stream` ⇒ слот `{}`» и «`would` ⇒ слот не
переписывается»; при `would ∧ ocls == Stream` порядок не задан. В `buffast=1` попадание возвращается на `:1411` ДО `:1549–1554` — слот
не очищается, и каждый следующий вызов того же ключа снова попадает, пока эпоха не сдвинется. Сценарий отказа: код шага 3 применяет
очистку ⇒ перепись видит одно «попало бы» вместо серии ⇒ `rs_bf_strm` занижен во столько раз, сколько вызовов этого ключа идёт без
сдвига эпохи, — доля риска п. 167(в) В5 может пройти порог 0,01 / 0,05 ложно. Изменить (ред. 2, §5.1–§5.2): «`would` ⇒ слот не
меняется ни на каком выходе (кроме `touch_tick`)» старше очистки `Stream`; `rs_bf_strm` считается по `ocls == Stream` (выход
`ObtainBuffer`), независимо от последующей переписи класса в `Cbank` (`descriptors.cpp:606–673`).

**RC3 — предикат контроля сверки.** Что не так: `rs_bf_diff` = `res_id ≠ rem_id ∨ (sync == 2 ∧ E_post == pre)`, а `rs_bf_xdiff` =
`sync == 2 ∨ id ≠` (§8). Живость `xdiff` доказывает рукопожатие `sync`, но не сравнение `E_post == pre`. Сценарий отказа: в коде
шага 3 второй член `diff` читает не тот свидетель (например, `E_post` снят в POST после обновления слота из `slot.region_epoch`, или
сравнение инвертировано) ⇒ `rs_bf_diff` = 0 на любых данных, а `rs_bf_xdiff` > 0 и `xchk` ≥ 1 000 ⇒ по п. 167(в) В4 «сверка доказана»,
доля расхождения 0 ≤ 0,01 — ложный проход (1) отбора. Изменить (ред. 2, §5.4, §8): `xdiff` — ТА ЖЕ функция-предикат, что `diff`
(одна `inline`, два вызова), на популяции `xchk`; на протухшем ключе запись CPU легла ДО PRE, поэтому `E_post == pre` там обычно
истинно и загрузка видна тем же выражением. Популяцию `xchk` задать полностью: `elig ∧ rb.cls == Slow ∧ instance, vaddr, size,
registration совпали ∧ try_get жив ∧ region_epoch ≠ pre`, включая `pre == 0` или исключая — назвать. Первый член (`id ≠`) живого
контроля не имеет — записать в §14 как недоказанное.

**RC4 — гонка PRE в U3.** Что не так: свидетель переписи снят в PRE, раньше `:1387` на всю голову `NativeStorageBuffer`; «попало бы»,
у которого полный путь сделал загрузку при сдвинутом свидетеле (`sync == 2 ∧ E_post ≠ pre`), не расхождение (§5.4) — и остаётся в
`rs_bf_would` и в `rs_bfw` вместе с `rs_sync`, т. е. с ценой загрузки. В `buffast=1` такая загрузка не снимается: запись до `:1387` даёт
промах, запись после — загрузку следующего вызова (отложена, не снята). Сценарий отказа: гостевые потоки пишут в тот же регион
4 МиБ (`regionDefinitions.h:13`) в окне PRE → `:1575` чаще, чем «≪ 10⁻³» [I без счётчика] проекта; `rs_sync` таких итераций — самая дорогая
часть (загрузки ≈ 50–80 пар/кадр [c с. 133]) ⇒ U3 перешагивает 400 за счёт загрузок, которых B3 не снимает. Изменить (решение лида,
новый счётчик — пункт `ROADMAP.md`): `rs_bf_race` (шт., `would ∧ sync == 2 ∧ E_post ≠ pre` на `Slow`) и либо исключить такие итерации
из `rs_bfw_ns`/`rs_bfw_k`, либо книжить их долю отдельно (`rs_bfw_race_ns`) и печатать U3 без неё; §14 п. 2 — со ссылкой на счётчик.

**RC5 — область «попало бы».** Что не так: §5.2 «`rb.cls == Slow` ⇒ `rs_bf_n` += 1; `would` ⇒ `rs_bf_would` += 1, сверка…» допускает
чтение, где `would` считается на любом `ocls ≠ None`. Сценарий отказа: код считает `rs_bf_would` и на выходах `Epoch`
(≈ 5 000/кадр [c `kp134`]) ⇒ Н2 (`rs_bf_n − rs_bf_would ≥ −1`) падает на каждой строке — `INSTRUMENT_FAIL` дыма; либо (если Н2
ослабят) доля «попало бы» и U3 смешивают классы. Изменить (ред. 2, §5.2, §5.4): `rs_bf_would`, `rs_bf_diff`, `rs_bf_xchk`,
`rs_bf_xdiff`, `rs_bfw_ns`, `rs_bfw_k` — только при `elig ∧ rb.cls == Slow`; в §14 — «попало бы» на выходе `Epoch` не считаются и не
сверяются (первый член сверки там не проверен), доля расхождения — доля класса `Slow`, не всех попаданий B3.

**RC6 — условие однопоточности.** Что не так: §2.1 утверждает «таблица одна, пишет только GuestGpu» без условия. Сценарий отказа:
тег с `m4baton ≠ 0` — реле `M4Baton` получает `g_gpu_thread = true` (`graphicsRun.cpp:2558`) и в `buffast` имело бы свою
`thread_local` таблицу; перепись сливает оба потока в одну ⇒ «попало бы» по ключам, которые настоящий `buffast` не видел бы
попаданием, — U3 завышен без следа в тождествах. Изменить (ред. 2, §2.1): «эквивалентность `thread_local` — только при `m4baton=0`»;
харнесс (`envchk135.py`) проверяет `m4baton=0` в каждом теге переписи, либо ручка отказывает `RbSlow: refused reason=baton` —
выбор лида.

**RC7 — признак книжения `rs_bfw`.** Что не так: проект не называет источник «выбрана» в POST (п. 167(б)(2) называет два допустимых), и
нет проверки, что `rs_bfw` лежит внутри пяти частей. Сценарий отказа: POST проверяет `rb_sel` после `:4291` (это решение следующей
итерации) ⇒ `rs_bfw` книжится на ≈ 1/8 «попало бы» НЕвыбранных итераций, где `rs.bfw` = 0 или остаток прошлой итерации, если снятие
пропущено ⇒ U3 искажён, И0 это не видит (в И0 `rs_bfw` не входит). Изменить (ред. 2, §3.3, §5.2): `RsSlotEnd` ставит `t_rs.bfw_set`
вместе с `bfw` и `bfw_k` (только `selected ∧ have ∧ rb.cls == Slow`); POST книжит `rs_bfw_ns`, `rs_bfw_k` ⇔ `would ∧ bfw_set`; POST
снимает `bfw_set`. Добавить в §7 неравенство Н5: бегущая сумма Σ(`rs_find_ns` + `rs_touch_ns` + `rs_sync_ns` + `rs_wr_ns` + `rs_rem_ns`)
− Σ `rs_bfw_ns` ≥ 0 на каждой строке тега (части книжатся раньше `rs_bfw` — знак фиксирован, запас не нужен). В список раздела 22
(§3.4) — поле `bfw_set` с местом установки и снятия.
