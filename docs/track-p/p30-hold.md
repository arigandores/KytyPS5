## Поведение по значению `KYTY_PVAR_HOLD`

Читается один раз (`HoldMode`, `cd4c2803:src/kernel/pvar.cpp:111` `int HoldMode() {`; +1 `static const int mode = [] {`):
не задана, пустая или `0` → 0; `1` → 1; иное → −1.

| P-var | `HOLD` | Итог |
|---|---|---|
| нет (`Mode()` 0) | не задана / `0` | как P23: ничего (ни строк, ни вызовов `PublishVblank`) |
| нет, или отказ взвода (`value`/`image`/`vbl`/`limiter`/`havok`) | `1` или иное | прежние строки отказа P23 (если были) + `PVar: refused reason=hold` один раз; больше ничего |

| взведён режим 2 | `1` | удержание (ниже) |
| взведён режим 2 | иное | строка `PVar: armed …` как P23, затем `PVar: refused reason=hold`; дальше путь `0` |

Строка `refused reason=hold` — без счётчика `pvar_bad` («ничего», п. 346(г)); строка `PVar: armed …`, загрузчик и строка `GamePatch:` не изменены.

## Поля строки `PVar:` (г)(4)

Дописаны в конец, после `mode=2` (`pvar.cpp:239`; старые поля и их порядок не изменены — старый разбор P26 читает строку как прежде):
`kt=` — цель этого M0 (до обновления; 0 без удержания); `fit=` — после этого M0; `wait_us=` — ожидание на этом M0; `slack_us=` — запас до
вблэнка цели (может быть < 0); `late=` — `d > kt` (0 без удержания); `t_us=` — время прихода M0 от старта процесса; **`exit_us=`** — задержка
выхода из ожидания после вблэнка цели (−1 — выход по дедлайну; 0 — ожидания не было).

## Решения реализации (выбор исполнителя; лиду — вопросы)

1. **Механизм ожидания** — сон с опросом, а не условная переменная: `CondVar::WaitFor` имеет миллисекундную гранулярность
   (`SleepConditionVariableCS`), а условная переменная на вблэнке добавила бы правку `videoOut.cpp` и сигнал под `m_mutex`. Цена опроса —
   ≈ 5–10 пробуждений на кадр рядом с вблэнком [I]; медиана `exit_us` ≤ 1 000 мкс — гейт P32, не измерена.
2. **`exit_us=` — поле сверх списка (г)(4)** («вариант исполнителя»): (г)(1) требует задержку выхода «в строку лога», а новых строк, кроме
   `refused reason=hold`, нет — поэтому поле той же строки.
3. **`slack_us` в режиме `0`** — буквально по (г)(4): цель `v_prev + kt` при `kt=0`, т. е. время до (предсказанного) вблэнка `v_prev`
   минус время M0 — отрицательное число, `−slack_us` = время от вблэнка прошлого M0 до этого M0. Вариант исполнителя на выбор лида: цель
   `v_prev + 2` (начальное `kt`) — сдвиг на 2 × 16 666 мкс, информация та же.
4. **`fit` и `late` в режиме `0`** — 0 (не считаются): без удержания цели нет; (г)(4) называет считаемыми только `t_us` и `slack_us`.
5. **`fit` при `kt = 1`** насыщается на 30 (не растёт без предела; смысл «≥ 30 подряд»).
6. **Перелёт счётчика за время сна** (вблэнки Present пачкой после его задержки) даёт `d > kt` при `wait_us > 0` — по букве (г)(2) это
   опоздание и подъём; видно в строке (`late=1` и `wait_us>0`). Вопрос лиду: считать ли такой случай опозданием; вариант исполнителя —
   оставить по букве до данных P33.
7. **`n=`** — счётчик флипов в момент прихода M0 (до ожидания), как в P23.
8. Время — `KernelGetProcessTime()` (TSC → мкс от старта процесса) и на M0, и на вблэнке; P23 не читал время на этих местах — в режиме `0`
   это единственное изменение работы, кроме полей (ниже).
