## Ответы на вопросы шага (п. 97(ж), п. 98(м))

1. **Потеря записи / устаревшие данные GPU.** Довод §5.2 для страниц пуловых кусков в коде верен [I]: применение —
   `TakePendingRun` читает `Perms()` под `lock` внутри хватки `apply` (`pageManager.cpp:884`, `:1011–1039`), копия читает
   вид backing (`bufferCache.cpp:237–244`) после возврата применения на том же потоке. Запись до применения без фолта
   попадает в копию; запись после — фолт (`ChangeState<Cpu,true>`: биты → эпохи → защита, `regionManager.h:159–222`).
   `HasCurrentUpload`/`SyncFreeSkip` при О4 безопасны: эпоха снята до синхронизации (`bufferCache.cpp:822`), запись в окне
   без фолта эпоху не двигает, но лежит в копии куска, которую подача ждёт по семафору (`commandScheduler.cpp:815–828`).
   Дыры — RC2 (непроверенные страницы GuestGpu), RC4 (чужие наблюдатели без ребра), RC7 (ранний выход `UploadCopies`).
2. **Устаревшее разрешение поверх снятия/запрета.** Невозможно: задание не несёт значения, `apply` исключителен,

   `:500`); GPU-запись (О5) — синхронный `NoAccess` под `apply`, кусок затем находит страницу не отложенной. Подтверждаю.
3. **Дедлок / инверсия замков.** Не найдено. Новые рёбра, которых нет при 0: «кусок пула → `apply` → `lock`» и «кусок

   при `protfast`, иначе исключительный). Проверено: ни один поток не ждёт пул или завершение GPU, держа `apply`, `lock` или
   `m_mutex` адресного пространства; помощники `WaitAll` — презентация под render mutex (`commandScheduler.cpp:808`, `:932`),
   GuestGpu под `RegionManager::lock` записываемой загрузки при несогласованном staging (`bufferCache.cpp:1118`) — пулу ни
   то, ни другое не нужно. Снятие отображения ждёт GPU под `g_memory_operation_mutex` (`memory.cpp:4113–4124` →
   `renderContext.cpp:281–307`), которого кусок не берёт. **Требование к ревью кода шага 4:** ни одного нового вызова
   `WaitAsyncCopies`/ожидания GPU под `m_mutex` адресного пространства или под `apply` — это замкнёт цикл, которого при 0 нет.
4. **Смещение ABBA.** Защёлка раз на операцию и режим в `Job` — смены плеча посреди операции нет. Перенос между плечами

5. **«0 — прежний путь».** По тексту проекта — да в чтении п. 94(б) (п. 98(и)); проверяет ревью кода шага 4.

## Требуемые изменения

**RC1 (MAJOR) — детектор 2/3 судит по бухгалтерии куска, контроль 3 срабатывает по построению.**
Что не так: формула §7.1 п. 5 `watched ∧ (¬pend ∨ p ∈ J_left)` содержит член `J_left`, определённый кодом куска («при 3 —
J_left = J»). Страница J — это страница с отложенным ребром 0 → 1; по инварианту P её хост записываем, пока отложенное не
применено. Поэтому при 3 `ac_bad` > 0 при любом непустом J независимо от того, исправен ли механизм: контроль доказывает
лишь «отложенная страница записываема» (тривиальный случай P) и что `VirtualQuery` отвечает. Ветка `¬pend ∧ host_w` — та,
что ловит вероятные дефекты механизма (биты сняты `TakePendingRun`, а `Protect` дан не на тот адрес/размер или пропущен;
`Handover` уронил окно; прогон обрезан на границе куска), положительным контролем не проверена ни одним значением.
Сценарий отказа: в коде шага 3 `ArmForCopy` применяет прогон со смещением на одну страницу (`base + run_first*PAGE_SIZE`
считан от начала куска, а не области). При 2: биты сняты, хост последней страницы остаётся RW → детектор должен дать
`¬pend ∧ host_w`; если в этой ветке тоже ошибка (например, `watched` снят под `lock` до применения или `VirtualQuery`
склеивает прогон по первой странице), `ac_bad` = 0, контроль 3 «жив» (через `J_left`), дым и `ack129` проходят, запись
гостя в эту страницу теряется навсегда.
Что изменить: (а) детектор — только по состоянию: `bad = watched ∧ ¬pend_now ∧ host_w` под той же хваткой `apply` (под ней
чужих применений в полёте нет); `ac_jleft` = |J ∩ pend_now| — отдельный страж при 2 (п. 98(г) не меняется); (б) контроль 3 —
в одной хватке `apply`: взять прогоны (`TakePendingRun`: биты сняты, `applying_run` опубликован) → детектор → `memcpy` →
`Protect` → снятие `applying_run`. Тогда при 3 `ac_bad` > 0 идёт через ветку `¬pend` по ответу `VirtualQuery`, вооружение
не пропускается, P держится (применение «в полёте» под `apply`, как у любого `FlushRegion`). Нарушение P для гостя при 3
то же, что в проекте (окно «копия → вооружение» открыто нарочно).

**RC2 (MAJOR) — страницы, которые при 1 вооружает новый код на GuestGpu, самопроверкой не покрыты.**
Что не так: детектор работает только в пуловом куске (§7.1). При 1 новые пути GuestGpu — `Handover`, сброс остатка окна
(`ac_kept_gap`), сброс диапазона каждой inline-копии (`ac_kept_inl`), временный буфер — вооружают страницы, которые кусок
не видит. Условия корректности п. 97(е)(3) эти страницы не проверяют; проверка по содержимому (§7.3) их тоже не видит —
страницы остатка не копируются.
Сценарий отказа: остаток окна считается как «окно слота минус пуловые копии»; ошибка на границе (полуинтервал, окно слота в
страницах области против адресов копии) оставляет страницу-дыру `pending` без применения. Она наблюдаема, CPU-чистая, хост
RW. Следующая запись гостя фолта не даёт, бит не ставится, эпоха не двигается, `HasCurrentUpload` пропускает синхронизацию —
GPU читает устаревшие данные до случайного объявления записи соседней страницы. `ac_bad` = 0, `ac_cbad` = 0, дым зелёный.
Что изменить: при 2 — после сброса остатка (последнее действие операции на GuestGpu) тот же детектор по состоянию (RC1(а))
по всем страницам окон `Handover` и диапазонам inline-копий, под `apply` каждой области; счётчики в `ac_chk`/`ac_bad` или
отдельные `ac_gchk`/`ac_gbad` (страж 0 при 2, ряд при 3); при 3 — сброс остатка в порядке RC1(б) (взять → проверить →
применить), чтобы у этой ветки тоже был положительный контроль. Имена и число счётчиков §9.1 меняются — поправить Т5.

**RC3 (вопрос лиду о константе) — нет нулевого контроля детектора.**
Что не так: детектор существует только при 2/3; на пути 0 он не запускается ни разу. Хост может быть записываем на
наблюдаемой неотложенной странице по причинам, не связанным с механизмом (например, `KernelMprotect` гостя на странице с
наблюдателем — `memory.cpp:4126` и далее, трекер о нём не знает [U]). Сценарий: в дыме `armcopy=2` `ac_bad` = 3 на 40 млн
проверок. Страж п. 97(е)(3)(а) проваливает `ARMCOPY_INCORRECT`, а отличить дефект механизма от прежнего нарушения на пути
0 нечем. Что изменить: либо значение ручки, где путь 0 (вооружение на GuestGpu как при 0) плюс тот же детектор в куске
перед `memcpy` (обязан читать 0), — это сверх п. 97(е)(1) (0..3), поэтому решает лид; либо лид строкой принимает долг:
«`ac_bad` > 0 при 2 без нулевого контроля — вопрос лиду, не автоматический провал» (по образцу п. 98(в)).

**RC4 (MINOR) — §5.5 не рассматривает чужих наблюдателей без ребра на странице с отложенным вооружением куска.**
Что не так: при 0 отложенное `BatchScope` живёт только внутри операции GuestGpu. При 1 оно переживает операцию (новый класс
отложенных: не в очереди воркера, не в `inflight`, `Drain` на флипе его не ждёт, `pageManager.cpp:1193–1207`). Кэш
текстур на GuestGpu может вооружить образ на такой странице: счётчик 1 → 2, ребра нет, `pending` и очередь не ставятся
(`pageManager.cpp:559–566`, `:508–521`). Защита образа тогда держится на куске K. Сценарий: копия образа → запись гостя до K →
K вооружает; образ записи не узнает. Держится ли контракт образов «вооружено до того, как гость увидит флип»? Держится, но по
другой причине: подача флипа ждёт семафор копий, презентация — `WaitAsyncCopies`, значит K завершён раньше, чем флип
исполнен. Что изменить: вписать этот класс и довод в §5.5 (и в О-таблицу); метки EOP, которые гость видит при разборе PM4, —
тот же класс, что при 0.

**RC5 (MINOR) — О12 закрыт для GPU-диапазонов, в проект — ответ и остаток [U].**
Что в коде: снятие отображения гостем идёт через `FreeGuestMemory` → `UnmapGpuRange` (13 мест вызова в `memory.cpp`) →
`RenderContext::UnmapMemory` → `SendCommandSync` на GuestGpu → `Finish()` (`renderContext.cpp:287–292`). Подача `Finish`
ждёт семафор копий (`commandScheduler.cpp:815–828`) ⇒ все куски, поставленные раньше, вооружены и скопированы до снятия
хоста. Остаток [U]: ветка `m_command_scheduler.Active() == false` и backed-диапазоны с `!IsGpuAddressRange` (снятие без
уведомления GPU). Исход при нарушении — `Fatal` в `Protect` (`pageManager.cpp:355–358`), то есть громкое падение, не тихая
потеря. Что изменить: заменить «вопрос ревью» в §5.3 О12 и §13 этим текстом со ссылками; пройти все 13 мест вызова.

**RC6 (MINOR) — фактическая ошибка: «`ParallelMemcpy` образов».**
`ParallelMemcpy` вне `parallelCopy.cpp` не вызывается нигде: `parallelCopy.h` включают только `bufferCache.cpp`,
`commandScheduler.cpp`, `masterSemaphore.cpp`, `swapchain.cpp`. Достижим он только через `AsyncMemcpy` при

несогласованный staging), `:1509` и `:1514` (staging образов, дамп); презентация — `commandScheduler.cpp:808`, `:932`;
`Submit` при `KYTY_ASYNC_COPY_GPU_WAIT=0` — `:840`; деструктор — `:334`. Поправить §2.2 (строка `ac_kept_help`), §4, §13.

**RC7 (MINOR) — сброс остатка стоит после цикла копий, а у `UploadCopies` есть ранние выходы.**
`UploadCopies` возвращается до `Map`, если `copies.empty()` (`bufferCache.cpp:1069–1071`), и на пути импорта. При 1 окна
`Handover` из TLS там не сбросит никто. Сейчас это недостижимо [I]: `UpdateProtection` работает по всей области
(`regionManager.h:516–536`), но `m_writable` отстаёт от `m_cpu_dirty` только через `m_armed`, а `armdefer` = 0 запинен
и в отказах. Тогда отложенное окна ⊆ очищенные страницы, а они и есть копии. Что изменить: сбрасывать остаток на любом
выходе (после `upload_func` в `ForEachUploadRange` или RAII в `UploadCopies`) и записать инвариант «окна непусты ⇒ копии
непусты» с его основанием. Иначе будущая правка `armdefer`/`m_armed` молча оставит отложенное без владельца.

**RC8 (MINOR) — разрез прогонов: при 1 вызовов ядра станет больше, оценка S этого не учитывает.**
При 0 один прогон `pending` может покрыть «копия A + уже вооружённые страницы-дыры + копия B» одним вызовом:
`UpdateRegionWatchers` включает дыры с тем же `Perms()`, `pageManager.cpp:543–566`; `FlushRegion` — до 64 страниц за вызов.
При 1 кусок берёт только свой диапазон (`TakePendingRun` обрезает по `last`, `:873`, `:889`). Тот же прогон
распадается на вызов(ы) A, вызов дыры на GuestGpu (`ac_kept_gap`) и вызов(ы) B. Сценарий: S в дыме меньше оценки 0,80
при том же числе копий, а суммарное время вызовов ядра больше, чем при 0. Что изменить: пометить оценку §2.3 «без
разреза прогонов [I]». Добавить ряды по плечам: Σ вызовов `Read` всех потоков (`prot_ro`), `ac_kept_gap_n`, страниц на
вызов (`ac_moved_pages`/`ac_moved_n`). Правило убийства п. 97(е)(2) не меняется.

**RC9 (MINOR) — какой `arm` кусок передаёт в `Protect`, не сказано; Т3 от этого ломается.**
`pc_elig_*` считается при роли `Gpu`, `arm != No` и `t_ceil_state` ∈ {`CeilZero`, `CeilDose`} (`pageManager.cpp:415–437`).
Кусок, который GuestGpu исполняет, помогая внутри операции (`bufferCache.cpp:1118`: там `CeilScope` уже защёлкнул 0),
попадёт в `pc_elig`, если передаст `arm != No`. Утверждение Т3 «помощь не в `pc_elig`» тогда ложно. Что изменить:
назвать значение `arm` у `ArmForCopy` (новый `Arm::Job` вне `pc_elig` или явное включение) и переписать Т3 под него.

**RC10 (MINOR) — п. 98(м)(4): ряды голодания воркера защиты.**
Вызов `Protect` из пула увеличивает `sync_waiters` (`pageManager.cpp:352–361`). Воркер защиты уступает, пока это
значение ≠ 0 (`:947–949`). Всплеск кусков перед флипом удлиняет `Drain` на GuestGpu (`graphicsRun.cpp:4047`, `:4068`,
`:4096`). Дедлока нет: пул конечен и сливается презентацией. Эффект войдёт в Δ, но в §11.4 его рядов нет. Что изменить:
добавить по плечам `prot_drain_ns`/`prot_drains` (`ProtectDrainNs`/`ProtectDrains`) и `protw_us`.

**RC11 (MINOR) — ещё одно ложное срабатывание `ac_cbad` (ряд, §7.3).**
Сценарий: запись W до вооружения K (без фолта) → K копирует W → вторая операция GuestGpu объявлением/синхронизацией
соседнего диапазона снимает CPU-грязный бит той же страницы и копирует W → `memcmp` K видит расхождение и чистый бит. Это
