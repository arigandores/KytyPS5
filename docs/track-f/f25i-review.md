## 2. Требуемые изменения

**RC1 — во всех 4 кадрах в счёте холодного слоя спящая запись — строка формы харнесса; объём лога — на 90 % форма харнесса.
Меняет решение F25j: да.**
- *Что не так.* F25h §3.3 читает n 17512 как «тот же механизм, другая точка ожидания» и §4 К-б — как механизм по умолчанию
  (запись лога потоками гостя). Но в отрезке строк кадра 17512 (`FrameTrace n=17511 … n=17512`) строк потока Gpu — две
  `FaultTrace-gpu:` (`volume_k05.out`), а `FaultTrace-gpu` пишется только при `FrameStats::Enabled()`
  (`35b454c6:src/common/hostException.cpp:192`, `:206` — внутри обработчика исключения доступа), то есть только формой
  `KYTY_FRAME_TRACE`. `PriorityStall: … us=1337653` того же отрезка — следствие: поток `POps` ждал отправки тика, которую Gpu
  не сделал, пока 1,34 с был внутри `Log::Write` (`commandScheduler.cpp:709`) [c]. Итого: Present писал `FrameTrace` в 3 кадрах
  (8966, 17344, 17394) и Gpu писал `FaultTrace-gpu` в 1 (17512) [что именно эта строка Gpu спала — I, других строк Gpu в
  отрезке нет]. Кроме того, строки `FrameTrace*`/`FlipHold` — 90,37 % байт лога `f25_k05` и 90,96 % у контроля `f25_z1`
  (`KYTY_DIAG_B32=0`); строки гостя по умолчанию (аргументы вызовов и заголовки) — ≈ 8,8 % (`volume_*.out`). Темп записи лога
  формы F25f — ≈ 1,6 МБ/с, у пользователя без `KYTY_FRAME_TRACE` — порядка 0,15 МБ/с [I: по доле строк гостя].
- *Сценарий отказа.* F25j по К-б назначает итерацию `KYTY_FIX_B36` на пути записи лога потоками гостя по умолчанию и критерий
  «нет K2 на холодном входе» под той же формой харнесса: форма сама создаёт 90 % записи и все 4 спящие записи кадров в счёте —
  исход серии не различит правку и форму; либо F25j закрывает строки Б36/Б40 как «вызваны харнессом», хотя частота задержек
  файловой системы при объёме пользователя не измерена [U].
- *Правка.* В §0 п. 2–3 и §3.3, §4: назвать писателя каждого из 4 кадров в счёте и источник строки (форма харнесса /
  по умолчанию) с меткой; напечатать долю байт лога по источникам; К-б переписать: «механизм возможен на пути по умолчанию
  (пример — n 17451, DrawThread пишет строку по умолчанию, Sw 27, 145 мс), но ни один кадр в счёте серии им не вызван» [c];
  в «Не заявляется» — что задержки файловой системы при объёме лога пользователя бывают.

**RC2 — вариант (iv)(1) «вынести печать из-под замков» не различает то, что должен. Меняет решение F25j: да (если выбран (1)).**
- *Что не так.* `dt_us` кадра меряет сам поток Present в своём снимке (`35b454c6:src/graphics/presentation/videoOut.cpp:1361`,
  `cur.host_ns = FS::NowNs()`), и следующий кадр показывает тот же поток. Если `Log::Write` строк `FrameTrace` перенести после
  `:3607`, но оставить на потоке Present, задержка записи 2 с всё равно даст `dt` 2 с и 2 с без показанного кадра; изменится
  только то, кто ждёт (Gpu перестанет ждать `FlipQueue::m_mutex` и встанет позже на очереди флипов).
- *Сценарий отказа.* Холодная серия по (iv)(3) с правкой (1) снова даёт K2 той же частоты; F25j читает это как «K2 холодного
  входа есть и без записи лога под замком флипа» — ложный вывод: запись лога на потоке, который меряет и показывает кадр,
  осталась.
- *Правка.* Различающий вариант обязан снять синхронную запись с потока Present (строки копятся в буфер под замком, пишет их
  отдельный поток, или вывод `FrameTrace` асинхронным приёмником), а контроль — назвать: тег той же формы с задержкой записи
  на стенде (сон в писателе) обязан не давать `dt` ≥ 1 с. Отдельно назвать, что пишет `mp4` и `.idx` записи видео в тот же
  каталог (`screenshot.cpp:520`, `:524`, поток кодировщика) — источник задержек файловой системы [U] не различён и с правкой.

**RC3 — неверное доказательство К-б «PRINT_NAME включён по умолчанию». Меняет решение F25j: нет.**

  Запись гостя по умолчанию доказывают безусловные `LOGF` аргументов (`35b454c6:src/libs/agc.cpp:2129` и т. п.) — 8,4 % байт

  Present в записи файла; в трёх кадрах это не следует из записанных полей.

**RC5 — перечень записей лога под `VideoOutConfig::mutex` по умолчанию неполон. Меняет решение F25j: нет.**
