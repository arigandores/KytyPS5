## RC кода

**RC1. `CommandRecorder::Reserve` — метка на каждый срез 1 мс, а не на цикл (нарушение буквы п. 574(г)(1)).**
Метка `W:rec_wait` ставится внутри внешнего цикла повтора `for (;;)` `9db7938b:src/graphics/host_gpu/renderer/commandRecorder.cpp:194`
(якорь «for (;;) {»; +1 — «// This thread's own head…»): `BeginWReg` — `…:225`, ожидание — `m_progress.wait_for(lock, WaitSlice, …)` `…:227`
(`WaitSlice` = 1 мс), после ожидания — `continue` к началу цикла. Каждый срез ≤ ≈ 1 мс < `kWaitRecNs` 10 мс ⇒ запись `-w` не создаётся никогда.
**Сценарий отказа:** арена записи полна 200 мс (поток записи `Record` отстаёт), производитель (GuestGpu) ждёт в `Reserve`: выборки — `W:rec_wait`
≥ 50 %, но в окне нет ни одной записи `-w` ⇒ по п. 574(д) шага к будящему или к `peer` нет (они берутся из записи) ⇒ класс `EMU_WAIT:rec_wait`
у GuestGpu, цепочка обрывается, хотя `peer` (= `Record`) метке известен. Ровно форма «метка на вызов», которую п. 574(г)(1) запрещает и которую
контроль `TestWaitLoopRuntime` показывает (0 записей). **Изменить:** объект `Mark` до `for (;;)`, `BeginWReg` на первом проходе с полной ареной
(`!b32.Active()`, как в `AudioOut2ContextPush`, `RwlockLockCooperative`, `pthread_once`), снятие перед `return` (или деструктор). Тот же приём
`Drain` (`…:578`) уже делает верно. Скрипт описи `waits_f20j3.py` охват цикла не проверяет (проверяет «метка выше строки в той же функции»),
поэтому пропустил; моя проверка охвата — `rt_loopmark.py` (§3): из 10 меток внутри цикла 9 верны (сервисные циклы или `!Active()`), неверна эта.

**RC2. `TrackedMutex`: `peer` = последний захвативший, который мог уже отпустить, — в том числе сам ждущий; у `std::shared_mutex` — систематически.**
`m_owner` пишется после захвата (`9db7938b:src/common/diagB32.h:242`) и при `unlock` не сбрасывается (`…:217`, якорь «void unlock() { m_m.unlock(); }»);
захват читателем (`lock_shared`) `m_owner` не пишет. Ждущий берёт `peer` = `m_owner` (`…:238`, `…:224`), и для мьютексного рода будящий = `peer`
(п. 550(г)(2)(iv) «мьютекс — к `peer`», `MutexLike`). **Сценарий отказа:** `RenderContext::m_mapped_ranges_mutex`
(`9db7938b:src/graphics/host_gpu/renderer/renderContext.h:99`) — GuestGpu держит его разделяемо в `PrepareBda` (`renderContext.cpp:325`,
≈ 180 раз за кадр, полный обход на промахе), поток гостя X зовёт `MapMemory` (`renderContext.cpp:276`, захват на запись) и ждёт читателей.
`m_owner` = прошлый писатель — нередко сам X (прошлый `MapMemory`) [I] ⇒ запись `W:emu_mutex` с `peer` = `waker` = слот X ⇒ шаг цепочки ведёт
к самому ждущему (цикл или класс по его же `W`), держатель (GuestGpu) не достигается. Тот же самоуказатель возможен и у обычного мьютекса: A
отпустил, B захватил и ещё не записал `m_owner`, A снова ждёт ⇒ `peer` = A (окно отчёт называет «[I]», но не следствие «сам себе peer»).
`Common::Mutex::LockB32` этим не страдает (`OwningThread` держателя или 0). **Изменить:** при `=1` сбрасывать `m_owner` в 0 перед `unlock`
(одна проверка `g_on`, путь `=0` — прежний); в `BeginWReg` (или в `TrackedMutex`) `peer` = собственный слот ⇒ 0; захват на запись при
держателях-читателях — `peer` 0 (будящий неизвестен ⇒ `EMU_WAIT:emu_mutex` по п. 574(д), честно). Модульный тест: писатель ждёт двух
читателей ⇒ `peer` 0; ни одна запись `-w` не несёт `peer` = свой слот.

**RC3. Время обновления M5 приписывается следующему окну, а не тому, в котором шло (нарушение буквы RC9: «время … снимков M5 внутри окна»).**
`ProcessFlips`: `m5r = m_m5r.TakeWorkNs()` (`9db7938b:src/common/diagB32.cpp:1804`) — время обновлений, закончившихся с прошлого флипа,
т. е. внутри закрываемого окна k; окно k закрывается `CloseWindow` (`…:1827`) БЕЗ него (там `extra = m_win_extra_ns + print_ns`, `…:1619`), затем
`m_win_extra_ns += … + m5r` (`…:1836`) — в окно k+1. До F20j3 обновление шло на потоке сэмплера на границе после флипа и правда было внутри k+1;
после переноса на свой поток это уже не так. **Сценарий отказа:** снимок 76,7 мс (цена из `b32_pp`, п. 574(а)(6)) идёт внутри кадра Б32
k (150 мс), следующий кадр k+1 тоже долгий (120 мс): у k+1 `instr_us` += 76,7 мс ⇒ `dt_us − instr_us` = 43 мс < 100 мс ⇒ `INSTR_MADE` —
настоящий кадр Б32 выпадает из счёта; у k `m5r_us` = 0, и мера возмущения У5 (`instr_us`) занижена именно там, где снимок шёл. `TestM5Async`
проверяет только «время берётся», не окно. **Изменить:** `AsyncRefresh` хранит [начало, конец] каждого прогона; `CloseWindow` окна k
берёт перекрытие прогонов с (`win_start`, `flip_ns`] в `m5r_us`/`instr_us` k, остаток — в k+1. Модельный тест: прогон целиком внутри k ⇒
`m5r_us(k)` = цена, `m5r_us(k+1)` = 0.

**RC4. Вложенная `W:emu_mutex` вытесняет `H:qlock` — ломает вход деления RC7 и обязательной строки RC5, которые п. 574(д) оставляет без изменений.**
Все три места `H:qlock` — `BeginH(QLock)` ровно вокруг `Common::LockGuard lock(<queue_mutex>)` (`9db7938b:src/graphics/host_gpu/renderer/commandScheduler.cpp:162`/`:164`,
`…:1012`/`:1014`, `9db7938b:src/graphics/presentation/window/swapchain.cpp:811`/`:813`, `systemOverlay.cpp:1077`). При `=1` захват под конкуренцией
идёт в `Mutex::LockB32` (`9db7938b:src/common/threads.cpp:337`), который ставит `W:emu_mutex` поверх (`…:344`); выборка показывает самую
внутреннюю метку ⇒ под конкуренцией `H:qlock` ≈ 0 выборок. Правило п. 550(в) RC7 (`eead6454:docs/ROADMAP.md:23220`): `EMU_LOCK` — «другой поток
в `H:qlock` ≥ 50 %», `qlock` — `EMU_CALL` без деления; RC5 — обязательная строка `-t` отправщика по выборкам `H:qlock`/`H:qsubmit`.
**Сценарий отказа (серия):** поток вывода в `H:present` ждёт `graphics.queue_mutex`, держит его `ASubmit` в `H:qsubmit`. До F20j3: держатель —
`H:qlock` ≥ 50 % ⇒ `EMU_CALL:qlock`. После: `W:emu_mutex` ≥ 50 % ⇒ шаг к `peer` (`ASubmit`) ⇒ `EMU_CALL:qsubmit` ⇒ деление RC7: «другой поток в
`H:qlock`» больше не выполняется (поток вывода — `W:emu_mutex`) ⇒ `DRV_GPU` или `DRV_HOST`; `DRV_HOST` идёт в сумму У3 (п. 550(г)(3)(iii)). Тот же
кадр меняет класс по умолчанию правила, которое п. 574(д) объявил неизменным. Правкой правила это не чинится: строки `-t` считают `W` по роду без
`obj`, `W:emu_mutex` на очереди не отличить от любого другого. **Изменить (код):** `LockB32` и `TrackedMutex::LockSlow` не ставят `W:emu_mutex`,
если текущая метка слота — `H:qlock` (метка RC5 уже называет это ожидание); `peer` для такого захвата — вне правила RC7, не нужен. Модульный
тест: захват `Common::Mutex` под конкуренцией внутри `H:qlock` ⇒ выборки `H:qlock`; без `H` ⇒ `W:emu_mutex`. Если лид решит иначе
(новое деление RC7 по `W:emu_mutex`) — это решение до F20l2 с фикстурой ридера; без одного из двух RC4 открыт.
