## 1. Решено измерениями и ресёрчем — не переоткрывать

- **FPS квантован по vblank**: 99,2 % кадров = ровно 2 vblank. Любая отметка выше 16,67 мс
  даёт ровно 30,0 FPS. Прогресс мерить в миллисекундах, FPS — только приёмка.
  Цель — `max(CPU, GPU)` **p99 ≤ 15 мс**, а не медиана 16,6.
- Закрыты: zero-copy backing (0,6–0,7 мс), межкадровый frame-replay (0,03 % повторов ключа),
  конвейеризация по кадрам (запас 1,9 мс), compute на отдельном потоке (общий
  `m_context.GetMutex()` у draw и dispatch), склейка в инстансы (`gl_InstanceIndex` занят),
  `VK_EXT_multi_draw`, фильтрация vkCmd динамического состояния, «прибить DRS», полный save state.
  Полный список — `docs/local-session-66.md` §8.
- Риск динамического разрешения снят (pace-скейлер прячет от игры скорость CPU), но per-frame
  сторож разрешения обязателен.

## 2. Работа сессии

Ни одного прогона Sky Garden с участием пользователя не планировать: вся проверка — на пустыне
и на автоматическом входе. Порядок — от самого ценного.

### 2.1 `KYTY_GUEST_ARGS` — отдать игре её командную строку (приоритет)

`runtimeLinker.cpp:1491-1492` ставит `argc = 1`, `argv[0] = "KytyEmu"`, хотя `EntryParams`
(`runtimeLinker.cpp:90-97`) вмещает `argv[3]`. Рядом с игрой лежит её родная строка:
`games/PPSA21564-app/args.txt` = `-package -sequence product -mode product -odxBinary
-perfDisplay false -debugDisplay false -debugInput false`.

Порядок: (1) read-only разведка eboot — найти парсер опций и таблицу имён уровней (якоря:
`-lvl`, `-sequence`, `-worldmap`, `-room`, `-finalStage`, `-skipIntro`, `-showLogo`,
`-debugSettings`, `-perfDisplay`); включить гостевой лог `KYTY_POKE="27e46c:909090909090"`
и посмотреть в `GuestOut:`, что движок разбирает; (2) расширить `EntryParams`/передачу argv,
строку брать из `KYTY_GUEST_ARGS` (по умолчанию — содержимое `args.txt`, чтобы поведение
не менялось без явного запроса); (3) проверить на пустыне, что игра стартует как прежде.

**Ворота:** `-lvl <sky garden> -skipIntro` (или эквивалент) доводит до сцены без человека
за ≤ 90 с и воспроизводится 3 раза подряд. Если парсер аргументов не найден или уровень
так не выбирается — зафиксировать это и перейти к 2.2+2.5 как к основному пути.

**Бонус того же пункта:** `-perfDisplay true` — встроенный профайлер игры. Если он рисуется,
это независимый от нас источник времени кадра.

### 2.2 Persist SaveDataMemory

`libSaveData.cpp:480` (`SetupSaveDataMemory2` только `resize`), `:508` Get, `:546` Set,
`:763` `SyncSaveDataMemory` возвращает OK без записи. Каталог
`_SaveData/PPSA21564/sce_sdmemory` смонтирован (`:470-476`) и пуст.
Гейт `KYTY_SAVE_PERSIST` (по умолчанию 0 на время проверки): в Setup читать `memory.bin`,
в Set/Sync и при выходе писать с дебаунсом. До реализации — один дешёвый прогон пустыни
с логированием вызовов SaveData: подтвердить, что прогресс идёт именно через memory-API.

### 2.3 `KYTY_GATE_SCHEDULE` — чередование плеч A/B по 20–40 present

`Gates::Poll` уже вызывается на каждом flip с номером кадра (`videoOut.cpp:1179` →
`gates.cpp:200`). Добавить внутреннее расписание: `KYTY_GATE_SCHEDULE="имя=0|имя=1"` с периодом
N present, границы блоков точные и не зависят от внешнего скрипта.
Обоснование — `docs/local-session-66.md` §5: длинные фазы дают sd базы 2,4 %, чередование
блоками по 20 — SE 0,32 % на том же времени прогона.

Вместе с этим — переписать сводку: первичная метрика `cpu_gpu_us` на кадр, вторичная `dt_us`
на кадр, `cpu/draw` — диагностика; решение по SE парных разностей, а не по одному числу;
обязательное холостое плечо A/A для объявления порога внутри самого прогона.

### 2.4 Сторожа каждого прогона

- `rt_w/rt_h` (максимальный extent привязанной цветной цели за кадр; значение уже посчитано
  в `colorRenderTarget.cpp:405-407`) и `vp_w/vp_h` (viewport крупнейшего прохода) — в `FrameTrace`.
  Без них все A/B невалидны: существующие логи обрезаны на 128 строках и 512 dispatch'ах.
- `guards.py`, обязательный для каждого прогона, PASS/FAIL по: разрешению (постоянство внутри
  и между плечами), `draws` на кадр в плечах ±0,5 %, доле тяжёлых кадров ±5 п.п., ядрам
  (±10 % медианы), частоте CPU и `clocks_throttle_reasons` GPU, десяти счётчикам MISMATCH
  (`pageManager.cpp:888`, `bufferCache.cpp:665/970/1539`, `descriptors.cpp:1497`,
  `pipelineCache.cpp:1557/1661/2539/3204`), `GpuWaitSlow|GpuHangAbort|ErrorDeviceLost|
  Unhandled exception|AsyncPipelines: skipped`, глитчам видео, числу present в `.idx` против
  числа строк `FrameTrace`, sha256 бинаря и полному тексту гейт-файла каждой фазы.

### 2.5 Рекордер/плеер пада (запасной путь входа в сцену)

Точка одна и узкая: `GameController::ReadState` (`controller.cpp:839`) и `ReadStates` (`:852`).
`KYTY_PAD_REC=<файл>` — дописывать (present, buttons, axes[6], motion) на каждом flip;
`KYTY_PAD_PLAY=<файл>` — подменять состояние по номеру present, сегменты привязаны к маркерам
`LevelDocument Loaded: <имя>`, плеер держит последнее состояние до маркера и прерывает прогон
по таймауту. Клавиатурная эмуляция маршрут не повторит: пользователь играет DualSense
(аналог против 0/128/255 в `hostInput.cpp:237-245`).
`enter_scene.py`: запуск → воспроизведение → ожидание `underwater_aerial_garden` + 90 кадров
≥ 3 000 draw → при `GpuHangAbort`/`ErrorDeviceLost`/таймауте убить и повторить, до 3 попыток;
первая попытка после новой сборки планируется как заведомо прогревочная (зависание первого
входа — правило сессий 54/61).

## 3. Чего в этой сессии НЕ делать

Не трогать горячий путь draw, кэши, кольцо записи, трекер памяти. Не реализовывать occlusion
queries, M4, адресные правки — их ворота в сессии 68. Не менять умолчания существующих гейтов.
