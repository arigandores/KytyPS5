## 1. RC

### RC1 — ответ на вопрос (в)(1): позиция лида (б) верна; `tint_mips ≥ 1` — тавтология, контроль механизма — чтением обратно

**Что не так.** Исход §8(4) («`=2` и `=3` — оба < 3 кадров ⇒ `НЕ ДЕФЕКТ`») не различает «образ события не доходит до экрана» и
«окраска не легла». Предложенный лидом в игре член `tint_mips ≥ 1` при `=3` считает **вызовы** очистки, а не тексели в образе —
это контроль пути счётчика, то есть тавтология.

**Сценарий отказа.** Emu Engineer пишет `vkCmdClearColorImage` в текущий буфер команд, а перезаливка `UploadImage` идёт через
отдельный поток/кольцо заливок, исполняемое позже (или очистка записана до `Transit` в нужную раскладку) — очистку тут же затирает
перезаливка. `tint_mips` = 10⁴, пурпура нет ни при `=2`, ни при `=3` ⇒ по нынешнему (4) T188 — `НЕ ДЕФЕКТ`, хотя потеря видна.
Тот же исход даёт очистка не того поддиапазона (не тот `baseMipLevel`).

**Что изменить.** (а) (4) по умолчанию читается «не определено» ⇒ `ТУПИК` по картинке (форма п. 698(з)(3)) — согласен с (б).
(б) Контроль механизма в игре — **чтение обратно**: при `=2`/`=3` для первых K окрашенных мипов каждого класса образа (K и
выбор текселя — константа издания 2) после очистки в том же порядке команд копировать один тексель окрашенного мипа в видимый
хосту буфер и сравнить после ограды с ожидаемым кодом цвета формата: поля `tint_rb_ok`, `tint_rb_bad` (инвариант 0 — иначе
исход (1), дефект кода), `tint_rb_none`. (в) Стенд на настоящем устройстве Vulkan: очистка мипа `l` поддиапазоном ложится на
`l` и не трогает соседние мипы и слои (мутант «не тот `baseMipLevel`» обязан ловиться). (г) (4) может стать `НЕ ДЕФЕКТ`
только при (б) живом для классов, несущих ≥ доли `lost_bytes`, названной изданием 2, и при RC2 (видимость не только пурпуром).

### RC2 — окраска (1, 0, 1, 1) видна пурпуром только у образов, чьи тексели идут на экран цветом; исход не различает классы

**Что не так.** Детектор §4.4 ищет пурпур. Потерянный мип карты нормалей, шероховатости, скоростей, LUT, тени в цветовом формате,
одно- и двухканального формата (`R8`, `R16F`, `RG16F`, `R32F`) при окраске (1, 0, 1, 1) пурпуром на экране не станет: у
одноканального это `R = 1`, у данных — искажение освещения или ничего. К-П (`=3`) жив, если пурпур дал **любой** класс.

**Сценарий отказа.** Sky Garden: основная доля `lost_bytes` — у образа нормалей RG8 (потеря видна как неверное освещение
отрисованного участка при `=0`); при `=2` освещение меняется, но пикселей R ≥ 200, G ≤ 60, B ≥ 200 нет ⇒ 0 кадров; при `=3`
пурпур даёт другой класс (цветовой RGBA8 HUD-слой) ⇒ К-П жив ⇒ исход (3) `НЕ ДЕФЕКТ` по картинке — ложно для класса,
несущего потерю.

**Что изменить.** (а) `T188Img` получает по классу `lost_bytes`, `tint_bytes`, `tint_mips`, `tint_skip`, `tint_rb_ok`
(сейчас по классу только `ev*` и четыре `cl_*`) — тождества И3/И6 по этим полям. (б) Покрытие и исход — по классу: К-П (`=3`)
обязан быть живым **для того класса**, о котором выносится `НЕ ДЕФЕКТ`. Форма атрибуции — за изданием 2: цвет окраски по рангу
класса (пурпур, голубой, жёлтый… с детектором на каждый цвет) или ручка ограничения `=3` списком ключей классов из `T188Img`
тега `=2`. (в) Для классов без живого К-П по классу — «не определено». (г) Дополнительно к детектору — пара листов `=3` / M6c
той же сцены (форма F9h): **любое** видимое отличие при `=3` (не только пурпур) — свидетельство, что поверхность класса доходит
до экрана; тогда `=2` этого класса читается тоже парой листов, не только детектором.

### RC3 — `IsGpuModified` не значит «буфер устарел»: после синхронизации образ остаётся `IsGpuModified`, окраска даст ложное «да»

**Что не так.** `SynchronizeBufferFromImage` (`textureCache.cpp:3226–3296`) и `DownloadImageMemory` (`:3299–3397`) качают образ,
но `IsGpuModified` не снимают; снимают его только `FreeImage` (`:501–503`) и `InvalidateMemoryFromGPU` (`:3421–3423`) [c `grep`
`ClearGpuModified`]. Модель §1(3) «в буфере вне W лежит устаревшее» помечена [I], но предикат события S2 и окраска §4.2 её
принимают как факт.

**Сценарий отказа.** Цель отрисована (`IsGpuModified`), затем прочитана как буфер текселей (`ObtainBuffer(..., !is_written,
is_texel)` → синхронизация, `bufferCache.cpp:1155`) — буфер = отрисованному; затем частичная запись DMA W ⇒ S2 открывает эпизод;
перезаливка берёт «отрисованное + W» — **верно**, потери нет; при `=2` окраска закрашивает мипы вне W ⇒ пурпур на экране ⇒ исход
(2) «T188 `дефект` K4 с видимым следствием [c окраски]» — ложно; `lost_bytes` и цена формы A завышены.

**Что изменить.** (а) Состояние образа в инструменте: номер записи ГП `t188_wseq` (растёт на каждом захвате образа под запись ГП:
`FindRenderTarget` `:2705`, `FindDepthTarget` `:2803`, `CommitGpuWrite` `:2875`, `CopyImage` `:883–884` — места называет
Emu Engineer, член ревью — «все места `MarkGpuModified`») и номер синхронизации `t188_sseq := t188_wseq` при успехе
`SynchronizeBufferFromImage` **этого** образа. (б) S2: при `sseq == wseq` — поле `part_synced` (не эпизод, не окраска); при успехе
только `DownloadImageMemory` после последней записи — `part_dlmem` (буфер после `WriteBacking` — [U]); И2 расширить этими полями.
(в) Текст исхода (2): окраска видна ⇒ «поверхность потерянных мипов доходит до экрана»; «видимое следствие при `=0`» — [I] до пары
§7(4); исход (2) ведёт к коду правки, но не пишет `[c окраски]` про отличие картинки.

### RC4 — отложенные мипы: окраска на S3 затирается `CompletePendingUpload`; [I] §11 опровергается кодом

**Что не так.** §11: «отложенные мипы — только у импортированных образов выборки, [I] что они не бывают `IsGpuModified`».
`DeferrableLevels` (`textureCache.cpp:1618–1633`) проверяет импорт **буфера-источника** (`source.imported`), `UploadBinding ==
Texture` и форму, но не `IsGpuModified`; образ только выборки становится `IsGpuModified` копией образа (`CopyImage`
`:883–884`); `KYTY_MIP_DEFER` по умолчанию включён (`graphicContext.h:72`, `textureCache.h:350`).

**Сценарий отказа.** Текстура-приёмник копии образа (`IsGpuModified`, usage — только выборка), частичная запись DMA её мипа ⇒
эпизод; выборка после исчерпания `KYTY_MIP_DEFER_FRAME_MB` ⇒ уровни `[source_first_level, deferred)` не заливаются на S3 (`:1860–1866`),
вид ограничивает LOD; проект красит их на S3 «после `UploadImage`»; позже `CompletePendingUpload` (`:1635–1650`) заливает туда
устаревшее из буфера поверх окраски ⇒ потеря видна, пурпура нет ⇒ ложное «нет следствия».

**Что изменить.** S3 красит только уровни, залитые этим вызовом (`[first_level, levels)`, `:1861–1864`); отложенные потерянные
уровни открытого эпизода красятся новым местом S3b в `CompletePendingUpload` после `UploadImage`; поля `ep_pend`, `lost_pend_bytes`;
[I] §11 заменяется строкой [c] этого RC. То же правило «красить только залитое» — для `source_first_level > 0`.

### RC5 — ответ на вопрос (в)(5): закрытия S3–S6 неполны — `BufferModified` снимается без перезаливки

**Что не так.** Кроме `InitializeImage` метку снимают без перезаливки: `CommitGpuWrite` (`textureCache.cpp:2866–2876`,
`ClearBufferModified` безусловно), куда ведут полная очистка образа `ClearImage` (`:3034` — перезаливка только при
`!full_image`; `:3082`, `:3101`), полная очистка в `PrepareDccClear`/`PrepareCmaskClear` при захвате цели (`:2764–2770`, комментарий
`:2713–2715`), `MarkGpuWritten` (`descriptors.cpp:3718`, `renderDraw.cpp:5589`, `depthRenderTarget.cpp:463`),
`ReinterpretColorAsMsDepth` (`:1015`); приёмник `CopyImage` (`:887`); перенос метки на приёмник при `source.IsBufferModified()`
(`:855–858`). Пути, где потерянное содержимое **читается** без `InitializeImage`, я не нашёл (`CopyImage` источника с меткой
выходит рано `:855–859`, `CopyImageMip` — `EXIT` `:900–902`, `DownloadImageMemory` — только при `SafeToDownload`); показ
несжатого `VideoOut` — не проверен [U].

**Сценарий отказа.** W1 открывает эпизод; захват цели с полной DCC-очисткой ⇒ `CommitGpuWrite` снимает метку (потери нет —
образ перезаписан) — эпизод остаётся «открыт»; цель отрисована; частичная W2 ⇒ `reopen`, объединение W1 ∪ W2; перезаливка ⇒
`lost_bytes` = образ − (W1 ∪ W2), мипы, пересекающие W1, не крашены (`tint_part_mips`), хотя в буфере на W1 лежит старое
относительно новой отрисовки — потеря недосчитана, окраска её пропускает (смещение к «нет следствия»), класс закрытия неверен.
Перенос `:855–858`: приёмник позже перезаливается из буфера без открытого эпизода — потеря не считается вовсе.

**Что изменить.** Место S7 в `CommitGpuWrite` и у `:887` — закрытие `cl_commit` / `cl_copydst` (без окраски); место S8 у
`:855–858` — эпизод приёмника (`ep_prop`); И2 расширить; член записки кода — список всех читателей `IsBufferModified()`
(все места `IsBufferModified()` по `git grep` в `1ffda330`: `textureCache.cpp` — 15, `descriptors.cpp` — 2, `renderDraw.cpp` — 1, кроме печати диагностики) с пометкой «закрывает / не закрывает»; показ `VideoOut` — строкой этого списка.
`ep_bad` определить как «закрытие **открытого** эпизода, которого нет в таблице, или двойное открытие»: S3 исполняется на каждой
перезаливке, и закрытие без эпизода — норма, не инвариант.

### RC6 — ответ на вопрос (в)(4): замок поля эпизода — только `m_lock` с самопроверкой; крюк формы A — выбор образа и частичная синхронизация

**Что не так.** (а) §3.2/S3: «замок — тот же… иначе атомарное поле эпизода». Состояние эпизода составное (флаг, флаг
«сохранён», до 8 интервалов, счётчик переполнения): атомарность поля не защищает составное значение — рваное чтение
объединения. (б) Крюк формы A §6: после отпускания `m_lock` (отпускание нужно — `TrackingSpinLock` `EXIT` на повторный вход,
`textureCache.h:325–326`) зовётся `ObtainBuffer(SourceRange, false, true)` → `SynchronizeBufferFromImage`, который выбирает образ
**по базе** через `FindImageFromRange` (`textureCache.cpp:2535–2573`): при двух образах с той же базой берётся образ с
`info.data.size == size` или первый. (в) `SynchronizeBufferFromImage` может синхронизировать только уровни, влезающие в буфер
(`:3254–3261`, `:3272–3279`), и вернуть `true`.

**Сценарий отказа.** (б) Псевдоним того же адреса в другом формате тоже `SafeToDownload` — скачан он, его байты легли в буфер
поверх верных; `fix_dl` = +1, флаг «сохранён» снял окраску ⇒ правка портит образ и прячет это от меры (аналог m5, стендом §7(1)
с одним образом не ловится). (в) Синхронизированы мипы 0–3 из 6 — эпизод «сохранён», мипы 4–5 потеряны и не крашены.

**Что изменить.** (а) Все места S1–S8 — под `m_lock`; в режиме `≥ 1` самопроверка владельца замка (поле `lock_bad`,
инвариант 0, исход (1)); вариант «атомарное поле» снять. (б) Крюк синхронизирует **названный** образ (перегрузка по `ImageId`
или проверка `selected == id`, иначе `fix_no_sel`); мутант «крюк качает псевдоним» — в список §7(2), стенд — два образа с одной
базой. (в) «Сохранён» — только если синхронизированы все уровни, которые зальёт следующая перезаливка; иначе `fix_part`
(в И7). (г) Порядок §6 (крюк до `ObtainBuffer` записи, проход до первой привязки draw) — верен, член ревью остаётся.

### RC7 — ответы на (в)(2) и (в)(3): `M_b` — по каждому кадру; К-Д проверяет логику детектора, но не кодек и не порог

**Что не так.** (2) Справка `M_b` взята 1 кадр/с — максимум недооценён. (3) Квадрат К-Д проходит одно кодирование ffmpeg, а не
управление битрейтом NVENC записи; 32 × 32 = 1 024 пикселя — в 5 раз выше порога 200, чувствительность у порога не
проверяется; при 960 × 540 потеря меньше ≈ 200 пикселей (≈ 800 при 1080p) мерой не видна, это нигде не сказано.
Кроме того, исход (2) машинный («≥ 3 кадров»), а прогон тега `=2` не повторяет кадры M6c: пурпур игры, которого не было в
видео M6c, даст ложные кадры.

**Сценарий отказа.** Окрашенный дальний мип занимает на экране полосу 120 × 2 пикселя при 960 × 540; цветность 4:2:0 и NVENC
её размывают ниже R ≥ 200 / B ≥ 200 ⇒ 0 кадров, хотя квадрат К-Д 32 × 32 найден 30 из 30 ⇒ К-Д «жив», исход «нет следствия».

**Что изменить.** (а) `M_b` — максимум `N_mag` по **каждому** кадру видео M6c в том же окне (после строки входа в сцену), до
серии, с sha видео и скрипта. (б) К-Д — три формы вставки: 32 × 32, 15 × 15 (≈ порог) и полоса 64 × 4; кодер — `h264_nvenc` с
параметрами записи `KYTY_REC`, если он есть в ffmpeg, иначе [I] остаётся и печатается; критерий — 30 из 30 для 32 × 32 и
печать доли для меньших (меньшие — мера чувствительности, не допуск). (в) В §11 «не доказывает»: окраска площадью < порога на
960 × 540. (г) Исход (2) — детектор ≥ 3 кадров **и** лист лида, где пурпур — плоская поверхность образа, а не содержимое игры;
иначе «не определено».

### RC8 — покрытие 0,5: исходы (3) и (4) выносят `НЕ ДЕФЕКТ` на сцену при непромеренной половине потерянного

**Что не так.** §8(3)–(4): при покрытии ≥ 0,5 — `НЕ ДЕФЕКТ` по картинке на сцене; §8(5) — «не определено» только при < 0,5.
При покрытии 0,6 непромеренные 40 % `lost_bytes` молча входят в `НЕ ДЕФЕКТ`. Байтовое покрытие к тому же определяет мип 0
(самый крупный), а мипы, пересекающие W (`tint_part_mips`), — типичная форма `hoover_beach` (запись с базы, короче образа) —
не крашены вовсе.

**Сценарий отказа.** `hoover_beach`: W — первые 60 % мипа 0; потеряны 40 % мипа 0 и мипы 1…n; крашены мипы 1…n — покрытие 0,55;
пурпура нет (дальние мипы не видны вблизи), остаток мипа 0 — тот, что на экране, — не промерен ⇒ (3) `НЕ ДЕФЕКТ` на сцене.

**Что изменить.** Исходы (3)/(4) — «`НЕ ДЕФЕКТ` по картинке для окрашенной доли (печатается в байтах и в эпизодах, по классу
RC2)»; неокрашенная доля — «не определено» при любом покрытии; порог 0,5 — только условие, при котором исход вообще читается.

### RC9 — объёмные образы: байтовая граница мипа неточна, проверка «мип ∩ W» и `tint_bad` по ней не годятся

**Что не так.** §4.2 и `w_mipal`/`w_inmip` берут диапазон мипа `[mip_layout[l].offset, +size)`. Для объёмных образов код сам
говорит, что линейный размах мипа не доказывает, где лежат его срезы (`textureCache.cpp:3245–3250`, синхронизация — только
целиком).

**Сценарий отказа.** Объёмный образ (вокселы, 3D-LUT), W внутри среза мипа 0, который по `mip_layout` числится как мип 1 ⇒
мип 0 крашен поверх верного W; `tint_bad` проверяет тем же неверным отображением и молчит.

**Что изменить.** Объёмные — `tint_skip` (отдельным полем `tint_skip_vol`) и вне `w_mipal`/`w_inmip` (в `w_other`); стенд кода —
случай массива (`layers ≥ 2`), доказывающий, что диапазон `mip_layout[l]` покрывает все слои уровня.

### RC10 — тексты контролей: И5 — контроль проводки, не истинности; `T188:` при `=0` — изменение пути `=0`

**Что не так.** (а) §3.5 подаёт И5 (`part = inv_part_src`) как «независимое место того же счёта». Оба счёта — в одном цикле
`InvalidateMemoryFromGPU` (`textureCache.cpp:3416–3418`) с тем же предикатом: И5 доказывает проводку, а не верность предиката.
(б) §3.1: строка `T188: mode=0 fix=0` печатается при `=0` — путь `=0` уже не «MS2 байт в байт по коду», а «MS2 + одна строка».

**Сценарий отказа.** (а) Обе реализации используют `SourceRange()` вместо покрытия по мипам или обе ошиблись одинаково — И5
сходится, лид читает это как подтверждение. (б) Ревью кода «путь `=0` = MS2 по коду» (член §3.5) проваливается на строке лога,
которую требует сам проект, — спор в ревью вместо данных.

**Что изменить.** (а) В тексте: И5 — контроль проводки; истинность предиката — только стенд (§3.5) и ГП-тест §7(1). (б) Член
ревью: «путь `=0` = MS2 по коду, кроме одной строки `T188:` раз на процесс».

### RC11 — цена формы A: считать по несинхронизированным событиям и с разрывами прохода

**Что не так.** §5.2 цена = событие × S. `SynchronizeBufferFromImage` качает весь образ (`copy_size` до `info.data.size`,
`:3245–3261`), `ObtainBuffer(SourceRange)` может создать или слить буфер размера образа; события с уже синхронизированным
буфером (RC3) качают зря; разрыв прохода — [U] без счётчика.

**Сценарий отказа.** `img_bytes / part` даёт 2 МиБ ⇒ пересчёт «0,1 мс, G5 проходит» ⇒ код формы A; в M3 Δ > +1,0 % из-за
разрывов прохода 4,8 на кадр и слияния буферов — G5 проваливается, итерация потрачена.

**Что изменить.** Поля звена измерения: `img_bytes_unsync` (события без `part_synced`), `in_pass` (событие при открытом проходе —
состояние планировщика, место называет Emu Engineer); пересчёт цены до кода — по ним; форма A пропускает синхронизацию при
`sseq == wseq` (RC3) — удешевление, член §7.
