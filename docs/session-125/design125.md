### 2.2 Обязанности на разрез

На разрезе контекст второго сегмента не может получить состояние из собственного исполнения: предшествующие записи
регистров в это время исполняет другой контекст (иначе это не W = 2). Значит **хотя бы одна строка, записанная чужим
потоком, должна быть прочитана им на разрезе** — сигнал готовности плана с указателем на снимок, номер сегмента и курсор.
Это член **A1** (§1).

**Единая формулировка для A2, A5, (c) `[RC4]`: нижняя сторона > 0 не доказана ⇒ по п. 55(д)(1) в LB_acc не входит.**
Ни у одного из них не доказано и «= 0»:

- **A2 — применение снимка.** Копия ≈ 6,8 КБ в `CommandProcessor` контекста либо перенос владения буфером снимка; во
  втором случае контекст читает строки снимка, записанные чужим ядром, во время сегмента, и часть этих чтений холодная.
  > 0 не доказано, = 0 не доказано.
- **A5 — проверка плана против поздних записей.** Обходчик читает слова класса (b) (`COND_EXEC`, предикация, 14-словное
  ветвление, содержимое IB, косвенные таблицы) при ОТПРАВКЕ, раньше исполнения; «страница чиста на GPU в момент плана»
  (`IsGpuClean`, с. 118 §2) на обходчике не гарантирует того же в момент исполнения. Форма и цена проверки и отката при
  неопределённом плане не доказаны ни в какую сторону [U] (на GuestGpu `spine_unc` = 0 из 25 904 планов,
  `local-session-118.md:33`; на обходчике частота [U]).
- **(c) — отложенный выпуск побочных эффектов** (метки EOP, `WRITE_DATA`, `DumpConstRam`, окклюзия, флип) в порядке
  потока — обязанность маршрута A при любом месте спины; > 0 для переноса спины не доказано.

**A6 — ожидание готовности плана на разрезе — член LB_acc по п. 57(г)** `[RC1(а)]`. Посылка ред. 1 «нижняя сторона 0:
обходчик идёт впереди» ложна: `dawalklead=1` — удержание, задание графики ждёт, пока `DrawAheadProcessing() + lead ≥
walk_id` (`graphicsRun.cpp:2382–2395`), то есть обходчик не дальше одной подачи впереди GuestGpu; `da_wjobs` —
число обходов, об опережении не говорит; разрез K4 выбирается по целому кадру. Нижняя граница A6 строится в §3 для
устройства с ЛЮБЫМ удержанием.

**Все устройства `[RC4]`:** LB_acc — нижняя граница по множеству ВСЕХ устройств приёма, включая некорректные (без

## 3. A6⁻ — нижняя граница ожидания плана на разрезе `[п. 57(г), RC1(в)]`

### 3.1 Определение и формула

Для кадра N: **T0** — начало обработки кадра N на GuestGpu (начало первого среза первой подачи кадра после флипа N−1);
**c** — подача, содержащая элемент разреза K4 кадра N; **T_sub(x)** — момент, когда гость отправил подачу x (вызов
`GuestGpu::Enqueue`, `graphicsRun.cpp:661`, на потоке гостя). Модель G₂(A-walker) (печать `g2_119`, `g2_119.py` §5,
спина снята с GuestGpu):

  M = S_ctx + F·P + T4 = cpu_net − G₂,  P = cpu_net − S_ctx,  F = 0,555.

Второй сегмент кадра в модели идёт параллельно первому и обязан кончиться не позже T0 + M. Его работа — не меньше
параллельной доли меньшей половины W₂⁻ = (1 − F)·P (серийная часть и налог T4 ему не приписываются — это занижает W₂,
то есть A6, безопасно для нижней границы). Второй сегмент не может начаться раньше момента готовности плана на разрезе
t₂ = T0 + D + ω, где D = T_sub(c) − T0, ω ≥ 0 — остаток обхода после отправки (нижняя сторона 0). Тогда

  **A6⁻ = mean_N max(0, D′⁻_N − (M − W₂⁻))**   [мкс/кадр опоры],

где D′⁻_N — доказанная нижняя сторона D в расписании МОДЕЛИ (не сегодняшнем) для кадра N (§3.2). Среднее — по строкам
окна популяции (§3.4). Каждый кадр кончается не раньше t₂ + W₂⁻, поэтому задержка против модели на кадр ≥ max(0, …), и
среднее по кадрам — нижняя граница средней задержки.

### 3.2 Нижняя сторона: только то, чего не обойдёт никакое устройство

- **Л1 (любое правило разреза):** обходчик не обходит подачу раньше, чем гость её отправил, ⇒ t₂ ≥ T_sub(c). Годно для
  любого устройства и любого удержания.
- **Л2 (разрез ровно K4):** K4 режет у начала прохода, ближайшего к середине кадра ПО ЧИСЛУ ЭЛЕМЕНТОВ
  (`designA4_part2.md` §3); середина требует общего числа элементов, то есть отправки последней подачи кадра с
  элементами, ⇒ t₂ ≥ T_sub(last). Устройство, предсказывающее разрез (например, по прошлому кадру), даёт тот же f₂
  только на кадрах, где предсказанный проход совпал с K4; доказательства «тот же f₂» нет [U]. Л2 сильнее Л1 и
  используется в A6⁻ **только строкой ROADMAP** (вопрос В4, §8); без неё A6⁻ строится по Л1.
- **Л3 (эндогенность расписания — «лучшее устройство»):** сегодняшнее D измерено в сегодняшнем расписании, где гость
  шагает по GuestGpu (прожиг с. 122: наклон 0,90 на опоре). Устройство A-walker укорачивает кадр GuestGpu, и отправки
  гостя сдвигаются. Нижняя сторона D′ в расписании модели доказывается только через точку освобождения гостя: пусть
  t_rel — последний возврат потока гостя, отправляющего c, из блокирующего ожидания события, производимого GPU (метка
  EOP, флип), до T_sub(c), и между t_rel и T_sub(c) других ожиданий GPU нет; Γ = T_sub(c) − t_rel — собственное время
  гостя, устройством не сокращается. (а) Если t_rel ≥ T0 (событие кадра N), то D′ ≥ Γ. (б) Если t_rel < T0 (событие
  более раннего кадра), промежуток T0 − t_rel в модели не длиннее сегодняшнего (модель сжимает обработку, а не
  растягивает) ⇒ D′ = Γ − (T0′ − t_rel′) ≥ Γ − (T0 − t_rel) = D_today. (б) держится для событий, чьё время задаёт
  обработка GuestGpu (метка EOP); для события флипа (показ по вблэнку, хост-GPU) сжатие промежутка не доказано [U] —
  тогда годна только (а)-форма D′ ≥ Γ − (T0 − t_rel). Без t_rel нижняя сторона D′ не доказана: при освобождении внутри
  кадра N по событию, которое модель наступит раньше, D′ < D_today.

## 4. Находка против самой модели G₂ (п. 57(г)) — ряд [I], вердикт не меняет

Модель G₂ (`g2_119.py` §5: G = cpu_net − [S_ctx + F·(cpu_net − S_ctx)] − spine − T4) сжимает обработку кадра, полагая,
что оба сегмента разреза можно исполнять одновременно с T0. Это требует, чтобы подача c была отправлена гостем (и
обойдена) к моменту, когда второй контекст должен начать, — **во всех вариантах маршрута A**, а не только в A-walker: при
спине на GuestGpu (центральный G = 2 216,5) второму сегменту нужен ещё и план спины до c. Допущение нигде не измерено:
сегодняшнее расписание (GuestGpu не простаивает, гость впереди на ≈ 2,2 подачи, §3.7) его не подтверждает и не
опровергает, а для разреза «точно K4» (Л2) нужна отправка всего кадра. Если данные §3.8 покажут D′⁻ > M − W₂⁻, это бьёт
G₂ любого варианта — решается на закрытии (п. 57(г)); вердикт LB_acc эта строка не меняет.

## 7. Риски и что проект НЕ доказывает

- **Условие 1 не проверено для A2, A5, A6, (c) и налога обходчика** `[RC2]`: ред. 1 утверждала, что никакая нижняя граница

  минимального устройства (п. 57(а), (в)).
- **A6 — названный кандидат убийства условия 1, не покрытый LB_acc** `[RC1(б)]`: порядок величины [I] — от 0 (Л1 при
  сегодняшнем опережении гостя, §3.7) до миллисекунд (Л2 — ожидание отправки всего кадра; удержание как сегодня — до
  ≈ 0,555 · 11 528 ≈ 6 400 мкс, отзыв RC1).
- **Налог нагруженного обходчика на GuestGpu** `[RC6]`: при A-walker план спины (≈ 959–1 268 мкс) переезжает на поток
  обходчика, который кормит M1 и делит `PipelineCache::m_mutex` с GuestGpu (с. 106–107: ≈ 420 мкс/кадр стены GuestGpu от
  этой конкуренции); рост `da_late`/`da_miss` и конкуренции ложится на GuestGpu. Вне LB_acc и вне G₂ (T4 мерился при
  сегодняшней нагрузке обходчика); направление — против A-walker; не оценён [U].
- **Что A-walker корректен:** A5 — открытый риск корректности (решения класса (b) при отправке могут устареть к
  исполнению). LB_acc о существовании корректного устройства ничего не говорит (§2.2).
- **Условие 2** (налог пишущего контекста ≤ 1 645 мкс) не трогается.
- **Что модель W = 2 с одним разрезом — единственная**; LB_acc считается в модели G₂ = 3 484,7.
- Режим OLD и другие сцены не рассматриваются (п. 55(д)(4)).
