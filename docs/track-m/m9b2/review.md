## 2. Новые RC (только к новому тексту)

### RC12 — строка лида п. 782(в)(1): место записи образа вне `Image::Upload` есть — `DetileToImage` (умолчание вкл.)

**Что не так.** §5.3 и строка лида ставят `t188_rb_wr` в `Image::Upload`, `MarkGpuModified` и очистке. Перезаливка
`TextureCache::UploadImage` при гейте `imgfuse` (`gates.cpp:148`, умолчание `true`) идёт ветвью `m_tiler.DetileToImage`
(`textureCache.cpp:1531–1535`): вычислительный проход пишет образ сам, `Image::Upload` не зовётся (`:1545–1550`, комментарий «No
scratch, no copy»). Ветвь берёт 2D тайловые несжатые образы с `eStorage` без глубины и MSAA — основной класс цветовых текстур.
Остальные записи образа покрыты [c `git grep` `copyBufferToImage|copyImage|resolveImage|clearColorImage|clearDepthStencilImage`]:
`Image::CopyImage`/`CopyImageWithBuffer`/`CopyMip` (вызовы `textureCache.cpp:868`, `:874`, `:903`) → `MarkGpuModified` `:884`, `:911`;
`Image::Resolve` (`renderDraw.cpp:5593`) — после `MarkGpuWritten` `:5589`; копия глубины `depthRenderTarget.cpp:492` — после
`MarkGpuWritten` `:463`; `descriptors.cpp:3700` — затем `MarkGpuWritten`; очистка глубины `renderDraw.cpp:2404` — глубина вне окраски
(`tint_skip_fmt`). Вызовов `UploadImage` два: `:1648` (`CompletePendingUpload`) и `:1863` (`InitializeImage`).

**Сценарий отказа.** Образ окрашен на S3 (эпизод закрыт). Через кадр гость ЦП переписывает его память (потоковая подгрузка) ⇒
`IsCpuDirty` ⇒ `RefreshImage` → `InitializeImage` → `UploadImage` → `DetileToImage`; эпизода нет, флаг не ставится (S3 в §4.3
работает только «эпизод открыт ⇒ …»); rb1 читает не пурпур ⇒ `tint_rb1_bad` ≥ 1 — инвариант (§7(1)) ⇒ стоп серии под замком и
ложная правка звена кода; при том же коде под `imgfuse=0` инвариант молчал бы.

**Что изменить.** Флаг `t188_rb_wr` ставится в теле `TextureCache::UploadImage` (покрывает обе ветви и оба вызова) независимо от
эпизода, плюс `Image::Upload` (копии `:830`, `:836`), `MarkGpuModified`, `ClearImage`; в §5.3 — этот список с пометкой [c] и
строкой «других записей образа нет по `git grep` на базе бинаря» (член записки кода). Член стенда — перезаливка окрашенного образа
без эпизода в обеих ветвях (`imgfuse` 0/1) ⇒ `tint_rb1_over`, не `_bad`.

### RC13 — штамп `Sw` и флаг `rb_wr` обязаны стоять до проверки перехода в `MarkGpuModified`; гонка проверки с `Ss`

**Что не так.** (а) `Image::MarkGpuModified` (`image.h:153–170`) делает работу только на переходе `!m_gpu_modified → true`. После
полной синхронизации образ остаётся `IsGpuModified` (RC3) — следующие записи ГП перехода не дают. Проект пишет «в
`MarkGpuModified()` при `mode ≥ 1`: если `sseq == wseq` … — `fetch_add`», не говоря, до или внутри ветви перехода (рядом в коде —
`GpuDirtyGen::Bump()` в ветви, `SkcStampW3` — «первым оператором», `:155–158`). Стенд §4.7 зовёт `DiagT188::Note…` на синтетике и
настоящий `Image::MarkGpuModified` не исполняет — m7 этого размещения не ловит. (б) `Sw` — «проверка, затем RMW» без `m_lock`
(места `renderDraw.cpp:1750`, `:3820`), `Ss` — `sseq := wseq` под `m_lock`: если `Sw` на другом потоке проверит `sseq` (старое) до
записи `Ss`, а `Ss` прочтёт `wseq` до RMW (которого не будет), запись после синхронизации штампа не получит.

**Сценарий отказа.** (а) Цель отрисована (`wseq` 1), полная синхронизация (`sseq` 1), цель отрисована снова (`m_gpu_modified` уже
`true` ⇒ ветвь не исполняется ⇒ `wseq` 1), частичная DMA-запись ⇒ `sseq == wseq` ⇒ `part_synced`, эпизод не открыт, хотя в буфере
— старая отрисовка; перезаливка теряет вторую отрисовку, `lost_bytes` её не видит, окраски нет ⇒ смещение к «нет следствия», И2
сходится. (б) То же через гонку — реже, тем же знаком.

**Что изменить.** (а) Текст §4.2/§4.3 `Sw`: «первым оператором `MarkGpuModified`, до проверки перехода» — и для `wseq`, и для
`t188_rb_wr`; мутант m13 «`Sw` внутри ветви перехода» и член стенда на настоящем объекте `Image`: синхронизация → два
`MarkGpuModified` → `wseq ≠ sseq`. (б) Член записки кода: потоки мест без `m_lock` против `Ss`; если не один поток — безусловный
`fetch_add` в `Sw` (цена [I], один RMW на вызов) или повторная проверка в `Ss`.

### RC14 — T109: счёт `DB_RENDER_OVERRIDE` по месту входа обработчика теряет запись диапазоном

**Что не так.** §8.2: «счёт записей в обоих обработчиках (прямой — через `g_hw_ctx_func[Pm4::DB_RENDER_OVERRIDE]`,
`pm4Dispatch.cpp:16`; косвенный — `pm4Handlers.cpp:3130`)». Прямой путь выбирает обработчик по **первому** регистру пакета
(`pm4Handlers.cpp:2482`); `HwCtxSetDepthMetadataRegisters` (`:406–414`) стоит и на `DB_COUNT_CONTROL` (`pm4Dispatch.cpp:15`, 0x1)
и сам перебирает `cmd_offset + i`. Пакет с 0x1 на ≥ 3 значения пишет `DB_RENDER_OVERRIDE` (0x3, `pm4.h:116`, `:134`) через запись
`:15`, не `:16`. Все пути (прямой и косвенные `:651`, `:762`, `:883`, `:932`, `:2103`, `:2496`) сходятся в одной ветви
`HwCtxSetDepthMetadataRegister`, `cmd_offset == Pm4::DB_RENDER_OVERRIDE` (`:329–336`) [c].

**Сценарий отказа.** Emu Engineer ставит счёт по букве §8.2 — в обработчик пакета при `cmd_offset == DB_RENDER_OVERRIDE` и в
лямбду `:3130`; игра пишет блок 0x1–0x4 одним пакетом с битом 16 = 1 ⇒ `ovr_vpc` = 0 ⇒ §8.4(2) не срабатывает, (3)/(4) читаются
атрибутируемыми по draw — ложно.

**Что изменить.** Одно место — ветвь `DB_RENDER_OVERRIDE` в `HwCtxSetDepthMetadataRegister`; член стенда — запись диапазоном
0x1–0x4 считается 1 раз, одиночная прямая и косвенная — по 1. Начальное значение регистра [I] — как в проекте.

### RC15 — T109 §8.4(4): `НЕ ДЕФЕКТ` без положительного контроля предикатов `zx_narrow`, `bias_d32`

**Что не так.** (4) выносит `НЕ ДЕФЕКТ` при `zx_narrow = 0` и `bias_d32 = 0` на всех тегах. Положительный контроль есть только у
знаменателя (`d32`) и `zx_d32`; ноль предикатов не отличает «не достигнуто» от «предикат неверен». И9 нули не ловит.

**Сценарий отказа.** Счёт `zx_narrow` берёт `vp.viewports[i]` гостя (`zscale`, `zoffset`) вместо вычисленных `minDepth`/`maxDepth`
(`renderDraw.cpp:445–447`, ветвь `dx_clip_space`) или стоит до цикла вьюпортов ⇒ всегда 0 ⇒ (4) `НЕ ДЕФЕКТ` для формы
`be4c35a2` на трёх сценах — ложно.

**Что изменить.** Предложение правила M9c2: (4) — только при живом контроле предикатов: функциональный стенд T109 (синтетические
вьюпорты `maxDepth < 1` / `minDepth > 0`, экспорт Z, смещение; мутанты «вьюпорт гостя вместо вычисленного», «только вьюпорт 0»)
или совпадение с ненулевыми `t109_*` M5c на той же сцене; иначе (4) — «не определено».

### RC16 — RC2(г): исход «лист `=2` отличается от M6c без пурпура» не определён

**Что не так.** RC2(г) требовал читать `=2` класса парой листов. В §7 отличие листа `=2` только запрещает (3)(а); исходом (2) оно не
служит (нужен детектор ≥ 3 кадров), прямо «не определено» тоже не названо — попадает в (7) молча.

**Сценарий отказа.** Основная доля `lost_bytes` — карта нормалей RG8: при `=2` освещение участка меняется (лист отличается), пурпура
нет; `=3(c)` — лист отличается (К-П жив). Потерянные уровни класса доходят до экрана, но (2) не наступает ⇒ «не определено» ⇒
`ТУПИК` вместо `дефект` K4 и этапа 2 — пропуск дефекта (знак ошибки — консервативный, но итог T188 неверен).

**Что изменить.** Одно из двух, решение лида в M9c2 до заданий: (а) исход (2b) — отличие листа `=2` без детектора ⇒ тег `=2` с
`KYTY_DIAG_T188_CLS=<c>` (ручка ограничивает и `=2`, §4.1) на той же сцене; отличие листа `=2(c)` / M6c ⇒ «поверхность потерянных
уровней класса `c` доходит до экрана [c листа]» ⇒ `дефект` K4, этап 2; бюджет тегов §9 — с этим плечом; (б) строка (7): «отличие
листа `=2` без детектора — не определено (ни (2), ни (3)), число таких сцен и классов печатается».
