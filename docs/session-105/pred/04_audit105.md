## Findings (all MINOR) and what is done with each

1. **`ctx_midsub` = 0 was never tested against a known positive.** The counter is reachable (`OpScope` sets
   `t_op` on the executing thread; mid-op `Wait`→`Submit` reads it), and the pre-existing submit-site table
   explains the zero: no `stream-wrap`, `sanitizer-slot`, `download*` row at all in any session-105 log, and
   `host-read`/`unmap` rows keep their own names. Blind spot: the part before the render mutex
   (`PopPendingOperationsLazy`) is not counted. → FACTS says "credible, no positive control"; a positive
   control is owed before Stage 5 publishes mid-operation submits by site (next-session plan).
2. **`check105.py` summed the µs group of `ctx-mid:` rows, not the count.** Moot here (0 rows in every log),
   wrong in general. → recorded; next scorer reads the `/count` group.
3. **The checks have little power beyond tick equality.** `owner`/`current` sub-checks cannot fail; "the
   stamp equals the tick this buffer signals" rests on `fetch_add` returning the old value and is not
   checked independently. → owed: assert `tick == m_command.m_tick` at the three `NextTick` sites under
   `ctxtick >= 2` (M3.2).
4. **`ctx_rec_block` covers seven APIs**, not `WaitPriorityOperations`, `CommandRecorder::Drain`,
   `WaitAsyncCopies`, `queue_mutex`. Today the record thread reaches only a non-blocking `Refresh`. → owed
   in M3.2 before any record-thread work moves.
5. **Cost at `ctxtick=1` not measured on its own** (out-of-line `OwnerTick`, knob loads, +16 B per buffer);
   bounded only by the A/A point 62.6 µs. → stated as such.
6. **`FrameTrace-submit` row renaming at `ctxtick >= 2`** would drop renamed `host-read` rows from exact-name
   scorers (`shift91.py`) and uses site-table slots (`MaxSites` 160). Default unaffected. → env-list note.

   `build_tests.cmd`) and exercises the `ctxtick=0` expression. → recorded as debt.
