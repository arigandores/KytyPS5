## 1. Главный сценарий отказа RC11 — не наступает

RC11 F32b: тест берёт готовую специализацию и не доходит до места выбора вида ⇒ 0 при обоих значениях ⇒ ложный
`НЕ ДЕФЕКТ`. Проверено тремя способами.

1. **Путь теста — специализация по T# [c кода].** `CompileF22IndirectTable` строит программу формы `CompileF19IndirectTable`
   и зовёт `RecompileForTest`: `TranslateProgram` → `ExtractResourcePlan` → `MaterializeResources(user_data, …)` по T#/S#
   из `user_data` и кучи → `CompileProgram`. Кандидаты таблицы появляются только материализацией (копии образа корня
   `ee9632be:RM:1158` `images.push_back(program.info.images[source.indirect_root]);`, цикл кандидатов `ee9632be:RM:492`).
   Доказательство не только чтением: мутант m3 (цикл кандидатов теряет последнего) роняет тест на материализации
   (`indirect image specialization has no typed candidate`, rc 321), m3b (теряет кандидата только у таблиц ≥ 3 членов) —
   собственным `Check` годности теста на M4, M5. Готовая специализация на эти правки не реагировала бы.
2. **Тест реагирует на правило при `=1` — мера M не тавтология.** Три мутанта кода (m1b, m4, m5) дают M ≥ 1 при `=1`;
   значит `M = 0` немутированного кода — свойство кода, а не слепота теста (таблица §3).
3. **Контроли К1, К2 живы при `=0` своими запусками** — K1 = 1, K2 = 1 (свой бинарь, §2), и К2 умирает от m2 (зеркало
   «всегда глубина») — контроль зависит от вида члена, а не только от пути счётчика.

## 5. Замечания без RC

- **Н1 (читать так — F35c и переоткрытие).** При провале годности `Check` с `KYTY_TESTS_CONTINUE=1` пишет строку
  `ShaderCfgTests: failed:`, а процесс возвращает **rc 0** и **печатает строку `[f22] total`** (m3b: при `=1`
  `K1=0 K2=0 M=0` при 4 строках `failed`). Сценарий отказа: читатель, берущий только строку `total` (или только rc), на
  невалидной материализации прочтёт `M = 0` ⇒ ложный `НЕ ДЕФЕКТ`. Сейчас не наступает: F35a §2 и мои запуски — 0 строк
  `failed`. Член чтения п. 685(д)(1): «0 строк `ShaderCfgTests: failed:` в логе фильтра при обоих значениях» — вместе с
  числами `total`; так же — любой повтор теста на будущем бинаре.
- **Н2 (эквивалентный мутант m1a).** Правило пустого T# при `=1` в формах с цветовым кандидатом тестом не наблюдается:
  цветовой кандидат ручной (`RM:45`), О1 (`RM:733`) делает таблицу ручной целиком, пустой корень ручной и без правила
  пустого T#. Для вопроса п. 685(б) это не слепота: вопрос — есть ли `Dref` при цветовом кандидате, и ответ от правила
  пустого T# не зависит. Форма, где m1a виден ({пустой, `k32Float`} — без цветового кандидата), меры не имеет (цветового
  вида при `Dref` нет: пустой член — `null_D32`). Добавлять её не требуется.
- **Н3 (сборка не воспроизводима по sha).** Один и тот же источник `399d3271` дал `434f7e07…` (base) и `d77f51d1…` (final)
  при одинаковом выводе; sha F35a `541cb290…` тоже своей сборкой не повторяется. Опознание бинаря теста — по выводу и
  коммиту, не по sha.
- **Н4 (зеркало не покрывает ветви вне форм §0).** Непустой T# с полем формата 0 зеркало сочтёт пустым (код привязки — нет);
  хвост `skip_tail_mip_storage` и класс Uint/Sint пустого T# не зеркалятся. Ни одна из этих ветвей не встречается в
  формах M1–M5, К1 и на меру не влияет (storage — не выборка; Uint/Sint пустого — тоже цветовой вид).
- **Н5 (довод по коду шире форм §0, не тестом).** При `=1` `OpImageSampleDref*` по цветовому виду члена таблицы по коду
  невозможна в любой форме таблицы: опкод — по `manual_depth_compare` корня (`EM:683`, `EM:766`, ветви `OpSwitch` тем же
  `EmitSample`), кандидаты — копии корня (`RM:1158`), О1 сводит ручное сравнение по «или» членов (`RM:729`–`RM:733`),
  проход общего сэмплера (`RM:1206`–`RM:1222`) только ставит `manual` и не снимает; при `Dref` все члены не ручные ⇒ пустой
  член — `null_D32`, непустой — только формат политики ⇒ вид глубины. Это [c кода], а не тест: формы F35a §5 (общий
  сэмплер с прямым образом, неявный LOD, пустой кандидат при непустом корне) тестом не проверены.
