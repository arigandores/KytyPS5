## 4. Находки

**MINOR-1 (текст, п. 107(г)).** Путь отката `armcopy=0` получил новые чтения: `ArmCopyInlineEntry(t_ai_batch.size())` на входе
каждого `UploadCopies` (`bufferCache.cpp:1213`: размер TLS-вектора и TLS `t_ac_op.ai_pending`, сравнение, невзятая ветка
`Fatal`) и `if (!t_ai_batch.empty())` после цикла (`:1265`) — при любом `armcopy`, включая 0. Ред. 2 `design130.md` называет эти
проверки отличием только «при `acinline=0`» (§10.2), а п. 107(г) — «путь отката … без единого нового чтения». Поведение пути 0 не
меняется (обе ветки при 0 недостижимы: пакет наполняет только `CopyGuestToStagingArmed`, которого при 0 нет). **Сценарий отказа:**
печать `ai130`, аудит или отчёт цитирует п. 107(г) как факт кода — утверждение ложно по букве. **Что сделать:** лиду — строкой
ROADMAP назвать эти два чтения исключением из п. 107(г) (правка кода не нужна; перенос проверки за `arm_copy != 0` сам был бы
новым чтением).

**MINOR-2 (чтение, п. 118(б)(3)).** `ac_cbm_stale` при 2 ≡ 0 по построению — тот же довод, что N1 п. 108(б) для `ac_jstale`:
`AcStampTake` читает биты в той же хватке `region.lock`, где `TakePendingRun` их снял (`pageManager.cpp:1488–1494`), значит
`St` ∩ `Pa` пуст всегда, а невзятое применение проявилось бы циклом `AcApplyRuns`, не числом. `ac_cbm_left` при 2 ≡ 0 по
инварианту §3.6 п. 3. **Сценарий отказа:** `CBAD_LOSS`-сумма R2 + R3 + R4 при 2 читается как три независимых стража, хотя
живой из них по данным — только R2 (R3 — страж инварианта кода, R4 — не срабатывает ни на каком коде этого дерева); «0» по R4
цитируется как свидетельство отсутствия класса «взял, но не применил». **Что сделать:** лиду — в чтении шага 6 и в печати
назвать R4 при 2 «страж не сработал по построению» (как п. 108(б)(1)), зависание при 2/3 — видимый провал этого класса
(п. 108(б)(3)).

**MINOR-3 (допуск разборщика шага 6, Т4).** Согласованное чтение И0 перечитывает только группу `ac_cbad … ac_cmp_pages`
ПОЗЖЕ основного цикла; `ai_cbad` и `ai_cmp_pages` (и прочие `ai_*`) остаются из основного цикла (`videoOut.cpp:1294–1296`),
а писатель добавляет их ПОСЛЕ `AcCbad` (`bufferCache.cpp:383–387`). Событие inline-класса, попавшее между основным чтением строки
k и перечитыванием группы, входит в `ac_cbad`/`ac_cmp_pages` строки k и в `ai_cbad`/`ai_cmp_pages` строки k + 1. **Сценарий
отказа:** разборщик шага 6 проверяет Т4 `ai_cbad` ≤ `ac_cbad` и `ai_cmp_pages` ≤ `ac_cmp_pages` точно на строке или на сумме блока
10–88 п. 55(б) — на строке/блоке, чей край пришёлся на такое событие, получается `ai` > `ac` на 1–64 страницы без дефекта ⇒
ложный «дефект шага 4». На накопительных значениях конца лога неравенство точное. **Что сделать:** Harness Engineer (шаг 6) —
для этих двух пар Т4 проверять на Σ по всему логу точно, а построчно/поблочно — с допуском «разность ≤ Δ`ac_cmp_pages`
соседней строки» или только рядом; фикстура на такой перенос. Код не менять.

**Замечания (не находки, ряды):** (1) при 2/3/4 классификация (хватка `apply` + ≤ 64 `VirtualQuery`) стоит в `Work` ДО
`Complete(job.sequence)` (`parallelCopy.cpp:374–377`) ⇒ отметка завершения пула, а с ней подача GPU и `WaitAsyncCopies`

(2) строка `CONTENT … why=nosnap` пишет `host=-` (не `host=0x-`) — разборщик шага 6 обязан принять `-` во всех полях S_a/S_k.
