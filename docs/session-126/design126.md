### 1.2 Доказательство «нет»

R_K3⁺ — время `pl_em_rt` на множестве S_K3 (draw, где с прошлого draw не было записи регистров-зависимостей и прочих
источников §3). Сверху его даёт только время на доказуемом НАДМНОЖЕСТВЕ S_K3. В `cen120` время известно для двух множеств:
всех draw (1 359,7) и would-hit S_A (1 001,2); время промахов по причинам не разделено (только счёты). S_K3 ⊄ S_A:
(а) промах `memo` — прошлый draw не записал память (например, взял медленный путь `Find*`), а регистры с тех пор не
писались; (б) промах `pass` — между draw проход закрыт диспатчем/копией без записи CB/DB; (в) промах `dsmp` — глубина
сэмплируется. Такие draw лежат в S_K3 (или могут лежать), но не в S_A. Значит, наименьшее надмножество с известным
временем — все draw: **≤ 1 359,7 ≥ 500**. `obs116` даёт то же: ≤ 1 599,9 ≥ 500. Остальные логи фазу не разбивают.
Вывод: без нового счётчика R_K3⁺ < 500 недоказуемо; (ж)(3) шаги 3–7 не отменяет.

### 1.3 Попутная находка: прочтение «по значению» предрешено в NEW

S_A (would-hit A) ⊆ S_V (draw, у которого байты ключей memo резолюции всех целей равны прошлому draw) — доказательство
§7.3. Значит, для любого механизма, пропускающего захват при РАВНЫХ значениях входов, время фазы на снимаемом множестве
≥ `pl_em_rt_hit` ≈ **1 001,2 мкс/кадр** (перепись, NEW, плечо P с инструментами R1/R2 — абсолют завышен неизвестно
насколько [c], но даже половина ≥ 500). В прочтении «по значению» тест убийства K3 исход «< 500» в NEW иметь не может;
K7 (`spcen` A) и есть этот механизм с платной проверкой (N_A 340,2 / верх 686,9). Поэтому проект определяет K3 «по
записи» (§2) — как п. 61(е) («доля draw без записи CB/DB-регистров с прошлого draw») и ретроспектива (`retro` §3.1:
«не удешевить проверку, а не делать её при отсутствии записи»). Вопрос В1.

## 2. Что меряется и каким числом

### 2.1 Механизм, который ограничивается сверху

**K3 (гипотетический):** для draw d на контексте регистров C (объект `HW::Context` процессора, `buffer.GetRegisters()`)
захват `AcquireRenderTargets` не вызывается и берётся `RenderState` прошлого draw на C, если с захвата прошлого draw на C
не было ЗАПИСИ ни одного регистра из множества зависимостей D_K3 (§3.1) любым путём и не сработал ни один нерегистровый
источник §3.2. Гранулярность — регистр (запись того же значения — запись). Цена проверки механизма не вычитается ((ж)(1)).

### 2.2 Число

R_K3⁺ (мкс/кадр опоры) = ⟨ Σ_{d ∈ S_R, d в кадре} `pl_em_rt`(d) ⟩_окно / 1000 + 2·SE — где S_R ⊇ S_K3 строится
переписью (§4) так, что каждое исключение из «всех draw» доказано необходимым (таблица §5):

- S_R = R0 ∪ WI; R0 — draw без действительной записи для своего контекста (входят целиком); WI — draw с записью, у
  которых поколение записи D_census не сдвинулось (W) И идентичность целей равна записи (E1, §3.4).
- `pl_em_rt`(d) — спан цепочки `pathlap` от отметки `pl_em_vtx` до отметки `pl_em_rt` (сегодня: `DrawStatTail`,
  конструктор `SpDrawScope`, `AcquireRenderTargets`, проверка `G3ApplyAttach`, `lap.Mark`) — шире, чем снимет пропуск.
- ⟨·⟩_окно — среднее строк `FrameTrace-x` плеча переписи, кадры 10–88 блока п. 55(б), блоки по строкам `GateArm:`;
  SE — по средним блоков (статистика уровня — среднее строк; медиана средних блоков печатается рядом, MINOR-3 п. 62(б)).
- «+2·SE» — выборочная сторона вверх (вопрос В4: константа (ж)(2) говорит «R_K3⁺ < 500», проект предлагает считать
  R_K3⁺ уже с +2SE, как CLOSED с. 120 п. 4).

Рядом (не число чтения): R_W⁺ (S = R0 ∪ W, без E1), R_V⁺ (S = R0 ∪ V, «по значению», для K7), R_res⁺ (время резолюции
целей на S_R, вопрос В2), доли `rk3_w/rk3_n`, `rk3_wi/rk3_n`, `rk3_v/rk3_n`.

### 3.3 Довод полноты

(1) Поля D_census — приватные члены `HW::Context` (`hardwareContext.h`, секция `private:` после `:1130`; `friend` в файле

присваивание и конструкторы. Записи в обход (memcpy в объект) поиском не найдены (`reinterpret_cast<HW::Context`, `memcpy(&m_ctx`
— 0 мест; Emu Engineer повторяет поиск в шаге 3). (2) Присваивание в ЖИВОЙ контекст процессора — одно место
(`graphicsRun.cpp:393`); `sp.m_ctx = m_ctx` (`:1662`) пишет теневой процессор спины, который не рисует; `m_saved_ctx = m_ctx`

отличаются от записи; обязан быть 0 для утверждения «список полон» (§4.3). **Для верхней стороны полнота НЕ нужна:**
пропущенный путь записи оставляет draw в W — множество растёт, R растёт (§5 Н4).

### 3.4 Исключение E1 (единственное нерегистровое исключение)

Draw из W исключается, если его `color_count`, наличие глубины, или у любой цели `image_id`, `target_slot`,
`desc.view_info` отличаются от записи прошлого draw этого контекста. Довод: вид вложения в `RenderState`
(`attachment.image_view`, `renderDraw.cpp:1355`, `:1484`) — функция пары (образ, `view_info`) (`AcquireTargetView` →
`FindRenderTarget`/`FindDepthTarget` или вид из записи `rtfast` того же образа); другой образ или другой вид ⇒ другой
`RenderState` ⇒ повтор прошлого результата неверен ⇒ ни один корректный механизм такой draw не пропустит. Если Red Team
доказательство не примет — число чтения строится на S = R0 ∪ W (R_W⁺, печатается всегда).

## 4. Ручка `rk3cen` (`KYTY_RK3_CENSUS`)

### 4.1 Значения, чтение, защёлка

- `{"KYTY_RK3_CENSUS", "rk3cen", 0, 2}` — ПОСЛЕДНЯЯ строка `KNOB_DEFINITIONS` и последний `Knob` перед `Count`;
  `check_gate_order.py` после патча и ДО сборки. В `gates_base.txt` имени нет — плечи называют его явно, **заменой на
  месте** (дописанное после имени базы игнорируется).
- **0** — ничего (см. §4.6). **1** — перепись (§4.2–4.3). **2** — перепись + разбиение `pl_em_rt` внутри захвата (§4.4;
  только дым, в число чтения не входит).
- Читается **на каждый draw** на входе `RenderExecutor::DrawIndex`/`DrawAuto` (до `PrepareDrawRenderState`,
  `renderDraw.cpp:3655`, `:3825`) и защёлкивается в TLS `t_rk3` на этот draw — может быть плечом расписания. Вооружается,
  только если: поток — GuestGpu, `FrameStats::Enabled()`, `PathLap` вооружён (`pathlap=1`, иначе `rk3_nt`), `spcen`,
  `slicecen`, `bindfloor`, `m4baton`, `skipceil` — 0 (иначе строка `Rk3Census: refused reason=<имя>` раз и 0).
- Переход защёлки 1 → 0 (или отказ) **обнуляет все записи**; первая вооружённая после этого draw каждого контекста — R0.
  Крючки сеттеров проверяют ту же TLS-защёлку: запись между последним draw при 0 и первым при 1 не видна, поэтому такой
  draw и не может иметь записи.

### 4.3 Классификация в посте (С6)

Запись на контекст (TLS-таблица ≤ 8 контекстов по адресу `HW::Context`, выделяется при первом вооружённом draw; переполнение —
`rk3_ovf`, draw ⇒ R0): `gen`, `color_count`, `has_depth`, по каждой цели `image_id` (индекс + поколение), `target_slot`,
`view_info`; байты V_D (поля D_census: `HW::RenderTarget` разрешённых слотов, их полубайт маски; при глубине — `z`, `rc`,
`dc`, `sc`, `sm`, две очистки) и V_key (V_D + границы глубины + `memo_extra` каждого цветного слота, §7.3).

Порядок (первое сработавшее): **R0** — записи нет / контекст новый / переполнение; **XW** — `gen` сдвинулся; **W** — не
сдвинулся; внутри W: **XID** — E1 нарушено; **WI** — иначе. Отдельно (не разбиение): **V** — V_key равен записи;
**VW** = V ∧ XW; **WMISS** = W ∧ (V_D ≠ записи). Затем запись обновляется текущим draw. `gen` читается и ДО захвата
(в С4) — сдвиг за время захвата — `rk3_acqw` (обязан 0: захват регистров не пишет).

### 4.4 Разбиение `pl_em_rt` (значение 2; вопрос задания (4))

`rk3_sp_view_ns` — вызовы `AcquireTargetView` (свидетели `rtfast` + медленный `Find*`); `rk3_sp_tr_ns` — вызовы
`image.Transit` в захвате; `rk3_sp_dm_ns` — HTILE-очистка и поиск петли обратной связи глубины (`:1375–1421`);
`rk3_sp_n` — draw; остаток = `rk3_rt_ns − Σ`. Таймеры внутри спана раздувают его (≈ 2·7 меток × 25 нс на draw [I]),
поэтому значение 2 — только дым, в печать и чтение не идёт; доли, не абсолюты. «Начало прохода» в `pl_em_rt` не лежит
(§3.2, конец) — строки для него нет. Уже измеренное разбиение того же спана: would-hit A 228 нс/draw против промаха
573 нс/draw (`cen120`, §1.1).

### 4.6 Тождества (для скорера) и контроли

- **Т1** `rk3_n = rk3_rec0 + rk3_xw + rk3_w` — на каждой строке точно (один сайт). **Т2** `rk3_w = rk3_wi + rk3_xid`.
- **Т3** `rk3_rt_rec0_ns ≤ rk3_rt_r_ns ≤ rk3_rt_w_ns ≤ rk3_rt_ns`; `rk3_rt_rec0_ns ≤ rk3_rt_v_ns ≤ rk3_rt_ns`;
  `rk3_res_r_ns ≤ rk3_res_ns`; `rk3_wmiss ≤ rk3_w`; `rk3_vw ≤ rk3_xw`; `rk3_r_* ≤ rk3_*`.
- **Т4** плечо переписи: `rk3_rt_ns = pl_em_rt_ns` (точно, одно и то же потраченное); `rk3_n = pl_em_n` с допуском ±8
  на окно блока (п. 6 с. 120: флип читает счётчики по одному).
- **Нулевой контроль:** в строках плеча `rk3cen=0` каждый `rk3_*` и `pl_em_rk3_ns` = 0 (защёлка 0 ⇒ ни крючков, ни поста).
- **Положительный контроль:** в каждом окне блока переписи `rk3_n > 0`, `rk3_wr_set + rk3_wr_obj > 0`, `rk3_xw > 0`
  (классификатор видит записи); `rk3_wmiss = 0` на всех строках — крючки видят ВСЕ изменения значений полей D_census
  между draw популяции (без этого — строка печати «полнота не подтверждена», чтение не блокируется, §5 Н4).
- **Стражи 0:** `rk3_nt`, `rk3_xthr`, `rk3_acqw` на каждой строке; `Rk3Census: refused` в плече переписи — провал допуска.

### 4.7 Цена и почему поведение не меняется

**Ни при каком значении эмуляция не меняется:** перепись только читает поля контекста, `colors[]/depth` и
`rt_fast_no`; пишет только свою TLS-таблицу и счётчики; не зовёт `GetImage`/`TouchImage`/`Find*`, не берёт замков, не
выделяет память на горячем пути (таблица — лениво при первом вооружении); ветвления эмуляции от ручки не зависят;
`MarkSpent` — та же отметка с возвратом потраченного. Правок в `src/graphics/shader/**` нет — подпись кэша трансляции не
меняется (Emu Engineer подтверждает: в дыме 0 новых трансляций, `pipelines.bin` принят).

**Цена [I], меряется в дыме (шаг 5), в вердикт не входит:** при 1 — пост 60–150 нс/draw (сравнение ≤ 9 целей и ≤ ~1 КиБ
байт) ≈ 0,3–0,75 мс/кадр в `pl_em_rk3_ns`, С4 ≈ 40 нс/draw ≈ 0,2 мс, крючки ≈ 3 нс × число записей D (число [U], печатается
`rk3_wr_*`), плюс `pathlap`/`mutsite` (≈ 0,1 мс, с. 69) — итого ≈ 0,6–1,5 мс/кадр; ни одна из этих работ не лежит в спане
С5 (§5 Н10). При 0 — на draw одно чтение ручки и TLS-запись, на сеттер D одна TLS-проверка; отдельно не измеряется
(плечо базы — ручка 0 на измерительной сборке, не `d3a981a2`).

## 7. Правило чтения

### 7.1 Дословно (ж)(2)

«R_K3⁺ < 500 мкс (порог трека, с. 121 п. 8–9) — **K3 ЗАКРЫТ**; K7 (`spcen` A) закрывается тем же числом, только если
проект докажет, что снимаемое K7 входит в множество, покрытое R_K3⁺, иначе K7 остаётся припаркованным; R_K3⁺ ≥ 500 — K3
не закрыт, но перепись трек не открывает: следующий шаг (прототип с самопроверкой по образцу `progmemocheck` + ABBA +
видео, либо ручка дозы) — решение закрытия с. 126; направление не доказано верхним — **НЕ РАЗРЕШЕНО**. R_K3⁺ — не
выигрыш, не цена построенной вещи и не прогноз.»

Строки печати: `K3_CLOSED` / `K3_NOT_CLOSED` / `NOT_RESOLVED` (последнее — провал любого стража §8 или непринятое Н3/Н3′/E1
без запасного R_W⁺); FAIL допуска — `NOT_ADMITTED`.

### 7.2 K7: включение для R_K3⁺ «по записи» не доказуемо

Контрпример: would-hit A, перед которым гость переписал `CB_COLOR0_INFO` тем же значением. Ключ memo резолюции совпал
побайтно (`colorRenderTarget.cpp:134`) — A считает draw попаданием; поколение сдвинулось — draw не в W и не в S_R. Значит,
S_A ⊄ S_R, и по (ж)(2) **K7 остаётся припаркованным при любом R_K3⁺** (размер разрыва печатается: `rk3_vw`).

### 7.3 K7 через R_V⁺ (другое число — вопрос В3)

S_A ⊆ R0 ∪ V. Доказательство: would-hit A требует для каждой цели равных `memo_slot` и `memo_version` с прошлым draw
(`renderDraw.cpp:998`); попадание memo сравнивает ключ ПОБАЙТНО (`colorRenderTarget.cpp:134`: `regs` и `extra`;
`depthRenderTarget.cpp:299`: весь ключ), а версия не растёт, пока запись memo не переписана (`:150`, `:170`, `:314`,
`:332`); значит, байты ключей всех разрешённых целей у двух draw равны = V_key (§4.3). Отсюда снимаемое K7 ≤ `pl_em_rt`(S_A)
≤ R_V⁺. Если лид примет (В3): «R_V⁺ < 500 ⇒ K7 ЗАКРЫТ». Ожидание по `cen120` — R_V⁺ ≥ 1 001 [c], то есть K7 и так остаётся
припаркованным; прогноза нет.

## 9. Риски и что проект НЕ доказывает

- Не доказывает выигрыш, цену построенной вещи, прогноз скорости; 60 FPS не обещаются.
- R_K3⁺ — граница для механизма «по записи с гранулярностью регистра»; механизм по значению — K7 (§1.3, §7).
- Н3/Н3′ держатся на таблице цитат шага 3 и ревью шага 4; ошибка в сторону «лишний регистр в D_census» занижает R.
- T13 вне числа, если лид не примет В2 — тогда «K3 ЗАКРЫТ» относится только к фазе `pl_em_rt`.
- Одна сцена (Sky Garden), один прогон; другие сцены не покрыты; режим OLD против NEW — только своими блоками.
- `rk3_wmiss = 0` — эмпирика популяции, не доказательство для всей игры; довод §3.3 — по коду.
- Цена переписи на GuestGpu (≈ 0,6–1,5 мс [I]) меняет расписание плеча C; число R от этого только растёт (Н11).
