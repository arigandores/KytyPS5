## 3. Класс входа D_b ((б)(1), (б)(4))

**Цепочка (F47a §4.2):** история пикселя точки на цели показа → последний писатель W₁ → его вход по координате точки → … до **D_b** — события, после
которого значение в точке даёт блок в цели показа. Класс входа D_b в точке определяется по программе D_b (свой разбор, §4):

| шаг | вопрос | ответ ⇒ класс |
|---|---|---|
| 1 | цвет точки на выходе D_b — литерал программы D_b (вход выборки не участвует или умножен на 0) | **C-imm** (§4) |
| 2 | цвет — из буфера констант / вершинного цвета (выборка не участвует) | **C-buf** (член §5, форма (б)(2)) |
| 3 | цвет — выборка ресурса X, и X — цель цвета / глубины или хранилище хоть в одном событии этого снимка | **R**: идём к последнему писателю X до D_b внутри снимка; писателя до D_b нет — **R-за-снимок, «не определено»** (RC1(а)) |
| 4 | цвет — выборка X, и X ни в одном событии снимка не цель и не хранилище (образ только выборки) | **T** (член §5) |
| 5 | X по шагу 3 без писателя до D_b, **и** ни один снимок сетки тега (12 снимков `f47_rd` и снимки `f47_rd2`, если был) не пишет X | **N-кандидат**; `дефект` (в)(4) только при (i) ≠ (ii) формы (б)(2) — §5; без (i) — «не определено» (вопрос В1) |

**Тождество ресурса между снимками одного тега** (шаг 5): ресурсы Vulkan в `f47_rd` без имён — имена с адресом гостя (`Kyty.<роль>.Image[guest=…]`,
`ea6c6e9e:src/graphics/host_gpu/renderer/cache/textureCache.cpp:199`) ставятся только под `--graphics-debug-dump`
(`ea6c6e9e:src/graphics/host_gpu/vulkanCommon.h:36`), а этот флаг меняет путь кода (F17a §4 — снимает быстрый путь разрешения и повтор `rtskip`),
в форму (г)(1) он не входит. Тождество X в снимках одного процесса — по идентификатору ресурса RenderDoc и параметрам создания (экстент, формат,
мипы, слои). **Член-контроль тождества:** цель показа гостя (буфер, который показ копирует) в ≥ 2 снимках тега имеет тот же идентификатор и те же
параметры; не так — тождество «не определено», N-кандидат не выдаётся (точка «не определено»). Что идентификатор RenderDoc одного объекта
постоянен между снимками одного процесса — [I], контроль это и проверяет.

**Чтение формы (на проверку F47b2, не правило):** Ч1 — события загрузки образа самим эмулятором (копия буфер → образ, вычислительный проход
детайлера, программа которого не из `eboot.bin` и не из корпуса T1) — не «писатель-продукт ГП»: образ, который пишет только загрузка, — T, а
содержимое ресурса после загрузки — величина (ii) §5. Ч2 — событие заливки цели (clear) — писатель шага 3; значение заливки — константа команды
гостя; читается по форме (б)(2) как C-buf (значение у гостя против значения, отданного ГП) — без дампа «не определено». Без Ч1 образ, загруженный в
этом же кадре детайлером, по букве шага 3 ушёл бы в R-за-снимок.

## 4. Член C-imm ((б)(4)) — без нового кода

2. **Слово программы из файла игры:** в `eboot.bin` (sha256 `3b5100797fe83663…`, F23a §2.3) — AMDGPU ELF, чей `.shader_text` даёт XXH3-64 = H
   (метод извлечения F11a / F23a; калибровка F23a 331 из 331). Свой разбор слов (`gcn_f23a.py`: длины по кодировкам RDNA2) находит
   инструкции, дающие экспорт цвета MRT0: литерал (32-битное слово за инструкцией) или встроенная константа (целые 128–208, плавающие 240–248) и
   цепочку `s_mov` / `v_mov` / упаковки до `exp`. Значение V_g по каналам — своим декодированием.
3. **Значение в снимке:** цвет, который D_b записал в точке (история пикселя, «после шейдера»), в формате цели D_b — V_s; константа SPIR-V модуля,
   питающая выход, — V_c (справка).
4. **«Равно»:** V_g, приведённое к формату цели D_b (UNORM8 — округление к ближайшему, float16 — точно), = V_s во всех точках блока **и** экспорт
   цвета зависит только от литералов (свой разбор потока данных: ни одна загрузка, выборка или чтение константы не входит в значение). Иначе —
   класс по шагам 2–4 §3.
5. **Положительный контроль поиска ((б)(3)) для C-imm:** программа события того же снимка с известным классом T — значок HUD (П2) или любая другая
   PS снимка — находится в `eboot.bin` тем же поиском (тот же контейнер — `eboot.bin`, тот же формат — `.shader_text` AMDGPU ELF); не нашлась —
   поиск «не определено», C-imm не читается.
6. «Точные 0 / 1» — строка справки, не член (RC4).

## 6. «Не равно» и положительный контроль поиска ((б)(3))

«Не равно» (⇒ `дефект` по (в)(4)) — **только**: файл и смещение названы по чтению игры в этот адрес ((iii) §5), байты отличаются от (i) или (ii)
своим разбором; для C-imm — слово программы из `eboot.bin` найдено (§4 п. 2) и V_g ≠ V_s. «Не найдено в файлах», «чтение < 64 КиБ без строки»,
«адрес не назван» — «не определено». **Положительный контроль поиска** — образ того же контейнера и формата, что вход блока: для T — другой образ
того же снимка, у которого есть строка `StreamRead` того же файла-контейнера (`.gnfp` с заголовком `GNF `, F47a §4.3) и того же формата T#, — поиск
обязан назвать его смещение; для C-imm — §4 п. 5. Контроль мёртв — «не равно» не выдаётся (точка «не определено»).

## 11. Вопросы лиду (решения не принимаются этим изданием)

- **В1 — N без дампа.** По (б)(1) N ⇒ `дефект` только при (i) ≠ (ii); (i) без ручки дампа не измеряется (б)(2) ⇒ N-кандидат — «не определено» ⇒
  по букве (в)(6) `ТУПИК`, тогда как T и C-buf в том же положении идут в (в)(5) (звено кода дампа). N-кандидат (ни один снимок сетки не пишет
  ресурс) — самый прямой след формы Б42. Вопрос: N-кандидат — (в)(5) или (в)(6)? Рекомендация исполнителя — (в)(5).
- **В2 — `_PipelineCache` существует.** Каталог есть, эмулятор на старте читает из него блоб драйвера (строка `Vulkan pipeline cache: loaded …
  from _PipelineCache\PPSA21564.bin` в `fs13_v`), файл обновлён 2026-10-09; (б)(12) — «каталога `_PipelineCache` нет». Издание включает его в
  манифест и возврат по принципу «по существующим каталогам». Вопрос: подтвердить.
- **В3 — П1 по цвету при C-imm.** Одна программа даёт два цвета одного элемента только выбором литерала по константе (класс по §3 — C-imm с
  выбором; оба литерала проверяемы в `.shader_text`) или через C-buf / T (тогда класс П1 другой ⇒ П1 «не определено» по букве (б)(5)); при другой
  программе на кадре другого цвета П1 по букве тоже «не определено». П1 по второму состоянию той же чёрной серии (тот же цвет, другая форма) такой
  трудности не имеет (§7.2: 41 из 79 фаз дают два состояния в двух снимках). Вопрос: при C-imm засчитывать П1 по состоянию, а по цвету — только
  случай «тот же H, выбор литерала»?
