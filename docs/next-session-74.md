## 2. Работа сессии 74, по убыванию «приз / риск»

### 2.1 Применить `patch_clrwide.py` и оценить приз `clr_none` (один ABBA)

    PATCH_DRY=1 python C:/kyty/s74/patch_clrwide.py && python C:/kyty/s74/patch_clrwide.py
    python C:/kyty/s74/enter_scene.py clw74a --hold 300 \
      "KYTY_GATE_SCHEDULE=30+1800:clrwide=0|clrwide=1" KYTY_GATE_SCHEDULE_ABBA=1

**Доказательство вооружения не требует ни одного нового счётчика:** `clr_ok`/`clr_ok_kb` растут
ровно на принятую популяцию, `clr_none`/`clr_none_kb`/`clr_over` падают на неё же.
**Решать по `gpu_busy_us` и по `img_up`/`img_up_kb`** — вторая половина приза в том, что заливка,
пачкающая диапазон, заставляет **любой созданный там ПОСЛЕ образ** родиться buffer-modified и быть
загруженным (`textureCache.cpp:1986-1989`). **Приёмка обязана включать боковое сравнение одного и
того же индекса present с прогоном на умолчаниях**: устойчиво протухшая поверхность стабильна от
кадра к кадру, и однокадровый детектор глитчей её не увидит.
**Ворота:** отгружать, если Δ`gpu_busy_us` значима на собственных 2·SE прогона, `img_up_kb` не
растёт, приёмка чиста и боковое сравнение не показывает разницы.

### 2.2 Применить `patch_m4_range.py` и закрыть вопрос транспорта арифметикой (три базовых прогона)

Три счётчика, ноль изменений поведения, **без A/B**: по одному базовому прогону при `m4baton` = 64,
256 и 512. `rng_inpass / rng_total` — доля границ диапазона, которые пришлось бы закрывать и
переоткрывать проходом рендера (1,537 мкс GPU каждая); `cram_write` решает 87,8 % размера форка.
**Что убивает направление, названо до прогона:** `rng_inpass / rng_total` около 1,0 при любой L, при
которой склейка терпима — при L = 64 налог склейки уже ~0,62 мс на кадр, а уводить L в сотни — это
ровно там, где граница наверняка попадёт внутрь открытого прохода. Если оба налога не могут быть
малы при одной L, **операционной точки нет и форк отвечен отрицательно арифметикой до того, как
написана его первая строка**. Что продвигает: `rng_inpass / rng_total` заметно меньше 1 при
L = 256–512 и `cram_write` = 0 — тогда форк 6,8 КБ и остаётся ровно один вопрос: кто упорядочивает
два потока записи в одну отправку.

### 2.3 Чистая петля свидетеля — остаток ~0,8 мс, кандидата нет
