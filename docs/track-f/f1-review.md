## 2. Требуемые изменения

**RC1. Без сцены-свидетеля вариант A не начинать — сделать это условием, а не «предложением лиду».**
Что не так: по своим данным (п. 1, строки 4–5) путь, который игра исполняет, до этих шейдеров не доходит ни на одном из 12 логов;
по п. 228(б) (`85c049d8:docs/ROADMAP.md:12088`, якорь «Строка реестра — **дефект**, если сигнатура ведёт к видимому последствию», контроль +1 —
12089 «пути, который игра исполняет [c]; иначе — **наблюдение**»)
такая строка — **наблюдение**, а не дефект; проект называет K1 «скрытым», но правку на 400–800 строк [I] предлагает без свидетеля.
Сценарий отказа: правка встраивания пишется и проходит тесты; доказательный прогон (е)(3) даёт «0 строк» — но шейдер ни разу не
исполнен, т. е. правильность встраивания не проверена ни одним кадром; три итерации → «ТУПИК (нет стенда)» после всей работы.
Что изменить: в §4 «Данные, нужные до кода» — превратить в **условие начала** с порогом: свидетель = в каком-либо логе свипа F0
строка `ShaderRecompiler CS phase begin: stage=CS hash=0x<h>` для одного из 101 хэша или `--- Error ---` с `ShaderCFG.cpp:44` без
префикса `CsPretranslate`; при 0 свидетелей — вариант A не начинается, строка уходит лиду на решение «НЕ ДЕФЕКТ / ТУПИК / наблюдение»
по п. 228(д). Свип искать по **строке фазы dispatch**, не только по тексту ошибки: в логах сборок до появления `CsPretranslate` строка
Б26 сама могла быть строкой dispatch.

**RC2. Критерий (е)(3) проходится правкой, которая прячет маркер, — проект обязан назвать свой критерий.**
Что не так: вариант A п. 5 заменяет в предтрансляции `unsupported decoded instruction` на `deferred: needs dispatch user data`, п. 2 —
«dispatch пропускается с явной строкой лога». Критерий п. 228(е)(3) считает только «0 строк `unsupported decoded instruction` с этими
тремя опкодами».
Сценарий отказа: правка, где разрешение цели не срабатывает **ни в одном** месте (все 96 шейдеров уходят в «отказ без EXIT»), даёт
0 строк `unsupported` (их заменили `deferred`) и 0 маркеров смерти (dispatch пропущен) → (е)(3) пройден, Б26 «FIXED», а игра
вместо крэша молча теряет compute-работу (K4/картинка). Это ровно форма «спрятать строку».
Что изменить: проект называет до кода (для принятия лидом пунктом, п. 228(е)) три числа на прогоне: строк `deferred`, пропущенных
dispatch этих хэшей и **успешно встроенных** dispatch (новая строка лога на каждый первый успех хэша); FIXED по SWAPPC — только при
≥ 1 успешном встроенном dispatch на свидетеле и 0 пропущенных; «отказ без EXIT» (вариант B, A п. 2) — под ручкой и считается
K4-наблюдением, не исправлением.

**RC3. «Тел функций в `eboot.bin` нет [c]» — снизить до [I] и разобрать 9 блобов `s_setpc_b64 s[6:7]` и 473-й SWAPPC.**
Что не так: проверено только слово `s_setpc_b64 s[14:15]`; возврат через другой регистр (функция копирует адрес возврата) не ищется.
Своя проверка (п. 1, строка 7): 9 блобов кода в `eboot.bin` **кончаются** `s_setpc_b64 s[6:7]` + `s_code_end` + метка — это форма
тела функции (возврат по указателю) [c для формы, I для «функции»]; плюс 473-й `s_swappc_b64` в блобе `0xe301c54`, которого нет
среди 101 (вызов в цикле с `s_branch` назад).
Сценарий отказа: риск (б) «тело вне `eboot.bin`, может ещё не быть в памяти» и вывод «нужен инструмент K5 с 256 словами» строятся на
неверной посылке; если тела — эти 9 блобов, соглашение о вызове разбирается **офлайн без игры**, и проект можно оценить до свидетеля;
если не они — это надо показать. Шейдер `0xe301c54` показывает, что набор SWAPPC-шейдеров шире зарегистрированных в логах с. 142
(вариант A обязан разрешать цель внутри цикла).
Что изменить: XXH3 каждого из 10 блобов (от начала блоба до `s_code_end`) и поиск этих хэшей в 12 логах с. 142 (регистрировались ли,
переводились ли — `CsPretranslate: ready` значит, что CFG уже переваривает `s_setpc_b64 s[6:7]` в конце программы); дизассемблер
9 блобов: что лежит в `s[6:7]` на входе; поправить §2 и риски (б), (г).

**RC4. Число выполнимости — до кода: сколько шейдеров разрешаются ЦЕЛИКОМ.**
Что не так: шейдер переводится, только если разрешились **все** его места вызова; F1a даёт 339 из 472 мест с поздней записью
регистра-источника по линейному порядку [U] и не даёт числа по шейдерам.
Сценарий отказа: из 96 шейдеров целиком разрешаются, например, только 16 с одним вызовом; остальные 80 уходят в отказ — правка
на 400–800 строк чинит 1/6 строки, а без числа до кода лид принимает проект вслепую (линза «верхняя оценка врёт в 2–20 раз»).
Что изменить: офлайн (без игры) — анализ достигающих определений по CFG каждого из 96 декодированных шейдеров (SWAPPC — конец
блока; цикл — неподвижная точка); число шейдеров, у которых **каждая** цель вызова = начальный SGPR без переопределения на всех путях,
— [c] в проект. Без этого числа §4 п. 2 «не разрешилось — отказ» не оценён.

**RC5. Ручка обязана входить в подпись и каталог кэша трансляции; «=0 байт в байт» не верно для состояния кэша.**
Что не так: план ALU (§5) и вариант A п. 6 обещают «0 — прежнее поведение байт в байт». (а) Кэш трансляции ключуется подписью
`KytySC<ver>:<KYTY_SHADER_SOURCE_HASH>` + токены вариантов (`shaderTranslationCache.cpp:564–587`); `KYTY_SHADER_SOURCE_HASH` — SHA1 по
всем `*.cpp/*.h/*.inc` транслятора (`src/generate_version.cmake:43–56`) → **любая** правка `src/graphics/shader/**` меняет подпись,
и бинарь правки при `=0` идёт с холодным кэшем. (б) Путь dispatch читает кэш до трансляции (`pipelineCache.cpp:4474–4482`), а токен
`KYTY_FIX_B26` в подписи план не называет.
Сценарий отказа (б): A/B одной сборки — прогон `=1` пишет в `_ShaderCache/PPSA21564` перевод бывших отказных шейдеров; контроль `=0`
на той же подписи грузит его с диска → при `=0` исполняется **новая** трансляция, контроль (е)(5) печатает «профиль 96/1/4 вернулся»
(предтрансляция печатает строки), а поведение dispatch уже не прежнее. Сценарий (а): K3 удержания при `=0` сравнивается с базой
`v142`/`c142_02`/`c142_03` на тёплом кэше — холодный вход выглядит регрессией правки.
Что изменить: токен `:fixb26` в подписи **и** отдельный подкаталог при `KYTY_FIX_B26=1` по образцу вариантов с. 103
(`shaderTranslationCache.cpp:570–577`, комментарий «a variant run would otherwise overwrite the default cache»); в план — фраза
«`=0` воспроизводит прежний **вывод** транслятора; подпись кэша меняется правкой исходников, первые входы холодные — п. 228(в)
(копия и возврат кэшей)»; контроль `=0` — с отдельным или очищенным каталогом и с проверкой, что перевод отказных хэшей при `=0`
не загружен (0 строк фазы dispatch для них и 0 загрузок из кэша).

**RC6. Тесты ALU-опкодов не различают края, которые различает ISA.**
Что не так: единственный литерал теста `S_BREV_B64` `0x20468000` имеет бит 31 = 0 — расширение нулём и знаком дают одно и то же.
ISA 6.2.1 «Literal Expansion to 64 bits»: «64-bit unsigned integer: zero extended … 64-bit signed integer: sign extended»; формула
`S_BREV_B64` — `S0.u64` → нулём.
Сценарий отказа: реализация берёт 64-битный литерал через общий путь со знаковым расширением; тест F1a проходит; на литерале
`0x80000001` источник становится `0xFFFFFFFF_80000001`, и результат `lo = rev32(0xFFFFFFFF) = 0xFFFFFFFF` вместо `0` → неверный
дескриптор буфера без маркера.
Что изменить, `S_BREV_B64`: литерал с битом 31 — `s_brev_b64 s[10:11], 0x80000001` → источник `0x00000000_80000001`,
`s10 = rev32(0) = 0`, `s11 = rev32(0x80000001) = 0x80000001`; инлайн-константа `−1` (64-битное значение все единицы → результат все
единицы); регистр-источник с разными половинами; SCC не меняется (следующий `s_cbranch_scc*` видит прежний SCC).
`V_CMP_LE_U64`: равно / меньше / больше; решает старшая половина; при равной старшей решает младшая; `0xFFFF…FF` против 0
(беззнаковость); wave32 (пишется `VCC_LO`) и wave64; **неактивные по EXEC дорожки дают 0 в VCC** — обязательно, если путь
`LogicalNot(UGreaterThan64)`: побитовое НЕ уже собранной маски даёт 1 на неактивных дорожках; форма VOP3 с SGPR-назначением;
`src0` — SGPR-пара (как на месте `v_cmp_le_u64 vcc, s[0:1], v[1:2]`) и литерал (беззнаковое расширение нулём).

**RC7. План ALU не закрывает критерий (е)(3) и не предсказывает профиль после правки.**
Что не так: после ALU-правки 96 строк SWAPPC остаются → (е)(3) «0 строк с этими тремя опкодами» не проходится; CFG останавливается
на **первой** неподдержанной инструкции (`ShaderCFG.cpp:2082–2089`), поэтому «5 шейдеров пройдут первую точку отказа; дальше
неизвестно».
Сценарий отказа: ALU-правка коммитится, тесты `ALL OK`, а 5 шейдеров падают на следующей неподдержанной инструкции — профиль
96 / 0 / 0 + 5 новых строк других опкодов; итерация расходуется на то, что можно было узнать офлайн.
Что изменить: до кода — полный проход декодера эмулятора по 5 шейдерам (тест `shader_cfg_tests` или свой вызов `DecodeProgram`)
со списком **всех** `UNSUPPORTED`, а не первого; ожидаемый профиль после правки — числом. Вопрос лиду (решение — за ним): делить ли Б26
на Б26а (`S_SWAPPC_B64`, проект A) и Б26б (два ALU-опкода, без игры) со своими критериями — иначе ALU-часть не может стать `FIXED`.

**RC8. GETPC внутри встроенного тела.**
Что не так: GETPC в SPIR-V — shader-relative, база 0 (`spirvEmitterFlow.cpp:748–752`, «The runtime descriptor evaluator supplies the
mapped shader base for host-side planning»); проект говорит «нужен отдельный сегмент pc», но не говорит, какую базу получит
вычислитель дескрипторов для кода функции.
Сценарий отказа: функция делает `s_getpc_b64` + смещение + `s_load` своих констант, лежащих рядом с её кодом; при синтетическом
pc «за концом шейдера» вычислитель прибавит базу **шейдера** — чтение чужой памяти, неверные данные без маркера.
Что изменить: в п. 4 варианта A — правило: GETPC в теле функции даёт смещение относительно **её** базы, и вычислитель дескрипторов
получает базу функции (её гостевой адрес) для этого сегмента; тест: функция с GETPC-относительной загрузкой.

**RC9. Ключи предтрансляции и программ.**
Что не так: `pretranslation.Take(code, hash, info, user_data_count)` (`pipelineCache.cpp:3869–3870`) и кэш программ ключуются без
значений user data; вариант A п. 5 расширяет только «ключ программы и кэш трансляции».
Сценарий отказа: два dispatch одного шейдера с разными указателями функций — второй получает трансляцию со встроенной **первой**
функцией (из памяти программ или готовой предтрансляции) → неверная функция без маркера.
Что изменить: перечислить все места ключа (предтрансляция, `programs`/`lookup_key`, диск-кэш, `pipelines.bin`) и для каждого —
как входит адрес и хэш тела; тест: два указателя → две разные трансляции.

**RC10. Метки и границы утверждений.**
Что не так: §3.3 «в наблюдаемых сценах ни один из 101 шейдера не исполнялся [I]» — по 12 логам это [c] (строка фазы dispatch 0 и
`--- Error ---` 0, п. 1 строка 5), а на «сценах вне 12 логов» — [U]; §2 «473 слова» без объяснения разницы 473 − 472.
Сценарий отказа: лид при выборе F2 читает [I] как «не проверено» и заказывает лишний прогон; или читает «нигде не исполняются».
Что изменить: метки по п. 1; 473-е слово — по RC3.
