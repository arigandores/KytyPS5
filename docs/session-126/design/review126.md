## Требуемые изменения

**RC1 (MAJOR, сторона «низ»). D_census статичен: запись в регистр, от которого результат ЭТОГО draw не зависит,
исключает draw из S_R.** Проект ставит одно поколение на контекст и сдвигает его записью любого из Р1–Р7 (§4.2 С1).
Но зависимость результата от регистров условна:
- слот n ≥ 0 разрешается, только если `mask(n) ≠ 0 ∧ base(n) ≠ 0` (`renderDraw.cpp:2071–2072`,
  `colorRenderTarget.cpp:113–118`, `:185–199`); иначе результат — пустой слот при ЛЮБЫХ байтах `CB_COLORn_*`;
- глубина при `!depth_active && !stencil_active` (`depthRenderTarget.cpp:277–280`) даёт «нет глубины» ранним возвратом
  (`:344–347`) при любых `DB_Z_*`, базах, HTILE, виде, размере, очистках, `DB_STENCIL_CONTROL`/`STENCILREFMASK`.

**Сценарий отказа:** проход с одной целью (mask = 0x1, глубина выключена); между двумя draw гость перезаписывает
`CB_COLOR3_*` следующего прохода или `DB_Z_READ_BASE`/`DB_HTILE_DATA_BASE`. Результат захвата и резолюции обоих draw
побитно тот же, механизм по грязным битам с маской слота/активностью глубины их пропустил бы; проект кладёт второй
draw в XW и вычитает его `pl_em_rt` + резолюцию из R_K3⁺. (ж)(1) определяет S_K3 как draw, у которого «не изменилось
ничто, ОТ ЧЕГО ЗАВИСИТ результат» — такой draw в S_K3 лежит, исключение не доказано верхним. Доля [U].
**Что изменить:** поколения по группам — `G_mask` (`CB_TARGET_MASK`), `G_slot[n]` (`CB_COLORn_*`), `G_dact`
(решающие присутствие глубины: `DB_DEPTH_CONTROL`, `DB_RENDER_CONTROL`, `DB_STENCIL_INFO`), `G_depth` (прочие DB);
draw в XW, только если сдвинулась ОТНОСИМАЯ группа: `G_mask`, `G_dact` — всегда; `G_slot[n]` — если слот n дал цель
(есть в `colors[0..color_count)`) в текущем ИЛИ записанном draw; `G_depth` — если `depth.image_id ≠ 0` в текущем или
записанном draw. Относимость по выходам (а не по регистрам) держит сторону «верх»: цель без образа и глубина «включена,
но не привязана» считаются неотносимыми, и запись в них не исключает draw. Класс прежнего правила печатать рядом
(`rk3_xw_irr` — XW, у которых все сдвинутые группы неотносимы; R по старому правилу — справка). Чтение В1 «по записи,
запись тем же значением — запись» не меняется; меняется только то, какой регистр — зависимость этого draw.

**RC2 (MAJOR, сторона «низ»; вопрос лида п. 63(и)(5)). Довод Н10 неверен для T13: пост С6 прогревает входы следующей
резолюции.** Пост draw d читает байты V_D/V_key (поля `HW::RenderTarget` слотов, `z`, `rc`, `dc`, `sc`, `sm`, очистки,
границы) — ровно то, что резолюция draw d+1 копирует в ключи memo (`colorRenderTarget.cpp:126`,
`depthRenderTarget.cpp:285–293`). Без переписи последнее касание этих строк до резолюции d+1 — резолюция d; с переписью —
пост d, позже на весь хвост захвата. **Сценарий отказа:** в draw из W (между draw нет PM4-записей — именно S_R) строки
контекста глубины (захват их не перечитывает, `renderDraw.cpp:1359–1491` берёт разрешённое `depth`) дольше живут в
L1/L2, `rk3_res_r_ns` в плече C меньше, чем был бы без переписи, — T13 занижен ровно на читаемом множестве. Величина [I]
(единицы нс/draw × ≈ 5 000 draw), но (ж)(1) требует доказанного направления, а Н10 объявляет «точно».
**Что изменить (одно из, решение лида):** (а) значение 1 (плечо чтения) не читает входов резолюции вообще: классификация
— поколения (RC1) + E1 по `colors[]`/`depth` (выходы, их только что трогал сам захват) + своя TLS-таблица; V, V_key,
WMISS — отдельным значением (3), только в дыме (или третьим плечом, если лид хочет K7 из запечатанного прогона);
(б) оставить, но в дыме шага 5 — ABBA значений 1 и 3 (без чтения V_D/V_key), Δ⁺ = верх 2SE разности `rk3_res_r_ns`/draw
× число draw S_R прибавляется к R_K3⁺ отдельным членом с направлением «верх». Н10 переписать для резолюции.

**RC3 (MINOR по величине, сторона «низ» по правилу; вопрос лида п. 63(и)(4)). Время резолюции draw, не дошедших до С6,
теряется.** С4 меряется для каждого вооружённого draw, а добавляется в классы только в С6. Draw, вернувшиеся между
ними: `PrepareDrawRenderState` = false (`renderDraw.cpp:3655–3657`, `:3825–3827`: резолв-draw `ResolveColorTargets`,
«нет целей и нет PS» `:2086–2090`), возвраты `ExecutePreparedDraw` до `:2929` (сетка без примитивов `:2528`, пустые
диапазоны рестарта `:2550`, `BindFloorClearSkip` `:2633–2636`, диагностика `:2508`). Механизм, пропускающий резолюцию
при отсутствии записи, снимает её и у них (повтор «нет целей»). По с. 71 таких ≈ 20 draw/кадр — единицы мкс, но член
без направления. **Что изменить:** счётчики `rk3_res_x_ns`/`rk3_res_x_n` (С4 draw, не дошедших до С6) входят в число
чтения целиком; TLS `t_rk3_res_ns` обнуляется в С6 и на следующем С4 (иначе устаревшее значение).

**RC4 (MAJOR, протокол: запечатанный прогон получит NOT_ADMITTED). Т1 и Т4 «точно на каждой строке» недостижимы.**
`FrameStats::Read` суммирует шарды счётчик за счётчиком (`frameStats.cpp:220–221`), пока GuestGpu продолжает `Add`;
флип забирает `rk3_n` и `rk3_rec0` в разные мгновения — строка рвётся на draw (прецедент с. 116: перекос строки до ±60,
допуск 256 по сумме). **Сценарий отказа:** скорер с Т1/Т4 «точно» по строкам валит допуск на первой же рваной строке.
**Что изменить:** Т1–Т4 проверяются на суммах окна блока с объявленным допуском (для штук — ±k draw на край окна, для нс
— ±k × максимум спана С5 одного draw из той же строки, k записать), фикстуры на край допуска; нулевой контроль — только
на строках окна 10–88 п. 55(б) плеча B (строка на границе блока несёт хвост плеча C).

**RC5 (MAJOR для K7; вопрос лида п. 63(и)(1)). §7.3 (S_A ⊆ R0 ∪ V) верно только при построении V, точно следующем
за тем, что сравнивает A.** A сравнивает для каждой ПОЛУЧЕННОЙ цели (`colors[0..color_count)`, глубина при
`image_id ≠ 0`) пару (memo_slot, memo_version) (`renderDraw.cpp:991–1002`); попадание memo — побайтное равенство
построенного ключа (`colorRenderTarget.cpp:134`, `depthRenderTarget.cpp:299`). Разрывы:
(а) V_D по §4.3 берёт «`HW::RenderTarget` разрешённых слотов» — слот с маской и базой, не давший образа, A не сравнивает,
а V сравнивает; (б) если V сравнивает поля через `operator==` (с. 117), то поле-float с одинаковыми байтами NaN
(`DB_DEPTH_BOUNDS_MIN/MAX`, `DB_DEPTH_CLEAR` — сырые регистры) даёт «не равно» при попадании memo; (в) ключ глубины
строится присваиванием членов в обнулённую структуру (`depthRenderTarget.cpp:284–295`), а не memcpy контекста —
байтовое сравнение «полей контекста» может отличаться в паддинге вложенных структур; (г) база A — предыдущий draw
исполнителя, база V — предыдущий draw того же контекста; совпадают, пока рисует один графический процессор
(`m_gfx_cp`, `graphicsRun.h:119`). **Сценарий отказа:** would-hit A, у которого различается только слот без образа или
NaN-граница, не попадает в V → R_V⁺ меньше снимаемого K7 → «K7 ЗАКРЫТ» ложно.
**Что изменить:** V_key := последовательность ключей memo, построенных ТЕМ ЖЕ кодом, что в резолюции (общая функция
построения ключа цвета — `memo_regs` + `memo_extra`, глубины — `DepthTargetMemoKey`), только для целей, которые
сравнивает A, сравнение memcmp; страж для утверждения K7 — `rk3_xctx = 0` на всех строках окна. С этим §7.3 принимаю;
то, что R_V⁺ не содержит резолюции, верно (`SpRtCheck` стоит после резолюции, `renderDraw.cpp:2894–2902`, K7 её не
снимал). Если по RC2 лид выберет (а), R_V⁺ получается только из дыма/третьего плеча — это решение лида, не мой пункт.

**RC6 (MINOR, таблица §3.1).** В строке Р3 указан сеттер `SetDepthRenderTarget`, но нет его регистра: единственный
вызов — обработчик `DB_SHADING_RATE_ENCODING` (`pm4Handlers.cpp:607–616`, через косвенную таблицу), и поле
`shading_rate_encoding` читает резолюция (`depthRenderTarget.cpp:152–153`, `:363`). **Сценарий отказа:** по правилу Н3′
(«вызов по чужому регистру — не крючок») Emu Engineer снимет крючок → запись пропущена → `rk3_wmiss > 0` → печать
«полнота не подтверждена» при полном на деле списке. **Что изменить:** добавить `DB_SHADING_RATE_ENCODING` в Р3 с
цитатой (в группу `G_depth` по RC1).

**RC7 (MINOR, «фаза уже того, что снял бы пропуск» — сказать явно).** Повтор `RenderState` прошлого draw позволил бы
механизму снять ещё: сравнение `RenderState` в `BeginRenderingImpl` (`context.cpp:325`, спан `pl_em_rec`), часть ключа
пайплайна по целям (`GetGraphicsPipeline(color_info, depth_info, …)`, `renderDraw.cpp:2978–2981`, спан `pl_em_pipe`),
частичный повтор по слотам (перезахват только грязного слота). R_K3⁺ их не содержит. **Сценарий отказа:** «K3 ЗАКРЫТ»
прочитан как закрытие механизма, который снимает и это, — число занижено для него. **Что изменить:** в §9 и в печати
строка «R_K3⁺ ограничивает механизм, пропускающий резолюцию и захват целей draw целиком; сравнение прохода, ключ
пайплайна по целям и частичный повтор по слотам не покрыты (другие рычаги, K4)».

**RC8 (MINOR, «поведение не меняется»).** Запретить явно любые правки раскладки `HW::Context` (поколение — только вне
объекта, в TLS-таблице §4.3): байты `HW::RenderTarget` целиком входят в ключ memo (`colorRenderTarget.cpp:123–126`),
`HW::Context` сравнивается спайном и печатается `sizeof` (`graphicsRun.cpp:1615`). Проверено: `hardwareContext.h` не
входит в подпись кэша трансляции (`generate_version.cmake:45–47`, список `CMakeLists.txt:156`) — утверждение §4.7 о
подписи верно, пока меняется только этот заголовок и `renderDraw.cpp`. В дыме — строка `sizeof` та же.

**RC9 (MINOR).** Список отказов §4.1 не содержит `spine`: при `spine ≠ 0` теневой процессор на GuestGpu зовёт те же

**RC10 (MINOR).** §1.3 «предрешено ≥ 500» опирается на перепись в инструментированном плече P другой сборки (`15cdbfc6`)

## Проверено по коду (пункты, против которых RC нет)

- **Дешёвый путь (ж)(3) — «нет» верно.** Ни одно поле запечатанных логов не несёт признака записи CB/DB между draw;
  S_A не подмножество S_K3 (A слеп к записям) и не надмножество (промахи `memo`/`pass`), поэтому ни нижней, ни верхней
  границы на S_K3 кроме всей фазы (1 359,7 / 1 599,9 ≥ 500) нет. Шаги 3–7 не отменяются.
- **Полнота §3.3 (п. 63(и)(2)).** Поля `HW::Context` закрыты (`hardwareContext.h:1133`), все записи D — сеттеры
  (`:864–936`, `:1047–1084`) и `Reset` (`:862`); вне `pm4Handlers.cpp` сеттеры не зовутся (рендерер только читает через
  `GetRegisters()`); присваивания живому контексту — только `graphicsRun.cpp:393`; прочие — `m_saved_ctx` (`:388`, `:399`),
  тень спины (`:1662`, `:1885`); обход (memcpy/reinterpret) — 0 мест; `CommandBuffer` связан с живым `m_ctx`
  (`graphicsRun.cpp:408`, `commandScheduler.cpp:398`), графический процессор один (`graphicsRun.h:119`). `LOAD_CONTEXT_REG`
  в таблице нет, неизвестный опкод — `EXIT` (`graphicsRun.cpp:2897–2910`). Пропущенный путь записи всё равно даёт «верх».
- **Н3′ (п. 63(и)(3)).** Все вызовы сеттеров D в `pm4Handlers.cpp` (48 мест) стоят в обработчиках своих же регистров
  (прямая таблица `pm4Dispatch.cpp:14–35` и косвенная `pm4Handlers.cpp:2714–3600`, `_BASE_EXT` пишут тот же сеттер
  базы); единственное место «сеттер D из обработчика регистра не из таблицы Р» — RC6, и этот регистр — зависимость.
  Ложный сдвиг поколения по построению возможен только через RC1 (зависимость условна).
- **E1 (п. 63(и)(1)).** Принимаю: при другом `image_id`/`view_info`/`color_count`/наличии глубины вид вложения другой
  (`renderDraw.cpp:1307`, `:1355`, `:1373`, `:1484`), повтор старого `RenderState` ссылался бы на другой или уничтоженный
  вид — корректный механизм такой draw не пропустит; сравнивать значения ПОСЛЕ захвата (повторный поиск `:1273–1290`
  меняет `image_id`).
- **Т4 при ранних возвратах (п. 63(и)(4)).** Между счётом `pl_em_n` (`renderDraw.cpp:2752`) и С5 (`:2929`) возвратов нет;
  `MarkSpent` = та же отметка (`frameStats.h:2822–2828`), 0 — цепочка не идёт (`rk3_nt`). Равенство держится с поправкой
  RC4 (перекос строки), потерянная резолюция — RC3.
- **Цена в чужой фазе (п. 63(и)(5)).** Крючки — в разборе PM4 вне всех спанов draw; пост — в своём спане `pl_em_rk3`
  после С5; пара `NowNs` С4 — в фазе `mh_rt`, её вклад внутри спана С4 — «верх». Единственный путь «низ» — прогрев (RC2).
- Н1, Н2, Н5, Н7–Н9, Н11–Н14, +2·SE (В4), максимум по режимам BDA (В6), окно 10–88 п. 55(б), блоки по `GateArm:` —
  направления верны.
