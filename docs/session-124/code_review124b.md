## 2. BLOCKING

### R1. Уже связанный образ не закрывается логической очисткой при переходе `PendingDcc` → `Dcc`/`CMask` (посылка решения 30 ложна)

**Что не так.** Решение 30: «новая связь» — только если у образа до присваивания был другой вид или адрес метаданных. Его
основание в отчёте: «Если образ был связан в момент события, его уже закрыл `CloseCandidates`». Для заливки `PendingDcc`
это неверно:
- `G3MetaFill` при `pending` запоминает очистителя и выходит ДО `CloseCandidates` (`textureCache.cpp:5503–5505`);
- усыновление (`G3MetaAdopt`) недостижимо для уже связанного образа: `AdoptPendingDccForTexture` принимает только
  образы с `metadata.kind == None` (`:3302–3307`).

Запись `PendingDcc` по адресу уже связанного образа возникает так:
- `FreeImage` другого образа с тем же адресом метаданных стирает запись поверхности (`:451–462`, условие проверяет
  только освобождаемый образ; комментарий прямо допускает повторное использование адреса), либо её стирает
  `UnmapMemory` (`:3363–3369`);
- затем заливка `TrackDccFill` создаёт запись заново через `try_emplace(address)` с типом по умолчанию `PendingDcc`
  (`textureCache.h:165`, `textureCache.cpp:3191`).

Следующее связывание того же образа идёт через `PrepareDccClear` (`:1884–1891`) или `PrepareCmaskClear` (`:1976–1983`).
Функция переводит запись в `Dcc`/`CMask` с ненулевой маской и материализует очистку (под `LazyMat` — только Lt). Но
`skc3_link` = false, поэтому `G3MetaLate` не зовётся. Ни одного закрытия по L и b нет.

**Сценарий отказа («низ»).** Два живых образа I₁, I₂ одной поверхности с общим адресом DCC A: псевдонимы формата или
образ, пересозданный раньше освобождения старого. В помеченном кадре N:
1. D₁ рисует в I₂ (W1, `lw` = D₁).
2. GC освобождает I₁ — запись A стёрта.
3. Заливка очистки по A создаёт `PendingDcc` с маской `UINT32_MAX`; очиститель запомнен, I₂ не закрыт.
4. Связывание I₂ (цель или сэмплер) переводит запись в `Dcc` и очищает I₂ на хосте.

В N+1 I₂ читается как текстура до новых записей. Посев next находит `lw` = D₁, и D₁ помечается нужным, хотя его выход
стёрт очисткой. Это ровно класс B3, который п. 47(в) велел закрыть «в каждой точке, где образ связывается с поверхностью
с ненулевой маской очистки».

**Что изменить.** В `PrepareDccClear` и `PrepareCmaskClear` до перехода состояния запомнить
`skc3_pend = t_mode == 3 && !inserted && metadata.type == PendingDcc`. Условие поздней связи заменить на
`(skc3_link || skc3_pend) && metadata.clear_mask != 0`. Очиститель берётся из `clr[A]`, как сейчас. Если заливку
признали устаревшей (`PendingDccFillStale` сбрасывает маску), закрытия не будет само собой. Решение 30 дополнить строкой
в отчёте. `FindDepthTarget` правки не требует: смена типа из `PendingDcc` там уже засев (`:2468–2475`).
Альтернатива — только решением лида: принять как долг строкой §7 «уже связанный образ при `PendingDcc` — низ» и рядом-
счётчиком таких переходов. Без счётчика масштаб «низа» на дыме не виден.

## 3. Non-blocking

- **M1 (47(а), «или пропуск»).** Пропуск draw в `AsyncPipelines` (`renderDraw.cpp:2984–3001`) стоит ПОСЛЕ `G3ApplyAttach`
  (`:2917`) и `ApplyW2` (`:2885`). W1/W2 draw, который не исполнился, остаются в графе: писатель на ключах, которых он не
  писал, — «низ». Буквально п. 47(а) это не выполняет. Но `AsyncPipelines: skipped draw` в окне фатален (G2,
  `design124.md:733`), а `lw` на узле финализированного кадра отсекается (`ReadKey` → `Bad`, `:4099–4100`, значит
  финализация такие ключи обязана снимать). Поэтому на числа окна это не влияет. Лиду — одной строкой ROADMAP записать,
  что правило «или пропуск» держится стражем G2, а не кодом.
- **M2 (N1, полнота).** Два хука без `NoteOffThread3`: явное событие загрузки в `UploadImage` (`textureCache.cpp:1389–1392`,
  по `t_w3`) и `G3PrefSeed` (`bufferCache.cpp:2672`). Отчёт не доказывает, что оба живут только на GuestGpu. Если это не
  так, потеря будет тихой («низ» для загрузки). Для дыма: если `skc3_xthr` > 0, первым проверить
  `DownloadImageMemory` на гостевом потоке (синхронные выгрузки `DrainTrace … reason=cpu-write`). Это настоящая потеря,
  и счётчик поймал её правильно.
- **M3 (N4 → P2).** Чтение источника MSAA идёт через `ReadRange` (`renderDraw.cpp:3908` → `textureCache.cpp:4752–4754`)
  и в непомеченном кадре запускает P2. Это чтение не входит в популяцию x1 режима 2, а `skc_seen` этот путь не ставит.
  Поэтому P2 может сработать дважды на один образ за кадр (resolve, затем привязка). `x1c_n` растёт, `bad ≤ chk`
  держится. Тот же класс уже был у источника `DepthStencilCopy`. В §10 печати — строкой, если дым покажет долю.
- **M4 (решение 35, Lt).** На пути FCE весь `FindRenderTarget` идёт под `LazyMat`. Поэтому `:2348`/`:2422` пишут
  Lt-запись узла K на весь образ даже тогда, когда очистки нет (маска CMASK 0) — K становится `ltw` всех ключей образа.
  Это только эталонная политика Lt (знак там не определён); строка §7 для Lt.
- **M5 (HTILE, аспекты).** `LateLink`/`CloseImage` для HTILE закрывает `Whole` вместе с трафаретом (`:4831`), хотя
  материализация HTILE — только глубина (`renderDraw.cpp:1459`, `G3MatDepth` с аспектом 2). Лишнее закрытие трафарета —
  «верх». Тот же класс, что у `CloseCandidates` первого круга.
- **M6 (для дыма).** По перечню §1 `skc3_w3_nw` обязан читаться 0: все W3 разобраны. Ненулевое значение значит, что
  найден пропущенный сайт W3. Это «верх», но это сигнал проверить перечень, а не шум. Кроме того, после N3 `CopyBuffer`
  читает источник после `ObtainBuffer(…, is_texel = true)` (`bufferCache.cpp:1864`). У DMA из памяти образа источник
  закрыт синхронизацией, и ребра M → писатели образа нет. Это «верх», по п. 47(г) (перенос не делается). Раньше ребро шло
  на прежнего буферного писателя — ложное, «низ». Правка это улучшает. Строка §7 «DMA из памяти образа — верх» закрывает
  вопрос.
