## 2. П. 153(д)(2): может ли контроль 3 («без сбросов вовсе») быть «жив» ложно

Помимо `shovf`/`read` (закрыты п. 153(в) В5) — да, одним путём (RC2) и одним условием реализации (RC3). Другие проверенные кандидаты
ложной живости не дают [I]: записи прежних значений мертвы (защёлка при смене значения всегда двигает поколение, §2.2 проекта); ключ
сравнивается целиком (без коллизий хэша); вид в ключе (`П`/`Д`/`В` не смешиваются); вставка В — только при `!gpu`; `gen_moved` при 3 не
бывает (поколение стоит); расхождения от записей гостя, HLE, `BumpMapEpoch` при 3 — настоящие изменения байт гостя, которые сверка
обязана видеть (это и есть её живость).

## 3. П. 153(д)(3): довод живости слота кольца §11 (б) — по коду

Верно по коду: оборот сбрасывает до `m_generation++` (`streamBuffer.cpp:298–306`, при `Usage() == Stream`; `GetUtilityBuffer(Stream)` —
тот же `m_stream_buffer`, `bufferCache.h:91`, так что Д/В и П — одно кольцо); `Submit` сбрасывает первым оператором
(`commandScheduler.cpp:782`); тик двигается только в `Submit` (`:759–761`, `NextTick` `:866`). Слот A перезаписывается только после
оборота, и `Map` при `allow_wait=false` без ожидания возвращает `nullptr` ДО изменения состояния кольца (`:293–296`).

**Неверно как сформулировано:** «A и B записаны в ОДИН командный буфер одного тика ⇒ GPU прочтёт слот до его переписи». Проба B и запись
draw B — не одно событие. Между ними в той же операции `Map` более позднего слота может обернуть кольцо с ожиданием ТЕКУЩЕГО тика:
`WaitPendingOperations` → `Scheduler().Wait(tick == CurrentTick())` → `Submit` + ожидание GPU + `BeginNext` (`commandScheduler.cpp:446–454`),
затем `Reset(Ring)` (`streamBuffer.cpp:304`) — уже ПОСЛЕ того, как B взял смещение A. Санитайзер dispatch тоже может отправить буфер
между привязками и записью (`renderCompute.cpp:1057`). Следствие — RC4.

## 8. Требуемые изменения

**RC1 (MAJOR — путь без сброса при видимом трекеру событии).** Объявление записи CPU — `ChangeState<Cpu, true>`
(`regionManager.h:161–213`; вызовы `memoryTracker.h:156` `InvalidateRegion`, `:202` `InvalidateWriteFault`, `memoryTracker.cpp:225`
`MarkRegionAsCpuModified`, `:273` `UntrackMemory`) — двигает `m_cpu_epoch` и `m_epoch` (`:209–210`), но не `g_rb_gen`; в 37 местах его нет
(`design133.md` §5.3: «записи CPU гостя — не сбросы»). **Сценарий:** Д-копия A const-bank диапазона на CPU-ЧИСТЫХ страницах (условие Д
CPU-грязи не требует, `descriptors.cpp:248–253`) → поток гостя пишет в страницу → ошибка защиты → `InvalidateRegion`/`InvalidateWriteFault`
→ `ChangeState<Cpu, true>` (эпохи сдвинуты, поколение — нет) → проба B того же интервала попадает → при 1 draw B получает байты ДО
записи, путь 0 дал бы байты ПОСЛЕ. То же для П, если диапазон A лежит на нескольких страницах и грязна лишь часть
(`IsRegionCpuModified…` — «хоть одна страница», `bufferCache.cpp:1525`): запись в чистую страницу того же диапазона. При 2 это
`b2r_bad` > 0 ⇒ `B2R_INCORRECT` по п. 151(г)(1) — класс, который трекер ВИДИТ и который закрывается одной атомарной операцией, по
правилу п. 142(б) В9 («сомнение по пути, меняющему байты, — в пользу сброса») и прецеденту В6. **Изменить (решение лида, до кода):**
новая причина сброса — объявление записи CPU: в `ChangeState<Cpu, true>` рядом с `:209–210` (под замком региона, любой поток —
`fetch_add` атомика, как хуки `TryWriteBacking`) сдвиг `g_rb_gen` при `b2reuse` ∈ {1, 2} (при 0 — одна загрузка флага, при 3 — нет,
как В5/В6); свидетель — счётчик (имя — лидом, по образцу `b2r_rst_cpu`); фикстура «37 + N» получает это место. Запись в УЖЕ грязную
страницу трекеру не видна и остаётся классом (ж) — только сверка значения 2 (п. 151(г)(1)). Частота [I]: объявлений на кадр — порядок
загрузок, снимающих грязь (≈ 80/кадр [c `spk118`] при `faultkb` окнах), попаданий теряется ≤ ≈ 2 % [I]. **Если не внести:** каждое
объявление записи CPU в чистую страницу живого ключа внутри интервала — устаревшие байты при 1 и `B2R_INCORRECT` при 2 по классу,
который можно было исключить построением; отличить его от невидимой записи в грязную страницу по строке `MISMATCH` нельзя.

**RC2 (MINOR — ложная живость контроля 3).** При 3 сброса нет вовсе, и попаданий со СМЕНОЙ пути много: каждая загрузка снимает грязь
(С1–С3), GPU-запись делает диапазон GPU-грязным. Для них §6.3 сверяет не байты копии (§6.2), а ОТДЕЛЬНОЕ `TryReadBacking`, а для
GPU-грязного диапазона — бэкинг, который GPU-данных не содержит. **Сценарий:** на `s4s134` все `b2r_bad` пришли из строк §6.3 «П → не
кольцо», «В → gpu», «Д → не кольцо»; ветка §6.2 (`memcpy` слот ← буфер, `memcmp` буфер/тень) — единственная, чей ноль читается при 2
(при 2 смена пути — уже `b2r_path` > 0) — ни разу не сработала, а контроль записан «жив» по п. 153(в) В5. **Изменить (текст ред. 2 /
п. лида):** при 3 `b2r_bad` растёт только при `why=bytes` на попадании, чей путь 0 кончился CPU-копией в кольцо (строка 1 таблицы §6.3);
попадания со сменой пути при 3 — в `b2r_path` (при 3 это ряд, не условие) без `b2r_bad`; условие п. 151(д)(3)(б) читается по этому
`b2r_bad`. **Если не внести:** «контроль жив» может не доказывать живость той сверки, чей ноль при 2 даёт корректность.

**RC3 (MINOR — длина сверки).** `Map` округляет резерв до `nonCoherentAtomSize` (`streamBuffer.cpp:247–261`, `:268–272`), `TryReadBacking`
читает `size` байт. **Сценарий:** код копирует в слот или сравнивает `mapped_size` байт (тень, буфер сверки, `memcpy`, `memcmp`) — хвост
не инициализирован ⇒ ложные `b2r_bad` при 2 (ложный `B2R_INCORRECT`) и ложная живость при 3. **Изменить:** в §6.1–6.2 записать: тень,
буфер сверки, `memcpy` в слот и `memcmp` — ровно `size` байт; хвост резерва не трогается (как в пути 0). **Если не внести:** зависит от
реализации, ревью шага 5 не имеет правила для сверки.

**RC4 (MINOR — довод §11 (б)).** См. §3. **Сценарий:** A на смещении X у самого начала круга (сразу после оборота) и тот же тик T до
пробы B без `Submit`; после пробы B более поздний слот той же операции делает `Map` с оборотом, чей возвращаемый диапазон [0, `mapped_size`)
покрывает X; ожидание тика T = текущего ⇒ `Submit` T (без draw B) + ожидание GPU + `BeginNext`; затем запись нового слота поверх X;
draw B записан в T+1 и читает на X чужие байты. Путь 0 этого не имеет: собственная копия B — у головы кольца, не у 0. Условие — полный
круг кольца (64 МиБ, `bufferCache.cpp:542`) внутри одного тика без `Submit`; при `Submit` каждого кадра [I] и круге ≈ 3 кадра [c `ring`
0,37/кадр] — практически недостижимо [I]. Без обёртки: `Submit` между пробой B и записью draw B (санитайзер `renderCompute.cpp:1057`,
ожидание без оборота) — запас до переписи слота A — круг минус путь от A до головы (≤ трафик кольца одного тика), у пути 0 — полный
круг; класс опасности тот же, запас меньше. **Изменить:** §11 (б) — заменить основание «один командный буфер» на «слот A
перезаписывается только после полного круга кольца; круг внутри одного тика без `Submit` недостижим [I]»; в §14 — строкой; свидетель

CurrentTick()` `commandScheduler.cpp:446` или `Map` при `wrap`). **Если не внести:** довод, на котором стоит допуск «ручка может быть
плечом», проверяется ревью кода против неверной формулы.

**RC5 (MINOR — состояние при попадании Д).** Ключ не содержит `id`; попадание Д пропускает `TouchReadOnlyBuffer(id_B)`
(`bufferCache.cpp:190–195`: `TouchBuffer` → `ClearPrefetchPending` `:186`, `:197–202`). Довод §10.2 «первое касание тика сделано копией A ⇒

буфер, поглощающий буфер A (создание — не сброс ни в одном из 37 мест); B несёт новый `id`; при 1 его LRU-тик и `prefetch_pending` не

**Изменить:** (а) либо при попадании Д оставить `TouchReadOnlyBuffer(id, …)` (цена — в L, снимаемое уменьшается), либо записать
разницу состояния в §10.2 и §14 как принятую (не байты) — выбор лида; (б) ряд покрытия: `b2r_hit`/`b2r_n` значения 2 (`s2s134`) против
плеча 1 `s1s134` — рядом со строками корректности, с текстом «значение 2 проверяет попадания при сбросах, которые порождает его
собственный путь 0». **Если не внести:** ноль `b2r_bad` при 2 читается как покрытие всех попаданий значения 1, хотя часть их при 2 не
возникает.

**RC7 (MINOR — условие пробы В).** §3.3 не называет `!written ∧ !formatted` для В; сейчас это держится на инварианте транслятора

**RC8 (MINOR — выделение при 1).** §4.3: холодная таблица, кольцо теней 32 МиБ и буфер сверки выделяются и касаются при первой защёлке

защёлке 2/3. **Если не внести:** цена памяти отгружаемого значения выше необходимой и не видна в строке убийства.
