## 1. Требуемые изменения

**RC1. Ветвь 1: «доказано для кадра 0» — неверно; ложность сброса — [I] у всех четырёх событий.**
Что не так: `F16H:84`–`85` и `F16H:300` называют ложное устаревание события кадра 0 доказанным «номером №5/№6 по схеме §1.3». Запись №6
`[0x56d8ac000, 0x56d8b8000)` лежит в корзинах `0x56d8a`/`0x56d8b` и доказывает ложный сброс только DCC-заливок `0x56d898000`/`0x56d8b8000`
(вопрос В-F16h-1), но не CMASK `0x56c058000` (корзина `0x56c05`, строка `stale … seq=5 last=11`, `F16H:60`). Для ветви 1 по журналу [c] только
следующее: соседняя заливка `[0x56c05e000, 0x56c060000)` (`f5_ef`:16388 с нуля) стоит в той же корзине между №5 и FCE (16508) и проходит
`ObtainBuffer` с записью (`DS:901` → `BC:1735`), значит, **корзинная проверка объявила бы сброс независимо от того, была ли пересекающая
запись**. Что пересекающей записи нет — [I] (номер №11 = эта заливка при одной записи на диспатч: Ripple_0 №7, заливка `0x55675f000` (16377) №8 —
она в журнале есть, вопреки `F16H:63`–`64`, — Wind_0 №9, №10, заливка `0x56c05e000` №11; Ripple/Wind с двумя буферами записи сдвигают счёт).
Сценарий отказа: Ripple_0 или Wind_0 пишет диапазон, пересекающий `[0x56c058000, 0x56c05e000)` (гость переписал CMASK) — сброс верен, ветвь 1
на этом событии не дефект; отчёт, где событие «доказано», ведёт F16j к критерию «ИСПРАВЛЕНО» на событии, которого правка не тронет (`kept` = 0),
и пара даст «исполнение < 1» без правила чтения. Что изменить: в §1.5 и §6 — ложность сброса [I] для всех 4 событий, [c] — только «сброс
объявлен бы и без пересечения»; исправить «№7–№10 не печатаются»; правило чтения на событие при `=1`: `kept` = 1 — ложный сброс [c пары],
`kept` = 0 без отката кольца (RC4) — сброс настоящий, событие уходит из ветви 1 (форма (Б) п. 489(д)) — **вопрос лиду В-F16i-3**.

**RC2. Правка `KYTY_FIX_F5CMU` действует на каждом захвате CMASK-цели, а не только на сайте ветви 1.**
Что не так: `F16H:91`–`95`: «`PrepareCmaskClear` передаёт `exact = FixF5CmuEnabled()`». `PrepareCmaskClear` зовётся из `FindRenderTarget`
на каждом захвате цвета (`TC:2483`), в том числе на пути draw (`fce_materialize` = ложь, `TC:2409`) для целей, которым `colorRenderTarget.cpp`
даёт CMASK (обе оси кратны 1024). Переход `PendingDcc → CMask` с корзинным сбросом там тоже есть, и при `=1` такие очистки начнут исполняться
на любой сцене. Сценарий отказа: на сцене пары `f5cmu_*` (или любой сцене W/V при `=1`) цель 2048×2048 с CMASK получает сохранённую очистку
на первом draw — лист `=1` отличается от `=0` на кадре, где события ветви 1 нет; по правилу п. 489(д) отличие «не связанное по времени» — помеха,
повтор пары даст то же отличие — пара не сходится; либо, если совпало по времени, отличие засчитывается ветви 1 ошибочно. Счётчик `kept`
(`F16H:120`–`122`) эти события смешивает с событиями FCE. Что изменить: передать `fce_materialize` в `PrepareCmaskClear` и применять точную
проверку только при FCE-захвате (ветвь 1 — это только `DS:3798`), **или** считать раздельно `kept_fce`/`kept_rt` с полем `site=` в строке
`FixF5Cmu:` и правилом чтения для `kept_rt` > 0 — **вопрос лиду В-F16i-1** (поправка констант п. 489(д)).

**RC3. Счётчик исполнения правки — решение, а не очистка.**
Что не так: `kept` (`F16H:120`) растёт в `PendingDccFillStale`, до проверок `PrepareCmaskClear`, которые возвращаются без `ClearImage`:
`fill_value` ≠ 0, `clear_mask` = 0, `range.size` = 0, `fill_size` < `range.size` (`TC:2045`), отказ `DecodePackedColorClear`, слои вида.
Сценарий отказа: событие сохранено (`kept` = 1), но `DecodePackedColorClear` для формата цели отказал — очистки нет, `cmask_fce_unapplied`
при `=1` не падает; правило п. 489(д) «исполнение правки ≥ 1 на каждой сцене, отличий нет ⇒ `НЕ ДЕФЕКТ`» закрывает ветвь, ни разу не
исполнив правку. Что изменить: счётчик исполнения пары — `kept_applied` (сохранено **и** в том же вызове очищен ≥ 1 слой) с полем
`applied=0|1` в строке `FixF5Cmu:`; тождество для чтения пары: `cmask_fce_unapplied(=1)` = `cmask_fce_unapplied(=0)` − `kept_applied` (FCE),
`cmask_fce_b42` растёт на то же число.

**RC4. Откат кольца на корзинный ответ неотличим от настоящей перезаписи.**
Что не так: `F16H:99`–`102`: если все K = 4 записи кольца новее `since`, ответ — номер корзины. K = 4 — [I], не измерено; метаданные
поверхностей лежат вплотную (`F16H:57`–`61`), корзина 64 КиБ получает несколько заливок за кадр. Сценарий отказа: между заливкой и FCE
в корзину пришло ≥ 4 непересекающихся записей — ответ корзинный, сброс остаётся, `kept` = 0; по RC1 событие читается как «сброс настоящий»
и уходит из ветви 1 — ложный `НЕ ДЕФЕКТ`/(Б). Что изменить: счётчик `f5cmu_fallback` и поле `exact=fallback` в строке; событие с откатом —
«не определено», не «сброс настоящий»; в отчёт кода — максимум глубины истории, нужной на событиях (≤ K).

**RC5. Пара `f5cmu_*` может не содержать событий в видео и на листе.**
Что не так: события ветви 1 — кадры GPU 0, 4, 9, 15 (`F16H:66`–`70`, `f5_ef`:16517 `frame=0`, ≈ 7,9 с от старта, холодная трансляция);
эффект — один кадр: следующая заливка гостя взводит очистку следующего кадра (`F16H:76`–`78`). Б38 (с. 144): видео теряет до 34 кадров на
холодном входе; номер кадра GPU (`GpuTimeProfiler::Frame`) ≠ номер флипа (`f5_ef`:16526 `frame=3` рядом с событием `frame=0`). Сценарий
отказа: кадр события в `.idx` видео отсутствует или лист берёт кадры по секундам — плечи совпадают «без отличий», при `kept_applied` ≥ 1
правило п. 489(д) даёт `НЕ ДЕФЕКТ` ветви 1, хотя кадр с событием не просмотрен. Что изменить: строка `FixF5Cmu:` печатает номер флипа/показа
того счёта, что пишет `.idx`; правило пары: кадр события есть в `.idx` обоих плеч, лист — по номерам показа события ±1, выравнивание плеч по
номеру показа, не по времени; иначе — «не определено». **Вопрос лиду В-F16i-2** (константа формы пары п. 489(д)).

**RC6. Набор подписи трансляции назван неверно.**
Что не так: `F16H:113`–`114` и §4 (`F16H:236`): «дерево `src/graphics/shader/**`, `shaderTranslationCache.cpp`, `gpu_format.h`, `gpu_defs.h`».
`cc096dbf:CMakeLists.txt:156` включает ещё `src/graphics/host_gpu/renderer/image/imageInfo.h` (RC1 F14f → F14e2). Сценарий отказа: код
`KYTY_DIAG_F5ID` кладёт поле причины или снимок метаданных в `ImageMetadataInfo` (`imageInfo.h`) — подпись меняется, каталог варианта
холодный у пользователя и у тегов, при этом отчёт кода, опираясь на F16h, пишет «подпись не меняется». Что изменить: исправить перечень;
в проект — «`imageInfo.h` не трогается» как член ревью кода (или названная смена подписи).

**RC7. Ветвь 3: пропущена сторона «потеряна новая очистка гостя».**
Что не так: п. 489(г)(3) называет риск двусторонним; `F16H:199`–`212` разбирает только «устаревшая очистка остаётся». К3 с подпричиной
`fill_shape` (однородная заливка, отвергнутая формой в `ResolveComputeBufferFill`) — это заливка гостя: возврат `RC:231` идёт до `TrackDccFill`
(`RC:252`), диспатч исполняется как есть. Сценарий отказа: гость заливает DCC кодом очистки `0x20202020` диспатчем непринятой формы на
адрес записи `Dcc` с `clear_mask` = 0 — в памяти гостя коды очистки, образ хоста не очищается ни сейчас, ни на FCE (`MaterializeDeferredDccClear`
читает `clear_mask` записи, не память гостя) — потерянная очистка, а правило §4.4 (`F16H:282`–`283`) прочтёт её как (Б) («К3 с `clear_mask` = 0
и `stale_apply` = 0»). Что изменить: в диагностике К3/`fill_shape` печатать значение заливки и его класс (`DccFillClassOf` / 0 для CMASK);
правило: К3/`fill_shape` с классом очистки — кандидат (А) «потеряна новая очистка»; для `nofill` — [U] (форма записи не известна).

**RC8. Правило §4.4 ветви 3: К1 и К2 ⇒ (Б) — несостоятельно.**
Что не так: (а) К1: сам отчёт пишет, что запись `PendingDcc` с `clear_mask` `UINT32_MAX` на адресе остаётся и применима при привязке,
назвавшей адрес метаданными, — [U] (`F16H:210`–`212`); правило ставит (Б) безусловно (`F16H:282`). (б) К2: адрес отказа в диспатче, не
принятом как очистка (`RC:590` — `NoteCsRefusals(…, f5_tracked)` после отказа `TryConsumeComputeImageClear`), исполняется как есть — для этого
адреса К2 тождествен К3. Сценарий отказа: К2 на записи `Dcc` с взведённым `clear_mask` — устаревшая очистка позже применяется поверх
нарисованного, а правило даёт (Б). Что изменить: К1 — пометка остатка в `m_f5id_marks` тем же путём, что `exec`, (Б) только при
`stale_apply` = 0; К2 — читать по типу записи и `clear_mask` как К3.

**RC9. Правило §4.4 ветви 2: «`entry` absent ⇒ (Б)» и «`kind=none` ⇒ (Б)» — несостоятельны; не использован `dcc_compression_enable`.**
Что не так: (а) отсутствие записи значит «эмулятор не отследил заливку», а не «гость не очищал»: заливка непринятой формы (RC7), отказ DMA
(`meta_dma_*`) записи не создают. (б) `fce_next` закрывается только привязкой образа с `data.address == base` (`F16H:253`); чтение поверхности
буфером или образом с другой базой событие не закрывает, а `kind=none` прочитан как «хост поверхность не использует». (в) Ветка DCC берётся
при `dcc_addr` ≠ 0 без проверки `dcc_compression_enable` (`DS:3836`): слот без DCC — не потерянная очистка [I: семантика железа без
первоисточника], а правило этого поля не читает, хотя диагностика его печатает (`F16H:250`). Сценарий отказа: гость очистил DCC заливкой
непринятой формы, FCE не нашёл образа, `entry` = absent ⇒ (Б) — ветвь закрыта поправкой набора B при настоящей потере очистки. Что изменить:
`entry` absent и `kind=none` — «не определено» (или с доп. свидетельством: счёт заливок/отказов на адрес за процесс, чтения буфером в
`[base, base + size)`); добавить член по `dcc_compression_enable` = 0 с первоисточником семантики или пометкой [I].

**RC10. Кандидат `KYTY_FIX_F5CS` теряет очистку при частичной записи.**
Что не так: `F16H:229`–`231`: отказ `ClearMeta` на `Dcc`/`CMask` в диспатче «как есть» снимает весь `clear_mask`. Сценарий отказа: гость
после быстрой очистки дописывает метаданные части поверхности (под-прямоугольник, один слой) — железо раскрывает коды очистки в
нетронутых плитках, а правка снимает очистку всей поверхности и всех слоёв — потеря в другую сторону. Что изменить: снимать только при
записи, покрывающей `[addr, addr + fill_size)` (по `GetSize` дескриптора), и только биты записанных слоёв; иначе — оставить и считать
`f5cs_partial`. (Решение о кандидате — F16j; RC — к проекту кандидата.)

**RC11. §2.3(а): «`AdoptPendingDccForTexture` … не достигался» — неточно; основание отсутствия не названо.**
Что не так: `F16H:159`–`162`. `AdoptPendingDccForTexture` может быть достигнут и вернуть ложь на `TC:3424` ((р5)/(р6)); [c] лишь то, что
проверка устаревания `TC:3429` эту заливку не сбрасывала. Вывод «строки нет ⇒ события нет» держится только потому, что бюджет 32
строк `stale` (`TC:3362`) не исчерпан: на `f5_ef` всего 15 строк (`scan1_ef.txt`), `adopted` — 0 при бюджете 32 (`TC:3455`); отчёт этого не
пишет. (р5) исключается только перечнем мест стирания (`TC:463` — удаление образа, только `Dcc`/`CMask`/`HTile`; `TC:3431` — `stale`;
`TC:3489` — unmap). Сценарий отказа: на другом теге строк `stale` ≥ 32 — тот же довод даёт ложный вывод. Что изменить: написать довод
бюджета с числом на каждом теге, где он применён, и формулировку «проверка устаревания не сбрасывала».

## 2. Вопросы лиду (поправка констант п. 489(д) — не правка)

- **В-F16i-1 (RC2).** Точная проверка — только на FCE-захвате или на всех захватах с раздельным счётом `kept_fce`/`kept_rt`?
  **Вариант исполнителя:** только FCE (ветвь 1 = `DS:3798`); захваты draw — отдельной строкой реестра, если `kept_rt` > 0 покажет
  диагностика (тот же механизм, что В-F16h-1).
- **В-F16i-2 (RC5).** Форма пары `f5cmu_*`: событие в `.idx` обоих плеч, лист по номерам показа ±1, иначе «не определено».
  **Вариант:** принять; без этого правило п. 489(д) на ветви 1 не применимо.
- **В-F16i-3 (RC1, RC4).** Правило на событие: `kept_applied` = 1 — ложный сброс; `kept` = 0 без отката — сброс настоящий, событие вне
