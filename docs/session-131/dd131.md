## 1. Что меряется и каким числом выражается вывод

**Вопрос.** Насколько среднее `dt_us` кадра на опоре чувствительно ко времени, которое GuestGpu проводит в отрезке
dispatch под render mutex. Уровень [M] — `mh_disp_us` 2 359,3 мкс/кадр, 268 dispatch ≈ 8,8 мкс (прогон S `spk118`, с. 118,
`mutsite=1`; `C:/kyty/s126/diag/prof/RECON.md` §1, §2).

**Число вывода** — п. 123(з)(4) дословно по методу: Δ = mean `dt_us` плеча `dispceil=1` − mean `dt_us` плеча `dispceil=0`
по парам ABBA `90+1800`, окно 10–88 п. 55(б), блоки по `GateArm:`, SE по парам; поправленный оценщик п. 77(б); режим BDA
п. 83(г); DRS п. 78(е). Члены:
- `dt_us` — главная строка `FrameTrace`, мкс;
- доза на кадр D = Σ`dc_dose_ns` строки (сырые нс, §7) ≈ `mh_disp_us` · 1000 (страж §6.3);
- Δ / (D/1000) — наклон [ряд]; п. 93(г)(2): при наклоне ≈ 0,90 (`sky122`) априор 0,90 × 2 359 ≈ 2 120 мкс [I].

**Что это за число (вслух до измерения).** Δ — калибровка: чувствительность `dt` к времени отрезка на критическом потоке.
Потолок снятия отрезка ≈ Δ при линейности [I]. Δ включает ожидание других потоков на render mutex, продлённом дозой
(§10 Р2) — снятие работы сняло бы и это удержание, поэтому Δ остаётся оценкой потолка [I], а не временем одного GuestGpu
(как п. 94(г)). Δ ≠ выигрыш любого механизма; из K16 снимаема только та часть, которую назовёт механизм.

**Перепись** (§5) отвечает на другой вопрос — ГДЕ внутри 8,8 мкс идёт время — рядами того же прогона; трек не открывает
(с. 121 п. 8–9).

## 3. Ручка `dispceil` (`KYTY_DISP_CEILING`, 0..1, умолчание 0) — чтение, защёлка, доза

### 3.1 Определение и порядок

Строка `{"KYTY_DISP_CEILING", "dispceil", 0, 1}` — **ПОСЛЕДНЯЯ** строка `KNOB_DEFINITIONS` (`gates.cpp`), после `lwin`
(п. 123(ж)(1): `lwin` — предпоследняя перед `dispceil`), и `Knob::DispCeiling` — последний член перед `Knob::Count`
(`gates.h`); `check_gate_order.py` после патча и ДО сборки. В гейт-файлах имя ставится **заменой на месте** (имя,
дописанное в конец после такого же имени базы, игнорируется).

### 3.2 Чтение и защёлка — раз на dispatch, плечо расписания возможно

`const uint32_t dc_value = G::Value(G::Knob::DispCeiling);` — рядом с чтением `mut_site` (`:279`), до захвата замка,
ОДИН раз на вызов `RenderExecutor::DispatchDirect`; всё решение о дозе этого dispatch — по этой локальной переменной.
Гейты переключаются на потоке презентации (`Gates::Poll`); чтение внутри одной операции дважды не делается ⇒ ручка может
быть плечом ABBA. Ловушка с. 126 (`ApplyText` ставит все гейты, затем все ручки): в `dds131`/`dd131` меняется только
ручка `dispceil`, `mutsite` одинаков в обоих плечах — смесь плеч на одном dispatch невозможна.

### 3.3 Состояние защёлки (решается на входе, до `hold_lap`)

```
arm = (dc_value == 1)
if arm:
    if !FS::Enabled()                    -> refused, reason=notrace   (п. 123(з)(1); dc_refuse +1 — no-op без трассы, п. 94(в))
    elif !mut_site                       -> refused, reason=mutsite   (Q3: отрезок не идёт в mh_disp_us)
    elif FS::CurrentRole() != Gpu        -> dc_offthr +1, дозы нет    (ряд; структурно 0, §7.3)
    else                                 -> DOSE
```
Строки лога — раз на процесс на каждое состояние (`std::atomic` битовая маска, как `pageManager.cpp:2530–2548`):
`DispCeil: mode 1` (первая защёлка DOSE), `DispCeil: refused reason=notrace|mutsite`. При `dc_value == 0` — ничего не
пишется и не считается.

### 3.4 Доза — место и форма (шаблон `pageManager.cpp:434–446`)

Объект `DispCeilDose dc_dose(dose_armed)` объявлен **между `:285` и `:286`**:
- конструктор: при `dose_armed` — `m_t0 = FS::NowNs()` (за один вызов `NowNs` до `t_hold_t0`);
- деструктор (после `~HoldLap`, до `~MutexMark` и отпуска замка): `t1 = NowNs(); tgt = t1 − m_t0;` затем
  `d0 = NowNs(); d1 = d0; while (d1 − d0 < tgt) { YieldProcessor(); d1 = NowNs(); }`;
  `Add(DcDoseN, 1); Add(DcDoseNs, d1 − d0); Add(DcTgtNs, tgt);`.

Свойства: (а) тот же поток (GuestGpu), те же часы (`FS::NowNs`, `frameStats.cpp:199`, TSC); (б) внутри удержания
render mutex — единственного замка, который держит отрезок в своей точке выхода (`PipeLockMeasured`, `cache.m_lock`,
`CtxTick`/`Skc` — уже отпущены: их объекты разрушены раньше); (в) ПОСЛЕ заряда `mh_disp_us` — доза не входит ни в
`mh_disp_us`, ни в фазы переписи (§5.3); (г) каждый из 9 выходов дозируется (RAII); (д) цель `tgt` ⊇ отрезок `HoldLap`
на одну пару `NowNs`+`Add` с каждой стороны (≈ 2 × 10–15 нс [I]); (е) ничего не пропускается и не переставляется — работа
отрезка исполняется как при 0.

### 3.5 Нельзя

Дозу нельзя ставить внутри отрезка (удвоила бы `mh_disp_us` в плече 1, страж прочёл бы ≈ 0,5); нельзя ставить после
`~LockGuard` (не «внутри удержания», другая семантика — ожидание других потоков не продлевается); нельзя брать цель из
`HoldLap` (правка общего класса пути draw).

## 4. «0 — прежний путь побайтно» (п. 93(г)(1), чтение п. 94(б)) — перечень правок кода для ревью шага 6

## 5. Перепись фаз отрезка

### 5.1 Почему новые счётчики, а не существующие

- `Dispatch{Program,Pipeline,Bindings,Commit,Emit}Ns` (`Lap`, `:337–1032`) заряжаются только при `TimingsEnabled()` —
  при `KYTY_FRAME_TRACE=lite` (все прогоны цепочек, `launch_run.py:220`) ≡ 0; к тому же не покрывают отрезок: пролог
  `:286–337` и хвост после `:1032` не заряжаются, подготовка `:341–809` слита с пайплайном. Переделать их на `Enabled()`
  значит изменить поле существующей строки при 0 — нарушение п. 4.
- `pl_cs_wait_us`/`pl_cs_hold_us`/`pl_cs_n` (`pipelineCache.cpp:5063–5072`) — живы в `lite` (`Enabled()`), **только при
  `plkstat=1`** (умолчание 0) и только из `GetComputeProgram`, единственный вызов которого — `renderCompute.cpp:339` ⇒
  строгое подмножество фазы `dc_ph_prog_ns` (Q2).
- `HoldLap::Mark` в dispatch НЕЛЬЗЯ: разрезал бы `mh_disp_us` (деструктор заряжает только остаток после последней метки)
  и сломал бы знаменатель стража. `PathLap` НЕЛЬЗЯ: его курсор `t_path_t0` — общий с внешней цепочкой `pathlap` потока.

⇒ «Неразделённый остаток» в прогоне `lite` = весь отрезок минус `pl_cs_*`; новые счётчики делят именно его.

### 5.2 Цепочка `DispLap` (локальный объект, сырые нс)

Конструктор — сразу после `HoldLap::Count` (`:287`), до `ctx_op`: `m_t = on ? NowNs() : 0`, `on = mut_site &&
FS::Enabled()` — **то же условие, что у `hold_lap`** (популяции совпадают по построению); при `on` — `Add(DcN, 1)`.
`Mark(c)`: `if (m_t) { now = NowNs(); Add(c, now − m_t); m_t = now; }`. Член `m_rest` — сначала `DcPhEarlyNs`; метка
записи меняет его на `DcPhTailNs`. Деструктор (перед `~HoldLap`, после деструкторов всех объектов, объявленных позже —
`ctx_op`, `skc_op`, `wide_disp`, `local_bindings`, `input_info`, …): `Add(m_rest, NowNs() − m_t)`, и при `m_rest ==
DcPhEarlyNs` — `Add(DcEarlyN, 1)`.

`ProtectGpuNs`/`ProtectGpuCalls` (`pageManager.cpp:404–407`) между конструктором и деструктором цепочки. Нужна функция
`FS::ReadOwn(Counter)` — `relaxed`-чтение слота `Detail::t_shard` своего потока (0 при `nullptr`); шард пишет только сам
поток ⇒ разность точна. Путь `Protect` не меняется. Время — подмножество Σ фаз (лежит в `prep`/`bda`/`img`/`buf`/`ind`).

### 5.3 Доза вне переписи

Цепочка разрушается раньше `hold_lap`, `hold_lap` — раньше `dc_dose` ⇒ ни одна фаза и `mh_disp_us` не содержат дозы. Фазы
плеча 1 обязаны совпасть с фазами плеча 0 в пределах шума (ряд §8.2(4)) — иначе доза вторично меняет работу отрезка.

### 5.4 Тождество «Σ фаз ≤ отрезка» и допуск

Обозначения: S = Σ`mh_disp_us` · 1000, P = Σ(`dc_ph_pro_ns` + … + `dc_ph_early_ns`) (13 членов), G = S − P, по суммам
строк окна 10–88 п. 55(б) каждого блока (блоки по `GateArm:`; строка n = F — к уходящему блоку, позиция 89), оба плеча.
Построение: цепочка вложена в отрезок; G на dispatch = (цепочка стартует на `Add`+`NowNs` позже) + (кончается на
`NowNs`+`Add` раньше) ≈ 20–40 нс [I] ⇒ G/S ≈ 268 × 30 нс / 2,36 мс ≈ 0,3 % [I]. Отрицательный G возможен только разрезом
dispatch чтением счётчиков на флипе (фазы в строке n, `mh_disp_us` — в n+1): на краях окна ≤ 2 dispatch.
**Предлагаемый допуск (Q6): G/S ∈ [−0,005; +0,02] на сумме окна каждого блока каждого плеча; по строке — ряд.**
Второе тождество (точное, по сумме окна): `dc_n` = `mh_disp_n` (±2 на блок — разрез на флипе). Третье: `pl_cs_wait_us` +
`pl_cs_hold_us` ≤ `dc_ph_prog_ns`/1000 + 1 на строку (при `plkstat=1`). Четвёртое: `dc_prot_ns` ≤ P.

### 5.5 Что перепись может сказать и чего не может

**Может:** (1) долю каждой кодовой фазы в 8,8 мкс на dispatch — в плече 0 (отгруженный путь при инструменте); (2) сколько
dispatch уходят рано (`dc_early_n`, `dc_ph_early_ns` — быстрые очистки) и сколько идут через `PrepareBda`/косвенный путь;
(3) долю вооружения K14 внутри dispatch (`dc_prot_ns`, Q5) — уже откалиброванного `pd128` (не новый рычаг); (4) долю
коммита — член K5 (`pl_em_com` у draw) у dispatch; (5) ожидание/удержание замка кэша программ (`pl_cs_*`, Q2);
(6) совпадение фаз в плечах — нет ли вторичных эффектов дозы.
**Не может:** (1) снимаемость фазы — фаза = время, а не снимаемое время (как «уровень» K14); (2) механизм внутри фазы
(например, в `dc_ph_buf` — `ObtainBuffer` против синхронизации против загрузок; в `dc_ph_prog` — поиск против
материализации); (3) распределение по dispatch (хвост редких компиляций) — только суммы; (4) время пути вне отрезка (§2);
(5) OLD — если прогон в NEW; (6) линейность; (7) цена инструмента в фазах входит в сами фазы (§9). Любое число переписи —
не потолок и не выигрыш (п. 123(л)).

## 6. Положительный и нулевой контроль

### 6.1 Доза вооружилась (плечо 1) — по образцу п. 94(в)
Во всём логе ровно одна строка `DispCeil: mode 1`; 0 строк `DispCeil: refused`; Σ`dc_dose_n` > 0 в КАЖДОМ блоке плеча 1
(по `GateArm:`) в окне 10–88 п. 55(б); Σ`dc_dose_n` = Σ`mh_disp_n` − Σ`dc_offthr` на сумме окна блока (±2 — разрез на
флипе). Строка `DispCeil: mode 1` без Σ`dc_dose_n` > 0 — провал (без трассы `Add` — no-op, `dc_refuse` читается 0 по
построению: п. 94(в), M1 с. 128).

### 6.2 Перепись вооружилась (оба плеча)
Σ`dc_n` = Σ`mh_disp_n` (5.4) и Σ`mh_disp_n` > 0 в каждом блоке; тождество G/S (5.4); `dc_ph_prog_ns`, `dc_ph_pipe_ns`,
`dc_ph_com_ns`, `dc_ph_emit_ns` > 0 в каждом блоке (каждый полный dispatch проходит их).

### 6.3 Доставка дозы (страж п. 123(з)(3))
R = Σ`dc_dose_ns` / (Σ`mh_disp_us` · 1000) по окну плеча 1 ∈ [0,95; 1,10]. Ожидание [I]: `dc_tgt_ns` ≈ S + 268 × ≈ 30 нс
(цель шире отрезка на пару меток), `dc_dose_ns` ≥ `dc_tgt_ns` (перелёт — одна итерация спина, ≈ 10–20 нс) ⇒ R ≈ 1,003–1,01.
Отдельно ряд R_t = Σ`dc_dose_ns`/Σ`dc_tgt_ns` (точность спина) и R_s = Σ`dc_tgt_ns`/S (совпадение цели с отрезком) —
при провале R различает «спин» и «цель». Нижняя граница R нарушается, если есть dispatch вне GuestGpu (`dc_offthr` > 0:
их отрезки в `mh_disp_us`, дозы нет) — это находка, не шум.

### 6.4 Нулевой контроль (плечо 0 и умолчание)
Плечо 0: Σ`dc_dose_n` = 0 и Σ`dc_dose_ns` = Σ`dc_tgt_ns` = 0 (страж п. 123(з)(3)), 0 строк `DispCeil:`; Σ`dc_refuse` = 0
во всём прогоне. «0 ничего не стоит» — довод кода §4 (ревью шага 6); измерением в этом ABBA не доказывается (плечо 0 и
есть эталон) — вслух.

## 9. Цена инструмента [I]

`NowNs` — `__rdtsc` / калибровка (`frameStats.cpp:199–206`), ≈ 8–15 нс; `Add` в свой шард ≈ 2–3 нс.
- `dispceil=0`: одно relaxed-чтение + ветви на dispatch — ≈ 0.
- Перепись (`mutsite=1`, оба плеча): 1 + 12 меток + деструктор ≈ 14 × (`NowNs` + `Add`) + 5 `Add` форм + 4 `ReadOwn` ≈
  0,2 мкс на dispatch ⇒ ≈ 268 × 0,2 ≈ **50–60 мкс/кадр** на GuestGpu; входит в фазы и в `mh_disp_us` обоих плеч.
- `mutsite=1` вне dispatch (Q1): цепочка `HoldLap` в каждом draw (5–7 меток) и в present ⇒ [I] ≈ 0,1–0,3 мс/кадр в
  обоих плечах; сокращается в Δ почленно (оба плеча платят одинаково), НО входит в базу п. 123(з)(5) (Q1).
- `plkstat=1` (Q2): `LockSplit` + `PipeLockMeasured` (`TryLock` затем `Lock`) на каждом замке кэша пайплайнов ⇒ [I] десятки
  мкс/кадр в обоих плечах.
- Плечо 1 сверх плеча 0: сама доза (≈ S) + 3 `NowNs` + 3 `Add` на dispatch. Доза больше неинструментированного отрезка на
  цену переписи (≈ 2 % [I]) — Δ калибрует чувствительность к ИНСТРУМЕНТИРОВАННОМУ отрезку; для порога +500 мкс
  несущественно, называется вслух.

## 10. Риски

- Р1 **`mutsite=0` в базе** ⇒ `mh_disp_us` ≡ 0 ⇒ страж п. 123(з)(3) — деление на 0, перепись мертва. Снимается Q1.
- Р2 **Доза держит render mutex.** Поток презентации (`mh_pres_wait_us`) и любые другие взятия того же замка ждут дольше;
  Δ включает это ожидание (как п. 94(г)). Снятие работы отрезка сняло бы и его ⇒ Δ — оценка потолка [I]; доля ожидания
  других потоков в Δ — [U] (ряд §8.2(5) показывает только present).
- Р3 **Вторичные эффекты по времени.** Плечо 1 длиннее на ≈ 2,1–2,4 мс/кадр: режим BDA, заполнение очередей записи/пула
  копий и префетча могут сдвинуться (ряды BDA, §8.2(4)); удлинение кадра может менять число dispatch на кадр (ряд
  `mh_disp_n` по плечам).
- Р4 **Живучесть.** `protceil=2` (+1 мс) дожил; здесь доза ≈ 2,36 мс/кадр под render mutex — сторож зависания GPU
  (`KYTY_GPU_HANG_ABORT_S=8`) далеко; смерть или зависон в `dds131` — стоп и вопрос лиду (п. 123(з)(2)).
- Р5 **Редкие длинные dispatch** (синхронная компиляция в `GetComputePipeline`) — доза удваивает и их; в среднем окна
  это честно (так и устроен отрезок), но даёт выбросы строк; DRS п. 78(е) и поправленный оценщик — как есть.
- Р6 **Популяция дозы.** Доза — ровно на dispatch, чей отрезок заряжен `HoldLap` (то же условие `mut_site && Enabled()`,
  `mut_site` — одна защёлка на dispatch). Смещение ABBA дозой ВНЕ отрезка невозможно по построению: других мест дозы нет,
  в плече 0 объект не вооружается.
- Р7 **Разрез на флипе** — Т1/Т3/G на строке могут расходиться на 1–2 dispatch; тождества — на суммах окна.

## 11. Что проект НЕ доказывает

Что доза доставлена и прогон доживёт (до дыма); линейность; что Δ `dd131` = выигрыш любого механизма; что какая-либо
фаза снимаема; время пути вне отрезка (пролог CP, `PopPendingOperationsLazy`, ожидание замка); OLD, если прогон NEW;
другие сцены; время установленной `9235a7ac`; что цена инструмента мала — это [I] §9; 60 FPS.

## 12. Вопросы лиду (решения — строками ROADMAP ДО кода шага 5 и до фикстур шага 0)

- **Q1 (срочный, блокирует харнесс и печать): `mutsite=1` в ОБОИХ плечах `dds131` и `dd131`** — заменой на месте
  `mutsite=0` в строке гейтов этих тегов (теги трека L не трогать). Без этого `mh_disp_us` ≡ 0, страж п. 123(з)(3) не
  вычислим, перепись мертва. Следствие: база п. 123(з)(5) = плечо 0 при `mutsite=1` + перепись (цена [I] ≈ 0,15–0,35
  мс/кадр) — «отгруженное состояние + названный инструмент»; с базой 53,36 % всё равно не сравнивается (другая сборка).
  Альтернативы, которые я НЕ рекомендую: (а) своя мера отрезка ручкой (`dc_span_ns`) при `mutsite=0` — страж тогда
  проверяет только спин, а не равенство дозы `mh_disp_us`, и переписи нет вовсе; (б) перепись без `mutsite` — новый гейт.
- **Q2: `plkstat=1` в обоих плечах** (иначе `pl_cs_*` ≡ 0 и «существующие `pl_cs_*`» не делят `dc_ph_prog`). Рекомендую
  да; цена — §9, в Δ сокращается.
- **Q3: второй отказ `DispCeil: refused reason=mutsite`** при `dispceil=1 ∧ mutsite=0` — отклонение от п. 123(з)(1)
  (там отказ только без трассы). Довод: «доза после каждого dispatch, чей отрезок идёт в `mh_disp_us`» при `mutsite=0` не
  определена; отказ делает это видимым (страж Σ`dc_refuse` = 0 ловит ошибку гейт-файла).
- **Q4: добавочный счётчик `dc_tgt_ns`** (цель дозы) — не из списка п. 123(з)(1); нужен рядам R_t/R_s (различение «спин» /
  «цель» при провале стража).
- **Q5: подмножество `dc_prot_ns`/`dc_prot_n`** через `FS::ReadOwn` (новая функция `frameStats.h`, чтение своего шарда;
  путь `Protect` не меняется). Отвечает на «сколько K14 внутри dispatch» — без него перепись не отличит вооружение (уже
  откалибровано `pd128`) от прочей работы `RebindBuffers`.
- **Q6: допуск тождества G/S ∈ [−0,005; +0,02]** на сумме окна 10–88 п. 55(б) каждого блока, оба плеча; нарушение — провал
  дыма `dds131` / страж `NOT_ADMITTED` `dd131` или только ряд? Рекомендую: провал дыма и ряд печати (не страж вердикта —
  перепись вердикт не несёт).
- **Q7: `dc_offthr`** — страж (= 0 в прогоне) или ряд? Рекомендую ряд: его следствие ловит страж доставки (§6.3).
- **Q8: перепись вооружается гейтом `mutsite`, без нового гейта** — меняет цену `mutsite=1` для любого будущего тега на
  новой сборке (≈ 50–60 мкс/кадр [I]); прежние числа `mutsite=1` со старых сборок и так не сравниваются. Альтернатива —
  отдельный гейт `dispcen` (последней строкой `DEFINITIONS`). Рекомендую `mutsite`: перепись делит ровно отрезок, который
  этот гейт создаёт, и живёт ровно тогда, когда он есть.
