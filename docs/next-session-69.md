## 1. Решено измерениями — не переоткрывать

### 1.1 Окклюзия закрыта: потолок ноль

Гейт `occzero` (`graphicsRun.cpp:2444`, event 0x39) публикует `ready_bit | 0` вместо
синтетического счётчика, то есть на любой запрос видимости игра получает «не видно ничего».

| способ | Δdraws |
|---|---:|
| A/B внутри одного прогона (`occ68a`, 113 пар, ABBA) | **−0,061 %** |
| целый прогон с гейтом (`occ68b`) против `aa68b` | **−0,26 %** (разрешение между прогонами ~2 %) |

Порог сессии 66 был **Δdraws ≥ 15 %**. Порог стенда — 0,33 %. Гейт при этом доказуемо работал:
113 переключений `Gate: occzero=` в логе, 226 блоков `GateArm:`, а новый счётчик `occ_dump`
показал **16,0 дампов на кадр в обоих плечах** (16 дампов × 16 слотов DB = 256 результатов на
кадр). `cpu_gpu_us` −0,044 % ± 0,666 %, `gpu_busy_us` −0,711 % ± 0,738 % — шум в обоих.
**И картинка не меняется**: кадр на 60-й секунде `occ68b` против той же точки `base68a` — та же
сцена, та же листва, тот же реквизит (`C:/kyty/s68/cmp_occ.png`).

**Вывод: игра не использует результат своих окклюзионных запросов ни для чего, что мы рисуем.**
Настоящие occlusion queries (`VkQueryPool` + PM4-предикация, которая в дереве уже есть) —
улучшение корректности с измеренной ценностью ноль **в Sky Garden**. Предупреждение, которое
эмулятор печатает в каждом прогоне («game uses occlusion queries… GPU usage may be higher and FPS
may be lower»), для этой сцены **необоснованно** и вводило в заблуждение каждую сессию, которая
его читала. Единственное, что не исключено, — сцена, где игра всё-таки отбрасывает по запросу;
проверка стоит один прогон и стоит в плане как пункт 2.4.

### 1.2 Ворота G-f открыты: f_full = 1,02

Ручка `m4baton` = длина диапазона PM4 в draw, который второй поток исполняет по-настоящему (те же
обработчики, те же кэши, то же кольцо записи), пока поток GuestGpu припаркован. Диапазоны
чередуются внутри одного прогона, поэтому f_full — отношение двух времён на draw по одной сцене.

| диапазон | f_full | эстафета мкс/draw | GuestGpu мкс/draw | диапазонов/кадр | splice | dt кадра |
|---:|---:|---:|---:|---:|---:|---:|
| 32 | **1,0977** | 6,8787 | 6,2667 | 86,9 | 11,57 мкс | **+13,49 %** |
| 128 | **1,0217** | 6,7354 | 6,5926 | 25,5 | 14,22 мкс | **+3,83 %** |
| 512 | **1,0217** | 6,4982 | 6,3600 | 10,5 | 15,77 мкс | **+1,89 %** |

Каждая строка — 6,0–6,5 млн draw на сторону, 76–82 пары блоков. **G-f дословно: «f_full > 2,0 →
M4 закрыт; 1,5 < f ≤ 2,0 → только после адресных правок; f ≤ 1,5 → идём». Измерено 1,02 — ворота
открыты, и не впритык.** Вторая половина ворот («цена диапазона > 25 мкс при 128 draw → диапазоны
≥ 512, эффективное K ≤ 3») тоже не срабатывает: при 128 draw splice **14,22 мкс**, ниже 25.

При 512 плечо с эстафетой ведёт поток GuestGpu **на 44,5 % дешевле** (`cpu_gpu_us` −44,497 % ±
0,627 %, `cpu/draw` −44,544 %) — половина диапазонов ушла с потока, — а стена кадра растёт всего
на **1,889 % ± 0,620 %**, при том что схема **не несёт никакой параллельности** (эстафета работает,
пока владелец спит). `gpu_busy_us` +0,190 % ± 0,219 % — шум, то есть работа идентична; это и есть
сильнейшее доказательство корректности исполнения. Приёмка `bat68acc` (`m4baton=512` весь прогон,
с видео): **7 PASS, 0 FAIL, 2 WARN, 3 SKIP — VERDICT PASS, 0 однокадровых глитчей на 2608 кадрах**.

Две ловушки замера, найденные на ходу и стоящие памяти: (1) первый прогон дал f_full = **0,956**
(второй поток «быстрее» владельца) — потому что `ProcessPm4Range` качал гостевые команды
(`g_gpu_state->ProcessCommands()`) раз на пакет, а эстафета этого делать не может; вынос качалки
из измеряемого диапазона сдвинул f_full с 0,956 до 1,02, то есть смещение ~6 % жило целиком внутри
измерения; (2) `CommandRecorder::AdoptProducer` сначала утверждал, что вызывающий владеет кольцом,
— кольцо принадлежит тому, кто первым вызвал `BeginRecord`, и это не поток GuestGpu.

### 1.3 A = 12,4–13,3 мс: G-A не закрывает и не оправдывает

Гейт `amut` меряет **мутирующую** часть пути draw на месте, через `MutScope`, считающий только
внешний интервал (объединение, а не сумма). Прогон `amut68a`, 87 пар, ABBA:

| величина | на кадр |
|---|---:|
| `a_mut_us` (A как измерено) | **13 300 мкс = 13,300 мс** |
| `a_mut_n` (внешних интервалов) | 60 537 |
| `a_hold_us` (удержание render mutex) | **29 507 мкс = 29,507 мс** |
| `a_hold_n` (draw + dispatch) | 5292 |
| `a_wait_us` (взятие мьютекса) | 157 мкс |
| `cpu_gpu_us`, плечо 0 / плечо 1 | 33 075 / 34 024 мкс |

Счётчик стоит **0,949 мс на кадр** (`cpu/draw` +2,732 % ± 0,307 %, `cpu_gpu_us` +2,870 %), и часть
этой цены падает внутрь измеряемых интервалов. Отсюда три оценки: верхняя **13,30 мс**, нижняя
**12,35 мс** (весь накладной расход списан на интервалы), лучшая **≈ 12,8 мс**. **G-A дословно:
«A > 13 мс → M4 закрыт арифметикой». A = 12,4–13,3 мс: ворота не закрывают M4 и не оправдывают его
— одно только A съедает 83–89 % пятнадцатимиллисекундного бюджета.**

## 2. Работа сессии

Порядок обязателен. Обоснование порядка — числами: мьютекс (29,5 мс) больше A (12,8 мс) и больше
любой другой измеренной величины CPU-стороны, а ворота G-f уже открыты, то есть исполнять draw в
другом потоке дёшево и корректно (f_full = 1,02) — значит **единственный оставшийся блокер
CPU-трека и есть этот мьютекс**, и без таблицы его держателей M4 не проектируется. GPU-трек идёт
вторым, потому что 3,0 мс из 13,6 мс — крупнейшая опознанная статья, обе стороны обязаны сойтись
(`max(CPU, GPU)` ≈ 13,6–15 мс при идеальном M4), а GPU-вердикт теперь стоит один обычный прогон
(§1.6). Уточнение A третье: оно не разблокирует ничего само по себе — G-A и не закрывает, и не
оправдывает, — но без него арифметика `W = F + P' + A` остаётся с погрешностью 0,95 мс. Окклюзия
в пустыне последняя: её ценность документальная, цена — один прогон.

### 2.1 Профиль render mutex по держателям — главный пункт сессии

**Зачем.** 29,507 мс удержания из 34,024 мс кадра (86,7 %), 5292 взятия по 5,58 мкс, ожидание
