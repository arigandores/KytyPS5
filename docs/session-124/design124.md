## 2. Режим 2′: правка разметки (константа п. 40(в)(1), дословно п. 38(д))

### 2.1 Дефект (п. 38(д), `FACTS.md` с. 123 «Step 6»)

В режиме 2 draw помеченного кадра исполняются и делают `LodStats::Touch`; `NoteLodTouch` (`frameStats.h:2914-2921`,
вызов `descriptors.cpp:2186`) ставит якорь `A = t_gframe`. В серии опроса из 4 кадров каждый кадр сдвигает A на 1 и
получает нечётное смещение — помечены 4 кадра серии и 6 прочих (10/16; Д2 `c_df/c_f` 0,6248). В режиме 1 draw
пропускаемого кадра до `Touch` не доходят, якорь держит чётность, помечено 8/16.

### 2.2 Правка

В `NoteLodTouch` (ветка `t_gpu`), первым оператором:

```
if (t_mode >= 2 && t_skip && t_kind == KindD) { t_lod_dtouch = true; FrameStats::Add(SkcLodDkeep, 1); return; }
```

`t_lod_dtouch` — новый thread-local флаг «в этом кадре был `Touch` из операции D» (нужен §3.5; сбрасывается в
`SkipCeilFlipBoundary` там же, где читается). Прочие `Touch` (dispatch любого кадра, draw непомеченного кадра, все
операции при `t_mode < 2`, эстафета `m4baton` через `g_lod_anchor_x`) — как сейчас. `Touch` из dispatch помеченного кадра
якорь сдвигает — так же, как в режиме 1 (N8, п. 37(б)): dispatch исполняется в обоих режимах.

### 2.3 Почему режимы 0/1 не меняются

При `t_mode == 0` `t_skip` ложно (`graphicsRun.cpp:3879`). При `t_mode == 1` операция вида D до `Touch` не доходит:
сайт пропуска §1.4 с. 123 (`renderDraw.cpp:3518-3523`, `:3721-3726`) возвращает раньше привязок, а `Touch` стоит в
`ResolveTextureWith` (`descriptors.cpp:2184`), который зовётся только из привязок. Условие `t_mode >= 2` стоит первым, так
что в режимах 0/1 новая строка — один тест TLS на `Touch` (кадры опроса, в обоих плечах любого ABBA поровну). Код-ревью
проверяет: diff не трогает ни одной ветки с `t_mode == 1` и сайтов пропуска.

### 2.4 Проверка (константа (1))

* **Т7 проекта с. 123 без изменений**, включая `skc_c_df / skc_c_f` ∈ [0,45; 0,55] (ожидается 0,500) и P5
  `skc_c_dd ≈ draws / 2`.
* **Чередование помеченных строк ≤ 2 %** (аналог Т5): в окне — доля пар соседних строк `FrameTrace-x`, у которых
  `skc_c_df ≥ 1` в обеих, не больше 0,02.
* Положительный контроль правки: Σ`skc_lod_dkeep` > 0 (в Sky Garden 2 помеченных кадра опроса на 16 — ожидается
  ≈ 0,125 кадра с `dkeep` на кадр; ряд) и `skc_lod_smp1` > 0 (отчёты с выборками в помеченных кадрах — ряд).
* Нулевой: Σ`skc_lod_dkeep` = 0 при значениях 0 и 1.

## 3. Режим 3: оракул, граф и замыкание (константа п. 40(в)(2))

### 3.1 Что именно считается «нужным»

**Корректная версия** (контракт п. 25(г), дополнен п. 40(в)(5)) в помеченном кадре N не переводит часть draw вида D,
удерживает флип N, исполняет всё прочее (K, dispatch, DMA, пакеты CP — как потолок). Узел D **нужен**, если его выход
прямо или транзитивно (в пределах N) доходит до наблюдаемого. Замыкание считается **на гранулярности операции и
привязки**: чтение — то, что операция связывает (привязки её программ, вложения при тесте/смешивании, вершины, индексы,
аргументы косвенных операций, источник копии), запись — то, что она может записать (вложения по эффективной маске,
storage-образы, записываемые слоты буферов, сайты W3). Что операция прочитала на самом деле по пикселям, проект не знает
и не утверждает (§7, A1–A2).

### 3.2 Узлы

Узел — операция переписи (`SkcCensus::OpBegin`, `textureCache.cpp:3642`) ПОМЕЧЕННОГО кадра N: draw после сайта пропуска
(вид D), операция K (`DrawIndex`/`DrawAuto` до сайта: `DepthStencilCopy`, материализации очисток — `renderDraw.cpp:3476`,
`:3679`), dispatch (`renderCompute.cpp:291`, виды CS/T), и **новый** узел M для DMA помеченного кадра (`FillBuffer`
`bufferCache.cpp:1738`, `CopyBuffer` `:1780`; сейчас они вне `OpScope` — в режиме 3 обёртка `OpScope(KindM)`
при `t_mode == 3`, если снаружи нет открытой операции; вложенная DMA внутри операции — часть этой операции). Узел
хранит: вид, серийный номер, флаг `timed` (D), время §5, список входов (ребра §3.4), биты нужности `need_L`, `need_b`,
`need_Lp`, `need_Ld` (§3.6, §3.7) и первую причину (§8).

Операции непомеченных кадров узлами не становятся: их чтения — посевы (§3.5), их записи — перезаписи (§3.3).

### 3.3 Ключи и записи

**Ключ образа** = (`ImageId` с поколением, мип, слой, аспект: цвет / глубина / трафарет). Чтение или запись вида (view)
покрывает ключи диапазона мипов × слоёв вида. Если вид покрывает больше **256** ключей (объёмные массивы, кубы с мипами),
**чтение** по нему ребра не даёт (`skc3_sub_drop` +1), а **запись** закрывает все ключи вида (§3.6: под L закрытие —
безопасная сторона; под b — запись добавляется во все ключи, как обычно). Причина порога — память; число — В5.

**Ключ буфера** — отрезок адресов гостя в карте интервалов режима 3 (отдельная от `m_skc_map` с. 123 карта в
`BufferCache`, только GuestGpu). **Ключ GDS** — отрезок `[offset, offset+size)` в отдельном адресном пространстве GDS; если
у доступа draw/dispatch к GDS (`descriptors.cpp:5429`) нет смещения и размера — ребра нет (`skc3_gds_unk` +1).

У каждого ключа — **список писателей открытого помеченного кадра** (серийные номера узлов в порядке записи) и признак
`lclosed` («после последнего писателя из N ключ перезаписан операцией вне графа»). Записи:

* **копия буфера показа ПОМЕЧЕННОГО кадра** — корректная версия удерживает этот флип; `skc3_s_flipx` +1 (ожидается 1 на
  помеченный кадр — тождество И5 §9);
* **упреждающая выгрузка** `PrefetchHotReadbacks` (`bufferCache.cpp:2635`) — предположение, что гость прочтёт; посев только
  в политике `Lp` (§3.7);
* **чтения через BDA** (`uses_dma`) — диапазон не виден; посев только в политике `Ld` (§3.7);
* чтения исполняемыми операциями помеченного кадра N+1 (`skc3_s_xmm`) и все чтения после финализации N (горизонт).

**Отложенное стирание CPU.** Запись CPU гостя стирает метки командой на GuestGpu (`SkcEraseCpu`, `bufferCache.cpp:3185`) с
задержкой; посев или ребро в окне ещё не применённого стирания нашли бы писателя, чей выход гость уже перезаписал. В
режиме 3 поток гостя кладёт окно в список ожидающих стираний под мьютексом (только при `g_mode == 3`), команда на GuestGpu
его снимает; посев/ребро, чьё окно пересекает ожидающее стирание, **отбрасывается** (`skc3_s_pend` +1): безопасная сторона.

### 3.6 Две политики и их порядок

* **L**: ребро/посев доходит только до последнего писателя ключа (если не `lclosed`).
* **b**: ребро/посев доходит до всех писателей ключа, записанных после последней несомненной перезаписи.

Для каждого чтения множество писателей L ⊆ множества b (последний ∈ список; `lclosed` только убирает), посевы L ⊆ посевов
b; распространение монотонно, поэтому **need_L ⇒ need_b** для каждого узла (`skc3_lnb` = 0 — нулевой инвариант, проверка
реализации).

### 3.7 Сопутствующие политики (ряды, не чтение)

* **Lp** = L плюс посевы окон `PrefetchHotReadbacks` (`(begin, end − begin)`, `bufferCache.cpp:2635`): если гость читает
  упреждённое без отказа, L их не видит.
* **Ld** = L плюс: каждая исполняемая операция непомеченного кадра N+1 с `uses_dma` засевает все отрезки буферов с
  писателями N (крайняя сторона невидимых чтений BDA).
Обе дают `f` ≤ `f_L` (больше посевов); печатаются рядом как чувствительность чтения к двум классам невидимых чтений.

### 3.8 Финализация и память

Открытый помеченный кадр N финализируется в `SkipCeilFlipBoundary` на границе, закрывающей следующий **непомеченный**
кадр (ДО защёлки следующего). Если за N идёт ещё помеченный кадр (N8), N остаётся открытым до конца первого непомеченного
(`skc3_open2` +1). На финализации: правило poll (§3.5); подсчёт узлов D по битам и первой причине; веса §5; затем граф N
освобождается (узлы, списки ключей, рёбра — арена кадра; ключи с писателями только из N очищаются). Посевы распространяются
сразу (обходы в глубину по рёбрам, «уже нужен» — стоп), финализация лишь считает. Оценка памяти: по Д2 с. 123 ≈ 5 000 draw D, ≈ 270
dispatch и ≈ 11 000 штампов (`skc_w_di`/строку) на помеченный кадр, чтений — порядка 50 000 [I]; единицы МиБ на открытый
кадр; порога нет.

## 5. Время перевода: весовая доля (константа (3), «доля по времени»)

### 5.1 Окно D

`w_i` — стена GuestGpu (`FrameStats::NowNs`, rdtsc) от конца `SkipSiteD` до начала `OpEnd` того же draw D; это ровно то,
что режим 1 не исполняет (сайт пропуска §1.4 с. 123 → выход рендерера). Время берётся под `FrameStats::Enabled()`, а НЕ
под `TimingsEnabled()` (ловушка `Scope` в `lite`, как `PathLap` с. 96) — прогон идёт с `KYTY_FRAME_TRACE=lite`.

### 5.2 Паузы: вычитание кода переписи

Каждая входная точка кода переписи, исполняемая внутри окна D (`SkcCensus::*`, `BufferCache::Skc*`, `SkcStampW3`, код
графа §3), — RAII `Skc3Pause`: на входе самого внешнего уровня (счётчик глубины) rdtsc, на выходе rdtsc, разность — в
`p_i`, `n_i` +1. `w̃_i = w_i − p_i`. Инлайновые тесты режима (`t_mode >= 2`) не паузятся — они есть и в сборке без
переписи.

### 5.3 Остаток: цена самой паузы

Вне отрезка паузы остаётся часть её собственной цены — `τ` на паузу, не больше полной цены паузы. Истинное время перевода
`c_i = w̃_i − τ_i·n_i`, `0 ≤ τ_i ≤ τ⁺`. **Калибровка в том же прогоне:** на каждой границе кадра режима 3 (вне окон) —
`K = 256` пустых пауз подряд между двумя rdtsc: `skc3_cal_ns` += внешняя разность, `skc3_cal_n` += K. `τ̂` строки =
`cal_ns / cal_n`; **`τ⁺ = κ_τ · max_строк τ̂`**, `κ_τ = 2` (холодный кэш в настоящих паузах дороже горячего цикла; В5).

### 5.4 GC помеченного кадра

Потолок приостанавливает GC в пропускаемых кадрах (§1.6 с. 123); корректная версия может так же. Время всех вызовов
`RunGarbageCollector` в помеченном кадре (включая критические, которые потолок не держит — избыток идёт в верхнюю сторону)
за вычетом пауз — `G = skc3_gc_ns`, паузы внутри — `skc3_gc_pn`. G засчитывается снимаемым целиком.

### 5.5 Доли

По окну прогона (суммы счётчиков финализированных кадров, политика X ∈ {L, b}):

```
f_n^X          = Σ skc3_free_X / Σ skc3_d
f_t^X(τ)       = (Σ skc3_wfree_X_ns + Σ skc3_gc_ns − τ·(Σ skc3_pfree_X_n + Σ skc3_gc_pn))
               / (Σ skc3_wd_ns      + Σ skc3_gc_ns − τ·(Σ skc3_pd_n      + Σ skc3_gc_pn))
f_t^{X+}       = min(1, max(f_t^X(0), f_t^X(τ⁺)))          (f_t(τ) монотонна по τ — максимум на концах)
f_x^{X+}       = max(f_n^X, f_t^{X+})
```

Почему это верхняя сторона истинной временной доли `f_t*` (при заданном множестве свободных узлов): числитель
`Σ_free(c) + G ≤ Σ_free(w̃) + G − τ_true·N_free` и знаменатель `Σ_D(c) + G = Σ_D(w̃) + G − τ_true·N_D` — истинное значение
есть `f_t(τ_true)` при `τ_true ∈ [0, τ⁺]`, а максимум монотонной функции на отрезке — на его конце. Условие — `τ_true ≤ τ⁺`
(допущение A3, §7). `f_n` входит в максимум как страховка от искажения весов кодом переписи (кэш, память — §7 R_poll).

### 5.6 Доля снимаемой работы кадра `d` (для множителя §6)

`skc3_fr_ns` — стена `GuestGpu::Process` (тот же отрезок, что `gw_proc`, `KYTY_GPU_WALL=1`), начатых в помеченном кадре,
за вычетом всех пауз в них (`skc3_fr_pn` — их число):

```
d(τ)  = (Σ skc3_wd_ns + Σ skc3_gc_ns − τ·(Σ skc3_pd_n + Σ skc3_gc_pn)) / (Σ skc3_fr_ns − τ·Σ skc3_fr_pn)
d⁺    = min(1, max(d(0), d(τ⁺)))
```

## 6. Правило чтения п. 40(в)(3) и что делает его верхним

### 6.1 Буква константы

U = (11 384,3 + 132,7) мкс × `f_free⁺`; U < 500 — пропуск ЗАКРЫТ переписью; U ≥ 500 — прототип в с. 125; направление не
доказано — НЕ РАЗРЕШЕНО. Проект **сохраняет формулу буквально** и определяет

```
f_free⁺ := U_d⁺ / 11 517 мкс                         (по умолчанию проекта; В2, В3 — выбор лида)
U_d⁺    := M⁺ · f_x^{L+}
```

### 6.2 Почему `11 517 × f_x⁺` сама по себе НЕ верхняя (два члена)

* **E — отложенная работа.** Δ потолка = снятое в пропущенном кадре R минус добавленное в переведённый кадр E (плечо 1:
  `img_up_kb` на переведённый кадр 166 667 против 99 402 плеча 0 в Д1, 220 724 против 101 076 в `sky123`). Корректная
  версия сдвигает в переведённый кадр E′ ∈ [0, E]; экономия `≈ f·R − E′`, а `Δ·f = f·(R − E)` меньше её при `E′ < f·E`.
  Направление: **ЗАНИЖЕНИЕ** U.
* **Наклон отклика.** Δ`dt`/Δ`cpu_gpu` потолка 11 384,3 / 13 195,2 = 0,863 (нижний край 11 251,6 / 13 324,2 = 0,845); доза
  2 мс на GuestGpu в `sky122` (NEW) дала 0,902 ± 0,065 (верх 0,967). Малое снятие переводится в `dt` не хуже крупного —
  пропорция от потолка **ЗАНИЖАЕТ** на множитель до 0,967 / 0,845 = 1,145 [I: другой режим BDA, доза добавлялась, а не
  снималась].

### 6.3 Верхний множитель M⁺ (по умолчанию проекта)

Экономия корректной версии на строку `FrameTrace` (флип) — половина снимаемой в помеченном кадре работы GuestGpu,
пересчитанная в `dt` с наклоном s:

```
S ≤ s⁺ · (Σ_free c + G) / 2 ≤ s⁺ · f_x⁺ · (Σ_D c + G) / 2 ≤ s⁺ · f_x⁺ · d⁺ · W₀⁺ / 2
M⁺ = s⁺ · d⁺ · W₀⁺ / 2,   s⁺ = 1,   W₀⁺ = среднее gw_proc_ns/1000 плеча 0 `sky123` в окне 10..87 + 2SE по блокам
```

* `s⁺ = 1` — допущение A4: снятие x мкс стены GuestGpu не сокращает средний `dt` больше чем на x, пока GuestGpu несёт
  кадр (`gw_idle` плеча 0 `sky123` 38,6 мкс/строку — простоя нет; ожидания показа — отдельный член §6.4). Поддержка: 0,863
  и 0,902 ± 0,065 < 1.
* `W₀` из того же запечатанного прогона, что и Δ (OLD) — справка `design/rows_sky123.md`: 32 089,7 мкс/строку, `W₀/2`
  ≈ 16 045; `d⁺` — доля из прогона переписи (только как доля). При `d⁺ ≈ 0,85` M⁺ ≈ 13 600 мкс против 11 517 (×1,18) [I].
* E не входит: экономия версии `≤ s·(Σ_free c + G)/2 − E′/2`, а `E′ ≥ 0` её только уменьшает; M⁺ строится из снимаемой
  работы R = `Σ_D c + G` (доля `d` стены кадра), а не из Δ = R − E. **Допущение A6:** доля `d`, измеренная в прогоне
  переписи, переносится на стену кадра плеча 0 `sky123` (`R ≈ d·W₀`); переносу помогает то, что OLD — режим с большей
  работой `PrepareBda` на draw [I].
* Если страж `d` (§11 G-d) не пройден — **`d⁺ = 1`** (M⁺ = W₀⁺/2 ≈ 16 045; грубее, но верхнее).

### 6.4 Член вне замыкания: путь показа (В3)

Удержание флипа корректной версией снимает и то, что не зависит от замыкания: ожидание GuestGpu флипа (`gw_flip_ns`),
мьютекса очереди флипов (`flip_rsv_wait_ns`) и render mutex, который держит `Presenter::Present` (`swapchain.cpp:890`).
По `sky123` плечо 0 (строки на флип): `gw_flip` 278,3 мкс, `flip_rsv_wait` 0,0, стена `Present` (`skc_pres_ns`) 782,5
(`design/rows_sky123.md`). Верхняя сторона: `U_p⁺ = gw_flip + flip_rsv_wait + skc_pres` ≈ 1 061 мкс/строку (ожидание
GuestGpu на render mutex под `Present` не измерено — поэтому целая стена `Present`); узкая [I]: `gw_flip + flip_rsv_wait`
≈ 278. **Если U включает U_p⁺ — U ≥ 1 061 > 500 при любом `f`, и перепись ЗАКРЫТЬ трек не может по построению.**
Проект по умолчанию считает **U = U_d⁺** (пропуск перевода draw — предмет переписи) и печатает U_p⁺ рядом строкой как
отдельный рычаг «удержание каждого второго флипа без пропуска draw» — корректный по построению (показанные кадры полные),
его потолок не измерен. Выбор — В3.

## 7. ТАБЛИЦА НАПРАВЛЕНИЙ (константа (3); образец — §11 `design123.md`)

Знак: «верх» — член завышает `f_free⁺`/U (безопасно для ЗАКРЫТИЯ); «низ» — занижает (опасно); «точно».

**Замыкание (политика L, по которой идёт чтение).** Общий принцип: пропущенное ребро или посев уменьшают замыкание —
«верх»; лишнее ребро или посев увеличивают — «низ». Каждый класс лишних рёбер ниже либо исключён правилом, либо назван
допущением.

| член | знак | почему / чем держится |
|---|---|---|
| чтения через BDA (`uses_dma`) не видны | верх | ребра нет; ряд `Ld` показывает крайнюю сторону |
| упреждающая выгрузка не посев | верх | ряд `Lp` |
| горизонт — только следующий непомеченный кадр; чтения k ≥ 2 и после финализации не посев | верх | константа (2); замыкание только уменьшается |
| транзитивность между помеченными кадрами не считается (`skc3_s_xmm`) | верх | константа (2) |
| чтение вида больше 256 ключей без ребра (`skc3_sub_drop`) | верх | |
| вложение без известного состояния теста/смешивания — без ребра (`skc3_att_unk`) | верх | |
| GDS без смещения — без ребра (`skc3_gds_unk`) | верх | |
| посевы/рёбра в окне ожидающего стирания CPU отброшены (`skc3_s_pend`) | верх | задержка команды стирания иначе дала бы лишний посев (М8 с. 123 — «низ» для замыкания) |
| выгрузка образа без переноса ключей | верх | ребро теряется |
| окно посева cpu = окно отказа, а не окно выгрузки 512 КиБ | точно для байтов отказа; верх для прочих прочитанных байтов страницы (без отказа не видны) | с. 123 брала окно выгрузки — это был бы «низ» |
| **L: любая запись закрывает ключ** | верх для частичных записей (G-буфер, тайлы атласа: ранние писатели выпадают) | накопление, которое идёт через тест глубины/смешивание, сохраняется рёбрами чтения-изменения-записи |
| **L: последний писатель мог не записать ни одного прочитанного текселя** (отсечён целиком; пишет не тот тайл, что читается) | **низ** | **допущение A2**; не измеряется |
| **чтение привязки, которую шейдер динамически не читает** (ветвление) | **низ** | **допущение A1** (статически неиспользуемых привязок в плане ресурсов нет) |
| возможная запись W2 (storage/RW), которой не было | низ под L (лишнее ребро на невписавший узел; истинный писатель остаётся через его ребро чтения RMW) | ряд `skc3_w2d` — число узлов D с записью W2 (верхняя граница класса по числу) |

**Число против времени (константа (3), отдельно).** Замена доли по числу долей по времени даёт верхнюю сторону тогда и
только тогда, когда свободный draw в среднем не дешевле нужного. Доказать этого нельзя: свободными скорее окажутся draw
без выхода в следующий кадр (часть проходов показа, UI, отладочная геометрия), а цена draw растёт с числом привязок
(`pxstat` с. 68: глубинный draw платит 18,4 % привязок полного). Поэтому чтение идёт по `max(f_n, f_t⁺)`: при
`f_t⁺ ≥ f_n` оно временное (доказано при A3), при `f_n > f_t⁺` — по числу, что больше временной верхней стороны.

**Итог.** `f_x^{L+}` — верхняя сторона доли снимаемой работы **для любой версии, решающей по операциям**, при A1–A3, A5;
`U_d⁺` — верхняя сторона экономии при A1–A6 (A6 не нужно при `d⁺ = 1`).
A1–A2 (гранулярность оракула) принять — **В1**; без них направление L не доказано и чтение по букве п. 40(в)(3) — НЕ
РАЗРЕШЕНО при любом числе.

## 10. Положительный и нулевой контроль

**Положительный (константа (4): «запись образа в кадре N → чтение в N+1» обязана попасть в замыкание):**
* **P1** (внутренний): каждое чтение исполняемой операцией непомеченного кадра N+1 ключа, чей последний писатель — узел D
  кадра N и не `lclosed`, — проверка `skc3_pc_n` +1; на финализации этот узел обязан иметь `need_l`, иначе
  `skc3_pc_bad` +1. Страж: Σ`skc3_pc_n` > 0 и Σ`skc3_pc_bad` = 0. Ловит ошибки распространения, финализации и
  освобождения арены.
* **P2** (сверка с независимым кодом с. 123): для каждого образа, давшего `skc_x1_img` (перепись режима 2′, метки
  `skc_wops`), каждый его писатель D — проверка `skc3_x1c_n` +1; если ни один ключ, записанный этим писателем в образ, не
  пересекается с ключами чтения — `skc3_x1c_sub` +1 (разные мипы/слои: режим 2 считает по образу); иначе писатель обязан
  иметь `need_b` — провал `skc3_x1c_bad` +1. Страж: Σ`skc3_x1c_bad` = 0, Σ`skc3_x1c_n` > 0.
* **P3** (известная цепочка, как P6 с. 123): хотя бы одна строка `Skc3Chain:` с `reader = writer_ps` (самописатель;
  в Д2 с. 123 — PS `0x5a34b303576ee324`, `selfw=1`) и `need_l=1`; ни одной такой строки с `need_l=0`.
* **P4** посевы разведены: Σ`skc3_s_next` > 0, Σ`skc3_cl_poll` > 0, Σ`skc_lod_dkeep` > 0; `skc3_s_cp`, `skc3_s_cpu`,
  `skc3_s_gds` — ряды (0 допустим: в Д2 с. 123 `rc_*_d` = 0, `r_gds` = 0).

**Нулевой:**

## 15. Риски и что проект НЕ доказывает

**Риски:**
* **R1 Оракул.** Версия с попиксельным знанием (покрытие, отсечение, динамически неиспользуемые привязки) может снять больше,
  чем показывает L, — там, где A1/A2 ложны. Такую версию нельзя построить без исполнения draw; проект её не рассматривает
  и называет это (В1).
* **R2 Разметка 2′ ≠ множество режима 1 на прогоне.** Под переписью игра идёт медленнее; якорь двигают `Touch` dispatch
  (N8) — двойные пометки; чередование ≤ 2 % и Т7 ловят сдвиг.
* **R3 Невидимые записи через BDA** под L — эпоха §3.3(ii) или строка шага 3 «записей через BDA нет».
* **R4 Загрязнение весов** (R_poll, A5) — `max(f_n, f_t⁺)`, справочный ряд.
* **R5 Память и темп режима 3** — прогон может уйти ниже темпа, при котором DRS держит ступень: G8.
* **R6 Сайт вложений** — состояние теста/смешивания может быть недоступно на хвосте `AcquireRenderTargets`: тогда рёбер
  нет (`skc3_att_unk`) — безопасно, но накопление G-буфера через тест глубины теряется и `f_L` растёт (не опасно для
  закрытия, опасно для полезности); Emu Engineer называет сайт, где статические параметры пайплайна draw уже известны.
* **R7 Несовместимые ручки** — как R9 с. 123; в прогоне переписи гейт-файл пинит только `skipceil=3`.

**НЕ доказывает:**
* выигрыш, ускорение или прогноз: U и `f` — верхняя сторона ОБЪЁМА снимаемой работы, а не экономия (цены переписи в этой
  программе ошибались в 2–20 раз); 60 FPS не обещается;
* что корректная версия существует, корректна или будет построена; что она «сэкономит» какое-то число;
* направление L без A1–A2; `f_t⁺` без A3; множитель без A4 (и без A6, если `d⁺ < 1`); веса без A5;
* что GuestGpu критичен (п. 24(б)); что потолок NEW равен потолку OLD;
* долю пути показа (U_p) — только его верхнюю сторону по `sky123`;
* ничего о сценах, кроме опоры; числа режима 2 с. 123 (множество 10/16) — не перепись множества режима 1.

## 16. Вопросы лиду (до строки ROADMAP недействительны; текст выше — редакция «по умолчанию»)

* **В1 — гранулярность оракула.** Принять, что «выход доходит до наблюдаемого» считается на гранулярности операции и
  привязки, а направление L — верхнее при A1 (прочитанная привязка читает хоть один байт/тексель) и A2 (последний писатель
  ключа записал хоть один тексель, который читатель читает)? Иначе ни одна политика не доказуемо верхняя, и чтение по
  п. 40(в)(3) — НЕ РАЗРЕШЕНО при любом числе.
* **В2 — множитель.** Буква п. 40(в)(3) (11 517 × `f`) по §6.2 занижает U (E ≥ 0, наклон). Проект по умолчанию читает
  `U_d⁺ = M⁺ · f_x^{L+}` с `M⁺ = s⁺·d⁺·W₀⁺/2`, `s⁺ = 1` (A4), `d⁺` при A6, и `f_free⁺ := U_d⁺/11 517` — формула
  константы при этом буквальна. Принять, или `d⁺ = 1` (грубее, без A6), или иной множитель строкой ROADMAP?
* **В3 — путь показа.** Включать ли U_p⁺ (≈ 1 061 мкс/строку по `sky123`, узкая сторона ≈ 278 [I]) в U? Если да — U ≥ 500
  при любом `f`, и перепись не может закрыть трек по построению (§6.4). Проект по умолчанию: U = U_d⁺, U_p⁺ — строкой как
  отдельный неизмеренный рычаг (удержание флипа без пропуска draw).
* **В4 — горизонт.** Только следующий непомеченный кадр (буква константы (2)); чтения k ≥ 2 не посев (сторона «верх»).
  Подтвердить.
* **В5 — константы метода:** порог 256 ключей на вид (§3.3), `K = 256` пустых пауз, `κ_τ = 2` (§5.3), предел `max τ̂` <
  1 000 нс (G10), полоса И7 [0,15; 0,35], блок 90 строк для режима BDA (G7).
* **В6 — DMA как узел M.** Обёртка `OpScope(KindM)` для `FillBuffer`/`CopyBuffer` вне операции в режиме 3 (§3.2) —
  новый вид узла без изменения поведения; принять.
