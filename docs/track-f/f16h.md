### 1.1 Что ждёт гость

### 1.3 Почему «устаревшая» — механизм [c кода; событие кадра 0 — c журнала]

`PendingDccFillStale` (`textureCache.cpp:3343`) считает заливку устаревшей, если `LastGpuWriteSeq(address, fill_size, false) > fill_seq`
(`:3355`–`3357`). `LastGpuWriteSeq` (`cc096dbf:src/graphics/host_gpu/renderer/cache/bufferCache.cpp:2863`) берёт максимум номеров по корзинам
`vaddr >> HotBucketBits`, `HotBucketBits = 16` (`cc096dbf:src/graphics/host_gpu/renderer/cache/bufferCache.h:453`) — **64 КиБ**; номер корзины
ставит `NoteGpuWrite` (`bufferCache.cpp:2849`) на каждую запись буфера GPU, вызов — `bufferCache.cpp:1735` с точными `vaddr`, `size`.
Значит, запись **соседнего** диапазона в той же корзине неотличима от перезаписи заливки.

Гость кладёт метаданные поверхностей вплотную. Кадр 0, `f5_ef` (строки 16341–16388), диспатчи-заливки по порядку: `0x56d8b8000`+`0x14000`,
`0x514050000`, `0x56d898000`+`0x14000`, `0x556759000`, `0x56c058000`+`0x6000`, `0x56d8ac000`+`0xc000`, …, `0x56c05e000`+`0x2000` (16388).
Три строки `stale pending DCC fill ignored` того же лога сходятся с этим порядком: `dcc=0x56d8b8000 seq=1 last=6`, `dcc=0x56d898000 seq=3
last=6` (16691), `dcc=0x56c058000 seq=5 last=11` (16516) — заливки №1, №3, №5. Запись №6 — `[0x56d8ac000, 0x56d8b8000)`: не пересекает
`[0x56d898000, 0x56d8ac000)` и `[0x56d8b8000, 0x56d8cc000)`, но делит с ними корзины `0x56d8a` и `0x56d8b` [c]. Для CMASK `0x56c058000`

### 1.5 Исход по п. 489(д)

для кадра 0 номером №5/№6 по схеме §1.3 и [I] для №11 и трёх прочих; счётчик исполнения правки (§1.7) покажет это в паре по событиям.

### 1.6 Проект правки `KYTY_FIX_F5CMU`

- **Ручка:** `KYTY_FIX_F5CMU`, умолчание 0; чтение раз на процесс (`static const bool` на `Common::EnvValueOn(std::getenv(...))`: не задано
  или `""` — ВЫКЛ); строка `FixF5Cmu: mode=1` один раз при создании устройства при `=1`.
- **Что меняется:** только решение `PendingDccFillStale` на сайте `PrepareCmaskClear` (`textureCache.cpp:2023`). `PendingDccFillStale`
  получает параметр `bool exact` (умолчание `false`); при `exact` номер последней записи берётся новой
  `BufferCache::LastGpuWriteSeqExact(vaddr, size, since)` вместо `LastGpuWriteSeq(vaddr, size, false)`. `PrepareCmaskClear` передаёт
  `exact = FixF5CmuEnabled()`. Вызовы из `PrepareDccClear` (`:1894`) и `AdoptPendingDccForTexture` (`:3429`) не меняются (их ложные срабатывания
  — вопрос В-F16h-1, §5).
- **Данные (журнал точных записей):** в `BufferCache` рядом с `m_bucket_write_seq` (`bufferCache.h:455`) — кольцо последних K = 4 записей
  на корзину `{lo, hi, seq}`. `NoteGpuWrite` при `=1` в том же цикле по корзинам (`bufferCache.cpp:2849`–`2861`) кладёт `{vaddr, vaddr + size,
  seq}` в кольцо каждой корзины диапазона; запись > 16 МиБ, как и сейчас, корзин не трогает (`m_large_write_seq`, при `include_large = false`
  её не видит и прежняя проверка). `LastGpuWriteSeqExact(vaddr, size, since)`: по каждой корзине диапазона — если её `m_bucket_write_seq`
  ≤ `since`, корзина чиста; иначе просмотр кольца: запись с `seq > since`, пересекающая `[vaddr, vaddr + size)`, — ответ её `seq`; если все
  K записей кольца новее `since` (история могла уйти) — ответ номер корзины (консервативно, как сейчас); иначе корзина чиста. Ответ —
  максимум по корзинам, 0 — нет записи.
- **Свойство «в другую сторону не теряет» [c по построению]:** точная проверка видит те же события, что и корзинная (одна точка записи
  `NoteGpuWrite`), и отбрасывает только записи с диапазоном, не пересекающим заливку; при неполной истории — ответ корзинный. Значит,
  «устарела по точной» ⇒ «устарела по корзинной»; правка может только сохранить заливку, которую корзинная проверка сбросила из-за
  непересекающейся записи; запись CPU (`IsRegionCpuModified`, `textureCache.cpp:3356`) проверяется как прежде. Записи, которые
  `NoteGpuWrite` не видит, не видны и сейчас — новой слепоты нет.
- **`=0` байт в байт:** при `=0` `NoteGpuWrite` делает одно ветвление на статическом флаге и не пишет кольцо; `PrepareCmaskClear` зовёт
  прежнюю проверку; решения, состояние кэша и журнал — прежние.
- **Поток и замок:** `NoteGpuWrite` и `LastGpuWriteSeq` уже вызываются в тех же местах (получение буфера с записью, `bufferCache.cpp:1735`; проверка — под
  `TextureCache::m_lock` из `PrepareCmaskClear`); кольцо живёт рядом с `m_bucket_write_seq` и читается/пишется теми же путями, с той же
  дисциплиной [c сайтов; ревью F16i проверяет отсутствие нового потока доступа].
- **Подпись трансляции:** правка в `bufferCache.cpp/.h`, `textureCache.cpp/.h`, `descriptors.cpp` (строка `mode`) — вне набора подписи
  (дерево `src/graphics/shader/**`, `shaderTranslationCache.cpp`, `gpu_format.h`, `gpu_defs.h`); подпись и каталог варианта не меняются.
- **Цена при `=1`:** до K·24 Б на корзину, запись кольца — на каждой записи буфера ≤ 16 МиБ (≈ 1 000 на кадр по счёту `dg_buf_all`,
  комментарий с. 74 у вызова `bufferCache.cpp:1735`); проверка — только при переходе `PendingDcc → CMask`.

### 1.7 Счётчик исполнения правки и пара

- В `PendingDccFillStale` при `exact` дополнительно считается корзинный ответ (только для счёта): «корзинная — устарела, точная — нет»

## 2. Ветвь `dcc_fce_no_image` — исход (В)

### 2.1 Что ждёт гость

FCE / DCC-decompress draw (`MODE` 2/6) со слотом, где `CB_COLORn_BASE` ≠ 0 и `CB_COLORn_DCC_BASE` ≠ 0 (ветка `descriptors.cpp:3836`–`3838`,
`dcc_compression_enable` не проверяется): железо раскрывает блоки DCC, помеченные кодом очистки (`0x00/0x20/0x40/0x80/0xc0`; `0x20` — цвет из
`CLEAR_WORD` слота), в память поверхности. Источник очистки — предшествующая заливка DCC (диспатч-заливка `0xa572ee17a880e71c`, напр.
`f5_ef`:16366 `addr=0x56d898000 value=0x20202020`, 16390 `addr=0x5637f0000 value=0x00000000`) [c журнала].

### 2.2 Что делает эмулятор

`FindDccSurfaceImage(base, dcc)` (`textureCache.cpp:3372`) ищет зарегистрированный не-depth образ с `data.address == base`
(`:3381`–`3387`): с метаданными `Dcc` на этом `dcc` — владелец (`:3388`–`3392`); с `None` — кандидат (`:3395`–`3398`); если владельца нет и
кандидат ровно один — `AdoptPendingDccForTexture` (`:3404`, `:3410`), который принимает только запись `PendingDcc` (`:3424`) и отбрасывает
устаревшую (`:3429`–`3436`). Найден — `MaterializeDeferredDccClear` (`descriptors.cpp:3859`) очищает образ по `clear_mask`. Не найден —
`dcc_fce_no_image` и строка `no image for slot` (первые 32; все — с `KYTY_DCC_TRACE`, `descriptors.cpp:3843`–`3855`), и ничего не делается.

Причины «не найден» по коду (их 7): (р1) нет образа с `data.address == base`; (р2) есть образ `Dcc` с другим адресом метаданных; (р3) есть
образ с иным видом метаданных (`Cmask` и др.); (р4) кандидатов `None` больше одного; (р5) у единственного кандидата нет записи на `dcc`;
(р6) запись есть, но не `PendingDcc` (`Dcc`/`CMask`/…); (р7) заливка устарела (`PendingDccFillStale`; запись стирается, `dcc_reset_stale`).

### 2.3 Пути, которые исполнят очистку позже, — зависят от причины [c]

- `AdoptPendingDccForTexture` на привязке текстуры с `MetaCompress` (`descriptors.cpp:3142`–`3143`, `:3269`) и затем
  `MaterializeDeferredDccClear` на привязке шейдера (`descriptors.cpp:6537`) — только при (р1)/(р5)-подобном состоянии с живой `PendingDcc` и
  образом `None` в момент привязки.
- `PrepareDccClear` на пути цели (`textureCache.cpp:1869`–`1993`) — если цель позже привязана с метаданными `Dcc` на этом адресе:
  переводит `PendingDcc → Dcc` (с той же проверкой устаревания, `:1894`) и очищает.
- При (р2), (р3), (р6) без новой привязки, а также если поверхность хост больше не использует, — никакой путь.

**До сцены (4 тега из 4) [c `scan1_*`, вырезка 16330–16700]:** (а) ключ `base=0x563800000 dcc=0x5637f0000` повторяется каждый кадр (20 из 32
строк `f5_ef`; рост `dcc_fce_no_image` до сцены ≈ 1 на кадр: 373 к кадру 361 у `f5_sg`), ни строки `stale`, ни `adopted`, ни
`MaterializeDeferredDccClear` с этим образом в журнале — значит, `AdoptPendingDccForTexture` с проверкой устаревания не достигался

## 3. Ветвь `meta_cs_untracked` — исход (В)

### 3.1 Что ждёт гость и что делает эмулятор

Диспатч гостя пишет буфер, база которого — адрес известной записи метаданных `PendingDcc`/`Dcc`/`CMask`. `TryConsumeComputeMetaClear`
(`renderCompute.cpp:73`): буфер, который и читается, или только читается, на адресе `IsMeta` (`PendingDcc` не входит,
`textureCache.cpp:3194`–`3198`) ⇒ ранний `false` без счёта (`renderCompute.cpp:87`–`88`); при `has_bitwise_xor` — `false` без счёта (`:92`,
`:128`); иначе на каждый записываемый буфер `ClearMeta` (`:106`), который для `PendingDcc`/`Dcc`/`CMask` отказывает и отдаёт вид отказа
(`textureCache.cpp:3249`–`3261`) ⇒ `other_writes = true` (`renderCompute.cpp:117`) ⇒ ответ `false` (`:126`). Затем
`TryConsumeComputeImageClear` (`:579`–`581`). Счёт — `NoteCsRefusals` (`cc096dbf:src/graphics/host_gpu/renderer/diagF5.cpp:311`):
адрес отказа = адрес, где этот же диспатч сделал `TrackDccFill`, ⇒ `tracked`, иначе `untracked`.

Классы `untracked` по коду [c]:

- **К1 — исполнен как очистка образа.** Диспатч — однородная заливка, `ClearImageFromBuffer` нашёл образ ровно на этом адресе и размере
  (`textureCache.cpp:2638`–`2707`) ⇒ `TryConsumeComputeImageClear` = истина ⇒ `NoteCsRefusals(f5_refusals, 0)` (`renderCompute.cpp:582`–`584`):
  **все отказы диспатча — `untracked`**, хотя запись гостя исполнена (образ очищен). Запись `PendingDcc` на адресе остаётся от прежней
  заливки, когда образа ещё не было (`TrackDccFill` заводит `PendingDcc` на любом не принятом адресе, `textureCache.cpp:3298`–`3300`).
- **К2 — заливка учтена на другом адресе.** `f5_tracked` ≠ адресу отказа (диспатч с несколькими записываемыми буферами).
- **К3 — исполнен как есть.** Не заливка (`uniform_fill` нет) или форма заливки отвергнута (`ResolveComputeBufferFill`,
  `renderCompute.cpp:131`–`172`): диспатч записывается в буфер команд и исполняется (`:592` и далее).

### 3.2 Обратная сторона: остаётся ли устаревшая отложенная очистка [c]

- **К3, запись `Dcc`/`CMask`:** ни `ClearMeta` при отказе (`textureCache.cpp:3249`–`3261` — возврат до изменений), ни
  `TryConsumeComputeImageClear` без заливки (`renderCompute.cpp:229`–`231` — возврат до `TrackDccFill`) запись не трогают: `type`,
  `clear_mask`, `fill_value`, `fill_size` прежние. Если `clear_mask` ≠ 0, её позже применят `PrepareDccClear` (`textureCache.cpp:1976`–`1992`),
  `PrepareCmaskClear` (`:2071`–`2082`) или `MaterializeDeferredDccClear` (`descriptors.cpp:3509`, `:3517`) — поверх того, что гость сделал после
  своей записи метаданных. Проверка устаревания этих записей не защищает: `PendingDccFillStale` возвращает «не устарела» для всех типов,
  кроме `PendingDcc` (`textureCache.cpp:3352`). Был ли `clear_mask` ≠ 0 в момент записи — [U].
- **К3, запись `PendingDcc`:** записываемый буфер диспатча проходит `ObtainBuffer` с записью ⇒ `NoteGpuWrite` (`bufferCache.cpp:1735`) ⇒ при
  следующем приёме (`AdoptPendingDccForTexture`, `PrepareDccClear`, `PrepareCmaskClear`) заливка признаётся устаревшей и сбрасывается —
  устаревшая очистка не применяется [c].
- **К1:** диспатч не исполняется (`ResetBindings(); return;`, `renderCompute.cpp:585`–`587`), записи буфера нет, запись `PendingDcc` на адресе
  образа остаётся с `clear_mask` `UINT32_MAX` и `fill_seq` без новой записи — применить её может только привязка, назвавшая этот адрес адресом
  метаданных (`AdoptPendingDccForTexture`/`FindDccSurfaceImage` по `dcc`) [c]; что такое бывает — [U].

## 4. Проект `KYTY_DIAG_F5ID` (только измерение; ветви 2 и 3)

Общее: умолчание 0; чтение раз на процесс (`Common::EnvValueOn`); `DiagF5Id: mode=1` один раз при создании устройства; ни одного
изменения состояния гостя, хоста или кэша; файлы — `descriptors.cpp`, `renderCompute.cpp`, `textureCache.cpp/.h`, `diagF5.cpp/.h` — вне
