# Ловушки платформы Paperclip, API задач и окружения агентов

Вынесено из `CLAUDE.md`, раздел «Правила работы», дословно 2026-09-28 (`HPP-157`, `ROADMAP.md` «СЕССИЯ 122»
п. 113). В `CLAUDE.md` осталась одна строка на ловушку. Новая ловушка пишется сюда полным текстом и одной строкой в
`CLAUDE.md`.

- **Ловушка API задач (2026-09-26): поле блокеров называется по-разному на запись и на чтение.** Писать блокер —
  `blockedByIssueIds` (POST/PATCH задачи; снятие — `removeBlockedByIssueIds`), читать — **`blockedBy`** в ответе
  `GET /api/issues/<id>` (объект или список; сводка — `blockerAttention.blockingTreeLive`). Запрос
  `blockedByIssueIds` у прочитанной задачи возвращает пустоту ВСЕГДА, и по нему живая цепочка шагов выглядит
  мёртвой. Сторож непрерывности — `ps5 em/docs/chain_check.py` (семь инвариантов, `--selftest`); правило и
  константы — `ROADMAP.md` «СЕССИЯ 122» п. 9–11.
- **Ловушка API задач 2 (2026-09-26): живая цепочка ДОЧЕРНИХ задач не является путём продолжения РОДИТЕЛЯ.**
  Задача цикла, оставленная `in_progress` без собственного блокера, не имеет чем проснуться
  (`blockerAttention.blockingTreeLive = false`), и платформа требует диспозицию у пользователя — даже когда все шаги
  стоят на формальных блокерах и `chain_check.py` печатает `ALL OK`. Пока цепочка сессии открыта, задача цикла стоит
  **`blocked` с блокером на терминальном звене** (последний шаг, принадлежащий лиду): сводка переходит в
  `state=covered`, `blockingTreeLive=true`, родитель просыпается сам. Инвариант I7; правило — `ROADMAP.md` п. 11.
- **Ловушка API задач 3 (2026-09-26): «состояние ожидания приёмки» — тупик, а не состояние.**
  Шаг цепочки, оставленный в `in_review` до приёмки лида, не завершается сам, а звено приёмки
  заблокировано им же и не проснётся — платформа выходит из этого требованием диспозиции у
  пользователя. Сдача шага — **`done`** («работа СДАНА», не «принята»); гейтом остаётся звено приёмки
  лида, на котором висит следующий шаг (I8). Инвариант I9; правило — `ROADMAP.md` п. 15.
- **Ловушка API задач 4 (2026-09-26): блокер снимается только у задачи в `blocked`, `backlog` не будит ничто.**
  Звено приёмки `HPP-11`, созданное в `backlog` с формальным блокером, пролежало после `done` своего блокера,
  пока пользователь не спросил «никто ничего не делает». Ждущее звено создавать и держать в **`blocked`**;
  инвариант I11 `chain_check.py`; правило — `ROADMAP.md` п. 18(а).
- **Ловушка API задач 5 (2026-09-27): фоновый процесс не будит никого после конца хартбита.** `HPP-7` запустил
  `skyp122` фоном и закрыл хартбит в `in_progress`, ожидая уведомления; запуск упал сразу (`bash: command not found` —
  в Bash-инструменте агента сломан PATH), а уведомление живёт только внутри сессии агента. Прогон и скоринг — **на
  переднем плане** (таймаут 600 000 мс), после запуска проверить старт (замок/процесс/лог); продолжение — только сохранённым пробуждением Paperclip с проверенным ответом API;
  монитор — только внешнего, не своего прогона (Процесс п. 1 аудита с. 142, `ROADMAP.md` п. 231(з); простой с. 142
  22:18:38–22:33:07). Страховка — рутина **«Сторож
  цикла KytyPS5»** (лид, `*/20 * * * *`, `chain_check.py HPP-3 --repair`: вставшее звено → `todo` + комментарий, это
  будит исполнителя); инвариант I12. Правило — `ROADMAP.md` п. 21.
- **Ловушка платформы 6 (2026-09-27): PATH в Bash агентов ломает лаунчер GitHub на Windows** (склеивает PATH
  двоеточием через `BASH_ENV`; `bash: command not found`). Локальная правка сервера («HPP-13 hotfix»,
  `execution-target.js`, рядом `.bak-hpp13`) грузится только перезапуском сервера Paperclip — перезапуск обрывает раны
  агентов, поэтому только без `SEALED_RUN.lock` и эмулятора; **обновление пакета `paperclipai` правку сотрёт**. Обход:
  PowerShell или `export PATH=/usr/bin:/mingw64/bin:$PATH` в начале команды Bash. С цепочки с. 123 приёмка шагов —
  стадия `executionPolicy` с лидом, сторож — штатный watchdog `HPP-3` (разбор `HPP-19`, `ROADMAP.md` п. 23).
- **Ловушка платформы 7 (2026-09-27, разбор лида в `HPP-95`): `nvidia-smi` у агентов «сломан» — `Failed to initialize
  NVML: Unknown Error`, а у пользователя в терминале работает.** Причина — окружение агента, не драйвер: Paperclip
  запускает агентов с урезанным окружением без стандартных переменных Windows (`ProgramFiles`, `ProgramW6432`,
  `ProgramData`, `APPDATA`, `LOCALAPPDATA`, `PROCESSOR_ARCHITECTURE`, `OS`, `DriverData`…), а `nvml.dll` без
  `ProgramFiles` (или `ProgramW6432`) не инициализируется. Проверено перебором по одной переменной: `ProgramFiles` —
  работает, `ProgramW6432` — работает, остальные поодиночке — нет; объект задания, токен (сессия 1, средний уровень)
  и выход из задания (`CREATE_BREAKAWAY_FROM_JOB`) ни при чём, Vulkan работает и без неё. **Обход (обязателен в
  каждом харнессе, который зовёт `nvidia-smi`: шлюз простоя, логгер частот `enter_scene.py`):** Bash —
  `export ProgramFiles="${ProgramFiles:-C:\Program Files}"` (так сделано в `C:/kyty/s126/go126a.sh`), PowerShell —
  `$env:ProgramFiles='C:\Program Files'`, Python — `env=dict(os.environ, ProgramFiles=r'C:\Program Files')`.
  **Вывод «`nvidia-smi` на машине сломан» без этой проверки не делать; шлюз `--require-idle` с `UNAVAILABLE` — сначала
  окружение.** Не доказано: влияет ли отсутствие `LOCALAPPDATA`/`APPDATA` на кэши драйвера и эмулятора в прогонах,
  запущенных агентами. Печатать окружение целиком нельзя — в пользовательских переменных машины лежат чужие секреты;
  сравнивать только имена.
- **Агенты не просят у пользователя апрувов (2026-09-26, `ROADMAP.md` п. 16).** Обращения
  `request_confirmation` / `ask_user_questions` / `suggest_tasks` в этой программе не создаются: решения
  принимает лид, специалист пишет вопрос в отчёт шага. Исключение — блокер физического ресурса
  (`blocked`, владелец — пользователь, действие одной строкой; шлюз `procload.py` не смягчать).
  Разрешения инструментов СНЯТЫ и это измерено: у каждого агента с прогонами первая строка сессии
  несёт `permissionMode: approve-all`, инстанс — `local_trusted`, апрувов не заведено; флаг агентским
  ключом не читается и не меняется (`/api/agents/<id>/configuration` — 403), поэтому за агентами без
  прогонов он не подтверждён — догадками не заполнять, сказать одной строкой при первом запросе.
- **Ловушка окружения агентов (2026-09-26): `GIT_AUTHOR_NAME`/`GIT_AUTHOR_EMAIL`/`GIT_COMMITTER_*` заданы ПУСТЫМИ**, а
  `GIT_CONFIG_GLOBAL=/dev/null` — `git commit` падает с `fatal: empty ident name (for <>) not allowed`, и `-c user.name=…`
  НЕ помогает (окружение старше конфига). Перед коммитом в сессии агента выставить все четыре переменные
  (`arigandores` / `<e-mail>`) в том же вызове шелла.
- **Ловушка платформы 8 (2026-09-29, `HPP-142`, `ROADMAP.md` «СЕССИЯ 122» п. 115): третье «Доработать» одного звена
  эскалирует стадию review на доску.** После третьего запроса изменений (`changesRequestedCount` 3) платформа ставит
  `currentParticipant` = пользователь и снимает исполнителя; лид больше не может вернуть звено исполнителю — отказ
  «Only the escalated reviewer can advance the current execution stage». Пользователя не просить (п. 16). Выход —
  новое дочернее звено с тем же заданием и перевод блокеров на него (шаг 1б с. 130); правило лида — третьего
  «Доработать» не выдавать, доработка сверх второй — новым звеном с явными блокерами (п. 115(г)).
- **Ловушка окружения агентов 9 (2026-09-29, с. 130 шаг 1б, аудит `HPP-153`): Python печатает в консоль cp1250.**
  `print` строки с кириллицей (в консоль или через перенаправление в файл) падает `UnicodeEncodeError: 'charmap'
  codec can't encode character`. В с. 130 так упал драйвер мутантов цепочки (часть p7): состояние не записалось,
  вердикты части потеряны, 338 с стены. Запускать Python с `export PYTHONIOENCODING=utf-8` (или писать файлы
  с `encoding='utf-8'`). Та же кодировка портит кириллицу в аргументах командной строки (`curl -d`) — тело JSON
  собирать в Python и передавать через stdin.
- **Ловушка платформы 10 (2026-09-29, с. 133, аудит `HPP-199`): истёкшая сессия OAuth раннера ACP.** Прогон агента падает до первого действия, а платформа пишет в звено комментарий «ACP agent reported a terminal access failure. Failed to authenticate: OAuth session expired and could not be refreshed». Звено остаётся в прежнем статусе и выглядит живым, но работы нет и само оно не просыпается. В с. 133 так упали 8 прогонов в 6 звеньях: `HPP-201` ×3 (14:51:56, 14:52:42, 14:53:39 UTC), `HPP-193`, `HPP-194`, `HPP-195`, `HPP-196`, `HPP-197` — по одному. Работа стояла 14:51–17:03 UTC (2 ч 12 мин), пока лид не повторил задание комментарием в 17:03:05. Признак — строка `terminal access failure` в комментариях звена без отчёта агента после неё. Правило обработки — решение лида (аудит с. 133, «Процесс» п. 1).
- **Ловушка платформы 11 (2026-09-30, с. 136 шаг 5а′ `HPP-245`, аудит `HPP-240`): обёртка `git` Paperclip в PATH.** В PATH прогона агента первой стоит обёртка `…/paperclip-github-runtime/…/git`. Она не передаёт `GIT_AUTHOR_*` и `-c user.*` — `git commit` падает `fatal: empty ident name`; из PowerShell отказывает молча (код возврата пуст, коммита нет). В шаге 5а′ так пропали три попытки коммита (08:52:45, 08:52:52, 08:53:03 UTC); коммит `ae8f30e5` сделан настоящим `C:/Program Files/Git/cmd/git.exe` с теми же `GIT_AUTHOR_*`/`GIT_COMMITTER_*` и `--only` (08:53:21 UTC). Правило: коммит агента — полным путём к `git.exe` (или проверить `command -v git` в том же вызове) и проверить `git log -1` после коммита.
- **Ловушка платформы 12 (2026-10-02, с. 145, `ROADMAP.md` п. 306): монитор стирает стадию review.** Запись `executionPolicy` с полем `monitor` заменяет политику целиком: если в записи нет текущих `stages`, стадия review лида исчезает, и звено закрывается `done` без приёмки. Так потеряли стадию `HPP-377` (2026-10-01T17:21:55Z) и `HPP-352` (19:47:59Z; закрыт 2026-10-02T05:03:41Z без лида). Обратное тоже верно: запись политики не исполнителем без поля `monitor` отклоняется («Only the assignee agent or a board user can manage issue monitors»). Правило: прочитать текущую `executionPolicy`, дописать `monitor`, записать её целиком и в той же команде проверить в ответе API, что `stages` не пуст; лид, восстанавливающий стадию у чужого звена, переносит текущий `monitor` без изменений. Проверка — `chain_check.py` I13.
