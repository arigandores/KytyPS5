## 0. Итог

2. **Это дефект не двух уровней, а всех сцен:** пара «промах страницы X и промах страницы X>>8» стоит в 11 из 12 логов с. 142 и в

   читала настоящих узлов BVH [c по адресам; что это меняет в картинке — [U]].

## 2. Шейдер обхода `380bb9d636390bae` [c по дизассемблеру из лога]

Полный дамп трансляции стоит в `c142_02` (строки 257247–266210; выписка `dump_380b_c142_02.txt`, дизассемблер — `asm_380b.txt`, 1 917
инструкций, `code_words=2824`; CFG: 144 блока, 15 обратных рёбер, после структуризации 182 блока и 9 циклов — совпадает с `loops=9`).

- **Обход скалярный, один на волну:** текущий узел — SGPR (`s42` — верхний уровень, `s32` — нижний), стек — дорожки `v7` через
  `V_WRITELANE_B32` / `V_READLANE_B32` с индексом `s39`, глубина зажата `S_MIN_U32 s39, s39, 60` (8 мест). Бюджет эмулятора — один на вызов (дорожку).
- **Вход:** `s18:s19` = указатель верхнего уровня из пользовательских данных (`S_LOAD_DWORDX2 s18, s0, offset=40`, pc `0x48`); флаг
  `[s18+24] & 0x00040000` → `S_TRAP` (pc `0x100`–`0x104`; в эмуляторе — пустая операция).
- **Дескриптор BVH строит сам шейдер:** `S_BFE_U64 s56, s18, 0x00280008` (pc `0x284`) и `S_BFE_U64 s40, s20, 0x00280008` (pc `0x3c8`) —
  поле с бита 8 шириной 40: **`s40:s41` = `адрес >> 8`**; `S_BITSET1_B32 s57, 31` / `s41, 31` — бит 63 (сортировка рамок);
  `s43 = (size_hi & 0x3ff) | 0x81000000` (pc `0x3c0`–`0x3d0`) — тип 8, `triangle_return_mode` 1. В IR эмулятора:
  `%535 = ShiftRightLogical64 %534, 8`, `%536 = BitwiseAnd64 %535, 0x000000ffffffffff`, `%537`/`%538` — половины, `%543 = %538 | 0x80000000`,
  `%635 = BvhIntersectRay %622, 0, …, %537, %543, %590` (строки лога 260835–260844, 260946).
- **Три вызова `IMAGE_BVH_INTERSECT_RAY`** (pc `0x474`, `0x52c` — нижний уровень, дескриптор `s40`; `0x8f8` — верхний, `s56`), 32-битный
  указатель узла: база берётся только из дескриптора.
- **Циклы и их выходы:** (а) список листьев pc `0x45c`–`0x500`: пары `(s26, s27)` читаются `S_BUFFER_LOAD_DWORDX2 s26, s20, s45 << 3`,
  выход только по `S_CMP_LT_I32 s27, 0` (pc `0x4e4`) — чтение за пределами буфера даёт нули и признака конца не даёт; (б) обход нижнего
  уровня (заголовки pc `0x408`/`0x40c`): типы узла 4–6 → вызов BVH и до трёх записей в стек, иначе путь листьев; выход — пустой стек;
  (в) обход верхнего уровня (pc `0x2c0`/`0x2c4`): то же, лист — запись экземпляра 128 байт (`S_LOAD_DWORDX16 s20, s50`), указатель нижнего
  уровня = поле `<< 3` (pc `0x380`); (г) внешний цикл по лучам. Счётчика шагов нет ни в одном.
- **Память BVH шейдер читает двумя путями:** напрямую по байтовому адресу (`S_LOAD_*`, `S_BUFFER_LOAD_*` с дескриптором буфера, собранным
  из `s20:s21` — pc `0x388`, `0x434`, `0x454`, `0x4f8`) — эти чтения в эмуляторе идут по верному адресу X; и через `IMAGE_BVH_INTERSECT_RAY` — по дескриптору `адрес >> 8`.

**12 остальных BVH-программ — не разобраны [U]:** их дампов трансляции в 12 логах с. 142 нет (`scan12_f3a.out.txt`: с `IMAGE_BVH` в логах
одна программа), каталог `_Shaders` отсутствует. Косвенно [c]: в `eboot.bin` 40 инструкций `S_BFE_U64 …, 0x00280008`, сгруппированных по
две в 20 местах (`bfe2_f3a.out.txt`) — форма «два дескриптора `адрес >> 8` на программу» не единична. Сопоставление этих мест с 13

## 3. Механизм

**3.1. Формат дескриптора — первоисточник.** Драйвер PAL (GPUOpen-Drivers/pal, ветка `dev`, коммит `c5e800072a32f68b6ccc4422936d96167c6e0728`
от 2025-04-29; прочитано 2026-10-01; копии — `src_ext/`):
`src/core/hw/gfxip/gfx9/gfx9Device.cpp:5334` — `bvhSrd.base_address = gpuVirtAddr >> 8;` (выше, :5332, — `PAL_ASSERT((gpuVirtAddr & 0xFF) == 0);`);
`src/core/hw/gfxip/gfx9/chip/gfx10_sq_ko_reg.h:99–111` — `union sq_bvh_rsrc_t`: `base_address : 40`, пропуск 15, `box_grow_value : 8`,
`box_sort_en : 1`, `size : 42`, пропуск 14, `triangle_return_mode : 1`, `llc_noalloc : 2`, `big_page : 1`, `type : 4`.
URL: `https://raw.githubusercontent.com/GPUOpen-Drivers/pal/c5e800072a32f68b6ccc4422936d96167c6e0728/src/core/hw/gfxip/gfx9/gfx9Device.cpp`,
`…/src/core/hw/gfxip/gfx9/chip/gfx10_sq_ko_reg.h`. Игра строит дескриптор тем же способом (§2) — два независимых свидетельства, что база хранится в единицах по 256 байт.

**3.2. Эмулятор [c по коду].** Оба пути трансляции берут базу без сдвига:
@@REF:native_base@@ и @@REF:native_add@@ (путь по умолчанию, один опкод `BvhIntersectRay`);
@@REF:ir_base@@ (путь `KYTY_BVH_NATIVE=0`). Комментарий @@REF:ir_comment@@ описывает поле как «`dword0 = base_address[31:0]`,
`dword1[15:0] = base_address[47:32]`» — байтовый адрес 48 бит; по первоисточнику это 40 бит в единицах по 256 байт. Итог: адрес узла =
`(адрес BVH >> 8) + (указатель узла & ~7) × 8` вместо `адрес BVH + (указатель узла & ~7) × 8`.

**3.3. Подтверждение логами [c].** Страница кэша — 16 КиБ (@@REF:pagebits@@). Корень обхода — узел 37 (смещение `(37 & ~7) × 8 = 0x100`).
Для `voxel_world` X1 = `0x401bc0000`: `(X1 >> 8) + 0x100 = 0x401bd00` → страница `0x4018000` — ровно второй промах той же строки отсчёта
(строки 206302–206303 `c142_09`). Для Sky Garden X1 = `0x401c3c000`: `0x401c3c0 + 0x100 = 0x401c4c0` → страница `0x401c000` — она и стоит в
паре (285 логов). Для второго BVH X2 = `0x40253c000` / `0x4024c0000` / `0x4024d4000` / `0x402478000` / `0x402518000` / `0x4024e4000` →
всегда `0x4024000`. Пары в логах с. 142 (`scan12_f3a.out.txt`): 11 из 12 логов содержат хотя бы одну пару, 12-й (`c142_03`) — страницу
`0x4018000` без пары (страница X уже была в кэше). Образ игры загружен с `0x900000000` (`base_vaddr`, строка 714 `c142_09`), гостевых
отображений в диапазоне `0x4000000`…`0x4ffffff` в логе нет — это память процесса эмулятора; на промах хост создаёт буфер и копирует её как есть
(@@REF:fault_find@@, @@REF:memcpy@@).

**3.4. Цепочка.** (1) игра кладёт в дескриптор `адрес >> 8` [c]; (2) эмулятор читает узел по `(адрес >> 8) + смещение` [c]; (3) до
кэширования страницы чтение даёт нули, обход кончается сразу [c по коду нулевой страницы: @@REF:nullpage@@; срабатываний до окна 0 из 24];
(4) после кэширования «узлы» — чужие байты: поля детей и рамки случайны [c для адреса, [U] для содержимого]; (5) случайный «ребёнок» типа
0–3/7 уводит в цикл списка листьев (выход только по знаку слова, чтение мимо буфера — нули), ребёнок типа 4–5 — в цикл стека (глубина
зажата 60, выхода при цикле в «дереве» нет) — какой из двух сработал, [U]; (6) бюджет 65 536 исчерпан, диспатч целиком работает до
предела [c]; (7) в 7 из 24 логов в окне есть промахи на других низких страницах (`0x7c000`, `0x78000`, `0x74000`, `0x8070000`, `0x8074000`,
`0x55d8000`, `0x55dc000`, `0x4e64000`, `0x4e68000`) — обход шёл по случайным указателям дальше [c]; (8) игра переходит на второй BVH — окно закрывается [c].

**3.5. Источник данных BVH.** Эмулятор BVH не строит: в `src/` опкод `BvhIntersectRay` только читает память (@@REF:uses_dma@@), построителя нет
(поиск `BvhIntersectRay|BVH_NATIVE|BVH_STUB|bvh_base|BvhNode` — 11 мест, все — трансляция чтения). Данные — память гостя: верхний уровень по
указателю из пользовательских данных шейдера, нижние — по полю записи экземпляра [c по дизассемблеру]. Кто пишет эту память (ЦП игры или её
вычислительные шейдеры) — [U]; недостающее данное — производители диапазона X1 (`KYTY_DUMP_ADDR=<X1>`), для правки не требуется.

**3.6. Место ограничителя [c].** @@REF:cap_default@@ — предел 65 536 и набор из одной программы; @@REF:guard_cmp@@ — сравнение `next > limit`
в заголовке каждого цикла; @@REF:guard_abort@@ — выход через счётчик срабатываний и обычный хвост возврата; @@REF:trip_emit@@ — три
атомарных слова в хвосте буфера промахов; @@REF:trip_log@@ — печать (не больше 64 строк на процесс). Ограничитель работает как задумано;
он ограничивает последствие, а не причину. Остальные 12 BVH-программ не ограничены (набор по умолчанию — один хэш).

**3.7. Конкурирующее объяснение, которое этими данными не различается.** «Первый BVH игры на входе уровня не готов или не синхронизирован
с ГП» (вывод с. 103, снят аудитом). Пока узлы читаются не из BVH, состояние настоящего BVH на исход не влияет вовсе; проверить его можно

  снимает диспатч на стороне хоста, трансляцию не трогает (@@REF:skipcs@@). **`KYTY_BVH_STUB=1` не применять:** читается при трансляции
  (@@REF:stub@@), в подпись кэша не входит — при включённом кэше не действует на готовые шейдеры и засоряет кэш новыми. **`KYTY_BVH_LOOP_CAP`
  с иным значением не применять:** меняет подпись и каталог кэша (@@REF:cap_token@@) — вход станет холодным. `KYTY_DUMP_CS_READBACK`,
  `KYTY_DUMP_CS_REUPLOAD` — не нужны (у программы нет записываемых привязок с данными BVH).
- **Цена.** Вызов тега в с. 142 — 3 мин 35 с от вызова до возврата (`c142_02`: 22:46:03Z → 22:49:38Z, `C:/kyty/s142/step2/times.txt`);

  база В4) — ≈ 8–10 мин.

  (предсказание [I]: пары в 6 из 6 тегов; срабатывание на `f3d_01`/`f3d_02` — P ≈ 0,6 на тег), дефект адреса есть при любом исходе.
