# Сессия 52 (коммит кода 0abc1be) — memo материализации SRT измерено и отклонено; найдено переполнение стека на входе в уровень

## 1. Результат одной строкой

**60 FPS нет.** Главная запланированная оптимизация — memo материализации SRT — **измерена и
проиграла**: в Sky Garden 89 % draw'ов материализуют уникальный ключ, попаданий 10,9 %, CPU на draw
**12,74 → 14,34 мкс**, FPS **15,23 → 13,51**. Опция оставлена, **по умолчанию выключена**.
Побочно найдено и исправлено настоящее: `ProgramCache::Get` резервирует **66 КБ стека**, и просмотр
PM4 при submit звал его **на гостевом потоке** — вход в уровень падал с access violation 2 раза из 2.

## 2. Падение входа в уровень (новое, исправлено обходом)

Два прогона подряд (`sky1`, `sky2`) умерли с `0xC0000005` сразу после
`LevelDocument Loaded: intro_next`, при потоковой загрузке ассетов уровня. Отладчик
(`scripts/s21_dbg.py`, лог `dbg1.txt`) дал:

```
SECOND-CHANCE code=0xc0000005 rip=...+0x7f3c5b kyty_emulator.exe  addr=0x33bae2618 access=1(write)
rsp=0x33bae2620 rbp=0x33bae26a0
```

- `rip` — `PipelineCache::ProgramCache::Get<ShaderComputeInputInfo>` **сразу после пролога**;
  падает запись адреса возврата по `rsp-8` первого же `call` — стек кончился ровно под кадром.
- Пролог: `mov eax, 0x103d8 ; call __chkstk ; sub rsp, rax` — **кадр 66 520 байт**.
- `addr` лежит не в стеке хостового потока Windows (иначе была бы `0xC00000FD`), а в области
  гостевой памяти: это стек **гостевого потока/фибера**, фиксированный и без авторасширения.

Кто зовёт `Get<Compute>` с гостевого потока: `KYTY_ASYNC_COMPUTE=1` (прежний default) делает
просмотр PM4 **в `GuestGpu::Enqueue`**, то есть на потоке, который вызвал submit — на гостевом.

**Что сделано:**
1. `KYTY_ASYNC_COMPUTE` по умолчанию **2** — тот же префетч, но при старте обработки, на потоке
   GuestGpu (его стек — эмуляторный). `=1` возвращает прежнее поведение и воспроизводит падение.
   Это обход, а не устранение: кадр остался большим.
2. Холодная половина `Get` (трансляция шейдера, добавление пермутации) вынесена в отдельную
   `Compile<InputInfo>` с `[[gnu::noinline]]`, вспомогательные функции memo — тоже noinline.
   Кадр `Get<Compute>`: **69 320 (база s51) → 69 368 (с memo) → 66 520**. То есть итог на
   **2 800 байт меньше базы сессии 51**; `Compile` — 3 912 байт.

**Что осталось открытым (первый пункт следующей сессии):** оставшиеся ~66 КБ. Замеры:
- без LTO кадр этой функции **< 8 КБ** (компиляция TU с `-Wframe-larger-than=8192` молчит) —
  значит его создаёт межмодульное встраивание ThinLTO;
- `[[gnu::noinline]]` на `MaterializeResources` и `LoadFromTranslationCache` кадр **не изменил**
  (и RVA не сдвинулся — эти функции и так не встраивались);
- дизассемблер (`llvm-objdump`, `get_disasm.txt`) показывает, что код обращается только к
  `rbp-48…rbp+0x2c00` и к `rbp+0xffd0…rbp+0x10340`: **дыра ~53 КБ между ними не адресуется ни одной
  инструкцией** — это зарезервированная, но не используемая alloca;
- `GetGraphicsPrograms` имеет такой же кадр 66 632 байта, то есть источник общий;
- `lld-link` этой версии **не поддерживает** `-warn-stack-size` и `-pass-remarks-analysis=
  stack-frame-layout`, поэтому назвать конкретную alloca ремарками LLVM не удалось.

Инструменты для продолжения: `C:/kyty/s52/frame_size.py` (кадр по прологу и .map),
`C:/kyty/s52/big_frames.py` (топ кадров всего бинаря).

## 5. Почему memo не работает (главный вывод сессии)

Счётчики на кадр (медианы фазы `memo_a`):

```
smemo_hit=970  smemo_miss=7877  smemo_stale=78  smemo_skip=0  smemo_reads=11040
```

- Обращений к memo ~8 900 на кадр (это и есть число материализаций: 2 стадии × ~4 800 draw).
- Попаданий ровно ~970 и это число **не меняется от фазы к фазе**: в кадре есть постоянный набор
  примерно из 970 материализаций с повторяющимся ключом, всё остальное уникально.
- **`stale` всего 0,9 %**: когда ключ найден, записанные слова гостевой памяти почти всегда ещё
  совпадают — то есть свидетель годности работает, узкое место не в нём.
- Проверка дёшева: 11 040 слов на ~1 048 сверок ≈ 10,6 слова, и они сравниваются
  сериями через `memcmp`.

**Ключ `(ResourcePlan, user_data, shader_base)` уникален у 89 % draw'ов** — игра кладёт в user data
указатель на пообъектные данные. Потолок memo здесь ~11 % от `p_mat`, то есть ~1,8 мс из 65 мс, а
платит он записью и сохранением результата на каждом из ~7 900 промахов. **Кэшировать
материализацию бессмысленно; дешевле делать саму материализацию.**

Правильность при этом подтверждена: фаза `check` прогнала настоящий обход SRT рядом с каждым
попаданием memo — **0 расхождений** (плюс 0 расхождений за два прогона интро по 150 и 130 с).

## 7. Код

1. `src/common/gates.{h,cpp}` — гейты `regionepoch` (`KYTY_REGION_EPOCH`), `srtmemo`
   (`KYTY_SRT_MEMO`), `smemocheck` (`KYTY_SRT_MEMO_VERIFY`); все три по умолчанию **0**.
2. `RegionManager` получил собственную эпоху записи (`Epoch()`, инкремент рядом с глобальной в
   `ChangeState<Cpu,true>`); `MemoryTracker::RangeWriteEpoch(vaddr,size)` смешивает эпохи регионов
   диапазона и возвращает 0, если хоть один регион не отслеживается.
3. `BufferCache::UploadEpoch` выбирает между глобальной эпохой и поранговой по гейту;
   `Buffer::upload_epoch_kind` не даёт сравнивать числа из разных «часов», `HasCurrentUpload`
   отвергает нулевую эпоху. Счётчик `bufepoch` — попадания быстрого пути.
4. `pipelineCache.cpp`: `SrtReadLog` (запись всех чтений гостевой памяти материализации),
   `LiveBackingPage`/`CleanBackingPage` (общие для чтений и для сверки), memo на 16 384 слота с
   ключом `(SourceEntry*, shader_base, user_data)` и свидетелем в виде записанных слов, сжатых в
   серии подряд идущих dword'ов одной страницы; `MemoCheck` — самопроверка настоящим обходом.
5. `Compile<InputInfo>` — вынесенная холодная половина `Get` (см. §2).
6. `KYTY_ASYNC_COMPUTE` по умолчанию 2 (см. §2).
7. Счётчики `FrameTrace-draw`: `smemo_hit`, `smemo_miss`, `smemo_stale`, `smemo_skip`,
   `smemo_reads`, `bufepoch`.

## 9. Сорванная сборочная конфигурация (важно знать)

При попытке добавить `/mllvm:-warn-stack-size` я запустил `cmake -S .` в каталоге сборки и обнулил
в `C:/kyty/build/CMakeCache.txt` **все** записи `CMAKE_*_FLAGS*` (сборка ломалась на xbyak:
«cannot use 'throw' with exceptions disabled»). Восстановлено: эталонная конфигурация собрана в
`C:/kyty/s52/scratchbuild` тем же `build_local.cmd configure`, значения флагов перенесены
скриптом `C:/kyty/s52/repair_cache.py`; сверка нефлаговых записей показала только различия путей.
Сборка снова Release + ThinLTO, размеры кадров совпали с замером до поломки.
**Правило на будущее: не запускать `cmake` в `C:/kyty/build` иначе как через `build_local.cmd`.**

## 11. Куда дальше

0. **Сжать кадр `ProgramCache::Get` (66 КБ).** Пока он такой, любой вызов с гостевого потока
   опасен, а `KYTY_ASYNC_COMPUTE=1` нельзя вернуть. Метод: см. §2; дыра 53 КБ не адресуется, значит
   искать надо alloca, чьи обращения свернулись. Следующий шаг — собрать без ThinLTO и сравнить
   дизассемблер, либо поднять версию lld ради `-pass-remarks-analysis=stack-frame-layout`.
1. **Материализация: делать дешевле, а не кэшировать** (§5). Цели по счётчикам кадра:
   `p_reads` 423 тыс. и `p_creads` 58 тыс. на ~8,9 тыс. материализаций — это ~48 + 6,6 чтений на
   каждую. Смотреть `EvaluateCompiled` (`SrtWalker.cpp:2120`): он считает **все** узлы и только
   потом достижимость, то есть оплачивает чтения заведомо неактивных источников.
2. **Кэш разрешённых привязок** (пункт 3 плана этой сессии, не начат): `b_texn` ≈ 50 тыс.
   `ResolveTexture` и столько же `FindTexture` на кадр; memo текстур попадает в 94 % случаев, но
   всё равно идёт второй заход в `TextureCache` под спин-локом с `TrackImage`/`RefreshImage`.
3. **Переиспользование descriptor set** (пункт 4, не начат): блокер — новые смещения stream-ring
   на каждый draw (`descriptors.cpp:929-937`).
4. GPU ~22 мс — отдельная ветка, нужен захват RenderDoc (F1 пользователем).
