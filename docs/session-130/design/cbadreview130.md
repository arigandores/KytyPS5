## 1. Главная задача: потеря при `armcopy` ∈ {1, 2} → E — попытки и почему каждая не удалась

бит CPU-грязи не стоял в T_d (§2.4 проекта; верно по коду: `ChangeState<Cpu, true>` ставит бит до `UpdateProtection`,
`regionManager.h:185–215`; `ArmCopyContent` читает бит после `memcmp` через `acquire`-забор, `bufferCache.cpp:290–295`).

## 2. Требуемые изменения

### RC1 — MAJOR: причины `remark` (R5), `new` (R6), `pend` (R7) меряют время чужих пометок, которое плечо меняет по построению; M₂ получает их без противовеса при 4 ⇒ ложный `CBAD_LOSS` при чистой Н2

**Что не так.** По самому доказательству проекта (§3.2 С1/С3, последний абзац §3.3) потеря, вызванная куском K, видна
только в R1–R4 (+ R8 через X2/X3). R5/R6/R7 — страница, чью `pending` поставила ДРУГАЯ операция O2 после взятия/после J/после
T_a: копия O2 идёт после её вооружения, поэтому событие K на такой странице — не потеря K (потеря — только дефект O2, X1).
Частота же этих причин определяется временем жизни чужой `pending`, а его плечо меняет по замыслу (это и есть Н2 п. 116(г)):

1. **R4/R5 при 4 ≡ 0, R6 при 4 ≈ 0 по построению.** При 4 кусок ничего не берёт (T = ∅ ⇒ R4 = R5 = 0), а снимок J и S_a — две
   соседние хватки `lock` без работы между ними (`:1488–1518`, при 4 ветки 2/3 пусты) ⇒ окно для пометки R6 — наносекунды.
   При 2 между J и S_a — цикл взятий с `Protect` (вызовы ядра, десятки–сотни мкс): пометки GuestGpu, пришедшие в это окно, — R5
   (на взятой странице) или R6. Противовеса при 4 у них нет.
2. **R7: чужое отложенное живёт при 2 дольше.** При 4 (путь 0) операция O2 применяет СВОИ отложенные на GuestGpu до
   `upload_func` (`batch.Flush()` + `FlushProtection`, `memoryTracker.h:350–362`) — через микросекунды после пометки. При 2 O2
   делает `Handover` (`:348–349`): страница пуловой копии остаётся `pending`, пока её не применит кусок O2, стоящий в FIFO
   ПОЗАДИ кусков более ранних операций (`parallelCopy.cpp:96–99`), в том числе позади самого K.

**Сценарий отказа (Н2, потерь нет).** Гость пишет W0 в p (фолт → p записываема, грязна). GuestGpu в плече 2 синхронизирует
буфер: O2 снимает бит p, ставит `pending`, `Handover`, уходит вперёд (быстрее, чем при 4 — это Н2). Гость пишет W в p без фолта
в окне (T_cp, T_cmp) куска K более ранней операции ⇒ событие K (p чиста в T_d). В T_k (микросекунды спустя) кусок O2 ещё в
очереди ⇒ `Pk` ⇒ R7 ⇒ **M**. W скопирует кусок O2 — потери нет. В плече 4 та же последовательность: O2 применяет p до своего
`upload_func` ⇒ к T_k чаще ¬`Pk`, хост только чтение ⇒ **E**. Одинаковое по физике безвредное событие — M при 2, E при 4.
Числа: на пустыне общая доля `ac_cbad` плеча 2 к плечу 4 — 0,98 (`s2s130`), `ac_jleft` при 4 — 232. Если доля M среди событий
при 2 (R5+R6+R7+R8) f₂ = 0,16, а при 4 (весь M₄, включая `left`) f₄ = 0,10, то M₂/M₄ = 0,98 · 1,6 = 1,57 > 1,5 ⇒ **`CBAD_LOSS`
⇒ `ARMCOPY_INCORRECT`, шаги 7–8 отменены** — на сцене, где избытка срабатываний нет вовсе. Меньшая разница f₂/f₄ уводит в
полосу п. 117(б) ⇒ `NOT_RESOLVED` (M₂/M₄′ > 1,5 при M₂/M₄ ≤ 1,5). Знак смещения по R7 — к M₂ [I]; обратного механизма (R7 при
4 длиннее) я не нашёл, но чужие `pending` при 4 в окнах кусков многочисленны (`ac_jleft` 2 160 на опоре), так что вклад R7₄ —
[U]. Поправка п. 117(б) убирает смещение `left` к `CBAD_EXTERNAL`, но не это — противоположного знака.

**Ответ на п. 117(з) («не делает ли поправка (б) проход невозможным, M₄′ ≡ 0»).** Не ≡ 0 по построению: M₄′ = R1 + R2 + R6 +
R7 + R8 при 4, где R1/R2 ожидаются 0, R4/R5 ≡ 0, R6 ≈ 0 ⇒ **M₄′ ≈ R7₄ + R8₄** — только причины S_k. M₂ при стражах §6.3
(R1 = R2 = R4 = 0) и R3₂ ≡ 0 на верном коде (П1) ⇒ **M₂ = R5₂ + R6₂ + R7₂ + R8₂**. Значит, правило (е)(2)/(3) в нынешнем виде
сравнивает (R5 + R6 + R7 + R8)₂ с (R7 + R8)₄: в числителе две причины без противовеса и R7 с более долгой жизнью. Проход
возможен, но смещён к `CBAD_LOSS`/`NOT_RESOLVED` не данными, а построением; и ни одна из причин, дающих M₂, по лемме проекта не
является потерей самим K.

### RC3 — MINOR: И4 «построчно» при И0 не следует; приём И0 держит только равенства
