### 0.2 Договор SDL2 о потоках [c заголовков и исходника]

1. **Насос видео — только на потоке, который инициализировал видео:** «**WARNING**: This should only be run in the thread that initialized the video subsystem» (`4b69833b:include/SDL_events.h:716`). Перенести `SDL_PumpEvents` / `SDL_WaitEvent` с главного потока нельзя — это и окно, и клавиатура, и мышь (`4b69833b:src/video/windows/SDL_windowsevents.c:1953` — `PeekMessage(&msg, NULL, …)` всех окон потока).
2. **Обновление джойстиков отделяется от насоса договором:** подсказка `SDL_HINT_AUTO_UPDATE_JOYSTICKS` — «"0": You'll call SDL_JoystickUpdate() manually» (`4b69833b:include/SDL_hints.h:327`), «can be toggled on and off at runtime» (`:332`). При `0` насос не зовёт `SDL_JoystickUpdate` (`4b69833b:src/events/SDL_events.c:922`) и не трогает замок ради интервала опроса: условие `SDL_WasInit(SDL_INIT_JOYSTICK) && SDL_update_joysticks` (`:967`) стоит раньше `SDL_NumJoysticks()` (`:968`), а та берёт замок (`4b69833b:src/joystick/SDL_joystick.c:666`). Поток вызова `SDL_JoystickUpdate` документ не ограничивает (`4b69833b:include/SDL_joystick.h:792`).
3. **Многопоточный доступ к API джойстиков разрешён замком:** «Locking for multi-threaded access to the joystick API … If you are using the joystick API or handling events from multiple threads you should use these locking functions» (`4b69833b:include/SDL_joystick.h:132`, `:134`); под замком «joystick and game controller events will not be delivered» (`:139`). Каждая функция джойстиков / пультов берёт этот замок сама (`4b69833b:src/joystick/SDL_joystick.c:2177`, `4b69833b:src/joystick/SDL_gamecontroller.c:2853`, `:3034`) — поток `PadOutput` (F19c) уже зовёт SDL не с главного потока (`730ed40a:src/libs/controller.cpp:346`).
4. **События, поставленные другим потоком, будят ждущий насос:** постановка события зовёт `SDL_SendWakeupEvent` (`4b69833b:src/events/SDL_events.c:846`), который в Windows — `PostMessage` окну (`4b69833b:src/video/windows/SDL_windowsevents.c:1939`), а ожидание — `MsgWaitForMultipleObjects(…, QS_ALLINPUT)` (`:1895`).

**Инвариант правки:** при `=1` после инициализации главный поток не исполняет ни одного вызова API джойстиков / пультов SDL из кода эмулятора, кроме стенда `KYTY_TEST_HIDLOSS` (присоединение / отсоединение виртуального пульта и режим `hold` — это стенд); при `=0` — путь прежний байт в байт.

**Что меняется для игрока при `=1`:** при обычной работе — ничего видимого (опрос пульта 1 мс, как у насоса SDL; событие от `JoyPump` будит главный поток сообщением окна — `4b69833b:src/events/SDL_events.c:846`, `4b69833b:src/video/windows/SDL_windowsevents.c:1939`); подключение без открытых джойстиков обнаруживается с задержкой до `JP_IDLE_MS`. При блокировке вызова ОС под замком — окно, клавиатура и мышь живы, ввод пульта стоит (§0.3).

**Риски — для враждебного отзыва F39b.**

- **Р1 [I] COM-квартира DirectInput:** объект создан на главном потоке (`4b69833b:src/joystick/windows/SDL_dinputjoystick.c:409`, `:416`), `JoyPump` зовёт его методы (`:555`, опрос открытых устройств DirectInput) без маршалинга. `ThreadingModel = Both` [c реестра машины]; формальное правило COM этим не снимается. Пульт DualSense идёт через HIDAPI, не DirectInput; DirectInput на этом хосте исполняет только перечисление по флагу изменений.
- **Р2 [I]** уровень кооперации DirectInput при открытии устройства берёт вспомогательное окно главного потока (`4b69833b:src/SDL.c:230`), а открытие при `=1` идёт на `JoyPump`.
- **Р3** глобальные счётчик и флаг обнаружения читаются без барьера с другого потока — так SDL устроен и сейчас (обратный вызов `CM_Register_Notification` приходит с пула потоков ОС, `4b69833b:src/joystick/windows/SDL_windowsjoystick.c:177`).
- **Р4** RAWINPUT при ручной подсказке `SDL_JOYSTICK_RAWINPUT=1` (по умолчанию выключен, `4b69833b:src/joystick/windows/SDL_rawinputjoystick.c:1030`) раздаёт `WM_INPUT` на главном потоке — вне пути по умолчанию, [U].
- **Р5** задержка обнаружения при `JP_IDLE_MS` — константу решает лид.

**Вариант Б (не предлагается в итерацию 1; на случай, если F39b признает Р1/Р2 неприемлемыми):** `SDL_InitSubSystem(SDL_INIT_GAMECONTROLLER)` исполняет сам `JoyPump` (главный поток ждёт окончания), `JoyPump` раздаёт сообщения своих окон (`PeekMessage` / `DispatchMessage` своего потока — это не `SDL_PumpEvents`). Объект DirectInput, окно обнаружения HIDAPI и вспомогательное окно тогда живут в квартире и потоке `JoyPump` — Р1 и Р2 снимаются; цена — инициализация SDL разнесена по двум потокам (последовательно) и `JoyPump` обязан разбирать свои сообщения [I].

**Отвергнуто:** `SDL_HINT_DIRECTINPUT_ENABLED=0` — снимает только перечисление DirectInput, не HID, и меняет набор видимых устройств; `SDL_HINT_JOYSTICK_THREAD` — переносит только окно уведомлений (§0.2).

**Цена при `=1`:** поток, который при открытом пульте просыпается раз в 1 мс, — та же работа, что делал насос главного потока (переезд, не добавка); без пульта — раз в `JP_IDLE_MS`. При `=0` — одна проверка статического флага в `WindowCreate` и `GameEventController`.

## 2. Мера видимого следствия (RC15 F32b): стенд `KYTY_TEST_HIDLOSS=<с>:upd`

**Почему не `hold`.** Режим `hold` держит замок задачей главного потока (`730ed40a:src/graphics/presentation/window/window.cpp:1199`…`:1201`) — при любом значении `KYTY_FIX_F24` он останавливает главный поток сам, поэтому правку не различает (RC15: контроль пути, не причины). Ввод сценария `KYTY_KEYS` тоже не годится — он идёт с потока показа мимо главного потока (`730ed40a:src/graphics/presentation/window/inputScript.cpp:197`).

**Режим `upd` (новый, только стенд, умолчание стенда — выключен).** Виртуальный пульт стенда (присоединяется как сейчас, `730ed40a:src/graphics/presentation/window/window.cpp:1172`) получает обратный вызов `Update` описателя (`4b69833b:include/SDL_joystick.h:402`). SDL зовёт его из `Update` драйвера внутри `SDL_JoystickUpdate` под замком джойстиков (`4b69833b:src/joystick/virtual/SDL_virtualjoystick.c:547`, `4b69833b:src/joystick/SDL_joystick.c:2193`) — на том потоке, который обновляет джойстики: при `=0` — главный (насос), при `=1` — `JoyPump`. В момент `fire` поток стенда поднимает атомарный флаг (не задачей главного потока: при `=1` главный поток не обновляет джойстики); первый вызов `Update` после флага спит `HOLD_UPD_MS` и записывает свой поток и стену сна. Это модель «вызов ОС внутри `SDL_JoystickUpdate` ждёт под замком» тем же путём, теми же замком и потоком, что настоящий; причина (умирающее Bluetooth-устройство) не воспроизводится. `HOLD_UPD_MS` — предложение 8 000 мс: длиннее порога «не отвечает» ОС (≈ 5 с [I]), иначе член окна недостижим.

**Проба доставки ввода.** Поток стенда каждые `IN_MS` = 100 мс в окне [`fire` − 1 с; `done` + 2 с] ставит окну SDL (`HWND` берёт главный поток при присоединении пульта через `SDL_GetWindowWMInfo`, `4b69833b:include/SDL_syswm.h:374`) пару `PostMessage(WM_KEYDOWN / WM_KEYUP, VK_F13)` со скан-кодом `0x64` и запоминает время постановки (кольцо по номеру). Сообщение идёт путём настоящей клавиатуры: насос главного потока (`4b69833b:src/video/windows/SDL_windowsevents.c:1953`) → `WM_KEYDOWN` (`:1074`; `VK_F13` → `SDL_SCANCODE_F13` — `:170`) → `SDL_SendKeyboardKey` (`:1094`; проверки фокуса нет — `4b69833b:src/events/SDL_keyboard.c:846` и ниже) → очередь → `ProcessEvent` (`730ed40a:src/graphics/presentation/window/window.cpp:554`). При включённом стенде `ProcessEvent` перехватывает `SDLK_F13` первым (до `F7`, `:559`, и до `HostInputKey`) — гостю клавиша не доходит; `k`-е увиденное нажатие сопоставляется с `k`-й постановкой (очередь сообщений потока — по порядку).

**Окно «не отвечает».** Поток стенда каждые `PROBE_MS` = 20 мс в том же окне зовёт `IsHungAppWindow(HWND)`; сумма — `hung_ms`.

**Строка** `TestHidLoss: f24 mode=upd fix=<0|1> …` (одна, задачей главного потока через 2 с после `done`, как строка `stat` — `730ed40a:src/graphics/presentation/window/window.cpp:1219`; счётчики — `std::atomic<uint64_t>` `relaxed`; записей в состояние гостя нет; в `FrameTrace-x` не входят):
