## 2. Что делает правка (решения — `names_before_code.md` §4, без изменений)

- `KYTY_M_T125` (умолчание 0), `MT125On()` — один раз на процесс, строка `MT125: mode=<0|1>`.
- При `=1`: `AudioOut2ContextCreate` с `max_object_ports > 0` открывает одно устройство смеси на контекст (MAIN,
  стерео float, 48 кГц, `num_grains` кадров) через `AudioInternal::AudioOutOpen` → `OpenSdlDevice` →
  `SdlAudioSubsystemInit` → владелец Ф8 `SdlAudioAcquire`; на каждом выводе контекста объекты (`port_type 0x100`,
  48 кГц, моно float / моно s16, PCM задан) смешиваются с `GAIN` (id 1) и стерео-декодом `AMBISONICS` (id 8) по форме
  upstream `audioout2_mix_object`; смесь — последний параметр `AudioOutOutputs`.
- Порты шин при `=1` — отбор, порядок, указатели и вызов `AudioOutOutputs` MS1 (строки отбора скопированы без
  изменений в `audioout2_m125_queue_context_audio`); `GAIN` им не применяется.
- `313b60e92` не взят (D1), заморозки атрибутов нет (D5), коды возврата игре не меняются (D2).
- `MT125Stat: when=exit mixed=<n> mixed_nz=<n>` — обработчик `std::at_quick_exit`, ставится в `MT125On()` при `=1`.
- В `main` (и в MS2) при `=1` счётчики M6a `KYTY_DIAG_M5W2` в выводе контекста не исполняются (вывод идёт путём T125) —
  справка для чтения тегов с обеими ручками.

## 4. Стенд — члены (г)(2)(i), (iii)

`tests/MT125Stand.cpp` + настоящий `libAudio2.cpp`; слой устройств подменён (запоминает каждое открытое устройство и
копирует байты каждого вывода). Драйвер `run_stand_m8a.py` запускает два процесса (`KYTY_M_T125=0`, `=1`).

Сцена A: контекст `max_object_ports` 8; 4 порта шин (типы 0, 1, 3, 6; стерео float; синусы 110/165/247/370 Гц, правый
канал = −левый); N = 4 объекта в смеси (моно float 220/330/440 Гц с `GAIN` 0,25 / 0,5 / 1,0 и моно s16 550 Гц с `GAIN`
0,75); объекты, которые в смесь идти не должны: `0x100` со стерео float, `0x100` 44,1 кГц, тип `0x101`, `0x100` без PCM;
второй контекст B со своим объектом. 4 вывода.

- `=0`: на каждом выводе 4 параметра, все — буферы PCM шин в порядке создания; ни одного вывода на устройство смеси;
  устройство смеси не открыто; контекст B — 0 выводов (**отказ воспроизведён**: объектный PCM в выводе 0).
- `=1`: устройство смеси открыто одно (тип 0, стерео float, 48 кГц, 512); 5 параметров на вывод, первые 4 — буферы шин,
  5-й — смесь, max |смесь − Σ gᵢ·½√2·xᵢ| ≤ 1e-6; B — только свой объект (½√2·1,0); после `ContextDestroy` живых
  устройств 0.
- Драйвер: 16 файлов выводов шин `=1` равны файлам `=0` **байт в байт** (`bus_byte_for_byte` 16 из 16); файлы смеси только
  при `=1`.
- Кейсы `TestObjectGainAndAmbisonics` upstream (float `0x100` и s16 `0x101`): таблица `AMBISONICS` {MAX, 0, 1, 2, 3, 64, 65,
  66, 99} × `GAIN` 0,5, по 2 вывода (без накопления), нулевой `GAIN` глушит, `GAIN` держится, плюс неверные `GAIN`
  (−1, NaN, 8 байт) и `AMBISONICS` (16, 100) не применяются при коде `OK`. При `=0` — 0 выводов.
- Строки: `MT125: mode=0` / `MT125: mode=1` ровно по одной; при `=0` строки `MT125Stat` нет; при `=1`
  `MT125Stat: when=exit mixed=47 mixed_nz=27` = строке `EXPECT` стенда.

Не воспроизводятся (названо до кода, D1, D5): блок теста upstream «владение PCM / заморозка атрибутов» и коды отказа
upstream (`INVALID_PARAM`, `OUT_OF_RESOURCE`, `INVALID_PORT`).

## 7. Не заявляется

Что смесь слышна или равна консоли (эталон — тест upstream, [I] о консоли); что игра задаёт `max_object_ports > 0`
(иначе устройства смеси нет и `mixed_nz` в игре 0 — это покажет член (г)(2)(v)); что чтение PCM объекта по указателю в
момент Push безопасно на любом адресе (M6c: `ao_obj_unread` 0 из 2 014 739; при недействительном указателе — падение
при `=1` [I], тот же класс, что у портов шин); частота `ContextAdvance` в игре [U]; что `GAIN` шин не нужен игре;
скорость (G5 — звено M3a2); 60 FPS не обещаются.
