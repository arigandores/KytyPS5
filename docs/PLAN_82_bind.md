## 2. ВЕРДИКТ: НАПРАВЛЕНИЕ БИНД-МЕМО

### 2.1 Что показывает `bindkey`

Код прочитан лично (`descriptors.cpp:1331-1361` и `:1372-1382`):

```
1374  thread_local std::array<uint64_t, 16> previous_key {};
1375  const auto slot = static_cast<uint32_t>(program.stage) % previous_key.size();
1376  prepared.key     = BindingInputKey(program, snapshot);
1377  prepared.key_hit = (previous_key[slot] != 0 && previous_key[slot] == prepared.key);
```

`ShaderType` имеет 9 значений (`shader.h:38-48`), все < 16, поэтому `% 16` не алиасит — **индексация верна, проблема в ШИРИНЕ таблицы (1)**. Хэш — FNV-1a **побайтно**, восемь последовательно зависимых `imul` на каждый dword (`:1338-1342`), по ~130 тыс. дескрипторных значений на кадр.

### 2.2 ВЕРДИКТ

**Мемо на уровне ЦЕЛОГО ЭТАПА — НЕ УСТАНОВЛЕНО НИ ЖИВЫМ, НИ МЁРТВЫМ. Установлено другое: цифра 5,9 % не поддерживает ни один из вердиктов, и наивная постановка «бинд-мемо ещё никто не строил» МЕРТВА — оно построено, на уровне дескриптора, 4096-путное, и попадает 92,98 %.**

Четыре независимых основания:

1. **Один слот отвечает не на тот вопрос.** 5,9 % — это «повторяет ли этап НЕПОСРЕДСТВЕННО ПРЕДЫДУЩИЙ draw того же этапа», а не «повторяет ли он ЛЮБОЙ недавний». В том же прогоне существующий 4096-слотовый мемо на уровне дескриптора (`renderMemo.h:103`, `TextureSlots = 4096`) читает **92,98 % попаданий** (`tex_hits` 44 520,3 из `b_texn` 47 883,6, `bind78a`), а видовой мемо `texfast` — **89,73 %**. Две цифры отличаются сразу по двум осям (гранулярность 1 дескриптор против ~5,3 на этап; ширина 4096 против 1), поэтому 5,9 % ничего не ограничивает.
2. **Ключ склеивает три разных мемо-цели.** `PrepareBindings` потребляет образы, сэмплеры **и user-data** (`descriptors.cpp:1402-1404` — прочитано лично: `prepared.shader_data.push_back(snapshot.user_data[...])`), а буферы разрешаются позже, в `PrepareGraphicsBindings`. При этом `dwords[0]` и младшие 16 бит `dwords[1]` каждого V# — гостевой базовый адрес пообъектного константного буфера, который **меняется по построению на каждом draw**. То есть K-целиком не повторяется **ни на какой глубине**, и ширина таблицы его не двигает.
3. **Диагноз уже есть в записи и он тот же самый.** Сессия 52 померила `srtmemo` с ключом (ResourcePlan, user_data, shader_base): **89 % материализаций уникальны** по той же причине — игра кладёт пообъектный указатель в user data. Результат: −11 % FPS, гейт по умолчанию 0. `pmemo` (75,02 % повторов программы при 5,9 % повторов привязок) — подпись того же явления: та же материя, другие пообъектные данные.
4. **Тайминг гейта void.** `bk_miss_us` на ~40–47 % состоит из собственной арифметики гейта (~6,5 млн последовательных байтовых шагов на кадр), и прогон, который его дал, не дошёл до окна записи. Ни одно число `bk_*` из брифа цитировать нельзя.

### 2.3 Дешёвый первый ход, который это закрывает

Правка **в одном месте, три строки**, `descriptors.cpp:1374-1378`:

```
-   thread_local std::array<uint64_t, 16> previous_key {};
-   const auto slot = static_cast<uint32_t>(program.stage) % previous_key.size();
-   prepared.key    = BindingInputKey(program, snapshot);
+   thread_local std::array<uint64_t, 4096> previous_key {};
+   prepared.key    = BindingInputKey(program, snapshot);
+   const auto slot = static_cast<uint32_t>((prepared.key ^ (prepared.key >> 32)) % previous_key.size());
```

**Доказательство вооружения внутри прогона:** новый счётчик-гистограмма `bk_dist` — на какой дистанции (в этапах назад) найдено попадание. Если ширина что-то поменяла, `bk_dist` обязан быть непустым за пределами корзины 1. Если **все** попадания остались на дистанции 1, то 5,9 % не было артефактом глубины и вопрос закрыт отрицательно **тем же прогоном**.

Но одной ширины мало: чтобы получить решение, а не второе непонятное число, в тот же прогон надо добавить ещё три вещи — раздел ключа, per-слот счётчик и другой хэш. Это прогон №1 (см. §5).

### Пункт 0 — ИЗМЕРИТЕЛЬНЫЙ ПРОГОН (делать первым, см. §5)

**Экономия:** 0 us напрямую. Решает вопрос ценой **0…~7 000 us/кадр** (`mh_bind_us` без тонких часов 10 416, минус буферная половина ~4 640, которую дескрипторный ключ лицензировать не может, минус вычеты на побочные эффекты `BindImage`/`TouchImage`/`needs_rebind`).
**Сайты:** `descriptors.cpp:1331-1361` (хэш), `:1372-1382` (один слот), `renderDraw.cpp:1947-1958` (AND-редукция по этапам).
**Что меняется:**
- ширина 16 → 4096, индекс по хэшу (см. §2.3);
- ключ делится на **K1** = `shader_hash` + `snapshot.images` + `snapshot.samplers` + user-data dwords (`:1353-1354`, `:1356-1359`) — ровно то, что потребляет `PrepareBindings` (`:1384-1409`), и **K2** = K1 + `snapshot.buffers` (`:1355`). Разделить надо именно здесь: в исходном разборе user_data ошибочно отнесли к третьему ключу;
- **новый счётчик уровня слота**: для каждого слота j этапа s — совпал ли разрешённый (ImageId, view) с предыдущим draw того же этапа. Это единственная величина на этом пути с потолком выше 1 мс;
- хэш FNV-побайтно → `MemoHashBytes` (XXH3, `renderMemo.h:29-41`); `DescriptorValue` — POD `{array<uint32_t,8>; uint32_t}` (`ResourceSnapshot.h:10-17`), значит `snapshot.images` хэшируется одним блочным вызовом;

**Вооружение:** `bk_dist` непуст вне корзины 1; `bk1_hit + bk1_miss == bk2_hit + bk2_miss == bk_hit + bk_miss`; в плече `bindkey=0` все семь пар читают 0.

### Пункт 2 — Конфликты в текстурном мемо

**Экономия: 250–550 us/кадр, ПРАВДОПОДОБНО, статус НЕ РАЗРЕШЕНО.** `texmemo_collide` = **1 932,9/кадр ИЗМЕРЕНО** (4,04 % разрешений), `texmemo_stale` 12,3, `texmemo_empty` 0,0; `texfast_rec` = **1 650 видов записывается КАЖДЫЙ кадр** — то есть записанные виды разрушаются и пересоздаются исключительно вытеснениями, а не инвалидацией (`texfast_no_stamp` = 4,0, `texfast_no_state` = 0,0).
**Сайты:** `renderMemo.h:103` (`TextureSlots = 4096`, прямое отображение), `descriptors.cpp:798` (`memo_hash % TextureSlots`), `descriptors.cpp:705-722` (`MemoTextureWay` — 2-путная версия за гейтом `texmemo2`), `gates_base.txt`: `texmemo2=0` (прочитано лично).
**Ловушка, которую надо снять ДО патча:** `texmemo_empty` инкрементится только при `!memo_slot.valid` (`descriptors.cpp:804`), поэтому после первого прогрева таблицы он равен нулю **независимо** от того, 100 живых ключей или 100 000. То есть **сегодняшние счётчики не отличают конфликт от нехватки ёмкости**, а `texmemo2` ёмкости не добавляет вовсе: он индексирует `hash & (TextureSlots - 2)` = 2048 множеств × 2 пути. Нужен счётчик числа РАЗЛИЧНЫХ живых ключей за кадр (64K-битовая карта, очищаемая на флипе, ~8 КБ) — он и решает, что делать: добавлять путь или поднимать `TextureSlots`.
**Источник инвалидации:** никакой новой. `RenderExecutorMemo::Texture::version` (`renderMemo.h:70`, двигается на `descriptors.cpp:839` и `:1009`) + `slot->image_id`; попадание и сегодня перепроверяется против живого `Image`.

Но однонаправленное предсказание «`bufepoch` вырастет, `sf_skip` упадёт» **не может провалиться**: более широкое окно оставляет больше грязных страниц, и `sf_skip` падает в любом случае. Пре-регистрировать **пять** счётчиков со знаками: `bufepoch` ↑, `sf_skip` ↓, `sync_ups` ?, `sync_up_kb` ↑, `ob_stream_kb` ↑.

### 4.3 Достижимы ли 60 FPS на этом пути

**Нет.** Не «трудно» — арифметически невозможно. Вся фаза привязок без часов — 10,4 мс; вместе с записью дескрипторов — 16,1 мс; разрыв — 18,3 мс. Обнуление обоих не доводит до 16 667 us. Поток GuestGpu занят 32,8 мс, и для 60 FPS его надо более чем вдвое сократить.

Что в принципе могло бы: **меньше связываемых слотов**, а не более дешёвый поиск. Сегодня 95 613 дескрипторных слотов на кадр (`b_texn` 47 883,6 + `bb_n` 47 729,6) при **138 ns на слот** (`d_bind`/слоты, ИЗМЕРЕНО). Собственная арифметика разбора: ~1,0–2,4 мс — переразрешение на промахе, ~1,8 мс — неустранимое движение данных (`ob_stream_us` 897,0 + `bb_upload` 268,0 + `bb_find` 651,9), 1,6–3,3 мс — инструмент, **а всё остальное, порядка 5–7 мс, — цена ПРОВЕРКИ мемо, которые попадают**. Снять её можно только связав меньше слотов. Именно эту дверь открывает или закрывает счётчик повторов на слот в прогоне №1.

Альтернативы уже закрыты записью: вынос на другой поток — чистый налог (+4…8 %, сессия 64, `shadowinline`/`shadowresolve`); мемо материализации — −11 % FPS (сессия 52, `srtmemo`); demand-обход SRT — 100 % узлов нужны (сессия 53); M1 покрывает **0 %** фазы привязок (он производит только `ResourceSnapshot` + специализацию, `pipelineCache.cpp:2578-2583`, и его таймер `da_take_us` сидит в `p_mat` внутри `d_prog` — Lap-интервале, **непересекающемся** с `d_bind`).

## 9. ЕСЛИ ПРОГОН №1 ВЕРНЁТ НИЗКУЮ ДОЛЮ ПОВТОРОВ НА СЛОТ

Тогда фаза привязок закрыта, и это надо записать как результат сессии, а не искать восьмой пункт по 50 микросекунд. Честная формулировка для `FACTS.md` §10 будет такой: **фаза привязок — 30–38 % потока GuestGpu, из неё ~5–7 мс это цена проверки мемо, которые попадают на 90–100 %, число проверок задаётся игрой (95 613 слотов на кадр), и снизить его нечем. Разрыв до 60 FPS — 18,3 мс, вся фаза — 10,4 мс. Программа отгрузила ≈2,2 мс гейтов за двадцать сессий; при этой скорости 18,3 мс — это ~160 сессий.** После десяти сессий без FPS это и есть то решение, которое сессия 82 обязана принять, вместо одиннадцатого измерения измерения.
