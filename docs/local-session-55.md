## 4. Разрывы render pass в Sky Garden — что на самом деле их делает

Медиана по 6871 кадру из `C:/kyty/s54/log_sky54.txt`:

```
ends=931 restarts=802
end_shader_write=773 (restart 771)   end_target=93   end_buf_upload=21 (restart 20)
end_submit=15   end_dispatch=10   end_state=5   end_clear=3   end_tiler=3   end_binding=2
end_gds=0
```

`end_gds=0` и `end_binding=2` — **не потому, что этих барьеров нет**, а потому, что проход к моменту
их выдачи уже закрыт shader-write барьером предыдущего draw'а: внутри одного OIT-draw порядок
`GDS-барьер → Transit → BeginRendering → draw → shader-write барьер`, и закрытие засчитывается
первому. Отсюда прямое следствие: **правка (A) в одиночку не уменьшает `rp_begin` — счётчик просто
переезжает в `end_gds`**. Нужны все три правки вместе.

предикат `ImageResource::atomic` действительно означает «только атомарно», и правка
`graphics/shader/**` (со сменой подписи кэша трансляции) не нужна.

**Вывод: M1 на пустыне стал стоить примерно вдвое больше, чем до сессии (−2,3…3,0 % против

| прогон | `trackfree` | `protfast` | вместе |
|---|---|---|---|
| `v2` | −1,1 % | −2,2 % | −2,1 % и −1,7 % |

**Вывод: на пустыне эффект в пределах шума (±1 %).** Правка второго ревью (быстрый путь

## 8. Что не сделано, оставлено и почему

- **M3 (запись команд отдельным потоком) — WIP.** Шаг 0 (рекордер, кольцевая арена, перенос
  владения командным пулом и резервирование тика на потоке разрешения) написан, собирается и с
  выключенным гейтом отработал интро и 300 кадров пустыни без отличий. **Включение `recordthread=1`
  на лету роняет процесс** (порча указателя, `dec dword ptr [rax]` по мусорному адресу, прогон
  `v3`). Гейт по умолчанию 0; шаги 1–7 плана не начаты. Это единственная незавершённая часть.
- **`atomimg` опирается на предикат `ImageResource::atomic`, который означает «использует атомики»,
  а не «только атомики»** (`ResourceTracking::Merge` сливает `Write` и `Atomic` в один `written`).
  Для этой игры это точно — скан всего кэша трансляции дал 0 смешанных дескрипторов, — но для
  другой игры предикат неверен. Записано в комментарии у кода и здесь.
- **`tfcheck=1` меряет не ту конфигурацию**, что `trackfree=1` в одиночку: залоченный запрос
  создаёт регионы трекера, безлоковый — нет. «0 расхождений» получено именно в режиме
  самопроверки; это доказательство ответа, а не побочных эффектов.
- **`prot_held_us` считается только при `KYTY_FRAME_TRACE`** и добавляет два `NowNs` внутрь
  удерживаемого спин-лока — тот же класс инфляции, что закрыт в сессии 53. Пользоваться им только
  как порядком величины.
- Тест `TestLockFreeQueriesUnderConcurrentFaults` в нынешнем виде не может обнаружить сломанную
  реализацию (все утверждения — про свою половину диапазона, запись идёт по однословной ветке).
  Оставлен как есть, ограничение записано.
- §6.1 (копии при переинтерпретации, перезаливки Sky Garden), M2, A1/A2 из плана удешевления M1
  (компактная таблица меток, один вариант вместо 2,4) — не начаты.

## 9. Где мы относительно 60 FPS

Sky Garden в сессии не измерялся (автоматикой недостижим). По замерам сессии 54 там 17,8 FPS при
CPU потока GuestGpu 50,6 мс и GPU 18,9 мс. Всё, что сделано в этой сессии и включено по умолчанию,
на пустыне стоит около −1 % CPU на draw; всё, что может дать больше, лежит под выключенными
гейтами и ждёт замера в Sky Garden. Разбор GPU (§3) показывает, что даже идеальный CPU упирается в
11,4 мс занятого GPU плюс 7,2 мс простоя между отправками, то есть **60 FPS этой сессией не
достигнуты и остаются за M3 (записью команд отдельным потоком) и за GPU.**

# Добавление: замеры в Sky Garden с пользователем (прогоны `sky56`–`sky58`, `m3on`)

## A. Почему §6.2 в первом виде не сработал

Первый свип (`sky56`) показал: `swlocal` берётся лишь на **27–38 барьерах из 738**. Причина в коде:
`shader_write_stages` получает `eMeshShaderEXT`, когда буферы пишет и mesh-стадия draw'а
(`renderDraw.cpp`), а mesh — не framebuffer-space стадия, и барьер с ней внутри render pass
нелегален. ASTRO BOT рисует через mesh-шейдеры, поэтому почти все OIT-draw'ы уходили на старый
путь. Заодно выяснилось, что GDS-барьеров всего 43 на кадр, а не 768 — вторая «причина разрыва»
оказалась не там, где предполагалось.

Первый свип непригоден для решений по CPU: сцена живая, число draw гуляло 4300→5700 **внутри одной
фазы**, а к концу прогона CPU скакнул с 50 до 66 мс при том же числе draw. Для таких сцен написан
`C:/kyty/s55/sky_summary2.py` — он сравнивает только кадры, попавшие в общую для всех фаз узкую
полосу по числу draw.

## B. `swdefer` — правка, которая сработала

Вместо «сузить барьер до framebuffer-local» он **откладывается целиком**, пока проход открыт, если
все записываемые буферы draw'а помечены в IR атомарными; широкий барьер платится при закрытии
прохода. Это покрывает и mesh-стадию. Потолок правки измерен счётчиком до её включения:
**`swdefer_ok` = 792 из 798** барьеров на кадр (плейн-запись всего у 4–40 draw'ов).

Замер (`sky57`, 17 фаз по 250 кадров, полоса draw 4571–5071, восемь чистых базовых фаз, разброс
базы 0,6 %):

| | выкл. | вкл. |
|---|---:|---:|
| `rp_begin` | 920 | **185** |
| `swbar` | 766 | **30** |
| **GPU** | **18,3 мс** | **12,9 мс (−29 %)** |
| CPU на draw | 10,758 | 10,626 (−1,2 %) |
| FPS | 19,71 | 19,82 |

Разделение по GPU идеальное, без перекрытия: шесть фаз с гейтом 12,9–13,7 мс, одиннадцать без него
18,1–18,6 мс. Повтор на `sky58` (7 фаз): `rp_begin` 924 → 185, CPU на draw −1,7 / −1,7 / −3,4 %,
FPS +1,5 / +2,4 / +4,3 %.

**Вывод: 740 перезапусков render pass и 766 барьеров на кадр стоили 5,4 мс GPU и почти ничего на
CPU.** FPS вырос слабо, потому что кадр упирается в CPU (50 мс против 13 мс GPU).
**Это снимает GPU как блокер 60 FPS**: 12,9 мс укладывается в бюджет 16,6 мс.

Проверка картинки: видео `rec_sky58.mp4` — **19 681 кадр, 0 однокадровых глитчей**; покадровое
сравнение фаз (камера стоит) — прозрачный цилиндр портала, вода, свечение, лианы, лепестки
отрисованы одинаково и в том же порядке слоёв. **`swdefer` включён по умолчанию.**

`gdsepoch` и `atomimg` поверх `swdefer` не добавляют ничего (у `new_*` те же числа, что у `sd_*`):
остаются по умолчанию 0. `trackfree`+`protfast` в Sky Garden — −1,4 % CPU на draw, `tf_bad=0` на
~38 тыс. безлоковых ответов в кадр: тоже по умолчанию 0, эффект в пределах шума.

## C. M3 — падение найдено и исправлено

Адрес падения `0x7fff0f8237e5` лежит **внутри `nvoglv64.dll`** (база драйвера `0x7fff0e8a0000`
осталась в `r10`), а `dec dword ptr [rax]` — аллокатор чанков командного буфера драйвера с
испорченным заголовком: подпись нарушения external synchronization на `VkCommandBuffer`.
Механизм: при `KYTY_GPU_TIME=1` метки `GpuTimeProfiler` уходили в пакеты, и **поток записи писал
`vkCmdWriteTimestamp` в тот же буфер**, в который разрешающий поток в этот момент писал
`vkCmdBindPipeline`/`vkCmdDraw` по закэшированному хэндлу. Исправление: метки вернулись
разрешающему потоку (он и так сливает очередь в `Handle()`), гейт `recordthread` зафиксирован при
старте процесса (гейт-файл его не двигает), добавлена диагностика `RecordThread:`.

Прогон `m3on` (пустыня, `KYTY_RECORD_THREAD=1` с самого старта): **интро и 4 фазы пустыни, 0
исключений**. Счётчики: `rec_full=0` (обратного давления нет), `rec_n=116` пакетов на кадр (пока
только границы буфера и метки), **`rec_direct=5468`** — столько раз за кадр `Handle()` сливает
очередь. Цена переходного режима — **+10 % CPU на draw** (14,0–14,3 против ~12,8). Это ожидаемо и
уйдёт на шагах 1–2, когда сам путь draw начнёт писаться пакетами. Гейт остаётся по умолчанию 0.

## D. Где мы теперь относительно 60 FPS

Sky Garden, измерено: **CPU потока GuestGpu ~50 мс, GPU 12,9 мс, ~4700 draw, 19,8 FPS**.
GPU в бюджет уже влезает. Вся задача — CPU: нужно 50 → 16 мс, то есть втрое, и единственный
механизм для этого — M3 шаги 1–7 (перенос записи команд и дескрипторов на отдельный поток),
плюс удешевление `VerifyWitness` и привязок.
