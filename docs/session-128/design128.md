## 0. Итог

1. **Инструмент:** ручка `protceil` (`KYTY_PROT_CEILING`, 0..1, умолчание **0**, ПОСЛЕДНЯЯ строка `KNOB_DEFINITIONS` и
   последний элемент `enum class Knob` перед `Count`; `check_gate_order.py` после патча и ДО сборки). **ТОЛЬКО
   ИЗМЕРЕНИЕ, никогда не отгружается.** **0** — прежний путь (§8.2). **1** — на потоке GuestGpu, внутри операции
   «синхронизация буфера» (§4.1), не выполняется ни одно применение защиты страниц гостя в режим «только чтение»
   (`VirtualProtect(PAGE_READONLY)` — вооружение перехвата записи CPU); состояние трекера страниц при этом меняется ТАК ЖЕ,
   как при 0, а о странице, чья защита на хосте осталась слабее, помнит новый бит «не вооружена» (U, §5).
2. **Что снимается и что остаётся** (§2–§3): снимаются 100 % вызовов «только чтение» внутри синхронизаций буферов на
   GuestGpu — собственное вооружение загрузки (синхронный путь и путь `protbatch`) и применение чужих отложенных
   вооружений (текстуры через воркер), попавших в сброс диапазона той же синхронизации. Остаются: режим «запрет доступа»,
   снятие защиты, снятие читающего наблюдателя (переход NA → «только чтение»), все вызовы воркера защиты, все вызовы на
   гостевых потоках (обработчики фолтов), всё вне синхронизаций буферов.
3. **Корректность трекера** (§5): защита на хосте никогда не СИЛЬНЕЕ, чем думает трекер, и отличается только битом
   записи на страницах с U; фолтов не прибавляется ни одного, чтения CPU GPU-данных (страницы NA) не затронуты —
   поэтому нового пути к падению или зависанию гостя нет. Теряются только записи CPU в невооружённые страницы (картинке
   разрешено сломаться, п. 87(е)(3), прецедент `imgskip`). На переходе плеча 1 → 0 первая операция плеча 0 перевооружает
   все U-страницы (§5.5) — плечо 0 не наследует невооружённые страницы плеча 1 (иначе Δ занижен).
4. **Верх ручки завышен и это видно рядами** (§3.2, п. 87(г)): без вооружения нет фолтов записи гостя (на опоре
   `fw_n` ≈ 1 246 на кадр, `fault_us` ≈ 15 140 мкс/кадр по всем потокам [c]), нет повторных загрузок буферов
   (`sync_up_kb` ≈ 23 191 КБ/кадр [c]) и почти нет ожидания замка применения (`pb_wait_gpu_us` ≈ 195 [c]). Корректный
   механизм (write-watch, `armdefer`, `protbatch2`) повторные загрузки НЕ снимает — Δ `pc128` для него верхняя граница, для
   `K14_CLOSED` решающая, для `K14_OPEN` — слабая (§11).
5. **Честно до измерения [I по c]:** на опоре GuestGpu платит `prot_gpu_us` 1 742 мкс/кадр за 210 вызовов (8,3 мкс на
   вызов — ядро сериализует их с ≈ 1 246 фолтами/кадр гостевых потоков); «только чтение» — ≈ 82 % вызовов и ≈ 90 % страниц
   GuestGpu (оценка по `prot_ro` всех потоков, §3.3). Если Δ соберёт хотя бы половину этого — `K14_OPEN`
   вероятен; прогноза нет, число — потолок, не выигрыш. 60 FPS не обещаются.
6. **Время — запечатанный `pc128`**, чтение — дословно п. 87(е)(5)–(6) (§9); стражи печати — §10; вопросы лиду — §12 (В1–В9).

## 1. Назначение и что меряется

**Вопрос.** Сколько среднего времени кадра `dt_us` на опоре снимет ЛЮБОЙ механизм, убирающий с потока GuestGpu
вооружение перехвата записи CPU (перевод страниц буферов в «только чтение» после загрузки)? Уровень K14 — `prot_gpu_us` +
`pb_wait_gpu_us` ≤ 1 876 мкс [I; 1 666–1 744 M] — это ВРЕМЯ ВЫЗОВОВ, а не снимаемое время (п. 87(г)). Ручка меряет
снимаемое: плечо 1 не делает вооружения, плечо 0 делает, всё прочее одинаково.

**Число вывода.** Δ = mean_окна(`dt_us` | `protceil=1`) − mean_окна(`dt_us` | `protceil=0`) по парам ABBA, SE по парам;
рядом поправленный оценщик п. 77(б) (§9). Единицы — мкс/кадр. Δ < 0 — плечо 1 быстрее. Правило чтения п. 87(е)(6): **потолок
≥ 0,5 мс, если max(Δ + 2SE) ≤ −500**. Члены: `dt_us` — главная строка `FrameTrace` (стена между флипами, мкс); `draws` — та
же строка; окно 10–88 п. 55(б) каждого блока, блоки по `GateArm:`.

**Почему это потолок (верхняя граница) всех механизмов снятия вооружения с GuestGpu.** Любой такой механизм либо
переносит вызов с потока (`armdefer`, воркер), либо сливает вызовы (`protbatch2`), либо заменяет перехват фолтом на опрос
(write-watch AnyPS5) — и в каждом случае он обязан ещё и узнать о записи CPU и загрузить записанное. Плечо 1 не делает
ни одного из этого: ни вызова, ни фолта, ни загрузки. Всё, что механизм оставляет себе, плечо 1 тоже убирает; ничего
сверх плеча 0 плечо 1 не добавляет (§3.4, кроме перевооружения вне окна). Значит снятое механизмом ≤ снятое плечом 1 [I],
с оговорками §11 (картинка плеча 1 другая — GPU-работа может отличаться; число draw — поправленным оценщиком).

## 2. Какие вызовы защиты — «вооружение в режим только чтение» (сайты, граф вызовов)

### 2.1 Единственная точка выхода к хосту

Все смены защиты страниц гостя трекером идут через `PageManager::Impl::Protect` (`pageManager.cpp:302–385`) →
`Libs::LibKernel::Memory::ProtectGuestHostMemory` (`VirtualProtect`). Режим — `PageState::Perms()` (`:161–169`):
`access_watchers ≠ 0` → `NoAccess`; иначе `write_watchers ≠ 0` → `Read`; иначе `ReadWrite`. Счётчик `prot_gpu_us`
(`ProtectGpuNs`, `:370–374`) — стена вызовов НЕ воркера на потоке роли `Gpu`, всех режимов; `prot_ro`/`prot_na`
(`:346–359`) — число вызовов по режиму на ВСЕХ потоках (кроме воркера); время по режиму есть только у `ReadWrite`
(`prot_rw_us`, все потоки). **Разбиения `prot_gpu_us` по режимам в коде нет** — его добавляет проект (§7.1).

Вызовы `Protect` приходят из пяти мест:

| место | файл:строки | поток | что применяет |
|---|---|---|---|
| П1 `ProtectRun` из `UpdateRegionWatchers` (синхронный путь, `!batch && !defer`) | `pageManager.cpp:399–405`, вызов `:449–452` | вызывающий | прогон страниц с одним `Perms()` после смены наблюдателей |
| П2 `FlushRegion` (сброс области `BatchScope` или диапазона `FlushProtection`) | `:740–797`, вызов `:787` | вызывающий | отложенные прогоны (`pending`), значение `Perms()` читается под замком |
| П3 `ApplyPending` (воркер `KytyPageProtect`) | `:705–732`, вызов `:729` | воркер | отложенные прогоны очереди |
| П4 `Verify` (гейт `pbcheck`) | `:823–898` | вызывающий | вызова нет (только `VirtualQuery`) |
| П5 перевооружение §5.5 (новое) | — | GuestGpu | см. §5.5 |

### 2.2 Кто вооружает запись (добавляет наблюдателя записи: `UpdateRegionWatchers<track = true, is_read = false>`)

- **Кэш буферов, загрузка.** `BufferCache::SynchronizeBuffer` (`bufferCache.cpp:796–864`) → `MemoryTracker::ForEachUploadRange`
  (`memoryTracker.h:289–364`) → на каждой области `RegionManager::ForEachModifiedRange<Cpu, clear = true>`
  (`regionManager.h:273–293`) снимает CPU-грязные биты и зовёт `UpdateProtection<true, false>` (`:516–536`) → маска
  страниц, покинувших «записываемые» (`m_writable = m_cpu_dirty & ~m_armed`) → `PageManager::UpdatePageWatchersForRegion
  <true, false>` (`pageManager.cpp:1226–1251`) → `UpdateRegionWatchers`. Ребро «0 → 1 наблюдатель записи» меняет
  `Perms()` только с `ReadWrite` на `Read` (при `access_watchers ≠ 0` страница NA до и после — ребра нет) — **это и есть
  вооружение**. Дальше:
  - **только чтение, `protbatch=1`** (умолчание `true`, `gates.cpp:48`; пин 1 в `gates_base.txt` с. 127): внутри
    `BatchScope` (`memoryTracker.h:313`) смена только ставит `pending` (`pageManager.cpp:435–448`, ёмкость 4 области);
    применяет её `batch.Flush()` (`memoryTracker.h:334`) → `FlushRegion` (П2, счётчик ожидания `pb_wait_scope_us`),
    затем `FlushProtection` на весь диапазон (`:341–345`) → `FlushRegion` (П2, `pb_wait_range_us`) — этот второй сброс
    применяет и ЧУЖИЕ отложенные вооружения на тех же страницах (текстуры, §2.3). Области сверх ёмкости 4 — синхронно (П1);
  - **только чтение, `protbatch=0`** — синхронно, П1;
  - **записываемый буфер** (`is_written`): `BatchScope` выключен (`:313`) → П1 «только чтение», и тут же под тем же
    замком области `ChangeState<Gpu, true>` (`regionManager.h:168–221`) добавляет читающего наблюдателя → П1 «запрет
    доступа». Вооружение здесь живёт микросекунды, но это вызов `Read` на GuestGpu, в `prot_gpu_us`.
  - вызывающие `SynchronizeBuffer` на GuestGpu: `ObtainBuffer` (привязки draw/dispatch), проход грязных диапазонов BDA
    `SynchronizeBuffersOfDirtyRanges` (`bufferCache.cpp:2836–2869`, при `protbatch2=0` — по `SynchronizeBuffer` на буфер,
    `:2864`), `SynchronizeBufferFromImage` и пр.; `ObtainBufferForImage` приходит и с других потоков (комментарий
    `:866–871`) — они вне ручки (§4.1).
  - `armdefer` (`ForEachUploadRangeArmDeferred`, `regionManager.h:320–377`) и `protbatch2`
    (`SynchronizeBuffersOfDirtyRangesBatched`, `bufferCache.cpp:2770–2833`) — пути вооружения через воркер и через сброс
    прохода; при `protceil=1` ОТКАЗ (§4.3).
- **Кэш образов.** `TextureCache` вооружает через `UpdatePageWatchersDeferred` (`textureCache.cpp:542`, `:567`, `:585`) —
  при `KYTY_ASYNC_PROTECT` ≠ 0 (умолчание, `pageManager.cpp:534–540`) только `pending` + очередь воркера (П3); снятие —
  `UpdatePageWatchers<false>` (`:600`, `:619`, `:638`) синхронно. Сам по себе кэш образов на GuestGpu «только чтение» не
  применяет; применяет его воркер или ЧУЖОЙ сброс диапазона (П2), если тот успел раньше.
- **Никто другой** наблюдателя записи не добавляет: `ChangeState<Cpu, true>` (фолт записи, `InvalidateRegion`,
  `UntrackMemory`, `MarkRegionAsCpuModified`) — только снимает (`UpdateProtection<false, false>`); читающие наблюдатели —
  `ChangeState<Gpu, …>`/`MarkStaleReadable` (`is_read = true`) — никогда не откладываются и не пакетируются.

### 2.3 Какие вызовы `Read` на GuestGpu бывают вообще

(а) П1 из вооружения синхронизации буфера; (б) П2 `BatchScope`-сброс вооружения синхронизации; (в) П2 `FlushProtection`
синхронизации — чужие отложенные вооружения (текстуры) на её страницах; (г) П1 из `UpdateRegionWatchers<false, true>` —
СНЯТИЕ читающего наблюдателя со страницы, где остался наблюдатель записи (NA → `Read`: GPU-грязная страница стала чистой —
`UnmarkRegionAsGpuModified`, `ForEachDownloadRange<true>`); (д) П2 сброса вне синхронизации буфера (например,
`InvalidateRegion` с `protbatch`, если он случится на GuestGpu). **Ручка снимает (а), (б), (в); (г) и (д) остаются.**
(г) — не вооружение, а разоружение чтения (п. 87(е)(3): «режим запрет доступа … как при 0» — переход из NA оставляем:
пропуск оставил бы страницу NA при трекере «только чтение» — лишний фолт чтения, которого трекер не ждёт, путь к
зависанию). (д) — вне операции.

## 3. Что ручка пропускает, что остаётся, что ещё снимается

### 3.1 Пропускается (при 1, внутри операции §4.1, на GuestGpu)

Каждое применение прогона страниц в режим `Read` в П1 при `track && !is_read` и в П2 — вызов `Protect` не делается.
Сопутствующее тому применению, кроме вызова, делается КАК ПРИ 0: снимаются биты `pending` прогона (П1 `:402–404`, П2 в
`TakePendingRun` `:687`), публикуется и снимается `applying_run` (П2 `:683–686`, `:788`), замок `apply` берётся и
отпускается там же. Добавляется: биты U прогона ставятся (§5.1), счётчики `pc_skip_*` (§7.1).

### 3.2 Остаётся (как при 0)

Все вызовы П1/П2 в режимах `NoAccess` и `ReadWrite`; П1 режима `Read` из снятия читающего наблюдателя (2.3(г)); всё на
потоках, отличных от GuestGpu (обработчики фолтов гостя — `ReadWrite` через `InvalidateWriteFault`, `bufferCache.cpp:448–456`;
чтения устаревших данных `MarkStaleReadable`); все вызовы воркера П3 (аргументы вызова — те же, что он получил бы; он
просто может не найти работы, которую GuestGpu забрал и пропустил); `Drain` на флипе (`graphicsRun.cpp:4043/4064/4092`);
логика трекера (`PageState`, `m_cpu_dirty`, `m_writable`, эпохи областей) — побитно та же функция своих входов.

### 3.4 Что ещё снимает пропуск кроме системного вызова (и чем это видно)

1. **Фолты записи гостя.** Невооружённая страница пишется без фолта: нет `InvalidateWriteFault` (`bufferCache.cpp:448`),
   нет вызова `ReadWrite` обработчика, нет `FlushProtection` в обработчике, нет ожидания `apply`. Ряды: `fw_n`,
   `fw_widened`, `faults`, `fault_us`, `faults_main`, `fault_main_us`, `prot_rw_us`, `prot_rw_pages`, `pb_wait_us`,
   `pb_wait_range_us`, `pb_refault`, `pb_inval_flush`. Это время гостевых потоков; в `dt_us` оно входит, только если
   гость на критическом пути (на опоре GuestGpu ≈ 98 % окна CPU — `diag/admin` с. 126 [c]).
2. **Повторные загрузки буферов.** Нет фолта ⇒ нет CPU-грязного бита ⇒ следующая синхронизация ничего не копирует.
   Ряды: `sync_up_kb` (байты копий `SynchronizeBuffer`, кБ), `sync_ups` (число загрузок), `sync_noop`, `sf_skip`
   (синхронизации без работы и пропуски `syncfree`), `bufepoch` (`BufEpochHits`), `stg_pool_b`/`stg_in_b` (копии в
   staging, если печатаются). Это время GuestGpu (запись копии, `UploadCopies`) и пула копий.
3. **Ожидание замка применения на GuestGpu** — `pb_wait_gpu_us` (обработчики фолтов больше не держат `apply` областей);
   `pb_wait_scope_us`, `pb_wait_range_us` рядами.
4. **Работа прохода BDA.** Нет фолтов ⇒ не двигаются эпохи областей (`RegionManager::ChangeState<Cpu, true>`
   `regionManager.h:209–212`) ⇒ `PrepareBda` сканирует меньше. Ряды: `bda_scan`, `bda_skip`, `bda_n`, `bda_us` (в `lite`
   — 0, `Scope`). **`bda_scan` в плече 1 может упасть — это та же величина, по которой классифицируется режим BDA** (§9.3,
   §12 В5).
5. **Загрузки образов на невооружённых страницах** (страница, где наблюдатель буфера уже есть, при вооружении образа не
   даёт ребра; и чужое отложенное вооружение образа, пропущенное сбросом 2.3(в)). Ряды: `img_up`, `img_up_kb`,
   `tex_inval`, `tex_inval_empty`.
6. **Конкуренция в ядре за блокировку адресного пространства** — остальные `VirtualProtect` (воркер `protw_us`,
   обработчики) дешевеют. Ряды: `protw_us`, `prot_rw_us / prot_rw_pages`.
7. **Счётчики инструмента.** Пропущенный вызов не платит 2 `NowNs` и ≈ 8 `Add` своих счётчиков — ≈ 173 × 30 нс ≈ 5 мкс/кадр
   [I] в пользу плеча 1 (только в трассируемой сборке); в Δ, в сторону завышения потолка, пренебрежимо против 500.

**Что пропуск ДОБАВЛЯЕТ:** перевооружение на первом кадре блока плеча 0 после плеча 1 (§5.5; вне окна 10–88 — страж §10);
возможное изменение GPU-работы из-за устаревших данных (ряды `gpu_busy_us`, `draws`; поправленный оценщик). Ничего
больше [I].

## 4. Ручка `protceil` (`KYTY_PROT_CEILING`)

### 4.1 Значения, чтение, защёлка, операция

- Строка `{"KYTY_PROT_CEILING", "protceil", 0, 1}` — ПОСЛЕДНЯЯ в `KNOB_DEFINITIONS` (`gates.cpp`, после `rtskip` `:437`),
  элемент `ProtCeiling` — последний перед `Count` в `enum class Knob` (`gates.h`, после `RtSkip` `:673`), комментарий
  «ТОЛЬКО ИЗМЕРЕНИЕ, защёлка раз на синхронизацию буфера на GuestGpu, может быть плечом расписания».
  `check_gate_order.py` — после патча и ДО сборки. Гейт-файл: п. 87(е)(5) — «замена на месте в `gates_base.txt`», а
  п. 87(е)(2) строки `protceil` в базе не даёт. Если имени в базе нет — им владеет расписание (с. 67), замены нет; если
  харнесс впишет `protceil=0` в базу — плечи заменяют его НА МЕСТЕ (имя, дописанное в конец после такого же имени базы,
  игнорируется: побеждает первое присваивание). Выбор — В9.
- **Операция** — один вызов `MemoryTracker::ForEachUploadRange` из `BufferCache::SynchronizeBuffer` на потоке GuestGpu
  (`bufferCache.cpp:835–843`, ветка `else` после `SyncFreeSkip`): цикл по областям, сброс `BatchScope` (`memoryTracker.h:334`)
  и сброс диапазона (`:341–345`). **Защёлка** — RAII-объект `PageManager::CeilScope` (новый, по образцу `SpinHeld`,
  `pageManager.h:146–156`), создаваемый непосредственно перед вызовом `ForEachUploadRange` (`bufferCache.cpp:835`), только
  если `GuestGpu::IsGpuThread()`; его конструктор ОДИН раз читает `Common::Gates::Value(Knob::ProtCeiling)` (одна
  relaxed-загрузка), проверяет отказы (§4.3) и ставит thread-local `t_ceil` (0/1) и `t_ceil_scope = true`; деструктор
  восстанавливает предыдущие значения. Вложенная операция наследует защёлку внешней (второе чтение ручки внутри одной
  операции невозможно — ловушка с. 97). **Не на входе `SynchronizeBuffer`:** на опоре ≈ 25 000 вызовов/кадр уходят в
  `HasCurrentUpload`/`SyncFreeSkip` без работы (`sync_noop` 24 989 [c]) — защёлка там стоила бы ≈ 25 000 чтений ручки на
  кадр; в ветке `else` — ≈ 85 (`sync_ups` [c]).
- **Почему защёлка на синхронизацию, а не на draw.** Корректность (§5) — попостраничная и от значения ручки в соседних
  операциях не зависит: каждая страница удовлетворяет инварианту P′ при любой последовательности значений. Защёлка нужна
  только для того, чтобы одно вооружение (сброс `BatchScope` + сброс диапазона одной синхронизации) не порвалось между
  значениями; операция, пересекающая смену плеча, лежит на позициях 0–1 блока, вне окна.
- **Поток.** Только GuestGpu. `SynchronizeBuffer` с других потоков (`ObtainBufferForImage`) — без `CeilScope`, путь 0;
  при значении 1 такой вызов считается `pc_offthr` (ряд).
- **Может ли быть плечом расписания — да:** значение читается на каждой операции; строка `ProtCeil: mode 1` в лог — один
  раз на процесс при первой защёлке со значением 1 (`stderr`/`LOGF`, как `RtSkip: mode 1`).

### 4.2 Решение о пропуске (где именно)

- **П1** (`UpdateRegionWatchers`, вызов `ProtectRun` `pageManager.cpp:449–452`): пропуск ⇔ `t_ceil == 1` ∧ шаблон
  `track && !is_read` ∧ `perms == Read`. Сигнатура `ProtectRun` получает флаг «вооружение» от шаблона вызывающего.
- **П2** (`FlushRegion`, после `TakePendingRun` `:782–786`): пропуск ⇔ `t_ceil == 1` ∧ `perms == Read`. Отложенные
  прогоны `Read` возникают только из рёбер наблюдателей записи (читающие смены не откладываются, §2.2), поэтому это всегда
  вооружение (своё или чужое).
- **П3** (воркер): не пропускает никогда (`t_ceil` у воркера 0 — он не открывает `CeilScope`).
- В `ApplyPending` и в ветке применения П1/П2 — только снятие битов U применённого прогона (§5.1).

### 4.3 Отказы (строка лога раз на причину + счётчик `pc_refuse`, ручка действует как 0 для этой операции)

| причина | почему |
|---|---|
| `armdefer=1` | вооружение идёт через воркер (`ForEachUploadRangeArmDeferred`), ручке нечего пропускать на GuestGpu, а `KeepApplied` (`pageManager.cpp:1048–1072`) считает непомеченную страницу применённой — снятие CPU-грязного бита на U-странице |
| `protbatch2=1` (при `protbatch=1`) | сброс прохода вне `SynchronizeBuffer` (другое место защёлки), и `swallow_gaps` (`:628–634`) повторно применяет `Read` к непомеченным страницам — молча перевооружает U-страницы посреди плеча 1 |

Строки: `ProtCeil: refused reason=armdefer`, `ProtCeil: refused reason=protbatch2` (≤ 1 на причину на процесс).
`pbcheck`, `applyskip`, `stkstat`, `faultkb`, `KYTY_ASYNC_PROTECT=0` — не отказ (§5.4, §12 В7). Отказы проверяются только
при значении 1 (при 0 — ни одного чтения гейтов, §8.2).

## 5. Состояние трекера после пропуска и довод согласованности

### 5.1 Бит U («не вооружена»)

В `PageManager::Impl::Region` (`pageManager.cpp:207–245`) — `std::array<uint64_t, REGION_PAGES / 64> unarmed {}` и
`bool has_unarmed`, `bool unarmed_listed`; в `Impl` — `std::vector<Region*> unarmed_regions` (пишет и читает только
GuestGpu). **Все чтения и записи U — под замком `apply` этой области** (П1 с `ApplyGuard` `:427`, П2 `:761`, П3 `:718`,
`Verify` `:846`, перевооружение §5.5) — поэтому без атомиков и без `lock`.
- **Установка:** пропущенное применение ставит U всем страницам прогона (`pc_u_set` — число страниц, у которых бит был 0),
  `has_unarmed = true`, область один раз в `unarmed_regions`.
- **Снятие:** любое СДЕЛАННОЕ применение (П1, П2, П3, §5.5) снимает U со страниц своего прогона после возврата `Protect`,
  пока `apply` держится (`pc_u_clr` — число снятых единичных битов; при `has_unarmed == false` — ни одной записи).

### 5.2 Инвариант P′ (заменяет P `Region::apply` `:209–229`, пока есть U)

Для каждой страницы без `pending`: если U = 0 — защита на хосте = `Perms()` (это P); если U = 1 — `Perms() == Read`, а на
хосте `ReadWrite` или `Read`. **Хост никогда не строже трекера; различие — только бит записи.**
Довод [I]:
1. U ставится только пропущенным прогоном `Read`. Страницы такого прогона до пропуска: в П1 — страницы с ребром
   `RW → Read` (хост `RW` по P) и страницы «внутри» прогона без ребра с `Perms() == Read` (хост `Read` по P или `RW` по P′);
   в П2 — отложенные страницы, чей хост — последнее применённое значение; `NoAccess` на хосте бывает только после
   синхронного применения `NoAccess` (читающие смены не откладываются), а выход из `NoAccess` — тоже только синхронным
   применением, снимающим `pending` (`ProtectRun` `:402–404`). Значит у страницы с `Perms() == Read` хост ∈ {`RW`, `Read`}.
2. `Perms()` меняется только ребром наблюдателя. Ребро либо применяется синхронно (П1 — хост = `Perms()`, U снят),
   либо ставит `pending` (страница выходит из условия «без `pending`» до применения, которое снимет U).
3. Смена числа наблюдателей без ребра (1 → 2, 2 → 1) не меняет ни `Perms()`, ни хоста — P′ держится.

### 5.3 Что будет со страницей дальше (п. 87(е)(3): «что трекер думает, что будет при снятии защиты и при записи CPU»)

- **Что думает трекер:** `write_watchers ≥ 1`, `Perms() == Read`, `pending` = 0; в `RegionManager` — `m_cpu_dirty` = 0
  (байты только что загружены), `m_writable` = 0. То есть «вооружена и CPU-чиста» — ровно как при 0. U помнит, что хост
  может пустить запись.
- **Запись CPU в невооружённую страницу:** фолта нет. Запись ложится в память гостя; `ChangeState<Cpu, true>` не
  зовётся, CPU-грязный бит не ставится, эпоха области не двигается. Следующая синхронизация видит страницу чистой
  (`HasCurrentUpload`, `SyncFreeSkip`, пустая маска) и НЕ загружает её — у GPU остаётся снимок момента пропуска.
  **Потеря записи** — всё, чем ручка портит результат; картинке разрешено сломаться (п. 87(е)(3)). Гость об отслеживании
  не знает и ничего не ждёт от этого фолта; ни один путь эмулятора не ждёт фолта записи [I].
- **Явное объявление записи** (`InvalidateMemory` — чтения файлов `KernelRead`, DMA; `UntrackMemory` — сборщик/снятие
  буфера; `MarkRegionAsCpuModified`) — `ChangeState<Cpu, true>` снимает наблюдателя: ребро `Read → RW`, применение `RW`
  (синхронно или отложенно) к странице, уже `RW` на хосте, — вызов успешен (та же страница, отображена), U снят; дальше
  страница обычная CPU-грязная, следующая синхронизация загрузит её и снова пропустит вооружение.
- **Последующее снятие защиты** (наблюдатель записи → 0 любым путём) — то же: `RW` поверх `RW`, U снят.
- **GPU пишет страницу** (записываемая привязка, `ChangeState<Gpu, true>`): ребро `Read → NoAccess`, синхронное
  применение `NoAccess` — хост NA, U снят, P восстановлен. Когда GPU-данные уходят (`ChangeState<Gpu, false>`) —
  `NoAccess → Read` синхронно (2.3(г), не пропускается) — страница по-настоящему вооружена.
- **Второй наблюдатель записи** (образ на той же странице): ребра нет, вызова нет — записи CPU, меняющие образ, тоже
  теряются (ряды `img_up`, `tex_inval`).
- **GC буферов** (`UntrackMemory`, `bufferCache.cpp:2058/2091/2602/2612`) — как «явное объявление записи»; GC образов —
  `UpdatePageWatchers<false>` (`textureCache.cpp:600/619/638`) — ребро только если наблюдатель последний, иначе ничего.
- **Воркер защиты:** видит только `pending`-страницы. У пропущенного прогона `pending` снят (П2) или не ставился (П1);
  позже отложенная смена может снова поставить `pending` — воркер применит `Perms()` и снимет U (§5.1). Аргументы его
  вызовов — функция `Perms()` и `pending`, как при 0.
- **Фолт на U-странице** невозможен: запись разрешена хостом, чтение — тоже (хост ∈ {`RW`, `Read`}). Фолтов на остальных
  страницах — те же пути, что при 0. `ProtectBatch: STUCK` (`pb_stuck`) — обязан оставаться 0.
- **Чтения CPU GPU-данных** (страницы NA, `ReadMemory`, `ServeStaleRead`, readback DRS/экспозиции) не затронуты: у этих
  страниц `access_watchers ≠ 0`, их применения — не `Read`, а U на них снимается применением NA.
- **Разрушение `PageManager`** (`:269–279`) проверяет только наблюдателей — U не мешает.

### 5.4 Отношения с гейтами-соседями

`pbcheck` (`Verify` `:823–898`): для страницы с U, записываемой на хосте, — не `pb_bad`, а новый ряд `pc_vfy_u`
(ожидаемо при 1); `pb_bad` (потерянная защита на странице БЕЗ U) обязан быть 0 при обоих значениях; U-страница, НЕ
читаемая на хосте, — `pc_vfy_u_na` (обязан быть 0: нарушение P′). `applyskip`: `FlushBlocker` (`:576–603`) верно отвечает
«ждать нечего» для U-страниц — их хост никто не меняет; при `applyskip=0` (пин) он считает только ряды. `stkstat`:
статистика вооружения (`NoteUploadStat`) считает «вооружённые» страницы по трекеру — при 1 это страницы, которые ручка не
вооружила (ряд, не сравнивается). `faultkb`: окно фолта открывает `RW` страницы без GPU-данных — U-страницы среди них
получают применение `RW` и снятие U — согласованно.

### 5.5 Перевооружение на переходе плеча 1 → 0 (нужно для несмещённого ABBA)

Без него блок плеча 0 после плеча 1 начинает с невооружённым рабочим набором: записи гостя не фолтят и не
загружаются, пока страница не пройдёт через явное объявление или GPU-запись — плечо 0 тоже «снимает» вооружение, Δ
занижен (опасно для `K14_CLOSED`). Правило: `CeilScope` на GuestGpu помнит последнее защёлкнутое значение
(`t_ceil_prev`); первая операция со значением 0 после значения 1 до вызова `ForEachUploadRange` проходит
`unarmed_regions`: для каждой области — `ApplyGuard(apply)`, под `lock` собрать прогоны страниц `U ∧ !pending ∧
Perms() == Read`, для `U ∧ pending` — только снять U (отложенное применение запишет `Perms()`), для `U ∧ !pending ∧
Perms() ≠ Read` — снять U и `pc_rearm_odd++` (по P′ невозможно, страж 0); отпустить `lock`, под тем же `apply` —
`Protect(Read)` каждого прогона (значение прочитано под `lock` внутри того же удержания — P сохранён), снять U, очистить
`has_unarmed`, `unarmed_listed`, список. Счётчики `pc_rearm_n` (проходы), `pc_rearm_runs`, `pc_rearm_pages` (снятые U-биты),
`pc_rearm_ns` (стена прохода, `NowNs` под `FrameStats::Enabled()` — жив в `lite`). Цена [I]: ≈ число прогонов U-набора ×
8 мкс; рабочий набор на опоре ≈ 5 966 страниц за 173 вызова на кадр [c] ⇒ ≈ 1,5–3 мс одним проходом на позиции 0–1 блока,
вне окна 10–88 (страж §10). Записи, потерянные в плече 1 на страницах, которые гость больше не пишет, остаются потерянными
(картинка) — на время плеча 0 это не влияет (горячие страницы пишутся каждый кадр и после перевооружения фолтят на
следующем кадре).

**Обратный переход 0 → 1** ничего не делает: вооружённые страницы плеча 0 разоружаются сами за один цикл «фолт → снятие →
загрузка → пропуск» (≈ 1 кадр для страниц, которые пишутся каждый кадр, [I]); ряд — `fw_n` по позициям блока плеча 1
(0–9 против 10–88), §10.

## 6. Положительный и нулевой контроль

**Положительный (инструмент вооружился и снимает то, что обещал):**

### 7.4 Тождества для скорера (суммы окна 10–88 п. 55(б) каждого блока; блоки по `GateArm:`)

- **Т1 (разбиение по режимам, разбиение):** `prot_gpu_ro_n + prot_gpu_na_n + prot_gpu_rw_n = prot_gpu`. Складываются в
  одном месте одного потока, но флип читает счётчики по одному (перекос строки) — точно на сумме блока до допуска
  ±2 на блок [I]; нарушения по строкам печатаются числом, не валят.
- **Т2 (время, разбиение):** |Σ(`prot_gpu_ro_ns + prot_gpu_na_ns + prot_gpu_rw_ns`)/1000 − Σ`prot_gpu_us`| ≤ число строк

- **Т3 (подмножество):** `pc_elig_n ≤ prot_gpu_ro_n`, `pc_elig_pages ≤ prot_gpu_ro_pages`, `pc_elig_ns ≤ prot_gpu_ro_ns`.
- **Т4 (подмножества мест):** `pc_elig_scope_n + pc_elig_rng_n ≤ pc_elig_n`; `pc_skip_scope_n + pc_skip_rng_n ≤ pc_skip_n`.
- **Т5 (плечо 1):** `pc_u_set ≤ pc_skip_pages`.
- **Т6 (сохранение U, весь лог):** Σ`pc_u_set` ≥ Σ`pc_u_clr` + Σ`pc_rearm_pages` (разность — живые U в конце).
- **Т7 (исчезновение вызовов):** в плече 1 `prot_gpu_ro_n` окна ≤ `prot_gpu_ro_n` плеча 0 − `pc_elig_n` плеча 0 + допуск

## 11. Риски и что проект НЕ доказывает

- Δ `pc128` — потолок, НЕ выигрыш и НЕ цена вызовов `VirtualProtect`: в него входят снятые фолты гостя, повторные загрузки
  (≈ 23 МБ/кадр [c]), ожидание `apply`, работа прохода BDA и загрузки образов (§3.4). Корректный механизм повторные
  загрузки записанных страниц не снимет никогда. **`K14_OPEN` не говорит, сколько возьмёт механизм** — только что
  потолок не мал; разделение потолка на «вызовы» и «загрузки» этой ручкой не делается (§12 В8).
- «Верхняя граница всех механизмов» держится, пока плечо 1 не добавляет работы. Устаревшие данные меняют картинку и,
  возможно, GPU-работу и число draw; `draws` — поправленным оценщиком, `gpu_busy_us` — рядом; GuestGpu-граница опоры
  (`cpu_gpu_us` ≈ `dt_us`) делает GPU-сторону второстепенной [c].
- Зависание гостя по потерянным записям CPU → GPU не исключено доводом: довод исключает только НОВЫЕ фолты и потерю
  GPU → CPU данных. Гость, чья логика ждёт результат GPU, посчитанный по данным CPU (например, GPU-driven отбор с
  обратным чтением), получит результат по устаревшим данным — это не ожидание, но может увести сцену. Проверка — дым
  150 с (п. 87(е)(4)); переносить на другие сцены нельзя.
- Перевооружение §5.5 возвращает защиту, но не данные: записи плеча 1 в страницы, которые гость больше не пишет, остаются
  у GPU устаревшими до конца прогона — картинка плеча 0 после плеча 1 тоже может быть сломана; время — нет [I].
- Переходное разоружение в начале блока плеча 1 (§5.5) — если длиннее 10 кадров, окно плеча 1 недобирает потолок (Δ
  занижен, сторона «закрыть»); ряд `fw_n` по позициям это покажет.
- Режим BDA может зависеть от плеча (§9.3) — популяция пар, не знак Δ.
- Не доказывает: время в других сценах, в пустыне, в OLD без ≥ 10 пар; цену сборки с ручкой при 0 против `4fc501f4`;
  потолок механизмов вне GuestGpu (вооружение образов воркером, фолты как таковые на других потоках — только в той мере,
  в какой они исчезают вместе с вооружением буферов). 60 FPS не обещаются.
