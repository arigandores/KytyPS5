## 0. Итог

1. **Assert — проверка места в командном буфере кадра (PM4) движка игры, а «access violation гостя» — её собственная ловушка `int 0x42`, не второй дефект** [c]. `pc=0x00000009004a020e` = база `eboot` `0x900000000` + `0x4a020e`, байты `cd 42` в заглушке переполнения `0x4a01e0` (`command_buffer_writer.ppr.cpp:31`); `int 0x42` в режиме пользователя даёт #GP, Windows сообщает его как `0xC0000005` с адресом `0xffffffffffffffff` — ровно строка обоих логов.
2. **Ресурс** [c дизассемблера]: линейный буфер команд одного кадра одной очереди (`Gpu::GpuDevice`: 5 очередей × 3 контекста кадра, размер N МиБ из таблицы `0x8495950` = {7, 7, 4, 4, 6}); команды пишутся снизу вверх, данные — сверху вниз; когда свободных слов не больше резерва — вызов обработчика, у этих буферов обработчик — assert. **Освобождение** — безусловный сброс курсоров в `CommandContext::Begin` (`0x4a55f0`) после ожидания метки GPU прошлого использования (`KernelWaitEqueue` + метка `AgcCbReleaseMem`). Путь освобождения от ответа эмулятора по величине не зависит: неверный ответ даёт ожидание или раннее переиспользование, не накопление.
3. **Причина на стороне эмулятора [c] не названа.** Единственная связь эмулятора с наполнением — PM4, который пишут HLE-функции `libSceAgc` эмулятора в тот же буфер (`AllocateDW`; 71 импорт, 1 175 места вызова в `eboot`); три пары «`…GetSize` ↔ писатель» эмулятора согласованы [c], размеры пакетов настоящей `libSceAgc` неизвестны [U].
