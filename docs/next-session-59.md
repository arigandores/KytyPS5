# Промпт для следующей сессии (сессия 59)

Ты — оркестратор. Пользователь за компом есть, но его время дорого: всё, что достижимо без него
(пустыня, сборки, тесты, ревью), делаешь сам, а зовёшь только для Sky Garden — довести игру до
сцены и отпустить ввод. Цель — **60 FPS в Sky Garden**. Сейчас ~26–28 FPS: CPU потока GuestGpu
33,0–33,6 мс, GPU 13–14 мс, ~4 700–4 800 draw, 6,9–7,2 мкс CPU на draw.

## 1. Решено измерениями — не переоткрывать

- **Трек A исчерпан.** Четыре правки сессии 58 дали суммарно меньше 1,5 %, две из них — 0.
  Дальнейшее удешевление отдельных операций последовательного остатка не окупается: браться только
  за то, что меняет **количество** операций.
- **`protbatch2` (`VirtualProtect` фаза 2) измерен и выключен.** Потолок в Sky Garden мал: на этом
  пути всего ~123 вызова на кадр, 58 % из них и так сливаются вплотную. Не переделывать.
- **`buffast` (memo запроса буфера) измерен и выключен.** 47 % попаданий, но сам по себе выигрыша
  не даёт. Он не мусор: это готовый быстрый путь для M2, включать вместе с M2 и мерить вместе.
- **`snapdiff` и `snapswap` включены** (−0,7…−1,7 % CPU на draw, три повтора, обе полосы).
  Копия снимка стоит ~0,3 мс — больше из неё не вынуть.
- **`faultkb=64`** подтверждено против 256 шестью повторами в двух свипах. Не трогать.
- **Гейты записи A4** (`recbatch`/`recrelax`/`recpin`) закрыты: три повтора в Sky Garden порога
  ±1,4 % не держат. Остаются 0, вопрос закрыт.
- **Зависание на входе в Sky Garden найдено и вылечено** (гейт `acopyidle`, умолчание 1): один
  батч в голове общей очереди застревал на семафоре пула асинхронных копий. **`KYTY_PIPELINE_CACHE=0`
  (средство сессии 57) больше не первое средство — в сессии 58 оно не помогло.** При повторе
  зависания первым делом смотреть `acopy=<поставлено>/<завершено>/<просигналено> acopy_pending=`
  в строке `GpuWaitSlow:`/`GpuHangAbort:`. Сам дефект в пуле копий по коду не доказан — правка
  снимает зависимость живости от его бухгалтерии.
- При FPS > 25 рисунок кадров игры меняется — сравнивать по нескольким полосам draw (`bands.py`).

## 2. Работы сессии (по отношению выгода/риск)

1. **B9 — dynamic offsets, первым номером.** Потолок подтверждён и не режется железом: 1 451 набор
   из 2 733 (53 %) повторяет предыдущий набор своего layout'а, `e9_dyn_over` = 0 при
   `maxDescriptorSetStorageBuffersDynamic` = 16. Подпись кэша трансляции **не меняется**,
   прогревочный вход не нужен. Что учесть (измерено в сессии 58):
   - половина наборов кадра идёт через push descriptors, а `ePushDescriptorKHR` **несовместим** с
     dynamic-типами — решение принимать per-pipeline, а не глобально;
   - `DescriptorHeap::CreatePool` не содержит `eStorageBufferDynamic`/`eUniformBufferDynamic` —
     иначе `ErrorOutOfPoolMemory`;
   - `pDynamicOffsets` идёт по возрастанию номера биндинга, а `program.bindings.descriptors` не
     отсортирован;
   - править два места привязки синхронно: `descriptors.cpp` и `commandRecorder.cpp` (гейт
     `recpack`).
2. **M2 — параллельное разрешение draw'ов.** Условие плана выполнено: memo запроса буфера есть
   (`buffast`, 47 % попаданий), 84 % draw'ов без жёстких мутаций, 78–89 % в чистых сериях ≥ 64
   (E1/E2 сессии 57). Единственный механизм с кратным потенциалом; включать `buffast` вместе с ним.
3. **Пакет правок в подписи кэша трансляции: B5, B7, B1d.** Меняют `graphics/shader/**`, значит
   нужен прогревочный вход пользователя — планировать на ту же сессию, где он и так заводит сцену.
4. Если останется время: B3 (эпоха статического состояния программы), B2b.

## 3. Методика (как в сессиях 57–58)

- Фазы по 500–600 present, A B A B, решение по разности со средним соседних баз, порог ±1,4 %,
  **три повтора** каждой конфигурации: одна пара в Sky Garden ничего не доказывает.
- `summary3.py <tag>` и **`bands.py <tag>`** (несколько полос draw); ядра — отношение сумм, а не
  медиана (`GetProcessTimes` тикает по 15,6 мс).
- **Свип бракуется, если базы уехали.** В сессии 58 `sky58c` разошёлся с 6,99 до 8,44 мкс/draw за
  44 фазы, и решение пришлось принимать по короткому `sky58d` (19 фаз, базы 6,96–7,15). Свип длиннее
  ~20 фаз в живой сцене планировать с оглядкой на это; базы печатать до выводов.
- **Потолок мерить счётчиком до реализации** — в сессии 58 это дважды сэкономило работу
  (`protbatch2`, B9) и один раз показало, что потолок есть, а выигрыша нет (`buffast`).
- Гейты записи мерить без `KYTY_GPU_TIME` (`KYTY_GPU_TIME=unset` в `launch_run.py`).
