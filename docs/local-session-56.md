## 2. Что оказалось не тем, чем считалось

**«Два режима» сцены — это не сцена.** В сессиях 54–55 Sky Garden показывал то ~50, то ~65 мс CPU
при одном и том же числе draw, и это списывали на живой уровень. На самом деле поток GuestGpu и
воркеры `DrawAhead` оказывались на разных CCD процессора (Ryzen 9 9955HX3D, два CCD, свой L3 у
каждого), и каждый результат воркера читался из чужого кэша. Ручка `dapin=1` сажает их на одну
L3-группу — медленный режим исчезает совсем (`da_ccd_x` 577 → 0 на пустыне).

Симптом, который это объясняет задним числом: горячие адреса профиля сессии 54 в `FindBuffers`,
`PrepareBindings`, `ResolveTexture`, `StreamBuffer::Copy`, `~ResourceSnapshot` — это первые касания
векторов снимка, построенного воркером. На пустыне при `drawahead=0` те же адреса нулевые.

**Веер задач M1 — артефакт сериализации, а не разные планы.** `PlanFingerprint` хэширует план так,
как его пишет кэш трансляции, а `IR::Value` хранит immediate в union, у которого конструкторы
заполняют только младшие байты, тогда как запись сохраняет все 64 бита (план, загруженный из файла,
навсегда несёт мусор своего файла). Из-за этого статические варианты одной программы (раскладка
вершин, которой план не касается) получали разные отпечатки: скан кэша — **68 из 69 многовариантных
программ имеют один канонический план**. Гейт `daclass` считает класс по каноническим байтам и ставит
одну задачу на класс: `da_q` 2186 → 1070 на пустыне, отход `da_unused` 1118 → 5.

**Потолок M3 меньше, чем ожидал план.** Весь `nvoglv64.dll` в профиле потока GuestGpu — 7,3 %, то
есть перенос записи команд даёт ≤4 мс из 65. Ожидание плана «−10…12 мс» пришло из таймеров
`d_commit`/`d_emit`, в которые входит и разрешение, и инфляция самих таймеров.

**Профиль по семплеру был завышен вдвое.** Дамп печатал только 400 строк, а ключ включает цепочку
вызовов, поэтому в дамп попадала половина семплов, и все доли считались от неё. Исправлено.

## 3. Что сделано (всё под гейтами)

| гейт / ручка | что | умолчание |
|---|---|---|
| `dapin` (Knob) | привязка потока GuestGpu и воркеров `DrawAhead` к L3-группе: 1 — группа с наибольшим кэшем, 2 — группа текущего ядра GuestGpu, иначе маска | **1** |
| `procpin` (Knob) | то же для всего процесса (`SetProcessAffinityMask`) | 0 (не лучше `dapin`) |
| `daclass` | одна задача материализации на канонический класс плана | **1** |
| `daprefetch` | `_mm_prefetch` снимка и свидетеля при попадании слота | **1** |
| `daclone` | копия снимка вместо swap (векторы остаются в слоте) | 0 |
| `recordthread` | поток записи команд; теперь **переключается на лету** на границе буфера | **1** |
| `recpack` | хвост draw/dispatch и привязки пакетами (M3 шаги 1–2) | **1** |
| `recspin` (Knob) | сколько мкс поток записи крутится перед сном | 300 |
| `syncfree` (+`sfcheck`) | безлоковый выход `SynchronizeBuffer` для чистого диапазона | **1** |
| `protbatch` (+`pbcheck`) | `VirtualProtect` вне спин-локов трекера | **1** |
| `texfaulthint` | write-fault не берёт `TextureCache::m_lock`, если на страницах нет образов | **1** |
| `trackfree` | безлоковые чтения битовых карт трекера (сессия 55) | **1** |
| `texfast` (+`texfastcheck`) | попадание memo текстур отдаёт записанный `vk::ImageView` | **1** |
| `texlru` | LRU трогается один раз на `m_gc_tick` | **1** |
| `clampvma` | memo `ClampRangeSize` по непрерывному committed-участку | **1** |
| `smpmemo` | потоко-локальный memo `SamplerCache::GetSampler` | **1** |
| `dsring` | кольцо descriptor set'ов на layout вместо пулов | **1** |
| `texmemo2`, `bindspare`, `protfast` | измерены, 0 % в обеих сценах | 0 |

Плюс: строка `FrameTrace-x:` со счётчиками по имени (новые счётчики больше не требуют правки
форматных строк), разбор гейт-файла по целым именам (`texfast` внутри `texfastcheck=1` раньше
перекрывал друг друга), семплер печатает все строки дампа.

**Почему `dsring`:** пул дескрипторов ключуется хэндлом layout'а, а layout свой у каждого пайплайна;
свежий пул вмещает ровно `dspool/dsbatch` = 32 layout'а, а переиспользованный сбрасывается целиком
первым же layout'ом, которого в нём нет. Отсюда ~250 `vkAllocateDescriptorSets` на кадр в Sky Garden
при ~4000 нужных наборов и ~8300 выделенных. Кольцо на layout с тиком на каждый набор: в стационаре
`ds_ring_grow=0`.

## 4. Два дефекта, найденных ревью и исправленных (оба старше этой сессии)

1. **Потеря записи гостя.** Загрузка «только чтение» копировала страницу в staging, пока отложенная
   защита текстурного воркера (`KYTY_ASYNC_PROTECT`, включён по умолчанию) ещё оставляла её
   записываемой на хосте: запись гостя в это окно не давала ни fault, ни CPU-dirty бита и терялась
   до следующего флипа. `ForEachUploadRange` теперь безусловно сливает отложенные защиты всех
   регионов диапазона до копии.
2. **Санитайзер indirect-аргументов** при занятом слоте звал `Wait(tick)` текущего тика, то есть
   `Submit` посреди draw'а, у которого закэширован хэндл уже завершённого буфера. Хэндл теперь
   берётся после ожидания.

Прочее по ревью: кольцо `dsring` ограничено (иначе память не возвращалась), неудачный
`SetThread/ProcessAffinityMask` больше не повторяется на каждой задаче, гейт-файл длиннее буфера
игнорируется целиком, `RecordCommandWriter` отменяет открытую запись в деструкторе, `Handle()`
запрещён при открытой записи, проверка границ потока команд безусловна, сторож `pb_stuck` считает
повторы в пределах миллисекунды (раньше ловил нормальный кадровый цикл).

## 6. Где мы относительно 60 FPS

Sky Garden: **CPU 47 мс, GPU 16 мс, ~5300 draw, 20,1 FPS.** Нужно ещё втрое по CPU.

Свежий профиль потока GuestGpu (`sky62`, 12,5 тыс. семплов; фаза со всем включённым против базы):

| статья | всё включено | база |
|---|---:|---:|
| `TrackingSpinLock::lock` | **2,3 %** | 8,5 % |
| `VirtualProtect` (`ProtectMappedUnlocked`) | 5,8 % | 3,7 % |
| `ApplyGuard` (новый замок применения защиты) | **4,2 %** | 0 |
| `CommandRecorder::EndRecord` (публикация пакетов) | **4,8 %** | 0 |
| `ResolveTexture` | 4,1 % | 4,1 % |
| `CommitBindings` | 2,6 % | 4,8 % |
| `VerifyWitness` + `AheadTake` + `QueueAheadSource` | 6,4 % | 9,5 % |
| листья драйвера `nvoglv64` | **2,8 %** | 7,1 % |

Два новых пункта — плата за механизмы этой сессии, и оба стоит снять: `ApplyGuard` 4,2 % — это
сериализация применений защиты, о которой предупредило ревью (замок берётся и когда `protbatch`
выключен), а `EndRecord` 4,8 % — публикация пакета, то есть кандидат на удешевление (сейчас каждая
запись будит потребителя через мьютекс).

**Дальше:** (1) убрать `ApplyGuard` с синхронного пути и удешевить `EndRecord` — это ~9 % почти без
риска; (2) M2 — предразрешение привязок на воркерах (единственный оставшийся механизм с кратным
потенциалом); (3) компактная таблица M1 (индекс из маленьких записей вместо 32 768 слотов по 504 Б);
(4) `protbatch` фаза 2 (слить защиты всей `SynchronizeBuffersOfDirtyRanges` в один флаш);
(5) GPU 16 мс: простой между отправками внутри кадра.
