# Сессия 64 — измерение M2 до реализации: E4 (`shadowresolve`) и E6 (`shadowinline`)

База: `merge-upstream`, HEAD сессии 63 — `1c2725d`. Итоговый коммит **6fd1247 + dc9d8bf** (Sky Garden) (хэш дописан
следующим коммитом). Push нет.

## 1. Главный результат

- **Решение сессии (вопрос §2 промпта задан пользователю, ответ — «сначала измерить M2»):** вместо
  двух подготовительных сессий C1+C2 сняты числа §6 плана, которых M2 не хватало, — E4 (репетиция
  конкуренции: K воркеров повторяют читающую часть разрешения привязок и выбрасывают результат) и
  E6 (та же читающая часть второй раз на самом потоке GuestGpu — валовая цена того, что M2 мог бы
  унести). E1/E2 не повторялись: они сняты в сессии 57 (84 % чистых draw, 89 % в сериях ≥ 64).
- **Реализовано:** ручка **`shadowresolve`** (`KYTY_SHADOW_RESOLVE`, 0 = выкл, до 16 воркеров),
  гейт **`shadowinline`** (`KYTY_SHADOW_INLINE`, 0), ручка **`shadowmask`** (`KYTY_SHADOW_MASK`,
  3: бит 1 — пробы образов, бит 2 — пробы буферов); новые файлы
  `host_gpu/renderer/shadowResolve.h/.cpp` (кольцо Vyukov на 1024 задания, K потоков, пиннинг по
  `dapin`), `TextureCache::ShadowProbe` (чтения memo-hit + `texfast` под `m_lock`),
  `BufferCache::ShadowProbe` (чтения `buffast`-memo, эпохи загрузки, трекер — без лока, у кэша его
  нет), `RenderExecutor::ShadowQueue` в конце `PrepareGraphicsBindings`; счётчики `sh_*` в
  `FrameTrace-x`. Всё по умолчанию 0, при 0 — два атомарных чтения на draw.
- **Пустыня (`d64c`, 29 фаз по 300 кадров, ~755 draw, база 7,63–7,80 мкс CPU на draw, спред
  ±1,3 %):**

  FPS во всех фазах с воркерами −1…−2,4 %. Состав проб в сцене тот же, что на пустыне: образов

  **Налог четырёх читателей на поток GuestGpu (+7,9 %) равен или больше валовой цены читающей
  части на нём же (+6,6 %); один читатель стоит +4,3 %.** Налог не складывается из содержимого
  проб (образы или буферы по отдельности дают почти столько же, сколько вместе) — это цена
  передачи и разделяемых линий на задание, а не конкретного кэша. Воркер тратит на те же чтения
  2,6× времени критического потока (`sh_us` 860 против `sh_inline_us` 342 мкс) — холодные линии,
  спин-лок, региональные локи трекера.
- **Что разрешимо на воркере (состав проб, пустыня, на кадр):** образов 7 120 — по записанному
  view 6 870 (**96 %**), memo протухло 206, storage/DCC 38, нужен `FindTexture` 12; буферов 5 320 —
  memo запроса 1 160–1 220 (23 %), эпоха загрузки 420–500 (9 %), **копия в stream-кольцо 1 030
  (19 %), `SynchronizeBuffer` 2 450–2 520 (47 %)**, без диапазона 102. При ~7 буферных привязках на
  draw и 47 % медленных draw, у которого воркер разрешил бы все привязки, почти нет — то же, что
  E1 сессии 57 (`BufSlow` на каждом draw). Копии в кольцо воркер мог бы делать сам только с
  приватным сегментом кольца (C1); `SynchronizeBuffer` — нет.
- **Вывод для плана: M2 (трек C, C1–C4) закрыт потолком.** И на пустыне, и в Sky Garden налог
  одного читателя (+4,3 % / +6,3 %) не меньше валовой цены всей читающей части разрешения
  привязок на критическом потоке (+6,6 % / +5…6 %, счётчиком 7 % потока); четыре читателя стоят
  +7,9 % / +6…7 %; сама постановка задания — 1,5 % потока в сцене. При этом воркер мог бы
  разрешить целиком лишь draw без единой медленной привязки, а `SynchronizeBuffer` нужен половине
  буферных привязок (~9 на draw). Чистый выигрыш отрицателен при любом КПД, C1–C3 не начинать.
  Оценка «≈20 % потока» §5.3 плана считала профильные статьи целиком; читающая часть в них —
  треть.
- Попутно: emulator при старте упал на `controller.cpp:497` (SDL прислал удаление пада, которого
  список не видел) — `Disconnect` неизвестного id теперь логируется и игнорируется.

## 2. Что мерилось и как

Гейты и счётчики (все под `KYTY_FRAME_TRACE=lite`, `FrameTrace-x:`): `sh_jobs` (draw, чьи привязки
перечитаны), `sh_drop` (кольцо полно), `sh_over` (> 48 привязок), `sh_img` / `sh_img_gone` /
`sh_img_stale` / `sh_img_slow` / `sh_img_view` / `sh_img_fast`, `sh_buf` / `sh_buf_none` /
`sh_buf_fast` / `sh_buf_epoch` / `sh_buf_stream` / `sh_buf_slow` / `sh_buf_new`, `sh_us` (время
воркеров), `sh_inline_us` (время на GuestGpu при `shadowinline`), `sh_push_us` (сборка задания +
постановка), `sh_lock_us` (захват `TextureCache::m_lock` в пробах), `sh_trk_us` (локовые запросы
трекера в пробах буферов), `sh_wake` (пробуждения воркеров).

Задание несёт то, что draw уже разрешил (id образов, поля desc для проверок, штамп записанного
view из memo, id и диапазоны буферов, флаг записи), а не указатели в память draw. Проба образа
повторяет проверки попадания memo `ResolveTextureWith` и быстрого пути `RebindImages` (`texfast`:
`bind_stamp`, `pending_levels`, `TextureSourceSettled`). Проба буфера повторяет `buffast`-memo
(своя потоко-локальная таблица), `UploadEpoch`/`HasCurrentUpload`, затем классификацию
`ObtainBuffer` (копия в кольцо / `SynchronizeBuffer`) по запросам трекера — на GuestGpu (inline)
безлоковыми, с воркера локовыми, как у любого чужого потока.

Три прогона пустыни: `d64a` (первая версия, воркеры спинят 2,6 мс до сна) — inline +6,0 / +5,1 %,
K=1 +5,1, K=2 +7,4, K=4 +9,4 / +8,4 %; `d64b` (спин 50 мкс — воркеры засыпают между draw'ами, и
producer платит notify на каждый push: `sh_push_us` 420 мкс = 7 % потока, K=4 +11…12 % независимо
от `shadowmask`) — урок: **протокол пробуждения — статья первого порядка, M2 обязан ставить
задания пачками, как M1**; `d64c` (notify не чаще раза в 64 push, спин 0,5 мс) — таблица §1.
Во всех трёх `sh_drop` = 0, `sh_over` = 1 на кадр.
