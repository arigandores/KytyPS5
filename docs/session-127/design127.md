## 2. Множество пропуска — п. 76(з)(2)

### 2.1 Регистровые источники (группы п. 64(б))

Поколения групп `G_mask`, `G_slot[0..7]`, `G_dact`, `G_depth` на контекст — те же крючки, что у `rk3cen` (с. 126, в
`main`): сеттеры `HW::Context` (`hardwareContext.h:869–915` — 12 сеттеров `CB_COLORn_*` → `G_slot[slot]`; `:928–931`
`CB_TARGET_MASK` → `G_mask`; `:937–985` глубина → `G_depth`, `DB_STENCIL_INFO` `:949–952` → `G_dact`; `:1097–1100`
`DB_RENDER_CONTROL`, `:1108–1111` `DB_DEPTH_CONTROL` → `G_dact`; `:1119–1127`, `:1140–1143`, `:1149–1152` → `G_depth`),
запись объекта `Context::Reset` (`:864–867`) и `m_ctx = m_saved_ctx` (`graphicsRun.cpp:393–394`) — все группы. Таблица
вызовов сеттеров D_census — 47 мест `pm4Handlers.cpp` (п. 68(б), `C:/kyty/s126/n3prime_table.txt`).

**Относимость для пропуска (строже п. 64(б)):** у пропуска нет выходов резолюции ТЕКУЩЕГО draw (её и снимают), поэтому
относимость берётся не «по выходам текущего или записанного draw», а по тому, какие группы МОЖЕТ прочесть резолюция
при неизменной маске:

Rel_skip(C) = {`G_mask`, `G_dact`, `G_depth`} ∪ {`G_slot[0]`} ∪ {`G_slot[n]` : n ≥ 1, `render_target_mask_slot(mask, n) ≠ 0`},

где `mask` — `CB_TARGET_MASK` записи (= текущей: `G_mask` в Rel_skip всегда, поэтому пропуск возможен только при
несдвинутой маске). **Довод Rel_skip ⊇ Rel п. 64(б):** цикл резолюции посещает слот 0 всегда, слот n ≥ 1 — только при
`render_target_mask_slot(mask, n) ≠ 0 && base.addr ≠ 0` (`renderDraw.cpp:2572–2574`); слот, давший цель в текущем
или записанном draw, посещён, значит, при несдвинутой маске его бит маски ≠ 0 (или n = 0) ⇒ `G_slot[n]` ∈ Rel_skip.
`G_depth` в Rel_skip всегда (п. 64(б) — только при глубине в текущем или записанном draw). Лишняя относимая группа
сужает множество пропуска — сторона «безопасно» (для корректности, не для числа). Пропуск по регистрам: ни одна
группа из Rel_skip(C) не сдвинулась с записи (сравнение 11 поколений, как `Rk3Post`, `renderDraw.cpp:1192–1197`).
**[RC2]** Этот же признак («сдвинулась ли группа Rel_skip с записи») вычисляется при 2 и 3 на каждом draw с записью и
печатается в строке `MISMATCH` как `reg=<0|1>` (§5.2); при 2 и `PA` он по построению 0.

## 4. Ручка `rtskip` (`KYTY_RT_SKIP`)

### 4.1 Значения, чтение, защёлка

- `{"KYTY_RT_SKIP", "rtskip", 0, 3}` — ПОСЛЕДНЯЯ строка `KNOB_DEFINITIONS` (`src/common/gates.cpp`), `Knob::RtSkip` —
  последний элемент перед `Count` (`gates.h`); **`check_gate_order.py` после патча и ДО сборки** (порядок компилятор не
  проверяет). В `gates_base.txt` имени нет — плечи называют его явно, **заменой на месте**.
- **Чтение — ОДИН раз на draw** (п. 76(з)(1), ловушка с. 97): на входе `RenderExecutor::DrawIndex` (`renderDraw.cpp:3991`,
  рядом с `Rk3Latch`) и `DrawAuto` (`:4209`) — одна relaxed-загрузка ручки и TLS-проверка, как `Rk3Latch` (`:993–998`);
  значение защёлкивается в TLS `t_rts` на весь draw; места A, B, пост, закрепление и крючки читают только `t_rts`.
  Поэтому ручка может быть плечом расписания ABBA.
- **Вооружение** (медленная половина защёлки, как `Rk3LatchSlow` `:940–990`): только на потоке GuestGpu
  (`Common::SkipCeil::t_gpu`, иначе `rts_xthr`++ и 0); при `rk3cen`, `spine`, `spcen`, `slicecen`, `skipceil`,
  `bindfloor`, `m4baton` ≠ 0, `rtfast` = 0, `graphics_debug_dump`, `KYTY_RENDER_MEMO_FAST=0` — отказ: строка
  `RtSkip: refused reason=<имя>` ОДИН раз на причину и 0 (§4.2). **`KYTY_FRAME_TRACE` не требуется** (п. 77(д)).
- **Выход из вооружения** (1/2/3 → 0 или отказ) обнуляет таблицу записей; первая вооружённая после этого draw каждого
  контекста — без записи (`rts_xa_rec`). Смена между 1, 2 и 3 записи не обнуляет. Крючки проверяют ту же TLS-защёлку:
  запись между последним draw при 0 и первым при ≥ 1 не видна — и не нужна, потому что записи в этот момент нет.
- **[RC1]** При 2 и 3 жизненный цикл записи тот же, что при 1 (§5.1); различаются только исполнение (полный путь всегда)
  и счётчики.

### 4.2 Отказы

| причина | почему несовместимо |

| `rk3cen ≠ 0` | общие крючки и общая TLS-маска вооружения крючков (§4.5); перепись с. 126 классифицирует выходы захвата, которого при пропуске нет |

### 4.3 Алгоритм

**Место A** (вместо вызова `PrepareDrawRenderState` в `DrawIndex` `:4167–4169` и `DrawAuto` `:4342–4344`; при
`t_rts = 0` — ровно прежний вызов). Предикат `PA` (первое несработавшее — причина, счётчики `rts_xa_*`, разбиение):

1. `rec` — запись контекста, изъятая на защёлке (§4.4), есть и закреплена — иначе `rts_xa_rec`;
2. конфигурация (Н6; гейт `rtfast` — свежей загрузкой) — иначе `rts_xa_cfg`;
3. ни одна группа Rel_skip не сдвинулась (§2.1) — иначе `rts_xa_reg` (**значение 3 этот пункт пропускает**, §6; признак
   `reg` вычисляется всё равно — для строки `MISMATCH`, **[RC2]**);

6. все слоты memo записи (посещённые цвета через memo и глубина) `valid` и той же `version` (Н8) — иначе `rts_xa_memo`;

При `t_rts = 1` и `PA`: копия `pre` записи в состояние draw (§3.2), `ps_active` свежий, воспроизведение
Touch/`BindRenderTarget`, решение «framebuffer skip» тем же условием `:2588`; TLS-флаг `t_rts_a = 1`. Иначе — полный
`PrepareDrawRenderState`. При `t_rts = 2/3` — §5.1. В цикле резолюции полного пути (только при `t_rts ≠ 0`, строки §8.2):
после каждого `ResolveRenderColorTarget` черновик записи получает (слот, `memo_slot`, `memo_version`, `image_id ≠ 0`,
индекс записи), после `ResolveRenderDepthTarget` — то же для глубины. **[RC9]** Сразу после возврата полной резолюции (на
месте A, до `RefreshShaders`) черновик снимает `pre` — копию `color_info[0..k]`, `color_count`, `depth_info`. Снимок
поколений контекста на месте A — для стража `rts_acqw`.

**Место B** (вместо вызова `AcquireRenderTargets` `:3411–3415`, только если `t_rts_a`; иначе прежний вызов). Предикат
`PB` (причины `rts_xb_*`; разбиение — §7.3 Т2):

### 4.4 Запись контекста

Таблица ≤ 8 контекстов по адресу `HW::Context` (TLS, выделяется при первом вооружённом draw; переполнение — `rts_ovf`,
draw без записи). Запись: 11 поколений на момент записи; `slice_offset`; `mask`; границы глубины (биты); **[RC9]** выходы
резолюции `pre` (`color_info[0..k]`, `color_count`, `depth_info` — как их вернула резолюция записанного draw, до захвата)
и `post` (те же поля после захвата); посещённые слоты памяти (слот, `memo_slot`, `memo_version`); по каждой цели —
`backing`, вид, `bind_stamp`, `source_size/first_level`, `state_serial`, `htile_clear_mask`, `is_bound`,
`attachment_layout/access`, экстент для счётчиков; `RenderState`; `g_pass_extents`; `MetaEpoch()`; `pass_serial`;
**[RC1]** `age` — число постов подряд, на которых запись только перезакреплялась (draw «`PA ∧ PB`»), сбрасывается в 0 при
каждом обновлении. Размер записи печатается в строке `RtSkip: mode … rec_bytes=`.

**Изъятие на защёлке (Н12):** вооружённый draw ищет запись своего контекста и снимает с неё флаг годности, держа
указатель в TLS; флаг возвращает только пост этого draw (полным обновлением, обновлением части захвата или
перезакреплением). Любой возврат до поста оставляет контекст без записи; при 2/3 следующая защёлка, найдя
невозвращённый указатель, считает `rts_lost` (и `rts_early`, если тот draw дошёл до места A) **[RC7]**.

**Строгое взятие записи:** записывается, только если захват этого draw был «чистым» — ни одного медленного пути
`AcquireTargetView` и повторного поиска, `MetaEpoch` не сдвинулся за время захвата, нет
`depth_clear_enable`/`depth_load_clear_enable`, глубина не `is_bound` и **не `info.data.Empty()`** **[RC5]**, у каждой цели
`memo_slot ≠ UINT32_MAX`, каждый посещённый слот цвета — либо неактивный по регистрам (`colorRenderTarget.cpp:113–118`),
либо через memo, **и `pre` == `post` по всем полям битов `0x001` и `0x400`** **[RC9]**; иначе — `rts_rec_x` и контекст без
записи. Это правило строгой записи `spcen` (`:1644–1656`), перенесённое на две фазы.

**[RC9] Почему нужно `pre` == `post`.** Состояние draw общее для всех draw потока (`DrawStateLease`,
`renderDraw.cpp:714–754`), и попадание memo с той же версией `r` не копирует (§2.3(1)), поэтому `pre` записанного draw d₀
несёт то, что оставил захват d₋₁, а `pre` следующего draw d₁ — то, что оставил захват d₀ (= `post` d₀). Если бы у d₀ было
`pre` ≠ `post`, фаза A у d₁ восстановила бы не то, что вернула бы полная резолюция d₁, а сверка `O` при 2 дала бы ложный
`MISMATCH` (`RTSKIP_INCORRECT` без дефекта) — ровно сценарий RC9. Единственный такой случай при прочих строгих условиях —
draw сразу после draw с `meta_clear` (`depth_load_clear_enable` у d₀: `pre` = true от `:1882` d₋₁, `post` = false, потому что
`TouchMeta` d₋₁ съел очистку, `:1884–1887`); повторный поиск цвета уже исключён. Такой d₀ записью не становится, следующий
— становится (его `pre` = `post` d₀ = false). При `pre` == `post` фаза A восстанавливает `pre`, фаза B оставляет `post` — одно
и то же, и сверка `O` «свежие до захвата против `pre`» (п. 78(д) RC9) корректна. Это сужение множества (сторона
«безопасно»), доля — ряд `rts_rec_x`; правило — проектное, в подтверждение лиду вопрос В7 §12.

## 5. Самопроверка `rtskip=2` — п. 76(з)(3), п. 78(б)–(в), (ж)

### 5.1 Что делается [RC1]

**Жизненный цикл записи при 2 и 3 — дословно как при 1** (п. 78(б)); отличие одно: полный путь (резолюция + захват)
выполняется ВСЕГДА, его результат используется дальше — эмуляция при 2/3 корректна по построению. По шагам на draw:

1. **Защёлка:** изъятие записи контекста (Н12), как при 1.
2. **Место A:** `PA` вычисляется ТОЛЬКО ЧТЕНИЕМ (`try_get`, без `GetImage`, без Touch, без записи) по изъятой записи; при 3
   п. 3 пропускается, признак `reg` вычисляется. Затем полная резолюция. **[RC9]** Точка выборки «свежие до захвата» —
   сразу после возврата полной `PrepareDrawRenderState`, до `RefreshShaders`. Если `PA`: `rts_chk`++, при `rec.age ≥ 1` —
   `rts_chain2`++, датчик `rts_chain_max` ← max(`rec.age`); сверка битов `0x001`, `0x400`, `0x002`, `0x004`, `0x008` (§5.2).
3. **Место B:** если `PA` — `PB` только чтением ДО захвата, снимки `MetaEpoch()`, `ImageStateSerial()`, состояния прохода;
   затем полный захват. Если `PA ∧ PB`: `rts_chk_b`++, сверка битов `0x010`–`0x200` (§5.2).
4. **Пост — обновление записи тем, чем обновилась бы при 1:**
   - `PA ∧ PB` (при 1 — пропуск целиком): запись **НЕ обновляется** свежими выходами; только перезакрепление, `age`++;
   - `PA ∧ ¬PB` (при 1 — «только A»): часть резолюции (`pre`, слоты memo, поколения, аргументы) остаётся записью — при 1 её
     восстановили бы из записи; часть захвата (цели, `post`, `state_serial`, `is_bound`, раскладки, `RenderState`,
     `MetaEpoch`, экстенты) — из свежего захвата по строгому правилу §4.4 (`rts_rec` или `rts_rec_x`); `age` ← 0;
   - `¬PA` (при 1 — полный путь): полное обновление из свежих выходов по строгому правилу (`rts_rec`/`rts_rec_x`/`rts_ovf`);
     `age` ← 0.
5. **Закрепление** после `BeginRendering` — как при 1.

При 3 запись живёт так же (как жил бы режим 1, не видящий регистров): на draw с `reg=1`, прошедшем остальные пункты, она
только перезакрепляется, поэтому расхождение повторяется на следующих draw, пока `PA`/`PB` не откажет по другой причине.

### 5.2 Сравниваемые выходы (всё, что читает путь дальше)

| бит | что сравнивается | с чем |
|---|---|---|
| `0x001` O — выходы резолюции, читаемые рендером **[RC2]** | `color_count`; для индексов `0..k`: `image_id`, `target_slot`, `guest_mip_level`, `guest_array_layer`, `export_mapping`, `desc` (все члены, `view_info` — `operator==`, прочие — почленно, float — по битам; не `memcmp` агрегата: паддинг, урок с. 83); `depth_info` — все члены `RenderDepthInfo` (`depthRenderTarget.h:21–43`, `stencil_front/back` — `operator==`, float по битам) **кроме `memo_slot`/`memo_version`** | свежие «до захвата» против `pre` записи **[RC9]** |
| `0x400` U — учёт памяти **[RC2]** | `memo_slot`, `memo_version` каждого индекса `0..k` цвета и глубины | то же |
| `0x002` K — memo | после свежей резолюции `version` каждого посещённого слота записи не сдвинулся (ни записи, ни повторного поиска) | записью |
| `0x004` T — привязки целей | хвост `m_bound_images`, добавленный резолюцией, == цели записи в порядке резолюции | записью |
| `0x008` F — ветка | свежая резолюция не пошла в `ResolveColorTargets` и не вернула false иначе, чем запись | — |
| `0x010` R — `RenderState` | возвращённый захватом `RenderState` (`operator==`, как `SpRtPost` `:1574`) | запись |
| `0x020` X — запоминаемые записи захвата | `attachment_layout/access` каждой цели; `depth_load_clear_enable` = false; `g_pass_extents` | запись |
| `0x040` S — барьер | `ImageStateSerial()` не сдвинулся за время захвата (как бит S `spcen`) | — |
| `0x080` P — проход | проход, открытый до захвата, не закрыт им | — |
| `0x100` M — метаданные | `MetaEpoch()` не сдвинулся за время захвата | — |
| `0x200` L — медленный путь | ни одна цель не пошла медленным путём `AcquireTargetView` или повторным поиском | — |

Биты `0x010`–`0x200` — только при `PB`. Любой ненулевой бит — `rts_bad`++; если при этом `reg=0` — ещё `rts_bad_noreg`++
**[RC2]**; строка **`RtSkipVerify: MISMATCH frame=<f> bits=0x<hex> reg=<0|1> chain=<age> colors=<n> depth=<0|1> pa=1
pb=<0|1> mode=<2|3>`** (≤ 40 строк на процесс); дальше используется свежий результат. **Гонка:** если медленный путь
начался с `bind_stamp`, сдвинутым после проверки `PB` (решается на входе медленного пути, как `t_sp_rt_stamp_race`,
`renderDraw.cpp:1326–1336`), расхождение считается в `rts_race`, а не в `rts_bad`. Счётчики `rts_bad`, `rts_bad_noreg`,
`rts_race` копятся и после 40-й строки.

**[RC2] Почему `memo_slot`/`memo_version` вынесены.** Запись `CB_TARGET_MASK`, меняющая только маску записи каналов слота
(например 0xF → 0x7), меняет ключ memo (`ColorTargetMemoExtra` кладёт маску слота в ключ, `renderMemo.h:66–71`,
`colorRenderTarget.cpp:128`), свежая резолюция уходит в ДРУГОЙ слот memo и возвращает те же `image_id`/`desc`/
`export_mapping` (последний берётся из формата цели, `colorRenderTarget.cpp:494`, не из маски) с другими
`memo_slot`/`memo_version`. Такое расхождение — не выход рендера; при 3 оно не засчитывает контроль (§6), при 2 по-прежнему
обязано быть 0 (все биты).

### 5.3 Что самопроверка доказывает и чего нет

Доказывает (на прогнанной сцене): для каждого draw, где пропуск сработал бы, его выходы и запоминаемые записи равны
полному пути относительно записи, которую вёл бы режим 1, — **многошаговая цепочка проверена на прогнанных сценах**
(`rts_chain2`, порог §5.4) **[RC1]**. Не доказывает: полноту источников вне прогнанных сцен; отсутствие расхождений,
которых таблица §5.2 не сравнивает (например, порядок LRU при равных касаниях — не сравнивается, потому что
воспроизведение делает те же касания; условие ревью шага 4 — воспроизведение зовёт ТЕ ЖЕ функции: `TouchImage` и
`BindRenderTarget`, который через `GetImage` касается второй раз, `textureCache.h:102–105`, `descriptors.cpp:2974–2978`).
**Остаточное различие 2 и 1:** при 2 состояние после draw «`PA ∧ PB`» — свежий полный путь, при 1 — воспроизведение; если
они разойдутся, сверка поймает это на ЭТОМ же draw (биты `0x010`/`0x020`) или на следующем (бит `0x001` против `pre`,
потому что свежие «до захвата» d+1 — это состояние, оставленное захватом d); сверка всегда идёт против записи режима 1.

### 5.4 Условия на прогонах самопроверки (п. 78(б), (в), (ж)) [RC1][RC2][Q1][Q2]

Прогоны самопроверки — дым шага 5 `rtskip=2` на опоре и в пустыне и зарегистрированный `k3k127` (п. 76(з)(3)(а), (в)).
На КАЖДОМ из них (суммы по строкам прогона — правило популяции, вопрос В8 §12):

- `rts_bad` = 0 на всех строках (все биты, включая `0x400`); `rts_chk` > 0;
- **Q1:** `rts_chain2` ≥ 0,05 · `rts_chk` — иначе самопроверка цепочки не жива, условие (з)(3)(в) не выполнено;
- **Q2:** `rts_race` = 0 — иначе отгрузки нет, исход `NOT_RESOLVED` (не `INCORRECT`);
- при 2 `rts_bad_noreg` = `rts_bad` = 0 (при `PA` признак `reg` по построению 0).

На дыме `rtskip=3` (з)(3)(б): `rts_bad` > 0 И правило §6; `rts_bad_noreg` = 0 (> 0 — дефект, приравнивается к `rts_bad` > 0
при 2, исход по п. 76(з)(5) как у неверной цели).

## 6. Положительный контроль `rtskip=3` — п. 76(з)(3)(б), п. 77(г), поправка п. 78(в)

**Игнорируемый источник — регистровый целиком** (п. 77(г)): пункт 3 предиката `PA` (§4.3, поколения групп Rel_skip) не
проверяется; всё остальное — как 2 (полный путь всегда, запись по §5.1, сверка §5.2, свежий результат). Остальные
источники проверяются, поэтому draw, у которого гость переписал цели или состояние глубины, проходит `PA`, если записанные
цели ещё годны и их слоты memo не переписаны, — а свежая резолюция возвращает ДРУГИЕ цели/состояние.

**Правило засчёта (п. 78(в), заменяет правило ред. 1):** контроль засчитан, если `rts_bad` > 0 И в логе есть хотя бы одна
строка `RtSkipVerify: MISMATCH … reg=1 … mode=3` с битом **`0x001`** (выходы рендера в смысле §5.2). **Не засчитываются:**
строки только с `0x400` (учёт памяти); строки с `reg=0` (такое расхождение пропустил бы и режим 2 — дефект, счётчик
`rts_bad_noreg` > 0); строки только с `0x040`/`0x080`/`0x200` (состояние, п. 77(г)).

**Почему не тавтология (урок `texmemo8`, с. 121):** расхождение возникает не на пути счётчика, а в том же сравнении §5.2,
которое при 2 обязано молчать, и на выходах, которые читает рендер (`image_id`/`desc`/`depth_info`), при ДОКАЗАННО
сдвинутом регистровом источнике (`reg=1`). Регистровый источник — самый частый (269,5 XW на строку в `k3c126` [c]; 52,7
записи объекта на строку, каждая двигает все группы), поэтому контроль жив на опоре по построению сцены [I]; доля строк
`0x001` среди `reg=1` — [U] (перемены маски дают только `0x400`), это ряд дыма шага 5.

## 11. Риски и что проект НЕ доказывает

- Не доказывает выигрыш, не даёт прогноза; 60 FPS не обещаются. R_K3⁺ и любое число §1 — не выигрыш.
- Полнота источников — довод §2.3 по коду на `072e7d51` плюс самопроверка на прогнанных сценах; будущий код, пишущий
  `HW::Context` в обход сеттеров, пишущий `VulkanImage::state` без `NoteStateChange` (**[RC4]**) или меняющий смысл
  memo-попадания, её ломает.
- **[RC1]** Самопроверка ведёт запись режима 1 и проверяет цепочку; её живость — порог Q1 (оценка доли цепочечных сверок
  ≈ `rts_pb` ≈ 80–85 % — [I]).
- **[RC3]** Остаточная асимметрия счётчиков в пользу плеча 1 (≈ −19…−38 мкс [I], §8.1) — в Δ `k3p127`, не в игре.
- **[RC5]** Предпосылка варианта RC5 — каждая привязка `pixel->images` проходит `BindImage` [I] (условие ревью шага 4).
- Строгое взятие записи (вкл. `pre` == `post`, **[RC9]**, и `!Empty()` глубины, **[RC5]**), Rel_skip шире п. 64(б) и проверка
  прохода Н10/Н11 (**[RC4]**) сужают множество пропуска относительно S_K3 — выигрыш меньше R_K3⁺ и по этой причине тоже.
- Пропуск резолюции без захвата (фаза A без B) — снимает только резолюцию; доля — `rts_pa − rts_skip` (выводится).
- Воспроизведение порядка Touch/`BindRenderTarget` делает LRU тем же; время жизни образов в GC — то же [I].
- Счётчики `rt_hits`, `rt_fast_*`, `DrawTargetsNs` в плече 1 падают по построению (§3.2) — между плечами не
  сравниваются.
- **[RC10]** Сторож DRS — среднее отношение по плечам, а не по блокам; смешение ступеней внутри плеча, симметричное по
  плечам, он не видит (п. 78(е) — допуск на плечо).
- Одна сцена для времени (Sky Garden), одна сессия; режим BDA — свойство популяции.
