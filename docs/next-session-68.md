# Промпт сессии 68 — четыре убийственных эксперимента

Ты — оркестратор. Цель программы — **60 FPS в Sky Garden** (сейчас 30,0). Эта сессия ничего не
оптимизирует и ничего не переписывает: она снимает три числа (Δ`draws` от окклюзии, `f_full`, `A`),
каждое из которых способно закрыть целое направление, и четвёртое (причины загрузок образов), без
которого не сходится арифметика GPU. После неё станет известно, достижимы ли 60 FPS вообще;
сегодня этого не знает никто (`docs/local-session-66.md` §7).

Сессия 67 была инфраструктурной и своё сделала: вход в Sky Garden без человека занимает
**16,9–19,9 с** (8 из 8 попыток, ни одного зависания) вместо 298 с ручной игры, а стенд замера
разрешает **0,35 % (2·SE) по `cpu/draw` за один прогон 240 с** при истинном нуле на холостом плече.
Оба числа измерены, не оценены. Поэтому «четыре эксперимента за один прогон» из плана сессии 66
**пересчитаны**: прогон теперь стоит 17 с входа + удержание, и каждый эксперимент получает свой
прогон с двумя плечами и контрбалансом ABBA (`KYTY_GATE_SCHEDULE_ABBA` поддержан только для двух
плеч — четыре гейта в одном расписании смешивать нельзя).

## 1. Решено измерениями — не переоткрывать

- **FPS квантован по vblank**: 99,2 % кадров = ровно 2 vblank. Любая отметка выше 16,67 мс даёт
  ровно 30,0 FPS. Прогресс мерить в миллисекундах, FPS — только приёмка. Цель —
  `max(CPU, GPU)` **p99 ≤ 15 мс**, а не медиана 16,6.
- Закрыто и не переоткрывается (полный список — `docs/local-session-66.md` §8): zero-copy backing,
  межкадровый frame-replay, конвейеризация по кадрам, compute на отдельном потоке, склейка draw в
  инстансы, `VK_EXT_multi_draw`, фильтрация vkCmd динамического состояния, «прибить DRS», полный
  save state. Трек C (M2, `shadowresolve`/`shadowinline`) закрыт потолком в сессии 64.
- **Методика замера решена и не обсуждается заново** (все числа — `FACTS.md` §2.3):
  значение блока — **отношение сумм** (парная оценка воспроизводит бесблочную истину с точностью
  0,006 п.п.; медиана завышает на 2,1 п.п.); первичная метрика — **`cpu/draw`**, `cpu_gpu_us` на
  кадр — вторичная; **контрбаланс ABBA обязателен** (порядок A B A B даёт не ноль, а **+0,356 %**
  при 2·SE 0,385 %, и это смещение не зависит от warm-up); **равенство работы судить только по
  сумме draw, никогда по медиане** (в `ab67a` медианы плеч разошлись на 4,2 %, доля тяжёлых кадров
  на 12,6 п.п., а сумма — на 0,19 %); кадры старше первой строки `GateArm:` отбрасываются.
- **Длина прогона по измеренным SE** (2 плеча, период 30 present): `cpu/draw` — **15 пар**
  (900 кадров) для SE 0,5 %; `cpu_gpu_us` — **20 пар**; **`gpu_busy_us` — 108 пар (6480 кадров)**.
  При 24,4–24,7 FPS входа через `-lvl` 6480 кадров — это около 265 с одного только удержания:
  **любой эксперимент, чей вердикт зависит от GPU, планировать длиннее CPU-шного в 7 раз.**
- **Базы сессий 63–65 непереносимы.** Вход через `-lvl underwater_aerial_garden` приводит в другую
  точку сцены: `lvl67b` (кадры 1500+) — draws 4610–4724, `cpu_gpu_us` 32,7–33,0 мс, `gpu_busy_us`
  **18,2–19,8 мс**, dt 33,7–33,9 мс, 24,4–24,7 FPS; ручная база `sky64a` (полоса 4700–5100) —
  draws 4718, cpu 31,4 мс, `gpu_busy` p50 14,56 мс. Разрешение основного прохода то же
  (`rt_kpx/rt_att` = 2016 Kpx ≈ 1920x1080), выходная цель 3840x2160 в обоих случаях.
- Рекордер/плеер пада не нужен и не реализован (`FACTS.md` §3): ворота G-inf пройдены входом через
  argv. Разведка сохранена в `C:/kyty/s67/recon/pad.md`, это работа на день, если вдруг понадобится.
- Путь в пустыню через `KYTY_KEYS` остаётся хрупким (`d67a` дошёл до `worldmap` и не доехал до

2. Холостой A/A с ABBA: два текстуально одинаковых плеча, период 30, `KYTY_GATE_SCHEDULE_ABBA=1`,

   **Если 2·SE вышел заметно больше 0,35 % — стенд сломан, дальше не идти**: искать причину
   (чужая нагрузка на машине, троттлинг, изменившийся вход), а не мерить гейты.
3. `python C:/kyty/s68/guards.py base68a --video` — обязательно, с видео и проверкой глитчей.

Только после этого — гейты.

### 2.1 `occzero` — потолок окклюзии (самый дешёвый эксперимент с наибольшим неизвестным)

`graphicsRun.cpp:2426-2458`, event_type 0x39: в гостевую память пишется
`ready_bit | m_synthetic_occlusion_counter` (монотонно растущий счётчик), нулевого результата не
бывает никогда — **игра не отбрасывает невидимое, потому что мы ей врём**. Эмулятор печатает об
этом предупреждение в каждом прогоне; игра грузит `data/prein/lox/occlusion_plane.lox`.

Гейт `occzero` (одна строка): писать `ready_bit | 0` вместо счётчика. Мерить Δ`draws` и
Δ`cpu_gpu_us`. **Картинка развалится — это замер потолка, а не правка.**

**Порог (дословно из `docs/local-session-66.md` §6): Δdraws ≥ 15 % — направление становится
приоритетом №1** (бьёт по CPU и GPU сразу, не требует переписывания, повышает корректность
эмуляции). Это верхняя граница выигрыша от настоящих occlusion queries; `VkQueryPool` — нативная
возможность Vulkan, PM4-предикация в дереве уже есть.

Три особенности замера, которые надо учесть заранее:

- **`cpu/draw` здесь не первичная метрика.** Гейт меняет само число draw, поэтому вердикт — по
  `cpu_gpu_us` и `dt_us` **на кадр** и по `gpu_busy_us`; `cpu/draw` остаётся диагностикой.
- Раз в вердикте участвует `gpu_busy_us`, прогон нужен **на 108 пар (6480 кадров, ≈ 265 с
  удержания)**, а не на 240 с.
- **`guards.py` пункт 4 (равенство работы по сумме draw) на этом прогоне провалится
  намеренно**: здесь Δdraws — измеряемая величина, а не сторож. Остальные девять проверок
  обязательны, и это надо явно записать в отчёт, чтобы FAIL не приняли за брак прогона.

### 2.2 Эстафета `m4baton` — число `f_full`

~200–300 строк, **ни одного кэша не трогаем**: второй поток исполняет **настоящий** путь draw на
диапазоне, пока поток GuestGpu стоит; передаются `g_gpu_thread` (`graphicsRun.cpp:56/631`) и
`m_producer` (`commandRecorder.h:290`). Это даёт `f_full` для всей работы, включая мутации, при
нулевом риске корректности — ни приватизации скрэтча, ни RCU, ни приватных колец записи.

Счётчик строить по образцу сессии 64 (`sh_us` против `sh_inline_us`): мерить обе стороны — время
диапазона на воркере и время того же диапазона на потоке GuestGpu, — чтобы `f_full` получался
отношением, а не разностью двух прогонов.

Свип длины диапазона **32 / 128 / 512** даёт постоянную цену диапазона (splice). ABBA — только два
плеча, поэтому свип — **три прогона по два плеча** (`m4baton=0` против `m4baton=<длина>`), а не
одно расписание на четыре плеча.

**Ворота G-f (дословно из `docs/local-session-66.md` §6): f_full > 2,0 → M4 закрыт;
1,5 < f ≤ 2,0 → только после адресных правок; f ≤ 1,5 → идём. Цена диапазона > 25 мкс при
128 draw → диапазоны ≥512 draw, а таких серий в кадре 12, то есть эффективное K ≤ 3.**

Контекст, который надо держать в голове при интерпретации: все прежние замеры замедления на
воркере на этой машине — K=1 → 1,48x, K=4 → 1,78x, пустыня 2,6x, воркеры M1 2,9x, плюс налог
самого наличия воркеров на критический поток +4,2…6,5 % даже при K=1.

### 2.3 Счётчик `A` — последовательный пол

Правильная модель работы кадра — `W = F + P' + A`, где `A` — применение мутаций и запись команд.
**При конвейере пол = A**, и A по разным оценкам 9,1…13,8 мс — **не измерено ни разу**.

Реализовать гейт по образцу `shadowinline`, но **наоборот**: на каждом draw измеряется мутирующая
часть (touch LRU, `ConfigureImageSource`, копии в stream-кольцо, `SynchronizeBuffer`, загрузки,
запись команд), а не читающая. Результат — честный последовательный пол в миллисекундах на кадр.

**Ворота G-A (дословно из `docs/local-session-66.md` §6): A > 13 мс → M4 закрыт арифметикой.**

**Сюда же — удержание `m_context.GetMutex()`** через `SiteScope`: draw (`renderDraw.cpp:2355,2486`)
и dispatch (`renderCompute.cpp:267`) берут **один и тот же** мьютекс, это настоящий
последовательный пол любой многопоточной схемы, и его нет ни в одном списке блокеров.

### 2.4 `KYTY_IMAGE_UPLOAD_TRACE` в Sky Garden

Инструмент есть с сессии 54 (`ImgUploadWhy:` — причина каждой полной загрузки образа,
`KYTY_IMAGE_UPLOAD_FROM=<кадр>`), и в Sky Garden он **ни разу не запускался**. В установившемся
кадре — 19,8 загрузок и **139 МБ** (медиана 137, p95 172), 47 detile; на CPU это почти ничего
(`Image::Upload` 0,2 % профиля), то есть статья целиком GPU-шная, а регрессия по живым кадрам
`gpu_us = 4607 + 1,476·draws + 21,03·МБ + 6,53·detile` делает её **единственной статьёй, без
которой арифметика GPU не сходится** (нужно снять p50 14,56 → 11,0 и p99 18,73 → 14,5).

Это диагностический прогон, а не A/B: одно плечо, `KYTY_IMAGE_UPLOAD_TRACE=1`, разбор причин по
гостевым адресам. Ответ нужен в виде таблицы «причина → число загрузок → МБ → detile».

### 2.6 Открытый вопрос сессии 67: почему сцена через `-lvl` тяжелее по GPU

`lvl67b` даёт `gpu_busy_us` **18,2–19,8 мс** против p50 **14,56 мс** ручной базы `sky64a` — **при
том же разрешении основного прохода (2016 Kpx ≈ 1920x1080) и том же числе draw (4610–4724 против
4718)**. Кандидаты: другая камера, другой набор загруженных образов (те самые 139 МБ загрузок на
кадр), отсутствие прогресса (гаджеты/разблокировки другие). `KYTY_AUDIO_SYNC=0` разрешение не
меняет (`lvl67c`: 3840x2160 весь прогон), так что гипотеза «pace-скейлер держит верхнюю ступень
лестницы» уже опровергнута.

Разница в 3,6–5,2 мс GPU — это треть бюджета кадра, и пока она не объяснена, GPU-трек сессий 69–70
будет мерить не то. Решается тем же `KYTY_IMAGE_UPLOAD_TRACE` (пункт 2.4) плюс сравнением состава
загруженных образов с ручным прогоном `C:/kyty/s64/log_sky64a.txt`. Если причина — прогресс, то
`savepersist=1` плюс один ручной проход пользователя даёт сейв, с которого `-lvl` будет приводить
в сравнимую точку; это единственное место сессии, где участие пользователя может понадобиться, и
просить его надо осознанно и один раз.

## 3. Чего в этой сессии НЕ делать

- Не реализовывать настоящие occlusion queries, M4 «Range Translate», приватизацию скрэтча,
  приватные кольца записи, RCU-заморозку кэшей. Их ворота — результат этой сессии.
- **Общей головы кольца записи не делать никогда**: сессии 61–63 доказали, что она стоит
  межчиплетного владения линией (только K приватных колец, если до них дойдёт).
- Не менять умолчания существующих гейтов. Все новые гейты — **default 0**.
- Не переоткрывать §8 сессии 66 и трек C сессии 64.
- Не чинить то, что не измерено: NID-правка сессии 67 (`strcmp`/`strncmp`) покадрово не
  сравнивалась, но она уже в дереве — переделывать её без нового измерения нечего.
- Не принимать решений по FPS в промежуточных замерах — только по миллисекундам.

## 4. Методика и правила

**Прогон.**
```
python C:/kyty/s68/enter_scene.py <tag> --hold <сек> --rec [--gates-file …] [KYTY_X=v …]
python C:/kyty/s68/summary4.py <tag> [--blocks] [--band 4300-4700]
python C:/kyty/s68/guards.py <tag> [--video]
```
Харнесс порта s67 → s68 (как s67 портировал s64/s65): у `summary4.py` и `guards.py` есть `--root`,
у `enter_scene.py` корень зашит константой `ROOT = pathlib.Path('C:/kyty/s67')` — поправить при
копировании. `gen_gates.py` перегенерировать после любой правки `gates.cpp`.

**Обязательное для каждого измерительного прогона.**

1. **Прогон не совмещать ни с какой другой работой на машине.** В сессии 67 это дало истинный FAIL
   сторожа по ядрам (`aa67b`, пункт 6: 2 группы из 36 отклонились больше 10 % от медианы своего
   плеча — во время прогона работали агенты той же сессии). Ни сборок, ни агентов, ни тестов
   параллельно с замером.
2. **`guards.py` обязателен для каждого прогона**, 10 проверок, exit 0/1. Ни одно число не стоит
   ничего, пока сторож не сказал PASS. Исключение одно и оговорено выше: пункт 4 на прогоне
   `occzero`. Маска троттлинга по умолчанию `0x405` (на этой машине в 100 % busy-семплов активна
   недокументированная причина `0x400`; жёсткие биты 0x8 HwSlowdown, 0x20/0x40 Thermal,
   0x80 PowerBrake остаются фатальными). Ориентир здоровой машины из s67: SM 2696 МГц (min 2467,
   sd 1,7 %), 72–82 °C, 114 Вт средних.
3. **Видео (`--rec`) и проверка однокадровых глитчей обязательны для приёмочного прогона.**
   В сессии 67 видео не писалось вообще, и глитч-проверка не выполнялась — этот долг закрывает
   пункт 2.0. `--rec` также даёт `.idx` и, значит, пункты 8 и E8.
4. **Гейт-файл: `FindAssignment` берёт ПЕРВОЕ вхождение `имя=`** как целого слова. Дописывать
   переопределение в конец базового текста бесполезно — только замена на месте
   (`python gen_gates.py --with occzero=1`). Имя, отсутствующее в тексте, **сохраняет** состояние;
   пустая строка не сбрасывает ничего. Файл читается кусками не больше 4095 байт; если он заполнил
   буфер целиком, не применяется ничего (`gen_gates.py` держит порог 3500). Имена, которые
   назначает любое плечо расписания, принадлежат расписанию, и проход по гейт-файлу их пропускает.
5. Расписание: `KYTY_GATE_SCHEDULE="<N>[+<start>]:<плечо>|<плечо>"`, `KYTY_GATE_SCHEDULE_ABBA=1`.
   `arm`/`blk` в `FrameTrace` уже сдвинуты эмулятором на отчётный интервал — **скрипты разбора
   дополнительный сдвиг не делают**. `summary4.py --warmup 3` (умолчание), `--stat sum`
   (умолчание, менять только осознанно).

**Сборка и тесты.** `cmd //c "C:\kyty\build_local.cmd"` — никогда параллельно с замером; тесты
`bit_array_tests`, `image_page_table_tests`, `virtual_memory_allocation_tests`,
`resource_materialization_tests`, `memory_tracker_tests` (и с `KYTY_ARM_DEFER=1`).
`resource_tracking_tests` падает как прежде — его лог должен побайтно совпасть с s60–s67
