# Сессия 59 — B9 закрыт потолком, обход PM4 на своём потоке, цели без замка, пакет B5/B7/B1d

База: `merge-upstream`, HEAD сессии 58 — `e70db75`. Итоговый коммит — см. HANDOFF. Push нет.

## 1. Главный результат

- **B9 закрыт потолком в единицах CPU**: 1–1,4 % потока GuestGpu (≈0,3–0,45 мс), ровно порог
  замера; реализация не делалась (§2).
- **`rtfast`** (цели без замка кэша текстур, гейт `KYTY_RT_FAST`): Sky Garden **−0,75 / −1,21 /
  −1,81 % CPU на draw** (три повтора, все в плюсе), пустыня −1…−4,6 %; 97 % захватов целей идут
  без `FindRenderTarget`/`FindDepthTarget`. **По умолчанию 1.**
- **`dawalk`** (обход PM4 для M1 на своём потоке): пустыня −2,6…−5,3 %, **Sky Garden +4,1 / +4,7 /
  +5,1 % — регрессия**, причина названа счётчиками (§3); **остаётся 0**, добавлена ручка
  `dawalklead` для следующего замера.
- **Пакет B5/B7/B1d** (подпись кэша трансляции) — без гейта, отдельно не мерится.
- **M2 в этой сессии не начат — с числами, почему** (§6): разрешение привязок — ≈20 % потока,
  при КПД M1 это ≈3 мс, не «кратно».
- Базы свипа `sky59`: **6,87–7,06 мкс CPU на draw, CPU потока 31,9–32,9 мс, 28,7–29,4 FPS** при
  ~4 650–4 690 draw (сессия 58: 6,9–7,2 мкс, 33,0–33,6 мс, 26–28 FPS). Сдвиг базы между
  бинарями протоколом не атрибутируется (в нём пакет B5/B7/B1d и другая точка сцены).
- Зависаний входа нет (0 `GpuWaitSlow`/`GpuHangAbort` за ~9 700 кадров в сцене); холодный вход
  с новой подписью кэша прошёл с первого раза.

## 2. B9 (dynamic offsets) — потолок в единицах CPU, реализация не делалась

Сессия 58 измерила потолок B9 в наборах: 1 451 из 2 733 пуловых наборов на кадр (53 %) повторяют
предыдущий набор своего layout'а. Эта сессия измерила его в единицах CPU потока GuestGpu — и он
ниже порога замера.

Что B9 может снять с критического потока: с гейтом `recpack` записи дескрипторов
(`vkUpdateDescriptorSets`, `bindDescriptorSets`) уже делает поток записи, а на GuestGpu остаются
построение списка записей, `DescriptorHeap::Commit` и копия пакета. Таймеры (гейт `drawstat`,
счётчики `cb_pool_*`/`cb_push_*`, пустыня, 510 кадров):

| на один пуловый набор | мкс |
|---|---:|
| переходы образов (обе стадии) | 0,39 |
| построение списка записей | 0,21 |
| commit + копия пакета | 0,34 |
| push-набор: записи / выдача | 0,06 / 0,08 |

Таймеры инфлируют (три `rdtsc` на набор ≈ 0,1–0,15 мкс), так что честная цена пулового набора
без переходов ≈ 0,45 мкс. Число буферных дескрипторов на набор на пустыне (22,5) и в Sky Garden
(23,6) совпадает, поэтому потолок в сцене: **1 451 × 0,45 мкс ≈ 0,65 мс, 2 % потока при
абсолютном верхе (пропустить и построение, и выдачу)**; реально повторный набор всё равно
надо сравнить и привязать (пакет bind), то есть **≈0,3–0,45 мс, 1–1,4 %** — ровно порог
протокола (±1,4 %). Поток записи не критичен (`rec_spin_us` ≈ 38 мс из 45 мс его CPU на кадр),
GPU 13–14 мс в бюджете. При цене реализации (per-pipeline layout'ы с dynamic-типами, пулы,
сортировка смещений, два места привязки) — **не делать**. Оценка плана «−3…5 мс» была сделана
до `recpack`, когда записи дескрипторов ещё шли на критическом потоке.

## 3. `dawalk` — обход PM4 для M1 на своём потоке

Профиль `sky1` (сессия 57): `WalkComputeDispatches` 1,9 %, `QueueAheadSource` 1,8 %, хэш
запросов ~0,2 % потока GuestGpu — ≈1,4 мс кадра уходило на производство запросов, результаты
которых считают другие потоки. Обход не нуждается в GuestGpu: PM4 и таблицы
`SET_SH_REG_INDIRECT` окончательны в момент отправки гостем и живут до завершения GPU; теневое
состояние (регистры compute, две графические стадии) — то, что оставили предыдущие отправки
очереди, и оно хранится на потоке обхода по очередям, как режим 1 `KYTY_ASYNC_COMPUTE` хранит
compute-состояние. Ошибка теневого состояния стоит лишней задачи, не результата: всё взятое
проверяется `VerifyWitness`.

Гейт `dawalk` (`KYTY_DRAW_AHEAD_WALK`): `GuestGpu::Enqueue` → `LookaheadSubmission` отдаёт
отправку потоку `DrawAheadWalk` (compute-prefetch и draw-ahead вместе), поток GuestGpu пропускает
свой обход (`Pm4Execution::SetDrawAheadWalk`). Обход теперь опережает GuestGpu на глубину
очереди, поэтому «старый обход» в таблице слотов больше не значит «не последний»: отправка
несёт id обхода (`Submission::walk_id`, только графические), GuestGpu публикует id
обрабатываемой (`NoteDrawAheadProcessing`), и слоты обходов ниже него — единственные, что можно
обновлять и вытеснять. С выключенным гейтом id присваиваются так же, и поведение прежнее.

Пустыня (`dw1`, `sig2`, фазы по 300 present, соседние базы): **−4,4 / −2,6 % и −5,3 / −3,5 % CPU
на draw**, `da_hit` без изменений (1075–1078), `da_wlag_us` ≈ 270 мкс на отправку, `da_wdepth`
≈ 1,7 отправки в очереди. Счётчики: `da_wjobs`, `da_wlag_us`, `da_wdepth`, `da_wskip`, `da_wdrop`.

**Sky Garden (`sky59`, три повтора): +5,09 / +4,06 / +4,72 % CPU на draw, FPS −4…−9 %.**
Счётчики называют механизм: обход уходит на всю глубину очереди вперёд (`da_wlag_us` ≈ 8 мс на
кадр на 8 отправок, `da_wdepth` ≈ 2), результаты лежат в таблице слотов до кадра, и взятие
дорожает — `da_take_us` 3,0 → 4,0 мс, `da_work_us` 25 → 29–31 мс (воркеры тоже медленнее),
`da_busy` 17 → 174–208 (таблица забита двумя кадрами запросов), `da_miss` 146 → 276–304. То есть
свидетель и снимок, построенные воркером на кадр раньше, остывают к моменту взятия (тот же
механизм, что «два режима» сессии 56, только во времени, а не между CCD), плюс контенция
`PipelineCache::m_mutex` с обходом compute-prefetch (287 dispatch'ей на кадр в сцене против
единиц на пустыне). На пустыне глубина очереди мала, и того же эффекта нет.

**Не выпущено:** гейт остаётся 0. Добавлена ручка **`dawalklead`** (`KYTY_DRAW_AHEAD_WALK_LEAD`,
по умолчанию 1, 0 = без удержания): графическая отправка ждёт на потоке обхода, пока GuestGpu
не окажется не дальше `lead` отправок позади неё — обход N идёт во время обработки N−1, вне
критического потока, но не раньше. На пустыне с ручкой прогон `dw3` (см. §7); в Sky Garden не
мерилось — время пользователя в сцене было потрачено на основной свип.

Правки по ревью: поток обхода бросает задания, которые GuestGpu уже обошёл или которые отстали
больше чем на 24 отправки (`da_wdrop`; иначе он читал бы память, которую гость мог переиспользовать,
а `SET_SH_REG_INDIRECT`/`INDIRECT_BUFFER` разыменовывают указатели из неё); постановка и остановка
идут под одним мьютексом (гонка use-after-free на выходе); `ShaderUserSgprs` клампит слишком длинный
блок вместо `abort`.

## 4. `rtfast` — цели без замка кэша текстур

Профиль `sky1`: замок кэша текстур внутри `FindDepthTarget` и `FindRenderTarget` — 0,97 + 0,92 %
потока, `ResolveRenderColorTarget` 1,1 %, `ResolveRenderDepthTarget` 0,5 % — каждый draw заново
захватывает цели, которые у ~99 % draw'ов те же, что у предыдущего (`rt_hits` 23,4 тыс. на кадр).
Тот же довод, что у `texfast`: всё, что заставило бы захват цели что-то делать, двигает
`Image::bind_stamp` (инвалидация CPU, maybe-dirty, срез трекинга, buffer-modified); регистрация,
`needs_rebind`, `depth_id`, `pending_levels`, срез источника проверяются прямо; backing пинит
view'ы; состояние метаданных (DCC/CMASK/HTile заливки и очистки, `m_surface_metas`) покрыто новой
эпохой `TextureCache::MetaEpoch()`, которую двигает каждая мутация этой карты (13 мест); для
трафарета помнится запись `AssociateStencil` и проверяется, что она жива и указывает сюда.
Слот, чей предыдущий захват записал всё это неизменным, берёт записанный view и повторяет только
идемпотентные флаги (`MarkGpuModified`, `usage`). Вторая половина: попадание memo целей больше не
копирует `RenderColorInfo`/`RenderDepthInfo` (~2,7 КБ на draw) в состояние draw, если оно уже
держит этот слот той же версии.

| | пустыня `rt2` | Sky Garden `sky59` |
|---|---:|---:|
| захватов целей на кадр | 2 220 | ~15 400 |
| из них по записи (`rt_fast_ok`) | 2 163 (97 %) | ~15 200 (99 %) |
| устаревших (`rt_fast_stale`) | 19 | 16–22 |
| CPU на draw, соседние базы | −4,6 / −1,0 (+`dawalk` −2,7) | **−0,75 / −1,21 / −1,81** |
| полосы draw 4300–4700 / 4700–5100 | — | −0,7/+0,1/−1,4 ; +0,3/−2,8/−1,4 |

Все три повтора в плюсе, среднее −1,26 % — на пороге протокола (±1,4 %), как `snapdiff`+`snapswap`
в сессии 58. **По умолчанию 1.**

Ревью (агентом) нашло три дефекта, все исправлены: ключ быстрого пути не сравнивал метаданные
desc (DCC-заливка по новому адресу при том же view прошла бы мимо `PrepareDccClear`) — теперь
сравниваются метаданные и `htile_clear_mask`, а запись делается только когда образ уже несёт
метаданные desc; повторное открытие образа в memo не двигало версию слота — двигает; запись в
`m_download_images` без замка — быстрый путь выключен при `--readback-linear-images`.

## 5. Пакет в подписи кэша трансляции: B5, B7, B1d

Все три правки трогают `graphics/shader/**`, который хэширует подпись кэша трансляции, поэтому
идут вместе и стоят одного холодного входа в сцену.

- **B5.** `GetShaderParams` аллоцировал `std::vector<uint32_t>` под user data на каждую стадию
  каждого draw (~10,5 тыс. пар new/delete на кадр; `operator new` под `GetShaderParams` — 0,9 %
  потока в `sky1`). `ShaderParams::user_data` — inline-буфер `ShaderUserSgprs` на 48 слов
  (32 user SGPR плюс 8-словный префикс NGG); все потребители и так брали span.
- **B7.** Два лог-счётчика в цикле вершинных атрибутов делали `lock xadd` на общей линии на
  каждый атрибут каждого draw (~42 тыс. на кадр), хотя их квота в 64 строки была исчерпана в
  первые секунды. Теперь счётчик сначала читается.
- **B1d.** `ShaderGetStaticInputInfoVS` обнулял всю `ShaderVertexInputInfo` (9,9 КБ, из них
  `buffers[32]` = 8 960 Б) на каждый draw — memset VCRUNTIME под `PrepareProgram` (1,2 % в
  `sky1`). Все читатели `resources`/`resources_dst`/`buffers` останавливаются на счётчиках, все
  писатели заполняют `[0, count)` до его увеличения, поэтому `Reset()` чистит только записи
  предыдущего draw и присваивает скаляры.

Без гейта; отдельно не мерится. Базы `sky59` (6,87–7,06 мкс/draw, 31,9–32,9 мс) ниже баз `sky58d`
(6,96–7,15 мкс, 33,0–33,6 мс), но это разные прогоны и точки сцены — не заявлять как эффект пакета.

## 6. M2 — почему не в этой сессии (числа)

Промпт ставил M2 «единственным механизмом с кратным потенциалом». Профиль потока GuestGpu
(`sky1`, всё включено, семплер по листьям) говорит иначе. Разрешение привязок — всё, что M2
унёс бы на воркеры (`PrepareBindings` 6,0 %, `RebindImages` 1,7, `RebindBuffers` 1,3,
`FindBuffer` 1,3, `ObtainBuffer` 1,2, `TouchImage` 0,9, `FindImagesInRegion` 0,8,
`HasGpuDirtyBytes` 1,0, `SynchronizeBuffer` 1,4, `ConfigureImageSource` 0,6, `FindView` 0,5,
доли спин-лока и `TryReadBacking`) — **≈20 % потока, ≈7 мс из 34**. Остальное: защита
страниц и fault'ы ≈13 % (`ProtectMappedUnlocked` 6,0, `ApplyGuard` 2,2, спин-лок трекера 3,5),
накладные M1 на критическом потоке ≈11 % (`VerifyWitness` 4,3, `AheadTake` 2,5,
`QueueAheadSource` 1,8, `CopyAheadResult` 0,8, копия снимка — снята в 58), поиск программ ≈9 %
(`PrepareProgram` 2,7, `GetGraphicsPrograms` 2,1, сравнение ключей 0,8+0,9, `BuildStageStaticKey`
0,7, `GetGraphicsPipeline` 0,9), запись и хвост draw ≈13 % (`CommitBindings` 2,9,
`ExecutePreparedDraw` 2,6, `EndRecord` 1,8, `Transit` 1,2, цели 1,6), обход PM4 ≈2 %,
`operator new` ≈2 %.

Арифметика: при КПД передачи M1 (45 %) M2 снимает ≈3 мс → 30 мс, 33 FPS; при невозможных 100 %
— 27 мс, 37 FPS. Это не кратно, и это после двух подготовительных сессий C1–C3 (`BufferCache`
без лока, `DescriptorHeap`, `StreamBuffer::m_offset`, `friend` кэша текстур — §5.2 плана), которые
сами ничего не дают. Поэтому сессия потратила усилия на то, что меняет число операций на
критическом потоке без потоковой перестройки кэшей: обход PM4 (2 % + 1,8 % постановки) на
свой поток, цели без замка (≈4 %), пакет B5/B7/B1d (≈2,5 %). Оставшийся крупный кандидат того же
рода — B3 (memo поиска программ по неизменным регистрам, ≈9 % × доля попаданий; `e9_adj` говорит,
что 79 % наборов идут подряд с тем же pipeline) — не начат.

## 7. Проверки

- **Vulkan + sync-валидация** на пустыне с исправленным бинарём, все гейты и самопроверки
  (`dawalk=1 rtfast=1 texfastcheck sfcheck pbcheck buffastcheck smemocheck drawstat`), интро и
  ~10 000 кадров: **0 ошибок, 0 sync hazards**, известное предупреждение о лимите 10 повторов;
  `texfast_bad`/`sf_bad`/`pb_bad`/`bfast_bad` = 0, `da_wdrop` = 0.
- **Видео:** `rec_dw1` 11 346, `rec_rt1` 12 102, `rec_sig2` 11 148 кадров (пустыня) и
  `rec_sky59.mp4` (Sky Garden, весь заход и свип) — **0 однокадровых глитчей**.
- **Пустыня** (`dw1`, `sig2`, `rt1`, `rt2`, `dw3`): 0 `GpuWaitSlow`/`GpuHangAbort`, 0 `MISMATCH`.
  Один прогон (`sig1`, бинарь `dw1`, гейт выключен) упал на 82-й секунде интро гостевым assert'ом
  «There are too many objects/batches in this scene» (`command_buffer_writer.ppr.cpp:31`) с
  последующим access violation гостя — ни в одном логе сессий 54–59 этой строки раньше не было;
  в семи других прогонах не повторился. Не объяснён; при повторении смотреть первым.
- **`dw3` (пустыня, `dawalklead=1`):** `dawalk` −3,7 / −1,2 %, но `da_hit` 1076 → 900–906,
  `da_miss` 0 → 163–170: на пустыне GuestGpu простаивает у vblank, и обход, ждущий обработки N−1,
  не оставляет воркерам запаса. В Sky Garden (очередь глубокая) ожидается обратное — мерить.
- **Тесты:** пять бинарей проходят, `resource_tracking_tests` падает как прежде («SRT runtime»).
- **Ревью двумя агентами:** 2 дефекта в `dawalk` (обход памяти, которую гость мог переиспользовать;
  гонка use-after-free при остановке) и 3 в `rtfast` (метаданные не в ключе; версия memo при
  повторном открытии; запись в `m_download_images` без замка) — все исправлены и пересобраны до
  свипа в Sky Garden (`rtfast`) / до контрольного прогона (`dawalk`).
- Бинарь установлен, A0249F43CEB63F179777E99873C7B8059E3CD6ECA62F177F981924567D535467256 **A0249F43CEB63F179777E99873C7B8059E3CD6ECA62F177F981924567D535467**.
