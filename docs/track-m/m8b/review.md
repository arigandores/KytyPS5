## 3. Ответы на вопросы лида п. 781(в)

### 3.1 (1) Гонка `ContextCreate` / `ContextDestroy` / повторное использование слота
Устройство смеси чужому контексту достаться не может [c кода]: ручка контекста — `g_audioout2_next_context.fetch_add(1)`
(`libAudio2.cpp:171`, `:649`), 64-битная, монотонная, значение не переиспользуется; повторная запись ищет контекст по
значению ручки (`:678`), а не по слоту. `Destroy` между `Unlock` (`:669`) и `Lock` (`:677`) — контекст не найден,
ручка закрывается (`:684`). Пуш между этими точками видит `object_audio_handle` = 0 — смеси нет на этом Push (не дефект).
Остаток: `*ctx` перечитывается из памяти гостя (`:678`) — если гость перепишет свою ячейку между `:649` и `:678`,
устройство потеряется (будет закрыто). Сценарий требует записи гостя в выходной параметр во время вызова — [I], не RC.
Гонка «`Destroy` во время `AudioOutOutputs` с уже прочитанной ручкой» (ручка закрыта или слот `m_out_ports` переиспользован
→ смесь в чужой порт) — тот же класс, что у ручек портов шин MS1 (`AudioOutOutputs` читает `m_out_ports` без
`Audio::m_mutex`, `audio.cpp:917–926`), не новый; автор назвал его в §3 отчёта.

### 3.2 (2) `has_queueable_device` при `=1` для контекста только с объектами; связь с G5
При `=0` такой контекст получает `use_device_clock` = false — темп задаёт модель очереди (`queue_depth`, сон
`grain_micros`, `:774`, `:792`); при `=1` (объект смешиваемый, устройство смеси есть) — true: Push всегда проходит и
ждёт очередь SDL устройства смеси (`audio.cpp:716–738`, цель 40 мс, сброс через 200 мс). Это смена источника темпа для
такого контекста [c кода]; стенд её не видит (m10 выжил). **Для этой игры не исполняется** [c логов M6c]: в каждом из трёх
тегов один контекст, и у него есть порты шин с SDL-устройствами (типы 0, 1, 3) ⇒ `use_device_clock` = true уже при `=0`;
при `=1` темп того же контекста задают те же устройства плюс устройство смеси, поданное в том же пакете последним.
Для G5: на каждом Push добавляются смесь под `g_audioout2_port_mutex` (≈ 5 объектов с PCM на Push по
`ao_obj_push` / числу Push SG [I]) и один `QueueSdlAudio` (растяжка темпа гостя на своё устройство при
`KernelGuestSpeedEnabled`) — на потоке звука, не рендера; цена [I], меряет G5. Плечо «без T125 первым» в п. 778(д)(5)
названо верно.

### 3.3 (3) Порядок замков
Новый код никогда не держит `g_audioout2_context_mutex` и `g_audioout2_port_mutex` вместе [c кода]:
`audioout2_m125_mix_device` (`:441–449`) берёт и отпускает контекстный до взятия портового (`:457`, `:483`);
`ContextCreate` открывает устройство вне замков (`:674`), затем только контекстный (`:677–682`); `ContextDestroy` —
как MS1 плюс закрытие вне замков (`:727`); `set_object_attributes` — только портовый (`:525`). Единственная пара в
файле — `PortCreate` (контекстный → портовый, `:830`, `:838`) — порядок новым кодом не обращается. Под портовым
замком новый код зовёт `AudioOutHasDevice` (`Audio::m_mutex`) — как исходная функция MS1 (`:567`). `AudioOutOpen`
(`Audio::m_mutex` → `g_sdl_audio_mutex`) — без замков `libAudio2`, как `PortCreate` (`:868`). Новых циклов нет.

### 3.4 (4) Что из `AudioOutOpen` → SDL стенд не покрывает и закрывает ли это член (г)(2)(v)
Стенд подменяет весь слой `AudioInternal` (`MT125Stand.cpp:461–512`): не исполняются `Audio::AudioOutOpen` (32 места,
`audio.cpp:777`), `OpenSdlDevice` и его отказ, `PrepareOutputBuffer`, `SDL_BuildAudioCVT`, растяжка темпа, ожидание и
`DROP` в `QueueSdlAudio`, `AudioStat`, закрытие `CloseSdlDevice`. Член (v) закрывает только владельца Ф8
(`init_calls` ≤ 1). `mixed_nz` ≥ 1 **не доказывает, что смесь дошла до устройства** — RC1.

### 3.5 (5) Счётчики `KYTY_DIAG_M5W2` при `=1` в `main`
При `KYTY_M_T125=1` путь `audioout2_m125_queue_context_audio` обходит весь блок M6a (`NoteAudioPort`,
`NoteAudioObjectNoPcm`, `NoteAudioPush` — `206cdbce:src/libs/libAudio2.cpp`, функция `audioout2_queue_context_audio`)
[c кода]. Для тегов M3 волны 2 годно: п. 778(д) не назначает ни одному тегу `KYTY_DIAG_M5W2=1`, члены T125 читаются по
`MT125Stat`. Ловушка для любого будущего тега с обеими ручками — RC2.

## 4. Требуемые изменения

**RC1 (член чтения (г)(2)(v), владелец — M3a2 / лид):** `mixed` и `mixed_nz` считают Push, в которых смесь *посчитана и
подана* в `AudioOutOutputs`, а не дошедшие до устройства. `Audio::AudioOutOpen` возвращает действительный `Id` и при
отказе `OpenSdlDevice` (возврат `OpenSdlDevice` игнорируется, `audio.cpp:805–812`); тогда `mix_handle` > 0, устройство 0,
`QueueSdlAudio` выходит на `audio_device == 0` (`:655`), а счётчики растут (`libAudio2.cpp:505–507`).
**Сценарий отказа:** четвёртый поток WASAPI не открывается (класс Ф23 программы «WASAPI can't initialize audio client»)
→ в логе `AudioOut: SDL_OpenAudioDevice failed`, смесь не звучит, а `MT125Stat … mixed_nz=` ≥ 1 ⇒ член (v) засчитан
ложно. **Изменить:** в печати M3a2 член (v) дополнить, до данных: на V Sky Garden при `=1` строк
`AudioOut: opened SDL device` ровно на 1 больше, чем в опоре MS1 того же уровня (M6c/M3a: 3 ⇒ 4), и 0 строк
`SDL_OpenAudioDevice failed` / `SDL audio init failed`. Вариант кодом (счёт только при `AudioOutHasDevice(mix_handle)`)
тоже закрывает RC1, но меняет коммит T125 и требует M8a2 — рецензент рекомендует член чтения.

**RC2 (строка таблицы умолчаний M8c, владелец — M8c / лид):** при `KYTY_M_T125=1` счётчики M6a вывода контекста
(`ao_obj_*`, `ao_bus_*`, периодическая строка `M5W2Stat:` от `NoteAudioPush`) не исполняются. **Сценарий отказа:** тег с
`KYTY_DIAG_M5W2=1` на MS2 (умолчание `KYTY_M_T125=1`) печатает `ao_bus_nz` 0 и `ao_obj_push` 0 — чтение по п. 772/776
примет мёртвый живой контроль `ao_bus_nz` за дефект измерения или «объектов нет». **Изменить:** в таблице умолчаний и
отката M8c строка «`KYTY_DIAG_M5W2=1` читается только при `KYTY_M_T125=0`; при `=1` счётчики `ao_*` — 0 по построению,
не читаются».

**RC3 (стенд, владелец — Emu Engineer звеном до G1 M8c; бинарь эмулятора не меняется):** компаратор `MaxDiff`
(`MT125Stand.cpp:214–225`) слеп к NaN: `std::max(m, NaN)` возвращает `m`, NaN-выход даёт `max_diff` 0. Член
`invalid_not_applied` объявляет проверку NaN-`GAIN`, но её не исполняет — мутант m9 (NaN принимается) выживает, а
`mixed_nz` его не различает (`NaN != 0` — истина и в коде, и в `EXPECT`). **Сценарий отказа:** будущая правка, теряющая
`std::isfinite`, проходит G1 (стенд T125 — член G1 п. 778(д)(1)) с `ALL OK`, а в игре NaN-`GAIN` превращает всю смесь в
NaN (SDL отдаёт NaN в WASAPI). **Изменить:** `MaxDiff` — неконечный отсчёт выхода ⇒ `+inf`; m9 — в список мутантов
стенда, обязан ловиться. Правка только `tests/MT125Stand.cpp` (цель `EXCLUDE_FROM_ALL`), код `libAudio2.cpp` и бинарь
`4445a49b` не меняются; коммит — в `main` и в worktree MS2 до G1.

## 5. Наблюдения без RC

- **Н1 (сдвиг номеров портов при `=1`):** устройство смеси открывается в `ContextCreate`, а контекст в игре создаётся до
  портов (лог SG) ⇒ при `=1` смесь берёт `Audio` id 0, порты шин сдвигаются на +1 (`audio_handle` в строках
  `AudioOut2PortCreate`, `port=` в `AudioStat:`, номера SDL `dev=` в `AvTrace: audio`). Читатели трека F
  (`f18e_read.py`, `fs7c_read.py`) считают по каждому порту с `dev ≠ 0` и номер не закрепляют [c текста]; член (v)
  (`init_calls`) не зависит. Любое будущее чтение «порт 0 = главная шина» на MS2 неверно.
- **Н2:** устройство открывается на каждый контекст с `max_object_ports` > 0, а `AudioOut2ContextResetParam` ставит 256
  (`:618`) — т. е. почти на каждый контекст, даже без объектов. В игре 1 контекст ⇒ +1 устройство из 32; для других
  игр — расход мест `m_out_ports` и потоков WASAPI [I].
- **Н3:** чтение PCM объекта под `g_audioout2_port_mutex` сырым указателем — новый путь чтения при `=1` (при `=0`
  объектный PCM не читается); M6c: `ao_obj_unread` 0 из 2 014 739, но 66 % — через частную память (`ao_obj_vq`).
  Падение по недействительному указателю — тот же класс, что у шин, [I]; автор это не заявляет (§7 отчёта). Серия G4 —
  единственная проверка.
- **Н4:** при `=0` путь — MS1 [c кода]: каждая точка входа начинается с `MT125On()`; `object_audio_handle` 0,
  закрытие 0 — ничего; вывод на шинах, Ф8 (`SdlAudioSubsystemInit` / `SdlAudioAcquire` не вызываются новым кодом при
  `=0`) и пад (`PushHapticsPcm` только для `AUDIO_OUT_PORT_TYPE_VIBRATION`, `audio.cpp:920`) не меняются. Новая строка
  при `=0` — только `MT125: mode=0` при первом вызове AudioOut2. Правило п. 756(б)(4): ни одна строка `LOGF`
  (`AudioStat:`, `AvTrace:`, `MTexOffset:`) коммитом не удалена и не изменена [c диффа]; при `=1` добавляются строки
  `AudioStat:`/`AvTrace: audio` порта смеси.
