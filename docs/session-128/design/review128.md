## 0. Коротко

- **Гость (крах/зависон).** Нового пути к ФОЛТУ ручка не даёт (P′ подтверждён по коду, §2). Но утверждение §0.3 «нового пути
  к падению или зависанию гостя нет» неверно: потерянные записи CPU → GPU делают данные GPU не просто старыми, а
  РАЗНОРОДНЫМИ по страницам (часть страниц той же структуры перезагружается другими путями), и такие данные кормят циклы
  шейдеров, косвенные аргументы и индексы — путь к зависону GPU/TDR существует (RC3).
- **Трекер.** P′ держится на всех путях вопроса п. 88(л)(1); применения без `apply` не нашёл; гонок U нет (§2). Неточность:

- **Смещение ABBA.** Проект не меряет перенос между плечами, хотя расписание ABBA даёт его даром: плечо 0 после плеча 1
  наследует устаревшие данные GPU, плечо 1 после плеча 0 наследует вооружённые страницы с периодом записи > 10 кадров.
  Оба переноса сдвигают Δ к нулю — в сторону `K14_CLOSED`, решающего исхода (RC2).
- **«0 — прежний путь».** Как поведение — да (перечень §8.2 полон, кроме оговорок RC7/RC9). Как «плечо 0 `pc128`» — нет:
  плечо 0 в прогоне с плечом 1 не равно отгруженному состоянию (RC2, база п. 87(е)(7)).
- **Верхняя граница.** Для `armdefer` и `protbatch2` — да [I]. Для write-watch — НЕ установлена по построению (RC1).

## 1. Требуемые изменения

### RC1 (MAJOR) — «потолок всех механизмов» не доказан для write-watch; `K14_CLOSED` его не закрывает без поправки

**Что не так.** §1 проекта: «Всё, что механизм оставляет себе, плечо 1 тоже убирает». По коду плечо 1 убирает только вызовы
`Read` (а)(б)(в) внутри синхронизации буфера на GuestGpu и то, что за ними следует (фолты и перезагрузки ЭТИХ страниц).
Остаются в плече 1, но исчезают у write-watch (`docs/levers/anyps5.md:26`: «защиты страниц для ресурсов GPU нет»):
(1) вооружение образов воркером П3 (`textureCache.cpp:542/567/585` → `UpdatePageWatchersDeferred` → `ApplyPending`
`pageManager.cpp:705–732`) и все фолты записи на страницах, вооружённых только образом (в `k3p127` `tex_inval` = `fw_n` =
1 246,4 на кадр [c] — каждый фолт записи идёт в кэш образов; доля страниц «только образ» [U]); (2) повторное вооружение
2.3(г) (NA → `Read` после ухода GPU-данных, не пропускается) — у write-watch это снятие NA → RW без последующих фолтов;
(3) фолты самого GuestGpu `faults_gpu` 21,1 / `fault_gpu_us` 104,6 мкс на кадр [c] (пишущий хост-код эмулятора в
вооружённые страницы — метки, DMA, `WRITE_DATA`) — на страницах, вооружённых не пропущенными вызовами, они остаются;
(4) `prot_gpu_rw` на GuestGpu. Обратная сторона (плечо 1 снимает больше механизма): перезагрузки `sync_up_kb` ≈ 23 191
[c]. Итого для write-watch знак «плечо 1 ⊇ механизм» не выведен: одни члены завышают, другие занижают.

**Сценарий отказа.** `pc128` даёт Δ − 2SE = −420 (>−500) ⇒ `K14_CLOSED` ⇒ по букве п. 87(е)(6) write-watch закрыт «со всеми
механизмами». При этом write-watch снял бы ещё фолты страниц образов на гостевых потоках и воркер (`protw_us`), которых
плечо 1 не снимало; если хотя бы 80 мкс из них на критическом пути, закрытие write-watch ложное, а переоткрыть его можно
только новой строкой ROADMAP.

**Что изменить.** (а) В §0.4, §1, §11 ограничить утверждение верхней границы механизмами, которые только переносят или
сливают вооружение буферов при загрузке (`armdefer`, `protbatch2`, пакетирование); для write-watch написать: «граница не
установлена». (б) Печать — ряды плеча 1 (среднее окна): остаток GuestGpu `R_gpu` = (`prot_gpu_ro_ns` + `prot_gpu_rw_ns`)/1000
+ `pb_wait_gpu_us` + `fault_gpu_us`; вне GuestGpu `fw_n`, `fault_us`, `protw_us`. (в) **Вопрос лиду** (константа п. 87(е)(6)
названа печатью, менять может только лид): закрывает ли `K14_CLOSED` write-watch, и при каком условии — предложение:
только если min(Δ − 2SE) − `R_gpu`(плечо 1) > −500 в том же режиме; иначе write-watch — долг «не закрыт `pc128`», а
`armdefer`/`protbatch2` закрыты по букве.

### RC2 (MAJOR) — перенос между плечами не измеряется; оба переноса смещают Δ к `K14_CLOSED`, а база берётся из «загрязнённого» плеча 0

**Что не так.** (1) **1 → 0.** Перевооружение §5.5 возвращает защиту, но не данные: записи гостя в U-страницы в плече 1
потеряны, трекер считает страницы CPU-чистыми (`m_cpu_dirty` не ставился — фолта не было), и страница, которую гость больше
не пишет, остаётся у GPU устаревшей в плече 0 до конца прогона. Если устаревшие буферы меняют работу (видимость, списки,
DRS, косвенные аргументы), плечо 0 после плеча 1 — не отгруженное состояние; проект это признаёт для картинки (§11), но не
для времени и не для базы п. 87(е)(7). (2) **0 → 1.** Страница, вооружённая в плече 0 и записываемая реже чем раз в 10
кадров, фолтит в окне плеча 1 один раз, прежде чем стать U; каждый такой фолт — работа, которую механизм снял бы. §11 это
называет, но единственный ряд — `fw_n` позиций 0–9 против 10–88, который перенос с периодом 10–80 кадров не видит (он в
окне). Оба переноса уменьшают |Δ|.

**Сценарий отказа.** Истинный потолок −540 мкс; перенос 0 → 1 добавляет плечу 1 +30, перенос 1 → 0 (устаревшие данные
уменьшают работу плеча 0 после плеча 1) даёт −20 ⇒ измерено −490 ± 60, Δ − 2SE = −610 → не `CLOSED`, но Δ + 2SE = −370 → не
`OPEN` ⇒ `NOT_RESOLVED`; при чуть меньшем SE — ложный `K14_CLOSED`. База курса п. 87(е)(7) несёт среднее плеча 0 с
половиной блоков после плеча 1 — не состояние отгруженной сборки.

**Что изменить.** Расписание ABBA (A B B A A B B A, `KYTY_GATE_SCHEDULE_ABBA=1`) уже содержит оба вида соседства: блок A
после B (позиции 3, 7, 11, …) и A после A (4, 8, 12, …); B после A (1, 5, 9, …) и B после B (2, 6, 10, …). (а) Печать —
по каждому плечу и режиму BDA: среднее окна 10–88 п. 55(б) `dt_us`, `draws`, `fw_n`, `sync_up_kb`, `gpu_busy_us` отдельно
для блоков «после своего плеча» и «после чужого», их разность ± 2SE (по блокам, без спаривания). (б) Ряд `fw_n` плеча 1 по
третям окна (10–35, 36–61, 62–88): спад по позиции — признак переноса 0 → 1. (в) **Вопрос лиду:** (1) база п. 87(е)(7) —
среднее блоков плеча 0 «после A» (не после B) или всего плеча с рядом разности; (2) правило, если разность «после чужого −
после своего» по `dt_us` превышает 2SE в каком-то плече (предложение: ряд `CARRYOVER` рядом с вердиктом, вердикт не
меняет, но `K14_CLOSED` с `CARRYOVER` плеча 1 > 0 пишется «с переносом»). (г) Вариант, снимающий перенос 1 → 0 по данным
(на выбор лида, иначе — оговорка): перевооружение §5.5 не `Protect(Read)`, а объявление записи U-страниц
(`ChangeState<Cpu, true>` по U-набору, как `InvalidateMemory`), чтобы первая синхронизация плеча 0 перезагрузила и
вооружила их обычным путём — данные плеча 0 снова верны, цена — одна загрузка U-набора на позициях 0–2.

### RC3 (MAJOR) — утверждение «нового пути к падению или зависанию гостя нет» (§0.3, §5 абзац 1) неверно; стражи не называют отказ устройства

**Что не так.** §5 доказывает только отсутствие НОВЫХ ФОЛТОВ. Но при 1 данные GPU не просто устаревают целиком: соседние
страницы одной структуры перезагружаются разными путями — окно `faultkb` (64 КБ) настоящего фолта на средней странице
пропущенного прогона (хост `Read`, U = 1 — RC4) открывает и помечает CPU-грязными соседей (`memoryTracker.h:187–191`),
явные объявления (`InvalidateMemory`) — свои диапазоны, а остальные страницы остаются снимком момента пропуска. Получается
«рваная» структура: узлы BVH со ссылками на устаревшие узлы, счётчики списков, не совпадающие со списками, индексы за
новыми вершинами. Ограничитель циклов BVH включён только для программы `380bb9d636390bae` (`KYTY_BVH_LOOP_CAP_SET` по
умолчанию), остальные циклы шейдеров без предела; санитайзер косвенных аргументов (`indirectArgsSanitizer`, и в
`renderCompute.cpp`, и в `renderDraw.cpp`) ограничивает размеры запуска, но не содержимое буферов, которые шейдер обходит.
Плюс записи хост-кода эмулятора в гостевую память на GuestGpu (метки, `DMA_DATA`, `WRITE_DATA`; `faults_gpu` 21,1 на кадр
[c]) на U-страницах не доходят до копии GPU.

**Сценарий отказа.** Плечо 1, кадр N: список источников света перезагружен окном `faultkb`, его счётчик на соседней
странице — нет ⇒ шейдер итерирует по мусорным индексам ⇒ бесконечный цикл ⇒ `GpuWaitSlow` → `GpuHangAbort:` через 8 с или
TDR ~60 с (`nvlddmkm` 153) ⇒ одна попытка `pc128` (п. 66(а)) потеряна; хуже — зависон в дыме объявлен «прогон не дожил»
без различения причины, и лид не знает, ручка это или окружение.

**Что изменить.** (а) Снять «нового пути к падению или зависанию нет» из §0.3; оставить: «нового пути к фолту нет;
зависон GPU по рваным данным CPU → GPU не исключён и проверяется дымом». (б) В маркеры смерти печати и дыма добавить
отказ устройства (`ReportVulkanFatal` печатает `… failed: ErrorDeviceLost (-4)` через `vk::to_string`,
`commandScheduler.cpp:32–42`; `MasterSemaphore::Refresh` — `EXIT_NOT_IMPLEMENTED` после `eErrorDeviceLost`,
`masterSemaphore.cpp:59–63`), `GpuWaitSlow:` — рядом с `GpuHangAbort:`; ряды `bl_trip`, `bl_near`, строки `BvhLoopCapTrip:` по плечам (срабатывание

изменить:** ряды печати — `pc_rearm_pages`, `pc_rearm_ns` по каждому переходу и `dt_us`, `fw_n` позиций 0–9 и 10–19 блоков
A после B против A после A (вместе с RC2(а)); оценку §5.5 переписать как [U] с верхом «U-набор блока», не кадра.

### RC9 (MINOR) — раскладка `Region` и «0 побайтно»

**Что не так.** §8.2(3) меняет `Region` (массив `unarmed` REGION_PAGES/64 слов + два `bool`) без указания места. Вставка
перед `pages`/`pending` сдвигает смещения полей, на которые ссылаются `FlushBlocker`/`KeepApplied` через `atomic_ref` (без
замка), и строки кэша `lock`/`apply` — поведение то же, но довод «побайтно» тогда надо доказывать заново. **Сценарий:** ревью
шага 5 принимает «поведение то же», а цена ручки при 0 в обоих плечах меняется от ложного разделения строк кэша — это
лежит в обоих плечах, но делает базу п. 87(е)(7) несравнимой с `4fc501f4` без оговорки. **Что изменить:** новые поля —
ПОСЛЕ `applying_run`, в конце `Region`; `unarmed_regions` и TLS — вне `Region`; в §8.2 записать размер `Region` до/после и
что база `pc128` — сборки с ручкой при 0, против `4fc501f4` не мерена (уже сказано в §8.1 — перенести и в §9(7)).

## 2. Проверено и находок нет (ответы на п. 88(л))

1. **P′ (л)(1).** Единственная точка выхода к хосту — `Protect` → `ProtectGuestHostMemory` (других вызовов `VirtualProtect`
   в `src` по гостевой памяти нет: `memory.cpp:4108`, `memoryAddressSpace.inc:637`). Применение без `apply`: П1 берёт
   `apply` при `!batch && !defer` (`:427`) и только тогда вызывает `ProtectRun`; при `batch`/`defer` применения нет. П2, П3,
   `Verify` — под `apply`. Окно `faultkb`: `ChangeState<Cpu, true>` по окну — снятие наблюдателя, ребро `Read → RW`, `RW`
   поверх `RW`/`Read` — согласованно, U снят. `InvalidateRegion` под `protbatch`: снятия — отложенные `RW`, применяет
   `FlushRange` фолтящего потока (`t_ceil` = 0) — U снят. `KeepApplied` — только `armdefer` (отказ). `FlushBlocker` при
   `applyskip=0` — только счётчики. `MarkStaleReadable`/`UntrackMemory` — снятия наблюдателей, синхронно, не `Read`
   вооружения. NA на хосте у отложенной страницы с `Perms() == Read` недостижим: переход в/из NA только синхронный и чистит
   `pending` (`:402–404`). Пути, где хост строже трекера, не найдено.
2. **Гость (л)(2).** Опрос результатов GPU гостем (`WAIT_REG_MEM`, метки EOP, `COND_EXEC`) читает гостевую память на CPU
   напрямую — не затронут. LOD-статистика — эмуляция на CPU по T# из гостевой памяти — не затронута. `PrepareBda` идёт через
   `SynchronizeBuffersOfDirtyRanges` → `SynchronizeBuffer` (`:2864`) → под `CeilScope` (данные устаревают, путь тот же).
   Косвенные аргументы — устаревают, размеры запуска ограничены санитайзером (dispatch и draw). Итог — RC3.
3. **Гонки U (л)(3).** Все записи U — под `apply` своей области (П1 `:427`, П2 `:761`, П3 `:718`, `Verify` `:846`); список
   `unarmed_regions` пишет и читает только GuestGpu; снятие U чужим потоком оставляет `has_unarmed` = true — лишний обход, не
   ошибка. Роль `Gpu` ставится только GuestGpu (`graphicsRun.cpp:690`) — `prot_gpu_*` не смешивает потоки.
4. **Перевооружение (л)(4).** Условие `U ∧ !pending ∧ Perms() == Read` достаточно при P′; `U ∧ pending` — снять U верно
   (отложенное применение запишет `Perms()`); отложенная смена, появившаяся между сбором прогонов под `lock` и вызовом
   (поток с `BatchScope` ставит `pending` без `apply`), применится после отпуска `apply` — конечное значение = `Perms()`, как в
   П3. Длина и цена — RC8; разоружение 0 → 1 > 10 кадров для страниц с периодом записи > 10 — RC2.
5. **Что ещё меняет плечо 1 (л)(5).** Меньше загрузок, копий, фолтов, сканов BDA, работы воркера — всё в сторону большего |Δ|
   (к `OPEN`). В сторону `CLOSED`: перенос 0 → 1 (RC2), лишняя работа от устаревших данных (draws — поправленный оценщик;
   `gpu_busy_us` — ряд), остаток вооружения вне ручки (RC1, только для write-watch). DRS — правило п. 78(е) покрывает. Режим
   BDA: в NEW падение `bda_scan` оставляет NEW; в OLD сканы идут от глобального сброса — как в проекте §9.3.
6. **Т6 (л)(6)** — RC6. **«0 побайтно» (л)(7)** — поведение: пропуск и U требуют `t_ceil == 1`, который ставит только
   `CeilScope` со значением 1; при 0 `has_unarmed` ложен, ни одна запись U не делается; отказы и `Verify` при 0 ничего
