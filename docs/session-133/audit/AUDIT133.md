### 1.5. Вопрос лида п. 149(в): нулевая доля расхождения при двусторонней гонке RC5

1. **Статистика.** При diff = 0 на 2 341 357 сверках верхняя граница 95 % истинной доли — ≈ 3 / 2 341 357 = **1,3·10⁻⁶**. Это на
   четыре порядка ниже порога 0,01. Сверки покрывают ключи равномерно: chk / would = 0,0622 при выборке теней 1/16 = 0,0625.
2. **Маскировка RC5 (опасная сторона) нуль не объясняет.** Скрыть расхождение может только запись CPU, попавшая в окно
   ≈ 0,1–0,3 мкс между копией A и снятием её тени (проект §5.1). Чтобы при доле ≥ 0,01 увидеть 0, нужно замаскировать каждое из
   ≥ 23 414 событий. Для записи, не связанной с моментом копии эмулятора, это невозможно: окно — малая часть промежутка A…B.
   Связанная запись гостя возможна только после пакета синхронизации (метка EOP/EOS, WAIT_REG_MEM). А такой пакет — сброс интервала
   (`rel`, `wait`), и он разрывает пару.
3. **Завышающая сторона RC5 не наблюдалась:** diff = 0, ложных расхождений нет.
4. **Контроль жив тем же кодом.** Через сброс байты меняются у 2,75 % повторов ключа: 19 225 из 698 439. Значит, тень, чтение гостя
   и `memcmp` видят изменения.
5. **Что нуль значит дополнительно.** Сверка сравнивает тень с текущими байтами гостя. Пропущенный хук сброса, если по нему
   меняются байты (путь вне списка §5.2), дал бы diff > 0. В этой сцене и в выборке 1/16 такого не было.
6. **Чего нуль НЕ доказывает:**
   - что не меняется ВЫБОР ПУТИ копии внутри интервала (биты трекера, `m_gpu_modified_ranges`, эпохи): байтовая сверка его не
     видит; это закрыто только чтением кода (Red Team, [I]);
   - что так же ведут себя другие сцены, режим OLD, пути вне дерева `0f539e02`;
   - что механизм B2 корректен: живость слота кольца, потребители копии;
   - что `rst_imgw` не нужен: это сброс по правилу, не по коду.

**Ответ:** член (3) «≤ 0,01» выполнен с запасом. Двусторонняя гонка RC5 его не подрывает. Оговорка RC5 остаётся текстом чтения, как
требует п. 143(в). Вопрос о корректности B2 остаётся открытым.
