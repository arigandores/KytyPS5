## 2. (i) Какой мьютекс назван `emu_mutex`

**Что пишет запись.** `W:emu_mutex` ставят два вида замков [c]: `Common::Mutex::LockB32` (`35b454c6:src/common/threads.cpp:345`,

### 3.3 Причина ожидания ядра и роль замка `spdlog`

Поле `SwR` — причина ожидания ядра (`WaitReason` из `NtQuerySystemInformation`) у сэмплов `Sw` [c кода:
`35b454c6:src/common/diagB32.h:318`]. Present в кадрах с цепочкой: `0` или `27`; поток, ждущий одновременно с ним вне меток, — `37`

заголовком на этой машине — заголовков ядра нет]. Толкование [I]: 0 и 27 — ожидание внутри ядра (синхронный ввод-вывод файла,
ресурс файловой системы); 37 — ожидание пользовательского замка (SRW / критическая секция). Записи согласуются с ним:

- n 8966 (`f25_k04`): Present `Sw 0:374` (в записи файла), DrawThread `Sw 37:374` (ждёт замок) — ридер назвал класс `UNMARKED:DrawThread`,
  но Gpu при этом ждёт `FlipQueue::m_mutex` 1 983 235 мкс у Present; `log_us` 13 998 154 — несколько потоков одновременно внутри
  `Log::Write` [c].
- n 17512 (`f25_k05`): Present `Sw 27:250`, Gpu `Sw 37:251` и `log_gpu_us` 1 337 716 — Gpu сам 1,34 с внутри `Log::Write` [c], то есть
  ждёт замок логгера (sink `spdlog` — `std::mutex`, не `TrackedMutex`, поэтому без метки) [I: какой именно замок — по полям не
  различить]. Поэтому записи `emu_mutex` у Gpu здесь нет — тот же механизм, другая точка ожидания.
- n 17451 (вне 20, справка): роли наоборот — DrawThread `Sw 27:25` (пишет), Present `Sw 37:25` (ждёт замок логгера, держа
  `FlipQueue::m_mutex`), Gpu ждёт `FlipQueue::m_mutex` [c].

## 4. (iii) Кандидат дефекта эмулятора

**К-а [c кода и записей]: `FlipQueue::m_mutex` и `VideoOutConfig::mutex` удерживаются потоком Present через синхронный ввод-вывод
хоста инструментов.** Место: `35b454c6:src/graphics/presentation/videoOut.cpp:1281` (`m_mutex.Lock();`) → `:3590`
(`m_mutex.Unlock();`); `:1213` → `:3607` для `VideoOutConfig::mutex`. Внутри — `LOGF` строк `FrameTrace` (`:1442`…`:3577`, только при

`KYTY_DIAG_B32=1`), чтение файла ворот (`gates.cpp:666`, только при `KYTY_GATE_FILE`); строка `FlipHold:` (`:3599`) — под
`VideoOutConfig::mutex` при любом умолчании, но только при удержании ≥ 50 мс и не больше 32 раз. В F25f этот путь — сон держателя
в 20 из 20 кадров (`FrameTrace`), в F20l3 `b32_pa` n 8797 — в `Gates::Poll` (`poll_us` 940 991, Present `Sw 27:179`). На умолчаниях
пользователя (`FrameStats` выкл., файла ворот нет, `KYTY_DIAG_B32=0`) записи лога под замком флипа нет [c кода]. Значит, кадры K2

Были бы K2 в тех же условиях без формы харнесса — не определено [U] (см. К-б).

**К-б [c кода; связь с K2 на умолчаниях — I]: синхронная запись лога на потоках гостя по умолчанию.** Логгер — `spdlog`
`basic_file_sink_mt` (`35b454c6:src/common/logging/log.cpp:54`), вызов `logger->log` (`:131`) под одним общим замком sink
(`std::mutex` внутри `spdlog`, `DiagB32` его не отслеживает); `PRINT_NAME` включён по умолчанию у части библиотек
(`35b454c6:src/libs/libAgcDriver.cpp:15`, `35b454c6:src/kernel/pthread.cpp:1203`), направление лога в форме харнесса —
`--printf-direction File` (те же аргументы, что у лаунчера, по `CLAUDE.md` [I]). Задержка записи файла останавливает любой
поток, пишущий в лог, в том числе поток рендера гостя (n 8966: DrawThread `Sw 37:374`; n 17451: DrawThread сам в записи `Sw 27`).
Вклад К-б в K2 у пользователя — [I], частота задержек файловой системы вне харнесса не измерена [U].
